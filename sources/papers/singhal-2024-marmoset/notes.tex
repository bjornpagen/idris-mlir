\subsection{Introduction}


\subsection{Problem Definition}

We want to develop an algorithm that takes some \textit{inputs} and returns some \textit{output}, based on \textit{costs and constraints}.
This algorithm should minimize these \textit{costs}.   

\subsubsection{Define inputs: }

\begin{itemize}
  \item $Input_a$: A function \textit{F} for which we want to optimize the ordering of fields $f_1$, $f_2$, $f_3$ \dots
                   for each data Constructor $d_1$, $d_2$, $d_3$, $d_4$ \dots that this function uses. Where $f_1$ is a list containing some fields used in 
                   data constructor $d_1$. 

  \item $Input_b$: A list \textit{l} where each element is a tuple (\textit{data constructor}, \textit{list(fields)}) that we 
                   want to optimize. 
                   
  \item $Input_c$: Hash table $H_c$ of costs.
\end{itemize}

\subsubsection{Define output: }

\begin{itemize}

  \item $List_{out}$: A list where each element is a tuple (\textit{data constructor}, \textit{list(fields)})
                      where \textit{list(fields)} defines the correct ordering on the fields for each data layout
                      used by the function \textit{F}.

\end{itemize}

\subsubsection{Define costs: }

We define two possible types of costs for a particular access to occur in a function \textit{F} between the time frame two fields
 $f_1$ and $f_2$ are accessed by \textit{F}; 
 Let us say that function \textit{F} has consumed field $f_1$ and is now going 
 to access field $f_2$.
 Either the traversal \textit{F} has to perform a \textit{pointer dereference} to get to field $f_2$ 
 or the traversal must \textit{backtrack} inside the data layout to get to field $f_2$.  
 For a pointer dereference the data layout must provide the presence of such an indirection pointer after the end of field $f_1$
 such that the traversal can jump to the location $f_2$ is serialized at. 
 For a backtrack to occur, the traversal \textit{F} must be written in such a way that it can effectively traverse back to field $f_2$ in the 
 data layout.  

\begin{itemize}
  \item \textit{pointer dereference:} The data layout provides the presence of a pointer which can be dereferenced to 
                                      reach the location of the desired field we want to access. We store the cost of this 
                                      pointer dereference as some \textit{p}.

  \item \textit{backtracking: } The function \textit{F} must traverse back to reach the desired field. Either the function \textit{F}
                                is already written in such a way that it backtracks to the desired field or it must be re-written so 
                                that is can effectively backtrack in the given data layout is it processing. 
                                We store the cost of such a backtrack by function \textit{F} to reach a particular field as \textit{b}. 
\end{itemize}


\subsection{Graph definition}

To optimize a particular data constructor \textit{d} for a given traversal \textit{F}. 
We will construct a graph which consists of nodes and edges.

Each node in the graph represents a particular field $f_1$, $f_2$, $f_3$ \dots in the given data constructor \textit{d} we are optimizing. 
The graph also consists of edges connecting these nodes. These edges capture the \textit{access patterns} of the 
traversal \textit{F} amongst the fields of data constructor \textit{d}.

\begin{itemize}
\item \textit{Edge definition:} An edge e in the graph is a control flow \textit{CFG} edge with an associated probability \textit{p}.
                                This edge e follows the control/data flow of the traversal {F}.
                                The probability \textit{p} associated with the edge e comes from the likelihood of the traversal \textit{F}
                                accessing the particular fields $f_1$, $f_2$, $f_3$ \dots 
                                For now, we will statically assign these probabilities. These probabilities will be uniformly distributed. 
                                For an \textit{if \dots else} branch it is 50 \% for each branch. 
                                For a case clause with n branches it is (100/n) \% for each branch. 

\item \textit{Node definition:} The nodes n $\epsilon$ fields $f_1$, $f_2$, $f_3$ \dots in the given data constructor. 
                                Each field is a unique node in the graph.

\end{itemize}

\subsection{SMT solver}

We use an SMT solver to find an optimal solution to the layout ordering problem.
The compiler will generate constrains for each edge in the layout graph that we generate using the field dependence graph of the program along with 
other necessary constraints.
We encode this problem as an ILP model, where each field is an \textit{Int} which can reside in the domain 0 to \textit{num fields - 1}.
Each edge in the layout graph has an associated cost C$_i$ unique to that edge. 
This cost can be either a backtrack, pointer dereference or a combination of both the costs. 
for each edge, the difference in the index's of the fields making up that edge decide this cost C$_i$ and we use the compiler to generate 4 constraints for each edge in the graph. 

The following python code shows the encoding for the graph~\ref{graph:blog1} generated by our compiler.
