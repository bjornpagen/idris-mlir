# P0 wave 2, lane 17: fork-boundary

The fork of Idris's compiler (`compiler/idris`) as the frontend consumes it:
the facts Idris computes that the compiler reads (multiplicities, erasure,
linearity, locations), the ones the compiler recomputes or guesses, how they
cross the boundary, how they should reach the redesigned dialect's types,
and the two-hosts rule.

Marks: *read* (path:line, commit, proposal section), *measured* (count, with
its command), *recalled*, *conjecture*.

## 1. Reading notes

What in the proposal bears on the fork boundary (the facts Idris proves and
how they reach the dialect), by section and finding ID. All *read* from
`proposals/0000-mlir-native.md` unless marked.

**§1, §2, §4 (directives, brief, bar).**
- §2 "Types that carry what Idris proved": `!idr.q<quantity, permission, T,
  lifetime>` with `!idr.lin<T>` = (one, plain), `!idr.own<T>` = (many, own),
  `!idr.excl<T>` = (many, excl), verified after every pass
  (`IdrTypes.td:270`). This is the landing type for the boundary's
  multiplicity facts. The Idris frontend is about 31,000 lines (§2 table).

  upstream of it.
- §4 "One fact, one place ... a fact recomputed is cached or carried in a
  type"; "AGENTS.md kept whole: grades in types, verified after every pass,
  never in a discardable attribute". The boundary is where Idris's
  multiplicities either enter that type once or get re-derived.

**§5.8 dialect-design (read most carefully).**
- Summary (1) and T1: "In MLIR a value's type is the only per-value fact
  every pass keeps, so AGENTS.md's grades-in-types rule is MLIR's grain";
  SIL's on-the-value ownership can only be "in the value's type" in MLIR.
  So every fact the fork hands over per binder must land in a type.
- T2: the grade is one attribute with an interface (`mayDuplicate`,
  `mayDiscard`, `isUnique`, `join`, `canRegradeTo`). The frontend's emitted
  grade is then one enum value, not a (quantity, permission) pair.
- T3, B5: "The unrestricted grade is the bare type, never a wrapper"; CIRCT's
  limit E2 (normalize only where no op's legality depends on it).
- T4: "Erased quantity 0 is already unrepresentable as a value (AGENTS.md);
  the type's quantity has only two values left." This lane checks the
  claim at the boundary: does the frontend in fact emit nothing for a
  `Rig0` binder, and is `Rig1` the only source of `lin`?
- T5, DD-Q6: lifetimes as regions first, never SSA values; "the fourth
  parameter of `!idr.q` is the place to look". The frontend's view of
  lifetimes (if any) is evidence for DD-Q6.
- T6, A4, D4: a function type carries conventions and effects. Idris's
  function types (`Pi` with a `RigCount` per argument) are exactly a
  per-argument convention; the fork already holds it in the definition's
  type. D5: "A closed, monomorphic program has neither constraint" (Swift's
  ABI and polymorphism).
- A2-A4, G6: Mojo keeps ownership in types up to one checking pass, then
  erases it in one step; we keep it to the end (AGENTS.md).
- O3: a regrade is a cast with computed result type; forwarding is a
  category. Bears on where the frontend introduces `lin.enter`/`lin.use`

- DD-Q1 (`!idr.lin<i64>` normalize to `i64`?), DD-Q6 (borrows as regions
  or lifetimes in types): owner's questions this lane gives evidence for.
- Wave-2 item: "Which (quantity, permission) pairs occur, what the lifetime
  parameter holds, and who reads each (DS1, T4, T5)." The boundary half
  (which the frontend can produce) is this lane's.
- DS4 row 1: `!idr.q<...>` to `!idr.g<T, #grade>`; the Idris side emits it.

**§5.9 mlton (read most carefully).**
- M1: "MLton changes the IR's *type* at each large change of representation
  (C2), so what a step proved is in the next IR's types and shape; we keep
  one dialect from defunctionalization to lowering, so what a pass proved
  must live in a type of that dialect ... MLton says to choose it for every
  fact that a later pass reads (G2.7)." The fork-to-frontend edge is our
  first such IR change (TT to `idr`): the first place a proved fact can be
  lost. Our boundary is a *translation* in MLton's sense (`'a -> 'b`, A1),
  and its output's types must carry what TT's types carried.
- C2: MLton spends a new IR type where the representation changes largely
  and a checked invariant where the change is an absence. The fork's
  erasure (quantity 0 gone) is an absence: a checked invariant (no value of
  quantity 0 in the module) rather than a type.
- D1: `Monomorphise` is one pass, linear, terminating by the program's
  scoping. M10: "Monomorphization never refuses in SML ... Idris allows what
  SML forbids, and AGENTS.md's `unsupported` refusal of megamorphic
  constructs is exactly the boundary MLton never had to draw." Lane 16 owns
  the refusals (Growth, Finite); this lane notes which fork facts they read.
- B5, G2.4: analysis state sized by types and constructors; a first-order
  type shares one abstract value. Idris's types are richer than SML's, and
  the fork delivers them; whether the frontend passes type shape (not only a
  mangled name) to the dialect decides whether this trick is available.
- I3 (Kovács, closure-free 2LTT): "bears on how the frontend might promise
  closure-freedom by type". A note for the frontend, not for P0's C++.
- Design 3 / Q-O3: "should every fact a later pass reads be written into a
  type by the pass that proves it ... with everything else recomputed, never
  carried as a side table between passes?" This lane gives evidence (§6):
  for the facts Idris proves, the "pass that proves it" is Idris's
  elaborator, and the fork boundary is where it is (or is not) written.

**§5.10 rc (read most carefully).**
- G1 (Marshall et al.): linearity restricts the future, uniqueness
  guarantees the past. G2 (Brady, `sources/papers/brady-2021-idris2-qtt/
  erasure.tex:34-39`): "A function which takes an argument with
  multiplicity 1 promises that it will not share the argument in the
  future; there is no requirement that it has not been shared in the past",
  and an ω variable may be passed at 0, 1 or ω. So the boundary may
  transmit `Rig1` as "consumed exactly once from here", never as "unique".
  Uniqueness comes only from a closed world of construction
  (`protocols.tex:15-27`). This is AGENTS.md's "A linear binder does not
  imply unique heap ownership".
- M5 "What each quantity decides, precisely": quantity 0, no value, no
  count; quantity 1 on a binder, "the parameter's convention is *owned* by
  its type, never borrowed, and borrow inference has nothing to decide for
  it", "a `dup` of it is unrepresentable (a verifier error, not an
  analysis result)". These are exactly the facts the fork holds per binder
  (`RigCount` on every `Pi`, `Lam`, `Let`, `PVar`, and on every data
  constructor field).
- R1.1 "Signatures in types. Each function's parameter and result grades
  ... live in its `!idr.q` types". The parameter quantities come from the
  fork (Idris's `Pi` binders); result grades do not exist in Idris
  (functions return at ω; the `(1 _ : a) -> ...` continuation idiom is how
  linearity reaches a result). Evidence for Q-E2 and Q-O3.
- M3 / W5: the grade verifier as OSSA's rule; W7: "`lin.enter` and
  `lin.use` against QTT's binder rules". The binder rules are the fork's
  (Idris's linearity checker, `Core.LinearCheck`); whether the frontend
  re-derives them is this lane's question.
- Q2 (owner): "is a run-time uniqueness test an acceptable fallback where
  the proof fails (AGENTS.md: linearity is a performance property ...)".

**§5.11 oom.** Nothing at the boundary beyond C7 (a budget in program
units, never bytes, for determinism): the fork has no budget left
(README "No count bounds a recursion of the fork's own",

### 2.3 How a definition crosses (*read*)

1. The driver calls `host.buildMain` (`Frontend/Driver.idr:270`), the fork's
   one elaborating entry (`Idris/ModTree.idr` `buildMain`,
   upstream/fork-build-main). Elaboration runs `processDef`, which per
   definition computes `eraseArgs`/`safeErase` (`TTImp/ProcessType.idr:178-186`,
   `TTImp/Elab/Utils.idr:38-75`, `TTImp/ProcessData.idr:565`,
   `TTImp/Elab/Case.idr:209-221`), the size-change graphs and coverage
   (`TTImp/ProcessDef.idr:1008-1020`), and, for every non-case definition,
   `compileRunTime`: `mkRunTime` builds the run-time case tree from the
   clauses run through `linearCheck ... True` (erasure), `%transform`s and
   `%spec`s, and `calcRefs True` records `refersToRuntime`
   (`ProcessDef.idr:722-843, 1022-1025`).
2. Every module, the main one included, is written to a TTC and read back
   (`compiler/idris/README.md:531-536`). `TTC GlobalDef` writes the full
   record only for user names (`Core/TTC.idr:1314-1337`); `TTC Def` writes
   `PMDef`'s compile-time tree and patterns and not the run-time tree
   (`TTC.idr:1177-1178`, read back as `Unmatched ""`, `:1207`).
3. The frontend looks definitions up by name or address (`Core.Context`,
   `Walk.resolve`), reads `type`, `definition`, `flags`, `totality`,
   `sizeChange`, `multiplicity`, `location`, `visibility`, `isEscapeHatch`,
   walks `treeCT` and the clauses' patterns, and asks the fork's evaluator
   and checkers only through `host` (`Idris/Host.idr:46-113`): `normalise`
   (4 call sites), `normaliseTypes` (1, behind `Closed.normaliseClosed`,
   which has 86 call lines in `Frontend/`), `normaliseHoles` (1),
   `normaliseAll` (1), `checkTerminating` (1), `argToPat` (1),
   `buildMain`, `processPackageOpts`, `emitError` (1 each) (*measured*:
   `grep -rno 'host\.[a-zA-Z]*'`, `grep -rn 'normaliseClosed\|closeNormalise\|normaliseClause' | wc -l`).
4. The translation builds `IdrisMLIR.Term` (`Term.idr`), whose binders are
   `Types.Binder {quantity : Quantity, type : Ty}` (`Types.idr:123-129`)
   with `Quantity = One | Many` generated from ODS's `Idr_Quantity`
   (`Syntax/Idr.idr:146-148`, `foreign/idr/include/idr/IR/IdrBase.td:83-87`).
   Emit writes a binder of quantity `One` (but the world) as
   `!idr.q<one, plain, T>`, the only grade the Idris side writes
   (`Emit/Index.idr:59`, `Emit/Monad.idr:80-83`), and `total` as an inherent
   `UnitAttr` of `idr.func` (`Emit/Declarations.idr:56`,
   `IdrOps.td:161`).

### 2.6 State, threading, who reads (*read*)

The fork is single-threaded and world-passing (`Core` is a function of the
world, `compiler/idris/README.md:502-508`); the context is `Ref Ctxt Defs`
with a growable table (`Libraries.Data.Table`, `:389-407`), decoded lazily
per definition (`TTC.idr:1384-1392`). The frontend's caches of what it
reads from the fork live in `TState` (`Translate/State.idr`): `tyCons`
(type constructor facts by address), `places` (module origin and file),
`loops` (termination verdicts), `blockNames`, `readings`. The readers of
the boundary's facts: the translation (`Translate/*`), the growth check
(`Growth/*`, lane 16), the profile (`Profile.idr`, lane 16), Emit
(lane 14).

### 2.7 The two hosts (*read*)

The fork is built by stock Idris on Chez (stage 0, `make fork`,
`compiler/idris/README.md:13-19`) and by idris-mlir itself; everything it
does for the second host is in the README's "Honest code", "Total where
the frontend calls it", "Rewritten so that this compiler can compile it"
and "Recursion at the types it is given" (`:104-385`). The one trust of
the frontend in the fork is `Idris.Host.host`, one `assert_total` over a
record of nine operations (`Idris/Host.idr:103-113`). The fork's TTCs are
refused by stock Idris and the reverse (`ttcVersion` has eleven digits,
`README.md:509-514`), so a TTC change in the fork touches no other
reader. Everything below proposes changes that are plain data in the
fork's existing types (`Term`, `Name`, `NatSet`, `CaseTree args`), inside
the subset both hosts compile (no field whose representation depends on
an erased value, no unbounded growth).

### 3.3 Wave-2 questions answered

- **§5.8 "Which (quantity, permission) pairs occur, what the lifetime
  parameter holds, and who reads each (DS1, T4, T5)"**, the boundary's
  half. The Idris side writes one pair, `(one, plain)`, and never a
  lifetime (`Emit/Index.idr:59`, the one `QType` written outside
  `SyntaxSamples.idr`); quantity ω is the bare type; quantity 0 is
  absent. Its source is Idris's `Rig1` on a `Lam`/`Pi`/`Let`/`PVar` binder
  or a constructor field (`Resolve.use`, `Types.coreBinderIn`,
  `Types.idr:1093-1097`), multiplied through a one-field type
  (`quantityTimes`, `Resolve.idr:217-219`). Every other pair and lifetime is
  a C++ pass's (lane 01, 08). The generated Idris constructor admits the
  whole product (`QType : Quantity -> Permission -> ... -> Maybe Lifetime`,
  lane 14 §3).
- **§5.10 W3 "whether parameter and result grades sit in function types so
  callers read them locally (R1.1)"**, the boundary's half: parameter
  quantities are in the callee's function type as emitted
  (`Declarations.idr:44-61`); results are never graded
  (`Emit/Bodies.idr:183`). What idr-rc-grades writes is lane 08's.
- **§5.10 W7 "`lin.enter` and `lin.use` against QTT's binder rules"**:
  `idr.lin.enter` is QTT's subsumption, an ω value given to a binder of
  quantity 1 ("an ω variable may be passed at 0, 1 or ω",
  `sources/papers/brady-2021-idris2-qtt/erasure.tex:34-39`), and
  `idr.lin.use` is a linear value's one use where a plain value is
  expected (`Emit/Operations.idr:142-155`). Neither exists in TT: Emit
  derives both from the value's quantity and the slot's.
- **§5.6 W-E2**, the boundary's share: how many values arrive linear.
  Not measurable without the stage-1 module. In the test corpus,
  `!idr.lin<` appears in 38 files; `!idr.lin<i64>` 128 times in 13 files,
  `!idr.lin<!idr.str>` 47 times (*measured*: `grep -rhoE
  '!idr\.lin<(i64|!idr\.str)...' tests | sort | uniq -c`).
- **§5.6 W-E4 "Does any pass carry an analysis fact in a discardable
  attribute?"**, the boundary's half: no. What the frontend proves of a
  function crosses as inherent properties of `idr.func` (`total`,
  `no_inline`, `instance`, `IdrOps.td:158-163`), quantities as types.
- **§5.3 "every switch on an enum of ours that appears in more than one
  place"**, the Idris side's quantity: six mappings (`Resolve.use`,
  `Resolve.multiplicity`, `Keys.quantity`, `Keys`' `showCount`,
  `Types.quantityText`, `Emit.Monad.linear`; §2.5); FB-22 to FB-26.

## 5. Target design

The boundary becomes a translation in MLton's sense (§5.9 A1, M1): a
typed function from checked TT to the dialect whose output types carry
what TT's types carried, with nothing guessed in between. Idris is the pass
that proves quantities, erasure and termination; the fork's TTC is the one
side table between it and the frontend, and it keeps those facts whole
(README "What a TTC keeps" is §5.9 Design 3's rule, Q-O3, applied to the
first step). Ranked by leverage.

### C1. The TTC keeps every fact a reader reconstructs (FB-01 to FB-06, FB-10 to FB-14)

- *Representation:* each fact in Idris's own type, written by the fork's
  encoder and read back exactly: a `let`'s, `PLet`'s and `PVTy`'s type
  (`Term`), a `Case`'s `scTy` (`Term`), a leaf's clause index (`Int`, as
  `STerm` already holds it), `WhyErased` (after the frontend's own marker
  moves to a probe), a block's parent as a resolved `Name` with its kind
  and ordinal, each import's `FC`, each pragma use (kind, `FC`), each
  loaded module's package. One fact per change, `ttcVersion` bumped,
  `decode . encode` checked on prelude, base and the tests, the
  reconstruction deleted in the same change (README rules,
  `compiler/idris/README.md:539-560`).
- *Deletes:* `Terms.valueType` and `applyOver`'s `ValueType` refusal of a
  value whose type the TTC dropped; Emit's second synthesis of a let's type;
  `Cases.instanceOf`'s inference and `siblings`' `[]`; `Forced.covers` and
  the alias merge; `Closed.outermost`, `rootOf`'s climb, `Keys.keyOrigin`'s
  search of the context; `Profile.imports`; `Resolve.homeOf`'s parse;
  `Resolve.elaboratedFile` (lanes 15 and 16 delete the readers).
- *One line:* a TT read back from a TTC holds no `Erased` placeholder,
  `STerm 0` or printed name where Idris had a term, an index or a name, so
  "not known here" is unrepresentable, and with it a refusal that a
  representation limit made (AGENTS.md: "no representation limit refuses a
  program").
- *Order:* the low-risk ones first (package, main path, imports' `FC`,
  0003's "locations first"), then C1's terms (let types, `scTy`, clause
  index), then `WhyErased` after lane 15 moves the marker, then the block
  parent (it changes `Core.Name`, read across the elaborator).

### C2. One runtime signature per definition, Idris's own (FB-15, FB-18, FB-22 to FB-27, FB-32)

- *Representation:* the fork supplies the facts: `eraseArgs`, complete
  (if a measurement shows `findErased`'s `nf` misses a binder that
  `normaliseTypes` finds, `findErased` takes the same unfolding), `paramPos`
  computed on the constructors' normal forms, and `ZeroOneOmega` made
  `public export`. The frontend reads them once per definition, cached by
  address as `tyConFacts` already is, into one value every reader takes
  (a sketch, inside the subset both hosts compile: the record is indexed by
  a parameter it does not store as a field's representation):

  ```idris
  ||| A position of a definition as the program runs it: absent where Idris
  ||| erased it (`eraseArgs`), else at the quantity Idris proved, its type
  ||| normalised once.
  public export
  data Position = Absent | Runtime Quantity ClosedTerm

  ||| A definition's runtime signature: one position per parameter.
  public export
  record Signature (arity : Nat) where
    constructor MkSignature
    positions : Vect arity Position
    result : ClosedTerm

  ||| The one reader of erasure and quantity: from `eraseArgs` and the type,
  ||| normalised once, cached by the definition's address.
  signatureOf : {auto c : Ref Ctxt Defs} -> {auto s : Ref TState TS} ->
                GlobalDef -> Core (arity ** Signature arity)
  ```

  `coreBinder` takes the `Quantity` of a `Runtime` position; `Keys` encodes
  a position from it once; `Resolve.multiplicity` stays the one conversion
  to the registry's `Multiplicity` (FB-24, essential by the import rule).
- *Deletes:* the five readers (`Closed.erasedArgs`, `Forced.quantities` and
  its "a binder past the type's is erased" default, `Sites.quantitiesOf`
  and its conditional normalisation, `Terms.lastRuntime`, `Types.conBinders`'
  quantity reading), the per-site `use` calls (43) and their `Erased =>` arms
  (30) where a caller only wanted the position's kind, `coreBinder`'s
  internal error, `Types.dataParams`' second reading of parameters, `Keys`'
  second quantity encoding.
- *One line:* an argument erased by one reader and runtime by another is
  unrepresentable (one signature is the only reader of erasure), and so is
  a binder of quantity 0 given a runtime representation (no caller holds a
  `RigCount` where a runtime quantity is due).
- *Depends on:* lane 15 (the readers in `Translate/`), lane 16 (`Growth/Sites`
  has 10 of the 43 sites). The fork's `paramPos` fix is a fork bug fix with
  its PINS.md entry and `upstream/<bug>/pull-request.diff` (AGENTS.md).

### C3. The run-time tree: translate what Idris erased, or stop computing it (FB-07, FB-38, FB-45)

Two coherent forms; the owner chooses (Q-FB1).
- *(a) Keep an erasure-only run-time tree and translate it.* The fork's
  `mkRunTime` keeps `linearCheck ... True` and `getPMDef RunTime` and drops
  `applyTransforms` and `applySpecialise` (they apply Idris's rewrites,
  among them `%transform "fastPack" pack = fastPack` to a `%foreign`
  function, `Prelude/Types.idr:853-861`, which the registry's `Faster` hook
  answers instead); the TTC writes it with its clause indices. *Deletes:*
  all of `Translate/Forced.idr` (the tree's leaves already read the runtime
  variable an erased binder equals), `applyOver`'s erasure at each
  application, `Terms.lastRuntime`, the one `host.argToPat` call
  (`Forced.idr:180`); perhaps the fork's `saved` deviation (FB-45).
  *One line:* the frontend translates the program Idris erased, not a
  program it erases again.
- *(b) Do not build it.* Delete `mkRunTime`, `compileRunTime` and
  `toCompileCase` from the fork (the frontend reads `treeCT`; nothing else
  reads `treeRT` once the TTC drops it), keep C1's `scTy` and clause index,
  and erase from C2's signature. *One line:* elaboration does no work no
  reader reads.

### C4. Quantities reach the redesigned dialect as one grade (FB-29, FB-30, FB-31)

- *Representation:* under DS1 (`!idr.g<T, #grade>`, unrestricted = bare
  `T`), the boundary writes one grade, the linear one, from a `Runtime One`
  position, and the bare type from `Runtime Many`; the generated Idris view
  offers the frontend only that grade (lane 14 generates it), so no
  permission or lifetime can be written on the Idris side. Parameter grades
  sit in the function type (they do, `Declarations.idr:44-61`), results
  have none (Idris has no linear result). `idr.lin.enter` and
  `idr.lin.use` stay: they are QTT's subsumption and a linear value's one
  use, essential (two cases the problem has). The world's linearity is its
  type's, read from the generated table, not a branch in Emit (or the world
  goes with DS2.1).
- *Deletes:* the hand `QType One Plain t Nothing` site's freedom (FB-30),
  `Emit.Monad.linear`'s world branch, `Types.quantityText`'s second spelling.
- *One line:* the Idris side cannot build a grade the boundary never
  produces.
- *Depends on:* lanes 01 (the grade type), 14 (the generated view, Emit),
  and Q3 (cut over in the same change: §6).

### C5. Linearity kept through the translation, not re-counted by Emit (FB-28)

- *Representation:* the translation hands Emit a `Term` whose binders'
  quantities are proved of that `Term`: where it only renames, Idris's proof
  carries over; where it rewrites (beta, a normal form, an implementation's
  method unfolded), one checker over `Term`, linear in the term, returns the
  quantities of what it returns, and states each demotion it makes at the
  binder (a parse at the boundary, not a count in Emit).
- *Deletes:* `mostUses` (quadratic), `heldAs`, `holdFor` in Emit
  (`Emit/Bodies.idr:48-138`, `Emit/Declarations.idr:45`).
- *One line:* the check moves to the boundary: a `Term` binder of quantity
  1 used twice cannot reach Emit, and Emit reads quantities, never counts
  them.
- *Depends on:* Q-FB2 (what a demotion means), lanes 14 and 15.

### C6. The fork's dead and duplicated parts (FB-39, FB-43, FB-44, FB-46)

- Delete the search timer (`startTimer`, `checkTimer` at every unfolding,
  `searchTimeout`, `Timeout`). *One line:* a check that can never fire is
  deleted, with its per-unfolding cost.
- Generate the ipkg's module list from `MODULES` and the fork's own files,
  or check it. *One line:* one list of the fork's modules.
- Export the fork's component search (`SizeChange.insideComponents`) and
  call it from `Recursion`. *One line:* one Tarjan over Idris's call graph,
  not two.

### C7. Elaboration's counts (FB-40, FB-41)

Owner's question Q-FB3. If they go, the shape is fork-totality-depth's:
a memo or a measure that terminates by construction, everything accepted
before still accepted; `%ambiguity_depth` and `%auto_implicit_depth`
refused by the parser. *One line:* if removed, acceptance stops depending
on a count; if kept, the case is essential only for proof search, a
semi-decision whose bound the owner then names as such.

### C8. One path model (FB-48)

Delete `Libraries.Utils.Path`'s Windows branches. *One line:* the
per-target case outside a target's entry is deleted, not guarded.

### Order inside the subsystem, and dependencies

**DD-Q1 (§8.3): may `!idr.lin<i64>` normalize to `i64` at construction, or
is that dropping what Idris proved?**
- It occurs: `!idr.lin<i64>` 128 times in 13 test files, `!idr.lin<!idr.str>`
  47 times (*measured*, §3.3); a constructor field can be one
  (`tests/expect-quantities/expect-quantities.mlir`: `@MkHandle(!idr.lin<i64>,
  i64)`). Its source is any `1` binder Idris checked over an `Int`
  (`Resolve.use`, `Types.coreBinderIn`, `Types.idr:1093-1097`).
- What it means: quantity 1 restricts the future only (§5.10 G2,
  `brady-2021-idris2-qtt/erasure.tex:34-39`); a word has no count, so
  counting, exclusivity and reuse have nothing to decide for it.
- What reads it today: the verifier's "every linear value used once on
  every path" (`IdrOps.td:124-125`; `tests/func-linear-twice`), and the
  `quantities-kept` contract, which treats `!idr.lin<i64>` becoming `i64`
  as an error: "A linear parameter made unrestricted ... is an error"
  (`tests/expect-quantities/expect-quantities.mlir:13-16`). So the fact on a
  word is today a detector of passes that duplicate a use, not an input to
  a transformation.
- Precedent on the Idris side: Emit already holds the world, linear in
  Idris, as its bare type, because the dialect makes it linear by its type
  (`Emit/Monad.idr:76-83`).
- AGENTS.md: "No pass may drop what Idris proved: multiplicities ...
  Quantity 1 is a type, `!idr.lin<T>`, which every transformation must
  keep"; normalizing at construction means the fact never enters the IR,
  which is the boundary dropping it, not a pass.

**DD-Q6 (§8.3): borrows as regions with no lifetime in the type, or
lifetimes as symbolic attributes in types?**
- Idris has no borrows and no lifetimes: QTT's quantities are 0, 1 and ω
  (`Algebra/ZeroOneOmega.idr:10`), and no TT node or `GlobalDef` field holds
  a scope or region of a reference (§2.2).
- The Idris side writes no lifetime and no `borrow` permission
  (`Emit/Index.idr:59`: `Nothing` lifetime, `Plain`). Every lifetime and
  borrow in the IR is a C++ pass's inference (lanes 07, 08), so the
  boundary is neutral: neither form has a source here, and neither costs
  the frontend anything.
- The nearest Idris fact is the scope of a pattern variable (a case
  alternative's binders, `CaseTree.idr:41-43`), which is already a region
  in the dialect (`idr.match`'s case regions).

## 8. Risks, unknowns, measurements needed

- **Nothing here was built or run.** No compiler is built in this
  checkout; every count is over the source with the command given.
- **TTC size.** Keeping each node's location grew the installed prelude
  from 2.2 to 3.6 MB and base from 17 to 30 MB
  (upstream/fork-ttc-term-locations). Keeping let types, `scTy` and, under
  C3(a), a second case tree grows them again; decoding is lazy per
  definition (`TTC.idr:1384-1392`), so the frontend pays for what it reads.
  Measure TTC sizes and the frontend's time on the benchmarks before and
  after.
- **`eraseArgs` against the frontend's readers.** `findErased` normalises
  with the elaborator's `nf` (`TTImp/Elab/Utils.idr:57-61`), in the defining
  module; the frontend normalises with `normaliseTypes`, which unfolds any
  type-level definition whatever its visibility
  (`compiler/idris/README.md:408-422`). Whether the two ever disagree on a
  position a program applies is *conjecture* (an application needs the
  binder visible where it is written); measure by comparing `eraseArgs`
  with the five readers' answers on every definition the test corpus and
  the self-compile reach, before C2.
- **The run-time tree's aliasing (C3(a)).** That a run-time tree built from
  erased clauses names a runtime variable where `treeCT` names an erased
  one (`Forced.idr:1-19`'s case, `upTo (Step t p) Here`) is *conjecture*
  from `mkRunTime`'s steps; check on `tests/erased-index-forced-index`,
  `erased-elem-match`, `erased-elem-later-match` and `erased-witness`.
- **`%transform` in the run-time tree.** Prelude and base declare
  transforms (`Prelude/Types.idr:469-888`, `Data/String.idr:130`,
  `Data/List.idr:462`, `Data/SnocList.idr:17, 80`, `Data/Fin.idr:31`), some
  to `%foreign` functions; an erasure-only run-time tree must apply none,
  or the frontend would compile Idris's rewrites in place of the registry's
  hooks.
- **The fork's `saved`.** It changed the compile-time tree's split order for
  the frontend's sake (FB-45) and its comment names a coverage and
  unification reason too (`Data.Fun`'s `chain`); undoing it under C3(a)
  needs those checks.
- **Two hosts.** Each fork change builds under stock Idris on Chez (stage 0)
  and idris-mlir (stage 1); each `ttcVersion` bump rebuilds prelude, base
  and `libs/` (`make prefix`). The proposed types (`Position`, `Signature`,
  a typed block parent) are plain data; no dependent field, no growth.
- **Linearity demotions.** How often Emit's `heldAs` demotes a `1` binder,
  and on what programs, is unmeasured; it decides how large C5 is (count
  the demotions on the corpus and the self-compile with a build).
- **W-E2.** The number of values that arrive linear on the stage-1 module,
  against those the solvers keep state for, needs the module.
- **Elaboration time spent on `compileRunTime`.** Idris logs it under
  `compile.casetree`; measure it on base and the frontend before choosing
  C3(b).
- **Q-FB3.** Removing `%ambiguity_depth` changes an exponential search
  (ambiguity resolution) into one that needs a memo, as `%totality_depth`'s
  removal did; its cost on base and the frontend must be measured.
