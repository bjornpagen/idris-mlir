# 5.11 oom: running out of memory, in the compiler and in the programs it builds

We may not be ready to decide this, but we should know what we do not
know. Today (*read*: proposal 0001) the compiler's pipeline has been
killed by the operating system at 43 to 627 GB (§3); a compiled
program's heap is snmalloc's with no limit of ours (the first 4 GiB of
cells in one aligned region) and its stack one 64 GiB reservation; and
nothing in the language's types represents an allocation that fails.
This lane maps the territory.
- **Go**: the soft memory limit (`GOMEMLIMIT`, `debug.SetMemoryLimit`,
  the design document of proposal 48409), the GC pacer and `GOGC`, the
  scavenger and returning memory to the OS, what happens at and past the
  limit (the death-spiral guard, the CPU cap on GC), goroutine stacks and
  their growth, how a Go program behaves under cgroups and the OOM killer,
  and `sources/docs/go-scheduler`.
- **Other runtimes**: Rust (the alloc error handler, abort on OOM,
  `try_reserve`, fallible allocation in the kernel), Zig (allocation
  failure as a value), Swift and Lean and Koka (what their RC runtimes do
  when an allocation fails), OCaml 5, GHC's RTS (`-M`, heap overflow as
  an exception), the JVM (`-Xmx`, `OutOfMemoryError`), Erlang (per-process
  heaps, `max_heap_size`), Seastar (memory per shard,
  `sources/docs/seastar`), tokio.
- **Allocators and the operating system**: snmalloc (`third_party/snmalloc`,
  third-party code, may be read: what it does when the OS refuses, its
  hooks), mimalloc and jemalloc limits; Linux overcommit, cgroup v2
  `memory.max` and `memory.high`, the OOM killer and PSI; macOS jetsam
  and memorystatus, compressed memory and the footprint that killed our
  runs; stack overflow detection with guard pages on each of the four
  targets.
- **Compilers**: how rustc, clang and LLVM, GHC, MLton, Go's own compiler
  and MLIR bound or report their memory; arenas and per-pass memory;
  whether a compiler should have a memory budget and what it does when
  the budget is met, given AGENTS.md's rule that a budget never rejects a
  program.
- **The questions for us**, in §0's layout: what a compiled program
  should do when memory runs out (a clean, named crash; a limit the user
  sets; a pressure signal), what the runtime and the shards proposal
  (0007) need, what the compiler's pipeline should do (measure, bound,
  degrade), and the unknown unknowns this lane surfaces. Our proposals
  (`proposals/`, documents, not code) may be read for context.

*Wave 1 complete (2026-10-21); a map of the territory, not a plan. Two
subjects kept apart throughout: **(A)** the compiler's own memory (the
pipeline, `idris-mlir`, and every tool built on the runner) and **(B)**
a compiled program's memory. Trees read: Go at `05dbbf91`
(github.com/golang/go, shallow clone of 2026-10-21, paths relative to
its `src/`); snmalloc 0.7.6 at `f126f1c9` (`third_party/snmalloc`); the
pinned `.toolchain/llvm-project` at 7208ba24; `sources/`; the other
runtimes' clones at the hashes §5.11.6 lists. Marks: read / measured /
recalled / conjecture. The short answer: Go's limit is mostly an answer
to a collector's question; for a counted heap the questions are a named
crash, a limit below the OS's, stack probes, reservations that commit
on use, and, for the compiler, memory bounded by each solver's
representation and budgets counted in the program's units
(§5.11.2).*

#### 5.11.1 Findings

**O. Our own record, as the proposals state it** (*read*; the facts
the rest is measured against).

O1. The pipeline's walls were all memory after the time walls fell:
jetsam killed a traced run at 43 GB RSS "(low-swap, on 96 GB)" in
idr-frames; an untraced run was stopped by hand at 52 GB; idr-rc-stack
died at 47 GB (proposal 0001 §2, S3). §3's table adds 627 GB of
footprint for exclusivity on `DataFlowSolver`. Each was fixed at the
representation, none by a limit.

O2. A compiled program's heap is snmalloc's, with "no limit of ours";
the first 4 GiB of cells lie in one 4 GiB-aligned region, past which
"snmalloc grows as it does with no bound" (0017 status, D7); the stack
is one 64 GiB reservation with a guard and an alternate signal stack
(0017 D9; 0007 §3.1), shared by programs and the compiler's tools
(`idris_rt_run_on_stack`). 0017 D9 plans to fold the heap's region and
the stack's top into one reservation.

O3. Memory is "a record, not a gate" (0001 D4); a limit is "a fact
measured, not guessed" (0001 D10); bounded memory is a G1 item measured
by `peak_memory` (0006 §1), whose test does not exist yet. Shards give
each core its own snmalloc allocator and count live cells per thread
(0007 §5.1, D1), so "how much memory does the program hold" is already
a sum over shards.

**G. Go: a soft limit on a collected heap** (*read*, Go `05dbbf91`
unless marked).

G1. *What is limited.* `GOMEMLIMIT` / `debug.SetMemoryLimit` bound
"all memory that the Go runtime has direct control over", defined as
`MemStats.Sys - HeapReleased` (design 48409, "API"; GC guide, "Memory
limit"), i.e. every mapped page in the *Ready* state, heap or not:
the runtime keeps one counter, `gcController.mappedReady`, incremented
by `sysAlloc`/`sysUsed` and decremented by `sysUnused`/`sysFree`
(`runtime/mem.go:49-70, 89-90, 127-153`, the four address-space states
None, Reserved, Prepared, Ready at `:11-31`). Memory outside Go (cgo, the kernel's,
co-tenants) is a non-goal. The default is `MaxInt64`, i.e. off; the
runtime parses `GOMEMLIMIT` once (`runtime/mgcpacer.go:1414-1425`) and
throws on a malformed value.

G2. *How the limit acts: through the one lever a collector has, GC
frequency.* The heap goal is the minimum of the `GOGC` goal and a
memory-limit goal, `memoryLimit - (nonHeap + overage)` less 3% (at
least 1 MiB) of headroom, never below the last marked heap
(`mgcpacer.go:1000-1043, 1046-1157`). When non-heap memory alone
exceeds the limit, the goal is the marked heap: "trigger GCs
continuously and let the CPU limiter reign that in. Something has to
give at this point" (`:1128-1135`).

G3. *The death-spiral guard makes the limit soft.* `gcCPULimiter` is a
leaky bucket filled by GC CPU time and drained by mutator time, so its
limit is 50% of CPU, with a capacity of one CPU-second per `GOMAXPROCS`
(`mgclimit.go:9-29, 312-329`). While it is full, goroutines stop
assisting the GC (`mgcmark.go:534-536`) and the allocator stops
scavenging for the limit (`mheap.go:1321, 1370`), so the program
overshoots the limit instead of stalling. The guide's argument: "an
indefinite stall is worse than an out-of-memory condition, which tends
to result in a much faster failure", and a mis-set limit slows a
program "at most by 2x". The design took the bucket from Netflix's
jvmquake but does not kill the process (design 48409, "Death
spirals"); a counter, `/gc/throttles:events`, reports each overflow.
Hard limits, GC-on-OOM and pressure notifications are not discussed;
SetMaxHeap's pressure channel was "ignored in most uses" (design,
"Prior art").

G4. *Returning memory is the second half of the limit.* The scavenger
releases free pages (`MADV_FREE` on Linux, falling back to
`MADV_DONTNEED`, `mem_linux.go:38-66`; `MADV_FREE_REUSABLE` and
`MADV_FREE_REUSE` on Darwin so the kernel's footprint accounting sees
it, `mem_darwin.go:23-34`). Its goal is 95% of the limit when one is
set, else 110% of the heap goal scaled by fragmentation; it runs in
the background at 1% of mutator time, and synchronously in the
allocator whenever an allocation would cross the limit, ignoring its
density heuristics ("forced") when the limit is at stake
(`mgcscavenge.go:1-88, 98-125`; `mheap.go:1310-1376`).

G5. *Past the limit, Go dies with a named, unrecoverable throw.*
Every OS refusal is `throw("runtime: out of memory")` (`mem_linux.go:92,
174`; `mem_darwin.go:69`; `mcache.go:207, 244, 259`), after a line
naming the request and the bytes in use (`mheap.go:1568`); `throw` is
`fatalthrow`, which `recover` cannot catch (`panic.go:1306-1316,
1501`). A goroutine's stack grows by copying, doubling, up to
`maxstacksize` (1 GB on 64-bit, 250 MB on 32-bit, `proc.go:163-171`;
`debug.SetMaxStack`), and exceeding it is `throw("stack overflow")`
with the limit printed (`stack.go:1200-1207`). Under overcommit, most
real Go OOMs are the kernel's kill, not this throw (*recalled*).

G6. *Containers.* Go reads the cgroup's `cpu.max` to default
`GOMAXPROCS` (`runtime/cgroup_linux.go:11-26`;
`internal/runtime/cgroup/cgroup_linux.go:13`) but never reads
`memory.max`: the design leaves the memory limit to the user, and the
guide says not to set one for "a CLI tool or a desktop application",
whose memory "is proportional to its inputs", and to leave 5-10%
headroom inside a container.

**M. snmalloc, our programs' allocator** (*read*, `third_party/snmalloc`
0.7.6 at `f126f1c9`, paths under `src/snmalloc/`).

M1. *Failure is a template parameter.* Every allocation takes a
`Conts` class with `success` and `failure`; the default `failure` sets
`errno = ENOMEM` and returns null (`mem/corealloc.h:21-61`), and
`alloc<Conts>` is `noexcept` exactly when `Conts::failure` is
(`:590-605`). So what a failed allocation *means* is chosen by the
caller's type, once, with no check at the call site beyond the one the
continuation makes.

M2. *The backend is a pipe of range types, composed at compile time.*
`StandardLocalState` builds `Pipe<Base, LargeBuddyRange<…>, LogRange,
GlobalRange>`, then `Pipe<GlobalR, CommitRange<PAL>, StatsRange>`,
then a thread-local `LargeBuddyRange` (`backend/standard_range.h:20-60`).
`CommitRange` calls the PAL's `notify_using` on the way out and
`notify_not_using` (the page release) on the way back
(`backend_helpers/commitrange.h:28-60`); `StatsRange` keeps the
committed bytes, current and peak, in two atomics
(`backend_helpers/statsrange.h:10-60`), exposed as
`Backend::get_current_usage()` / `get_peak_usage()`
(`backend/backend.h:202-211`). A limit, a pressure signal or an
accounting hook is one more range type in that pipe.

M3. *Returning memory.* A thread's allocator returns a size class's
empty slabs once more than two, and more than a quarter of that class's
slabs, are unused (`mem/corealloc.h:1178-1188`); chunks leave the
thread-local buddy cache (2 MiB, `LocalCacheSizeBits = 21`) and the
global one (16 MiB, `GlobalCacheSizeBits = 24`,
`backend/base_constants.h:16-19`) through `CommitRange`, which
releases the pages: `MADV_FREE` on Linux (`pal/pal_linux.h:128-145`),
`MADV_FREE_REUSABLE` on Apple, chosen because plain `MADV_FREE` is not
counted as reusable there (`pal/pal_apple.h:131-160`), nothing on
generic POSIX (`pal/pal_posix.h:205-230`). Linux reservations carry
`MAP_NORESERVE` (`pal/pal_linux.h:46-51`).

M4. *Low-memory notification exists, on Windows only.* The PAL feature
`LowMemoryNotification` (`pal/pal_consts.h:13-21`) with a callback
list (`pal/pal_ds.h:58-90`) is implemented by `pal_windows.h:86-241`
alone; no Apple or Linux PAL offers it, and nothing in `mem/` or
`backend/` consumes it in this version.

M5. *The page size is a compile-time constant:* `SNMALLOC_PAGESIZE`,
else `PAGESIZE`, else the architecture's smallest page (4 KiB on arm64,
`aal/aal_arm.h:47`) on Linux (`pal/pal_posix.h:134-142`); 16 KiB on
arm64 Apple (`pal/pal_apple.h:79`). On arm64 Linux at 16 KiB pages the
right value is the target's entry's to give (AGENTS.md).

M6. *Reservations are writable unless a mitigation says otherwise.*
`PALPOSIX::reserve` maps `PROT_READ | PROT_WRITE` unless
`pal_enforce_access` is on (`pal/pal_posix.h:337-360`), and that
mitigation is in `full_checks`, which only `SNMALLOC_CHECK_CLIENT`
builds get (`mitigations/mitigations.h:211-255`). See K2 for what a
writable reservation costs under strict overcommit.

M7. *The other two allocators* (*read*). mimalloc (`31d034d9`): failure
sets `errno` and returns null unless built `MI_XMALLOC`, which aborts
(`src/options.c:598-605`); a hard bound is an address-space layout,
not a counter: reserve an exclusive arena (`mi_reserve_os_memory_ex`,
`include/mimalloc.h:346`) and forbid OS allocation outside it
(`mi_option_disallow_os_alloc`, `:468`); unused memory is purged after
`purge_delay` (default 1000 ms here, `src/options.c:145`). jemalloc
(`975f3b0b`): `opt.xmalloc` aborts on failure, off by default; dirty
pages are purged on a sigmoidal decay curve, 10 s by default
(`doc/jemalloc.xml.in:1183-1200, 1403-1418`). None of the three has a
built-in byte limit that fails an allocation; each offers the pieces
(a failure policy, a fixed range, a release schedule).

**R. Other runtimes** (*read* in the clones named; paths relative to
each).

R1. *Rust* (`6a586779`). Allocation failure is a diverging call,
`handle_alloc_error(layout) -> !` (`library/alloc/src/alloc.rs:640-695`):
with `std`, the default hook prints "memory allocation of N bytes
failed" and aborts, skipping the backtrace on a second failure to
avoid recursion (`library/std/src/alloc.rs:375-400`); without `std` it
panics. Fallible allocation is a separate API, `try_reserve` returning
`TryReserveError` whose kind is `CapacityOverflow | AllocError {layout}`
(`library/alloc/src/collections/mod.rs:102-123`); and a configuration,
`cfg(no_global_oom_handling)`, removes every infallible allocating API
from `alloc` (`library/alloc/src/lib.rs:69, 262-277`), so code built
under it cannot express an allocation that might abort (the Linux
kernel's use, *recalled*). Stack overflow: a guard page under every
thread's stack and a `SIGSEGV`/`SIGBUS` handler on an alternate signal
stack that prints "thread '…' has overflowed its stack" when the fault
lies in the guard range, else re-raises
(`library/std/src/sys/pal/unix/stack_overflow/handler_signal.rs:17-73,
101-145, 170-190`); it relies on LLVM's stack probes so no frame skips
the guard (*recalled*; see K6).

R2. *Zig* (`738d2be9`). Failure is a value in every signature:
`Allocator.Error = error{OutOfMemory}`, and every allocating function
returns `Error!T` (`lib/std/mem/Allocator.zig:11, 281-296`); the
allocator is an explicit argument. A byte limit is a configuration of
one allocator, `DebugAllocator(.{ .enable_memory_limit = true })`, whose
counter field has type `usize` when enabled and `void` when not
(`lib/std/heap/debug_allocator.zig:118-121, 180, 204-205, 240,
616-625`): the configuration removes the field, not a branch.

R3. *Swift* (`ba215ca6`). `swift_slowAlloc` calls malloc and, on null,
`swift_abortAllocationFailure`, a fatal error "failed to allocate N
bytes of memory with alignment A" with a backtrace
(`stdlib/public/runtime/Heap.cpp:86-103`;
`RuntimeErrorReporting.cpp:525-529`). No limit, no fallible API.

R4. *Lean 4* (`541dbdcd`). Compiled code allocates small objects
through one entry that bumps a thread-local `heartbeat` and calls
mimalloc; null is `lean_internal_panic("out of memory")`
(`src/runtime/mimalloc.cpp:39-50`; `object.cpp:98-100`). The
elaborator's limits are two: `maxHeartbeats`, a count of small
allocations, *deterministic*, so a proof that fits on one machine fits
on every machine (`alloc.cpp:33-46`; `interrupt.cpp:17-51`); and a
byte limit, `set_max_memory`, polled every 200 checks against peak RSS
then current RSS (`getrusage`, Mach `task_info`, `/proc/self/statm`),
throwing a catchable `memory_exception` (`memory.cpp`, whole file).
Stack: a guard-page `SIGSEGV` handler printing "Stack overflow
detected. Aborting." (`stack_overflow.cpp:53-80`) and a soft check
against a recorded stack base (`stackinfo.cpp:95-125`), both reached
from `check_system` (`interrupt.cpp:102-109`).

R5. *Koka* (`198fc3bb`). Block allocation does not test mimalloc's
result (`kklib/include/kklib.h:511-530, 665-686`), so a failure relies
on mimalloc's policy (M7); fatal errors log and `abort()` with a
"todo: call error handler" (`kklib/src/init.c:122-129`). With
compressed pointers the heap is one reserved arena (16 GiB at 32-bit
boxes) and failure to reserve it is fatal at start (`init.c:182-196`):
the heap's bound is its address range, as M7's arena is.

R6. *OCaml 5* (`3798be90`). Major-heap allocation failure raises the
exception `Out_of_memory` (`runtime/memory.c:540-555`;
`fail.c:113`), a value programs can catch, while some runtime-internal
failures are fatal ("No memory for minor heap", `minor_gc.c:138`;
`domain.c:642, 752`). Stacks are heap-allocated fibers that grow up to
`l` (default 128 Mi words, `caml/config.h:189`;
`startup_aux.c:64, 110`) and raise `Stack_overflow`
(`fiber.c:350, 390`).

R7. *GHC's RTS* (`3d326d7d`). `-M` (off by default,
`rts/RtsFlags.c:161`) makes a major GC that leaves more than the limit
throw the asynchronous exception `HeapOverflow` to the main thread,
then again only after `-Mgrace` more bytes (1 MiB default,
`RtsFlags.c:162, 581-585`; `Schedule.c:1620-1622, 1990-2017`). The
RTS's own comment calls this "not a good way to tell a program to
release resources. It is neither reliable (the RTS crashes if it fails
to allocate memory from the OS) nor very usable (it is always thrown to
the main thread…)" (`Schedule.c:2006-2014`). Per-thread *allocation
limits* (bytes allocated, a deterministic count) throw
`AllocationLimitExceeded` (`Schedule.c:1095-1104`). Stacks are heap
chunks, bounded by `-K`, default 80% of physical memory
(`RtsFlags.c:140-151, 335`).

R8. *The JVM* (Java SE 25 `java` manual, docs.oracle.com). `-Xmx` caps
the heap; its default is `MaxRAMPercentage` (25%) of `MaxRAM`, "the
minimum of the machine's physical memory and any constraints set by
the environment (e.g. container)", since container detection is on by
default (`UseContainerSupport`, Linux). Exhaustion throws the catchable
`OutOfMemoryError`; `UseGCOverheadLimit` (on) throws it when more than
98% of time goes to GC and less than 2% of the heap is recovered: the
opposite of Go's choice in G3 (fail fast rather than overshoot);
`HeapDumpOnOutOfMemoryError` and `OnOutOfMemoryError` are diagnostics
hooks.

R9. *Erlang/OTP* (`1e86608b`). `max_heap_size` is per *process*
(an Erlang process, a heap of its own), checked when a GC sizes the
heap (`erts/emulator/beam/erl_gc.c:1197-1211, 1454, 1903,
3730-3803`): past it the process is killed (untrappably, `am_killed`)
and/or an error is logged, and its supervisor decides what follows.
The VM itself, refused by the OS, writes a crash dump naming the
allocation type and size and exits (`erl_alloc.c:2100-2110`).

R10. *Seastar and tokio.* Seastar gives each shard a fixed share of
memory at start (by default all memory but max(1.5 GiB, 7%); `-m` and
`--reserve-memory`), allocates only from it, and throws `bad_alloc`
when a shard's share is exhausted; memory is budgeted in units with a
semaphore (`sources/docs/seastar/tutorial.md:180-190, 856, 1305-1382`).
tokio has no memory limit; its only bound is backpressure through
bounded channels and semaphores (*recalled*).

**K. The operating systems.**

K1. *Linux overcommit* (*read*, docs.kernel.org,
`mm/overcommit-accounting`). Mode 0 (default) refuses only "obvious
overcommits"; mode 1 always overcommits; mode 2 refuses past
`CommitLimit` (swap plus `overcommit_ratio`, default 50%, of RAM), and
"in mode 2 the MAP_NORESERVE flag is ignored". Private writable
anonymous mappings are charged at their full size; `mprotect` changes
are accounted. So under the default, an allocation almost never fails:
the process is killed later, when it touches pages (K3).

K2. *What that means for a big reservation* (*read*, Linux
`a804c574`, then *conjecture* for us). The kernel charges a mapping to
the commit limit when it is private and writable and lacks
`VM_NORESERVE` (`mm/vma.c:2458-2476`, `accountable_mapping`), sets
`VM_NORESERVE` from `MAP_NORESERVE` only when the mode is not 2
(`mm/mmap.c:563-571`), and charges a `PROT_NONE` range when `mprotect`
first makes it writable (`mm/mprotect.c:805-818`). So under mode 2 a
writable reservation is charged in full when made: a 4 GiB writable
heap region, or a writable 64 GiB stack, would fail or exhaust the
commit limit at start for every program, while a `PROT_NONE`
reservation committed on use is charged only as it is used. A user's
`ulimit -v` (`RLIMIT_AS`) counts every mapping, writable or not
(*recalled*; `may_expand_vm` above), so a 64 GiB stack reservation
fails every program under any `ulimit -v` below it. The OOM killer's
score is resident pages plus swap entries plus page tables, adjusted by
`oom_score_adj` (`mm/oom_kill.c:216-229`).

K3. *cgroup v2* (*read*, docs.kernel.org, `admin-guide/cgroup-v2`).
`memory.high` throttles and reclaims and "never invokes the OOM
killer"; `memory.max` is the hard limit, past which, "if a cgroup's
memory usage reaches this limit and can't be reduced, the OOM killer is
invoked in the cgroup"; `memory.events` counts `high`, `max`, `oom`,
`oom_kill`; `memory.peak` and `memory.current` read usage;
`memory.oom.group` kills a cgroup's tasks together. The OOM killer
sends `SIGKILL` (*recalled*), so a killed process writes nothing.

K4. *PSI* (*read*, docs.kernel.org, `accounting/psi`).
`/proc/pressure/memory` and each cgroup's `memory.pressure` report the
share of time "some" or "all" ("full") non-idle tasks stalled on memory,
over 10, 60 and 300 s; a process can write a trigger ("some 150000
1000000") to an fd opened `O_RDWR | O_NONBLOCK` and wait for `POLLPRI`
with poll or epoll; windows run from 500 ms to 10 s, unprivileged
monitors need multiples of 2 s, notifications are rate-limited to one
per window. A PSI fd is an ordinary pollable descriptor: it fits a
reactor's epoll set (0007 §3.2).

K5. *macOS* (*read*, XNU `f6217f89`, `bsd/sys/kern_memorystatus.h:270-315`;
`bsd/kern/kern_memorystatus_policy.c:270-345`; the SDK headers).
Jetsam's kill causes are an enum: high-water, per-process limit, VM
page shortage, compressor thrashing, compressor space shortage,
*low-swap* (13, our 43 GB run's), sustained pressure and others; with
swap enabled, low swap kills swappable processes first. A killed
process gets no chance to report: the kill is `exit_with_reason(...,
SIGKILL, ...)` or `psignal(p, SIGKILL)`
(`bsd/kern/kern_memorystatus.c:2334, 3566, 3675`). Per-process limits
are footprint limits (`task_set_phys_footprint_limit_internal`,
`:262`), so what jetsam measures is the task's `phys_footprint`, which
`task_info(TASK_VM_INFO)` reports beside `compressed`,
`ledger_phys_footprint_peak` and `limit_bytes_remaining`
(`SDK/usr/include/mach/task_info.h:355-405`); resident size alone
misses compressed pages, so an "RSS" figure under-reads what jetsam
counts (*conjecture* for our records). The public pressure signal is
libdispatch's `DISPATCH_SOURCE_TYPE_MEMORYPRESSURE`, with `NORMAL`,
`WARN` and `CRITICAL`, whose header asks applications to change
*future* memory use and "NOT traverse and discard existing caches",
which would aggravate pressure (`SDK/usr/include/dispatch/source.h:134-145,
228-256`); it is in libSystem, which every macOS program links already.

K6. *Stack guards* (*read*, pinned LLVM). A guard page catches an
overflow only if no frame skips it. LLVM emits inline stack probes on
AArch64 (non-Windows) and x86 when a function or the module carries
`"probe-stack"="inline-asm"`, probing every `stack-probe-size` bytes,
default 4096, also a module flag
(`llvm/lib/Target/AArch64/AArch64MachineFunctionInfo.cpp:145-180`;
`AArch64ISelLowering.cpp:36442-36446`; `X86ISelLowering.cpp:65635`);
clang sets it for `-fstack-clash-protection`
(`clang/lib/CodeGen/CodeGenModule.cpp:1798, 3170`); the inliner
propagates it (`llvm/lib/IR/Attributes.cpp:2652-2654`). The attribute
is generated code, not inline assembly in our source. The probe size
is a page size: 4 KiB on x86_64 and arm64-4K Linux, 16 KiB on macOS
and arm64-16K Linux, a fact of the target's entry. Linux's main-thread
stack has a 256-page guard gap since the 2017 stack-clash fix
(*recalled*); our runner's reservation brings its own guard (O2).

**C. Compilers and their own memory.**

C1. *LLVM* (pinned tree). Allocation failure is
`report_bad_alloc_error`: a handler if installed, else (no exceptions,
our build) "LLVM ERROR: out of memory" written with `write` and
`abort()` (`llvm/lib/Support/ErrorHandling.cpp:178-209`); `InitLLVM`
installs a `new` handler that routes failed `operator new` there
(`:211-230`; `InitLLVM.cpp:103`). Measurement: `-time-passes` gains a
memory column with the hidden `-track-memory`
(`llvm/lib/Support/Timer.cpp:114-141, 523-526`), read from
`Process::GetMallocUsage()`: `mallinfo2`, or Darwin's
`malloc_zone_statistics(malloc_default_zone())`
(`llvm/lib/Support/Unix/Process.inc:89-115`), i.e. the system
allocator's counters, blind to an allocator that replaces malloc
(*conjecture*: snmalloc statically linked as malloc). clang's
`-fproc-stat-report` prints each subprocess's peak RSS from `wait4`'s
`ru_maxrss` (`llvm/lib/Support/Unix/Program.inc:462-466`;
`clang/lib/Driver/Driver.cpp:4710-4720`). No LLVM tool bounds its
memory.

C2. *MLIR* (pinned tree). No memory accounting anywhere:
`mlir/lib/Support/Timing.cpp` has no memory column; the pass manager's
only memory policy is to clear a nested pipeline's analyses when it
finishes, "to reduce the current working set"
(`mlir/lib/Pass/Pass.cpp:673-679`). Uniqued types and attributes live
in per-thread `BumpPtrAllocator`s for the context's lifetime
(`mlir/include/mlir/Support/StorageUniquer.h:91-136`), except in the
new *transient scope*: `MLIRContext::beginTransientScope` /
`endTransientScope` (and an RAII `TransientScope`) free every type,
attribute and affine expression made inside the scope, provided no IR
still refers to them and the scope is single-threaded
(`mlir/include/mlir/IR/MLIRContext.h:149-190`;
`mlir/lib/Support/StorageUniquer.cpp:340-445`). `PassInstrumentation`
(before/after each pass) is where a per-pass memory record would go.

C3. *rustc* (`6a586779`). `-Z time-passes` prints, per pass, the
duration and the RSS before and after, and prints a pass whenever its
RSS changed (`compiler/rustc_data_structures/src/profiling.rs:837-854,
886-930`); RSS comes from `proc_pidinfo(PROC_PIDTASKINFO).pti_resident_size`
on macOS and `/proc/self/statm` on Linux (`:955-1005`): resident size,
not footprint (K5). rustc bounds nothing; out of memory is R1's abort.

C4. *GHC* (`3d326d7d`). The simplifier's budget is *deterministic*:
`(program size + 100) × 40 × tick-factor / 100` ticks
(`compiler/GHC/Core/Opt/Simplify/Monad.hs:106-124`), but spending it
*rejects the program*: "Simplifier ticks exhausted", a program error
telling the user to raise `-fsimpl-tick-factor` (`:238-256`). The
budget idris-mlir's rule allows (AGENTS.md) is GHC's measure with the
opposite consequence. GHC's own memory is its RTS's (R7): `+RTS -M`
turns an OS kill into a named heap overflow (*recalled*).

C5. *MLton* (`5fe94339`). The compiler is an SML program on MLton's
runtime: `max-heap`, `fixed-heap` (which counts the stacks) and
`ram-slop` (the share of physical RAM the runtime may plan for)
(`doc/guide/src/RunTimeOptions.adoc:40-100`); failure is a `die`
naming the limit, "Out of memory with max heap size %s"
(`runtime/gc/heap.c:55, 128-134, 535`; `sequence-allocate.c:120`).

C6. *Go's compiler* (`05dbbf91`). `cmd/compile` bounds nothing; it
tunes its collector for *speed*, raising `GOGC` until the heap reaches
a starting goal and restoring it once the live heap is half that
(`cmd/compile/internal/base/startheap.go:30-100`; `gc/main.go:96`),
calibrated so its footprint "resemble[s] that of GOMEMLIMIT=2000MiB
GOGC=10000". Its memory is bounded by its unit, one package, not by a
budget.

C7. *Determinism is the binding constraint on a compiler's budget*
(*conjecture*, from R4, R7, C4 and 0001 D5/0006 G1). A budget counted
in the program's own units (ticks, allocations, ops, rewrites) gives
the same output on every machine and thread count; one counted in
bytes of RSS or in seconds does not, so a pipeline that "degrades when
memory is short" would make its output depend on the machine, and
`stage 2 = stage 3` (0001 D8) and the determinism tests (0006 G1)
could no longer hold.

#### 5.11.2 What it means for idris-mlir

All of this is *conjecture* until wave 2 reads our code.

**The one fact that separates us from Go.** Go's limit works because a
collector holds garbage it can trade CPU for: the pacer collects
sooner, and the limit is soft because the CPU cap lets memory overshoot
(G2, G3). A counted heap frees garbage at its last use, so there is no
frequency to turn (R3 to R5). What a counting runtime can give back
under a limit is only slack: the allocator's caches and empty slabs
(M3), the stack's pages below the deepest frame it reached, and
whatever the runtime memoizes (forced thunks, top-level constants,
0007 §6). Past that, live data is the program's, and a memory limit on
a counted heap is a *hard* limit with exactly two outcomes: a named
crash, or a report and carry on. Go's *scavenger* half (G4) carries
over; its *pacer* half does not. That is the first unknown this lane
retires: "how Go limits memory" is mostly the answer to a question a
counted heap does not have.

**(A) The compiler's own memory.**

- *Every wall so far was a representation, and every fix was one* (O1,
  §3). No limit would have fixed any of them; a limit would only have
  named the death sooner. The bound that matters is the one each
  solver's state representation gives: sized by the program's types and
  constructors and its ops, never by pairs (member × result type,
  terminator × successor) or by value × program point. MLton's
  analyses are sized that way (§5.9, B5); that is the contract §4's
  "honest solvers" header can state and wave 2 can check.
- *A budget may only stop optimization, and only in the program's
  units* (AGENTS.md; C4, C7). GHC's tick budget is the right measure
  with the wrong consequence (it rejects); Lean's heartbeats are the
  right measure for determinism. A budget in bytes or seconds would make
  the output depend on the machine and break `stage 2 = stage 3`. So
  "degrade when memory is short" is not a design available to us, and
  the passes acceptance rests on (defunctionalization, the label solve,
  counting, lowering) cannot be budgeted at all: their memory must be
  bounded by construction.
- *Running out is a crash of the machine, not a refusal of the
  program.* Today the OS kills the pipeline with `SIGKILL` and nothing
  is written (K3, K5), so a run leaves no name. Two mechanisms name
  it: an allocation that fails into our handler (rare under overcommit,
  K1), and a pressure signal before the kill (K4, K5) on which the
  compiler flushes its trace and writes one line naming the pass, the
  function and the footprint. Whether such a line is allowed is a
  question of how AGENTS.md's "a budget never rejects a program" reads
  (§5.11.4, Q2).
- *Measure what the OS kills on.* 0001 records "43 GB RSS"; jetsam
  kills on `phys_footprint`, which counts compressed pages that RSS
  misses (K5), and Linux's OOM killer scores resident plus swap plus
  page tables (K2). rustc's per-pass RSS (C3) is the pattern; MLIR has
  no memory column at all (C2), and LLVM's `-track-memory` reads the
  system malloc's counters, blind if snmalloc replaces malloc in our
  tools (C1). A `PassInstrumentation` that records the footprint after
  each pass is the MLIR-native place.
- *MLIR's own memory*: the context's uniqued types and attributes are
  never freed (C2), so attributes passes make per function accumulate
  for the whole pipeline; `MLIRContext::TransientScope` (new at the pin)
  is the one upstream way to free them, single-threaded and only when no
  IR refers to them. Analyses of a nested pipeline are dropped when it
  ends (C2).

**(B) A compiled program's memory.**

- *Out of memory is outside the program's meaning.* Every runtime read
  either aborts with a name (Go, Rust with `std`, Swift, Lean's compiled
  code, MLton, Koka) or raises a catchable exception (OCaml, GHC, JVM,
  Seastar), and only Zig makes failure a value in every signature (R2).
  For idris-mlir a value would be Hoare's null in every allocating type
  (§4's Insight 5): every constructor application would return a
  `Maybe`. An effect would be no better: if every allocating op carried
  the `Crash` resource (§2), no pure allocation could be speculated,
  sunk, CSE'd or deleted. The representation-first reading: allocation
  failure is the machine's, like stack overflow, and the runtime's one
  job is to make it a *named* crash. Rust's `no_global_oom_handling`
  (R1) is the counterpoint the owner should see: a library can be
  compiled so that an infallible allocation is unexpressible; that only
  pays where a caller can do something with the failure, which a pure
  program cannot.
- *The named crash needs three things, each one place.* One failure
  policy (snmalloc's `Conts::failure`, a type, M1); one measure (the
  backend's `StatsRange`, committed bytes, M2); and, if a limit exists,
  one more range in the pipe that fails into the same continuation. No
  check reaches compiled code: small allocations never touch the
  backend. The crash flushes the output buffer (0007 D3) and must not
  allocate on its way out (Rust's second-failure guard, R1).
- *Under overcommit, the kill usually comes first* (K1, K3, K5). A
  named crash therefore needs a limit below the OS's: one the user sets
  (Go's choice, G6; off by default, since a CLI's memory "is
  proportional to its inputs"), or the cgroup's `memory.max` read at
  start (the JVM's choice, R8). Either is a program resource of the
  kind `IDRIS_RT_SHARDS` is (0007's "no option selects behaviour").
- *Stack overflow is the same story, with a correctness edge.* The
  runner's 64 GiB reservation has a guard and an alternate signal stack
  (O2), so an overflow can be named (Rust's and Lean's handlers, R1,
  R4). But a guard only catches a frame that touches it: without stack
  probes (K6), a frame larger than the guard skips it and writes into
  whatever lies below, which 0017 D9 would make the heap's region. That
  is a silent miscompile in effect, which AGENTS.md forbids. Probes are
  an LLVM function attribute and a module flag whose probe size is the
  target's page size, so they belong to the target's entry.
- *Reservations meet the host's policies* (K2). A writable reservation
  is charged in full under strict overcommit, and every reservation
  counts against `ulimit -v`; a program that reserves 64 GiB of stack
  and 4 GiB of heap at start fails at once on such a host. Go's four
  address-space states (None, Reserved, Prepared, Ready, G1) are the
  representation that makes the distinction explicit; snmalloc has the
  `PROT_NONE` path behind a mitigation (M6). The code is target-neutral;
  only the hosts differ.
- *Returning memory.* snmalloc already releases empty chunks, with the
  Apple-specific advice that makes the footprint drop (M3). What
  nothing returns is the stack: a recursion a million frames deep
  (0017 D9's budget, `tests/foldlm-deep`) leaves its pages resident
  after it unwinds (*conjecture*). 0006's bounded-memory item is the
  measurement that would show it.
- *Shards* (0007). A shard owns an allocator, but snmalloc's backend
  ranges and `StatsRange` are process-wide statics (M2), so a
  process-wide limit falls out and a per-shard one (Seastar's share,
  Erlang's per-process heap, R9, R10) does not. A per-shard limit would
  only pay with failure isolation, and 0007 D5 ends the process on any
  shard's crash. Memory in flight is the new risk: a detach copy is
  allocated by the sender (0007 §5.1), remote frees wait in a shard's
  queue until it drains them, and the pipe's ring lives outside the
  cell heap (§9), so none of it is in the live-cell count. A shard
  about to block in its reactor should drain its allocator's queue
  first (*conjecture*).
- *A pressure signal has little to act on.* A pure program holds no
  caches to drop, and Apple's header says not to traverse caches under
  pressure anyway (K5). Inside the runtime the signal could trigger a
  release of slack (above); a pressure API for programs would be a
  language feature with no use found yet.

#### 5.11.3 Candidate designs, ranked

Each says what it buys, what it costs at §3's scale, and what it would
delete. None is a decision; the subjects stay apart.

**(A) The compiler.**

- **A1. Memory is a stated property of each solver's representation**
  (the bar, not a mechanism). Each solver's header in the solver layer
  (§4) states its state's size in the program's units (per op, per
  value, per function, per type, per constructor) and wave 2 checks it;
  a state sized by a product of two program quantities is a wall waiting
  to be met. *Buys:* the walls of §3 become unrepresentable in review
  instead of found at 47 GB. *Costs:* a line per solver and the
  discipline. *Deletes:* nothing directly; it is what the representation
  wave already does by hand, written down.
- **A2. A per-pass footprint record, MLIR-native.** One
  `PassInstrumentation` (`runAfterPass`) reads the footprint through one
  platform function (macOS `TASK_VM_INFO.phys_footprint` and its peak;
  Linux the cgroup's `memory.current`/`memory.peak` when the process is
  in one, else resident plus swap) and writes it into `-mlir-timing`'s
  report and the action profile. *Buys:* §3's table gets "how much,
  where" from every run; jetsam's measure, not RSS. *Costs:* one system
  call per pass, negligible against 70,000 functions; per optimizer node
  it would have to be sampled. *Deletes:* the guesswork between
  `sample` runs; the external peak stays the harness's.
- **A3. Name the death.** On the platform's pressure signal (libdispatch
  `CRITICAL` on macOS; a PSI trigger, or `memory.events`, on Linux) the
  compiler flushes the action profile and writes one line: the pass, the
  function or optimizer node, the footprint. It refuses nothing and
  stops nothing. *Buys:* every killed run leaves a named record; 0001's
  "trace it, don't guess" survives a `SIGKILL`. *Costs:* a watcher
  thread or the reactor's fd (0007 §3.2) in the tools, behind the
  platform layer. *Deletes:* nothing.
- **A4. Budgets in program units only.** Inlining, specialization and
  every optional pass may stop at a count of ops, rewrites or clones,
  never at bytes or seconds (C7). *Buys:* determinism across machines
  and thread counts. *Costs:* a count per optional pass. It is a rule
  for whatever P0 builds, not code.
- *Rejected:* a byte budget that degrades optimization (the output would
  depend on the machine); a hard RSS limit that ends compilation as if
  the program were at fault (a refusal by resource, which AGENTS.md
  forbids; a named crash is A3's).

**(B) A compiled program.**

- **B1. One named crash, in the allocator's types.** The runtime's
  snmalloc configuration supplies the failure continuation (M1): one
  `OutOfMemory` crash carrying the request, the committed bytes
  (`StatsRange`, M2) and the limit if any; it flushes the output buffer,
  allocates nothing, and exits with a status of its own. *Buys:* every
  failed allocation, whatever its site, means one thing. *Costs:*
  nothing on the fast path. *Deletes:* every null test after an
  allocation in the runtime's C++, if there are any (wave 2).
- **B2. Stack probes on every function**, through the module flags
  `probe-stack = "inline-asm"` and `stack-probe-size` = the target's
  page size, set from the target's entry (K6), with the runner's guard
  at least one page. *Buys:* an overflow always reaches the guard and
  becomes the runtime's named crash; no frame can write past it into the
  heap's region (0017 D9). *Costs:* a probe loop only in functions whose
  frame exceeds the probe size (rare in our code, *conjecture*).
  *Deletes:* the silent-corruption case.
- **B3. Reserve, then commit** (Go's address-space states, G1). The
  runner's one reservation (stack, guard, heap region, 0017 D9) and
  snmalloc's reservations are `PROT_NONE` until used, committed in
  chunks by the existing `notify_using` path (M2, M6). *Buys:* programs
  start under strict overcommit, and the footprint is honest. *Costs:*
  an `mprotect` per chunk committed, on the slow path. *Deletes:*
  nothing; it changes one flag and one path.
- **B4. A limit, as one more range in the pipe.** A program resource
  (an environment variable, off by default, or the cgroup's
  `memory.max` read at start) bounds `StatsRange`'s committed bytes;
  an allocation past it fails into B1's continuation. Alternatively the
  limit is the size of the one reservation itself (snmalloc's
  `FixedRangeConfig`, mimalloc's exclusive arena, Koka's 16 GiB heap,
  M7, R5): the heap cannot grow past its range, and no counter exists.
  *Buys:* a named crash before the OS's `SIGKILL`. *Costs:* one compare
  per chunk; or, for the reservation form, a fixed address-space
  budget chosen at start. *Deletes:* nothing.
- **B5. Give slack back.** Release the stack's pages below a high-water
  mark when a deep recursion has unwound (at a shard's idle point, or
  under B6's signal), and keep snmalloc's release as it is (M3).
  *Buys:* a program that recursed deep once does not keep that
  footprint. *Costs:* a `madvise` on the slow path. Waits on 0006's
  bounded-memory measurement.
- **B6. A pressure signal inside the runtime only** (libdispatch, or a
  PSI fd in the reactor's epoll set, K4, K5), whose one action is B5.
  Can wait; little to act on (§5.11.2).
- *Rejected:* allocation failure as a value or as an effect in the
  language (§5.11.2); a catchable heap-overflow exception (GHC's own
  comment, R7: unreliable and unusable); a soft limit with a CPU cap
  (there is no collector to cap); per-shard limits while a shard's
  crash ends the process (0007 D5).

#### 5.11.4 Questions for the owner and for wave 2

**For the owner, urgent** (they shape P0's runtime C++ and the
pipeline's instrumentation):
1. **Is running out of memory outside the language's meaning**, a
   named crash of the machine as stack overflow is, and never a value
   or an effect in the types? (This lane's reading: yes, §5.11.2.)
2. **Is "the compiler ran out of memory" a crash, distinct from a
   refusal**, so that a named line on pressure (A3) is allowed by "a
   budget never rejects a program"? And is every compiler budget
   counted in the program's units, never bytes or seconds (A4, C7)?
3. **Does P0 include the per-pass footprint record (A2)**, and which
   measure is the record's: `phys_footprint` on macOS; on Linux the
   cgroup's or resident plus swap?
4. **Stack probes on all four targets (B2)**: a correctness item, since
   without them an overflow past the guard is silent.

**For the owner, can wait** (until a program or a shard needs them):
5. A memory limit for programs (B4): off by default, set by an
   environment variable, or read from the cgroup's `memory.max` by
   default? A counter in the allocator's pipe, or the reservation's
   size?
6. The exit status of an out-of-memory crash and of a stack overflow:
   one status each, distinct from other crashes?
7. Returning the stack's pages after deep recursion (B5), once 0006
   measures it.
8. A pressure signal in the runtime (B6), for releasing slack only.
9. Shards: a process-wide limit only, and a reactor that drains its
   allocator's remote frees before it blocks?

**For wave 2** (what our code must be checked for):
1. What happens today when snmalloc returns null: whose `Conts`, which
   message, which exit status, and does the crash path allocate?
2. How the runner reserves its 64 GiB stack and how `HeapConfig`
   reserves its 4 GiB region: `PROT_NONE` or writable, `MAP_NORESERVE`
   or not; whether snmalloc is built with `SNMALLOC_CHECK_CLIENT` or
   `pal_enforce_access`.
3. Whether snmalloc is the compiler's own malloc (statically linked
   over libc's): if so, LLVM's `-track-memory` reads nothing (C1), and
   `peak_memory` (`tools/host.sh`) is the only measure: which one does
   it read (`ru_maxrss` is resident and misses compressed pages)?
4. Whether lowering sets `probe-stack`; the guard's size; whether an
   overflow is named today.
5. Whether `SNMALLOC_PAGESIZE` comes from the target's entry (16 KiB on
   arm64 Linux at 16 KiB pages, M5).
6. Whether an array's byte size (`n × element size`) is checked for
   overflow before it reaches the allocator (Rust's
   `CapacityOverflow`, R1).
7. Every solver and pass whose state is sized by a product of two
   program quantities (A1): the next walls, for §6's solvers lane.
8. Attributes the passes create per function or per value, and whether
   any phase could run under a `TransientScope` (C2).
9. Whether the action profile is written incrementally, so a killed run
   keeps its tail.

#### 5.11.5 Notes for other lanes

- **mlir-analysis (§5.1):** every state-model cost you measure is this
  lane's (A); the pass manager drops a nested pipeline's analyses when
  it ends (`mlir/lib/Pass/Pass.cpp:673-679`), and the context frees
  uniqued storage only in a `TransientScope` (C2).
- **llvm (§5.3):** `report_bad_alloc_error` and the `new` handler are
  LLVM's whole OOM policy (C1); `-track-memory` is blind under a
  replaced malloc; `probe-stack`/`stack-probe-size` are module flags
  the lowering can set (K6).
- **cxx26 (§5.5):** with no exceptions, `std::bad_alloc` is never seen;
  `operator new` failing goes to LLVM's handler and aborts (C1). A
  `std::expected` for allocation buys nothing under overcommit.
- **mlton (§5.9):** MLton's analysis state sized by types and
  constructors is A1's contract; its runtime's `max-heap`/`ram-slop`
  (C5) is how its compiler bounds itself.
- **rc (§5.10):** a counted heap has no collector to trade CPU for
  memory, which is why Go's soft limit does not carry over
  (§5.11.2); Lean's and Koka's OOM policies are R4 and R5; reuse lowers
  the peak, which is the only memory lever counting has.
- **dialect-design (§5.8):** out of memory should not be an effect
  resource: `MemAlloc` on a constructor must stay free of `Crash`, or
  nothing allocating is pure (§5.11.2).
- **library (§5.7):** worth snapshotting: Go's design 48409, the
  kernel's `cgroup-v2`, `psi` and `overcommit-accounting` pages, XNU's
  `kern_memorystatus.h`; `sources/docs/go-scheduler/gc-guide.html`
  already holds the GC guide.
