# 5.3 llvm: LLVM's ADT, solver frameworks, TableGen and threading

- ADT and Support as idioms against ladders and callbacks: `Casting.h`
  (variadic `isa`, `CastInfo`), `TypeSwitch`, `PointerUnion`,
  `PointerIntPair`, `STLExtras`, `function_ref` against templates
  (inlining and compile time), `unique_function`, the containers and
  their costs (`DenseMap`, `MapVector`, `SetVector`, `BitVector`,
  `SparseBitVector`, `IntEqClasses`, `EquivalenceClasses`,
  `ScopedHashTable`, `SpecificBumpPtrAllocator`), graph traits and the
  generic graph algorithms (`scc_iterator`, post order, RPOT,
  `GenericCycleInfo`, `GenericDomTree`).
- Solver frameworks in the pinned tree and how they compose analyses:
  the Attributor (abstract attributes, the dependency graph, the
  fixpoint), `SCCPSolver` and IPSCCP, `LazyValueInfo`, MemorySSA,
  clang's flow-sensitive dataflow framework
  (`clang/lib/Analysis/FlowSensitive`), clang's CFG dataflow worklists.
  Which are templates or CRTP and which are virtual, and why.
- Threading: `DefaultThreadPool`, `ThreadPoolTaskGroup`, `parallelFor`,
  `parallelForEach`, `parallelTransformReduce`, `RWMutex`; how lld and
  BOLT parallelize a whole program's data.
- TableGen as a language (multiclasses, `foreach`, `defset`, bang
  operators) and its backends; `SearchableTables`/`GenericTable`
  (lookup tables generated from records) as a model for generated
  tables replacing hand-written lists.
- LLVM's own C++ baseline at the pin, its coding standards on RTTI,
  exceptions, templates and `std::function`, and what it says about
  template compile time.

#### 5.3.1 Findings

**A. LLVM's C++ baseline and rules at the pin.**

A1. *(read)* LLVM itself is C++17: `llvm/CMakeLists.txt:93`
(`LLVM_REQUIRED_CXX_STANDARD 17`); `llvm/docs/CodingStandards.md:52`
("standard C++17 code"); the floor compilers are GCC 7.4, Clang 5.0,
Apple Clang 10.0, MSVC 19.28
(`llvm/cmake/modules/CheckCompilerVersion.cmake:7-16`). Nothing in LLVM's
headers stops a client compiling them as C++26 (we already do, §2).

A2. *(read)* No RTTI, no exceptions, "to reduce code and executable
size" (`CodingStandards.md:573-584`); LLVM's own opt-in RTTI is the
`isa`/`cast`/`dyn_cast` family. Callbacks: "you should not use the
traditional C approach of taking a function pointer and an opaque
cookie"; use a function template, or `function_ref` when the callee does
not keep the callable ("`function_ref` is to `std::function` as
`StringRef` is to `std::string`") (`llvm/docs/ProgrammersManual.md:1009-1066`).

**B. The idiom catalog: ladders, callbacks, variants, worklists.**

B1. *(read)* **Variadic `isa` costs what a trait check costs; the case
against it is representational, not speed.** `isa<A, B, C>(x)` is the fold
`(CastInfo<To, const From>::isPossible(Val) || ...)`
(`llvm/include/llvm/Support/Casting.h:546-549`). For an MLIR op each
disjunct is `TypeID::get<ConcreteType>() == info->getTypeID()`
(`mlir/include/mlir/IR/OpDefinition.h:1731-1741`): one load and one
compare per listed type. `hasTrait<T>()` is one virtual call into a fold
of the same compares (`OpDefinition.h:1566-1575`,
`mlir/include/mlir/IR/OperationSupport.h:611`), and an interface lookup
is a binary search over a sorted `SmallVector<pair<TypeID, void *>>`
(`mlir/include/mlir/Support/InterfaceSupport.h:272-281`). So an
`isa<ReturnOp, YieldOp>` ladder is not slow; it is a fact (an op class
membership, i.e. a trait such as `ReturnLike`) restated in every user,
which §4 forbids. `CastInfo` (`Casting.h:440-536`) is the hook by which a
type of ours that is not a class hierarchy (a value wrapper, a
`PointerUnion`, a handle) joins `isa`/`cast`/`dyn_cast`; `IsaPred<Ts...>`,
`CastTo<T>`, `DynCastTo<T>` are function objects for ranges
(`Casting.h:862-892`) and `make_isa_range<T>(r)` filters and casts in one
adaptor (`llvm/include/llvm/ADT/STLExtras.h:567-573`).

B2. *(read)* **`TypeSwitch` is a declared ladder.** It is a chain of
`dyn_cast`s that stops at the first hit, holding an
`std::optional<ResultT>` (or a `bool` for `void`)
(`llvm/include/llvm/ADT/TypeSwitch.h:88-158`, `166-205`); `Case<A, B>`
with one generic lambda covers several types, each `Case` is
`always_inline` and `nodebug` (`:39-50`), and `DefaultUnreachable()` (or
converting the switch to `ResultT`) asserts that a case matched
(`:150-157`). Dispatch stays linear in the case count. Upstream MLIR uses
it 234 times in `mlir/lib` (*measured*: `grep -rn "TypeSwitch<"
--include='*.cpp' mlir/lib | wc -l`), mostly in printers, exporters and
lowerings, where the set is "the ops this translation knows", not a
semantic class. It is the right form for a per-op table inside one
pass; a classification that more than one pass reads is still a trait or
an interface.

B3. *(read)* **Closed sets of our own C++ types: LLVM's three forms.**
(a) *An enum generated from a `.def` file and a CRTP visitor.*
`InstVisitor<SubClass, RetTy>` builds `switch (I.getOpcode())` from
`Instruction.def` and calls `static_cast<SubClass *>(this)->visitX(...)`,
with unhandled cases delegating up the class hierarchy
(`visitICmpInst` to `visitCmpInst`)
(`llvm/include/llvm/IR/InstVisitor.h:27-29`, `78-160`): a jump table, no
virtual call, and a subclass overrides only what it handles.
`SCCPInstVisitor` is one (`llvm/lib/Transforms/Utils/SCCPSolver.cpp:568`).
(b) *LLVM-style RTTI*, a kind enum in the base plus `classof`
(`llvm/docs/CodingStandards.md:581-584`). (c) *`std::variant` and
`std::visit`*, which LLVM barely uses. `llvm/lib`, `llvm/include`,
`mlir/lib` and `mlir/include` together hold 4.2 million lines of C++,
82 `std::variant<` and 123 `std::visit`/`std::get_if`/
`std::holds_alternative` (*measured*, grep and `wc -l` over those four
trees; only 8 `.cpp` files in `llvm/lib` and `mlir/lib` call
`std::visit`), against our 60 variants and 192 accesses in 59,886 lines
(§2): per line, about a hundred times LLVM's density (*measured*,
arithmetic). The pinned libc++ dispatches `std::visit`
on one variant of at most 11 alternatives with a `switch`
(`libcxx/include/variant:1596-1690`), so a visit is inlinable and as fast
as an enum switch; above 11 it goes through a table of function pointers.
`llvm::makeVisitor` (`STLExtras.h:1488-1537`) builds the overload set, and
is used in-tree only by its unit test. The ladder is not `std::visit`; it
is the `std::get_if`/`holds_alternative` chain (`if (auto *a =
get_if<A>(&v)) ... else if ...`), which is exactly as open to a missed
case as an `isa` chain, while one `std::visit` over an overload set is a
compile error when an alternative is unhandled.

B4. *(read)* **One-word sums.** `PointerUnion<PTs...>` keeps the
discriminant in a pointer's low bits and joins the casting family through
`CastInfo<To, PointerUnion<PTs...>>`
(`llvm/include/llvm/ADT/PointerUnion.h:190`, `350`); MLIR's own
`OpFoldResult` is `PointerUnion<Attribute, Value>` (`OpDefinition.h:273`)
and the dataflow `LatticeAnchor` is one too
(`mlir/include/mlir/Analysis/DataFlowFramework.h:251`).
`PointerIntPair<T *, Bits>` packs a small enum beside a pointer: the
Attributor stores each dependence edge as
`PointerIntPair<AADepGraphNode *, 1>` with REQUIRED/OPTIONAL in the bit
(`llvm/include/llvm/Transforms/IPO/Attributor.h:498-499`). Where our
variants are over pointers or handles (an op, a value, a block), these
are 8 bytes against `std::variant`'s 16 and keep `isa`/`dyn_cast`.

B5. *(read)* **Callbacks: three costs.** `function_ref<R(Ps...)>` is two
words, a thunk pointer and the callable's address, so every call is one
indirect call and the callable is never inlined into the callee's loop
unless the callee itself is inlined
(`llvm/include/llvm/ADT/STLFunctionalExtras.h:39-66`); it must not
outlive the callable (`LLVM_LIFETIME_BOUND`,
`ProgrammersManual.md:1062-1066`). `unique_function` owns a move-only
callable in three words of inline storage
(`llvm/include/llvm/ADT/FunctionExtras.h:55`, `76`, `239-287`).
`std::function` appears where LLVM stores a getter: `SCCPInstVisitor`'s
`GetTLI` (`SCCPSolver.cpp:569`) and IPSCCP's five analysis getters
(`llvm/lib/Transforms/IPO/SCCP.cpp:108-113`). A template parameter is
inlined, at the price of one instantiation per callable type. MLIR's own
balance is in `walk`: a template front end that `dyn_cast`s to the
callback's argument type and wraps it, over a non-template core taking
`function_ref` (`mlir/include/mlir/IR/Visitors.h:137`, `296-309`), so the
traversal is compiled once and each visited op costs one indirect call.
LLVM's rule (`ProgrammersManual.md:1009-1066`): never pointer plus
cookie; a template, or `function_ref` when the callable is not kept.

B6. *(read)* **Ranges that delete index bookkeeping.** `enumerate`,
`zip_equal` (asserts equal lengths, `STLExtras.h:856`), `concat`
(`:1167`), `map_range` (`:366`), `make_filter_range` (`:552`),
`make_early_inc_range` (erase the current element while iterating,
`:649`), `seq`, `interleave`, `is_contained`, `all_of`/`any_of`,
`erase_if`, `to_vector`. Each replaces a loop whose index ties two
parallel lists by position, the C++ form of what the representation-first
skill calls "three lists matched by position".

B7. *(read)* **Containers, and the shift to dense numbering.**
- `DenseMap`: open addressing over one allocation holding the bucket
  array of `pair<K, V>` and, after it, a bitmap of used buckets
  (`llvm/include/llvm/ADT/DenseMap.h:108-160`), sized
  `NextPowerOf2(N * 4 / 3 + 1)` (`:1080-1086`), unspecified iteration
  order. **A `DenseMap` (or `DenseSet`) allocates at least 64 buckets on
  its first insertion** (`roundUpNumBuckets`, `:272-274`; the programmer's
  manual says so, `llvm/docs/ProgrammersManual.md:2233-2246`). A map
  from 10 million values to a 40-byte lattice is about 2^24 buckets of
  48 bytes, some 800 MB, before any heap the lattice owns (*conjecture*,
  arithmetic). Worse is a small map *per* node: MLIR's solver keeps a
  `DenseMap<TypeID, unique_ptr<AnalysisState>>` per anchor
  (`mlir/include/mlir/Analysis/DataFlowFramework.h:481`) and a
  `SetVector<WorkItem>` of dependents per state, whose `DenseSet` is the
  same 64-bucket table (`:559`, `SetVector.h:55-57`): with 16-byte buckets
  that is about 1 KB each, some 2 KB per anchor before its lattice
  (*read*, the sizes; *conjecture*, that this is a large share of §3's
  627 GB). `SmallDenseMap<K, V, N>` and `SmallSetVector<T, N>` keep N
  inline; `SortedVectorMap` (a sorted `SmallVector`, `ProgrammersManual.md:2233-2258`)
  has no bucket overhead at all.
- `MapVector`: a `DenseMap<K, unsigned>` plus a vector of pairs, both
  paid for, for a deterministic order (`MapVector.h:273-274`).
  `SetVector`: a vector plus a `DenseSet`, with an optional linear-scan
  small mode up to 32 (`SetVector.h:50-61`, `330-339`): the standard
  deduplicating LIFO worklist. `PriorityWorklist`: reinsertion moves an
  element to the top (`PriorityWorklist.h:55-93`).
- `BitVector` (dense words); `SparseBitVector`, a `std::list` of 128-bit
  elements (`SparseBitVector.h:42-60`, `255-258`), cheap when sparse,
  pointer-chasing when not.
- `IntEqClasses`: union-find over `0..N-1` in one `SmallVector<unsigned>`,
  `compress()` renumbering classes densely (`IntEqClasses.h:29-65`);
  `EquivalenceClasses<T>`: a `DenseMap<T, ECValue *>` over bump-allocated
  member lists (`EquivalenceClasses.h:74-134`).
- `ScopedHashTable`: a scoped table with an allocator parameter
  (`ScopedHashTable.h:42-106`), what upstream MLIR's CSE keeps its
  available expressions in (`mlir/lib/Transforms/Utils/CSE.cpp:20`, `68-69`).
- `BumpPtrAllocator` / `SpecificBumpPtrAllocator<T>`: arenas; the
  Attributor allocates every abstract attribute in one
  (`Attributor.h:1354`, `2431`).
- **Dense numbering is LLVM's newest representational move.** IR blocks
  carry a number and functions a maximum and an epoch
  (`llvm/include/llvm/IR/BasicBlock.h:95`, `Function.h:813-827`);
  `GraphTraits` gained `getNumber`/`getMaxNumber`/`getNumberEpoch`
  (`llvm/include/llvm/ADT/GraphTraits.h:75-106`); `GenericDomTree` now
  requires node numbers (`llvm/include/llvm/Support/GenericDomTree.h:265`,
  `383-390`); and `LazyValueInfo`'s per-block cache is a vector indexed by
  block number, not a map (`llvm/lib/Analysis/LazyValueInfo.cpp:137-164`).
  MLIR at our pin has the same: `Block::getBlockID()`,
  `Region::getMaxBlockID()` (`mlir/include/mlir/IR/Block.h:65-67`,
  `426-427`; `Region.h:80-86`), wired into `GraphTraits`
  (`mlir/include/mlir/IR/RegionGraphTraits.h:35`, `69`, `105-110`). Solver
  state keyed by a dense index into a vector, instead of by pointer into a
  hash map, is where LLVM is going.

B8. *(read)* **Graphs: write `GraphTraits`, get the algorithms.**
`scc_iterator` is iterative Tarjan whose whole state is a
`DenseMap<NodeRef, unsigned>` of visit numbers and two vectors
(`llvm/include/llvm/ADT/SCCIterator.h:46-95`); `post_order`,
`ReversePostOrderTraversal`, `depth_first` with an external visited set,
`GenericDomTree`, `IDFCalculator` (MemorySSA places its phis with it,
`llvm/lib/Analysis/MemorySSA.cpp:1508-1519`), and `GenericCycleInfo<ContextT>`
(`llvm/include/llvm/ADT/GenericCycleInfo.h:79`), which is templated over
an "SSA context" and instantiated for LLVM IR and machine IR but not for
MLIR (*read*: `llvm/include/llvm/IR/CycleInfo.h`, no MLIR instantiation in
`mlir/include`). MLIR specializes `GraphTraits` for the call graph
(`mlir/include/mlir/Analysis/CallGraph.h:231-252`), blocks and regions
(`RegionGraphTraits.h`) and dominator nodes (`Dominance.h:248-258`), and
its inliner walks call-graph SCCs with `llvm::scc_iterator`
(`mlir/lib/Transforms/Utils/Inliner.cpp:259-288`). §2's
`lib/Support/Scc.cpp` is, by its name, a hand-rolled `scc_iterator`.

**C. Solver frameworks that compose analyses.**

C1. *(read)* **The Attributor** (`Attributor.h`, 6,520 lines;
`llvm/lib/Transforms/IPO/Attributor.cpp`, 4,227;
`AttributorAttributes.cpp`, 13,897).
- *State.* One abstract attribute (AA) object per (kind, IR position),
  created lazily on first query and found in
  `DenseMap<pair<const char *, IRPosition>, AbstractAttribute *> AAMap`
  (`Attributor.h:2483-2484`); the kind's identity is the address of its
  `static const char ID` (the TypeID idiom). Every AA is bump-allocated
  (`:1354`, `:2431`) and is an `IRPosition`, an `AADepGraphNode` and a
  state at once, the state mixed in by `StateWrapper<StateTy, BaseType>`
  (`:3154-3168`). States carry a *known* and an *assumed* part: "the
  assumed bits are always a subset of the known bits. Users can only add
  known bits and, except through adding known bits, they can only remove
  assumed bits. This should guarantee monotonicity" (`:2617-2626`);
  stock states are `BooleanState`, `{Bit,Inc,Dec}IntegerState`,
  `IntegerRangeState`, `SetState`, `PotentialValuesState`
  (`:2627-3150`, `:4919`).
- *Composition.* An AA reads another through
  `getAAFor<AAType>(QueryingAA, IRP, DepClass)` (`:1520-1530`,
  `:1610-1633`), which records a dependence on a stack while an update
  runs (`Attributor.cpp:3347-3374`). Dependences are dynamic: cleared when
  an AA changes and re-recorded by its next update (`:2217-2221`), and
  typed `REQUIRED` or `OPTIONAL` (`Attributor.h:487-491`); an AA that
  becomes invalid moves every `REQUIRED` dependent straight to its
  pessimistic fixpoint without running it, folding long chains in one step
  (`Attributor.cpp:2184-2212`). Generic deductions are template mixins:
  `AAReturnedFromReturnedValues<AAType, BaseType, StateType, ...>`,
  `AAArgumentFromCallSiteArguments`, `AACalleeToCallSite`
  (`AttributorAttributes.cpp:412-607`), each implementing `updateImpl` by
  `clampStateAndIndicateChange<StateType>` (`Attributor.h:3448-3454`:
  meet with `S ^= R`, report whether the assumed part moved). Which class
  to instantiate for a position kind is a macro-generated switch per AA
  (`AttributorAttributes.cpp:13741-13767`).
- *Dispatch.* `AbstractState`'s four queries and
  `AbstractAttribute::updateImpl` are virtual (`Attributor.h:2589-2622`,
  `:3399`), because the set of AA kinds is open: other passes add kinds
  of their own. Everything generic over a lattice is a template.
- *Fixpoint.* Rounds over a `SetVector` worklist
  (`Attributor.cpp:2162-2263`), capped by `attributor-max-iterations`,
  default 32 (`:93-95`). At the cap every AA that changed in the last
  round, and everything depending on it, is forced to its pessimistic
  fixpoint (`:2280-2302`); the rest take their optimistic state
  (`:2320` on). Monotonicity is not enforced: "these conditions are not
  enforced because the iteration limit will guarantee termination"
  (`Attributor.h:57-58`). A spent budget costs precision, never soundness.
- *Walk once.* An `InformationCache` indexes each function's instructions
  by opcode (`OpcodeInstMapTy = DenseMap<unsigned, InstructionVectorTy *>`)
  and keeps a list of its memory-touching instructions, built once, so
  that no attribute walks the IR again (`Attributor.h:88-93`,
  `:1214-1226`, `:1311-1332`). A position is one word, a
  `PointerIntPair<void *, NumEncodingBits, char>` (`:1020`).
- *Scope and threads.* Module or call-graph SCC (`AttributorCGSCCPass`,
  `:3424`); a light mode restricts kinds by an `Allowed` set
  (`Attributor.cpp:3960-3987`). Single-threaded.

C2. *(read)* **`SCCPSolver` and IPSCCP.**
- *State.* `DenseMap<Value *, ValueLatticeElement> ValueState`, a second
  map keyed by `(Value *, field)` for structs, tracked globals, a
  `MapVector<Function *, ValueLatticeElement>` of return values, an
  executable-block set and `DenseSet<pair<BB *, BB *>> KnownFeasibleEdges`
  (`SCCPSolver.cpp:568-633`). **No stored dependents**: when a value's
  element moves, its users come from the IR's own use lists
  (`pushUsersToWorkList`, `:1119-1135`), with a side map only for
  dependences SSA does not show (`AdditionalUsers`, `:633`).
- *Composition.* Not by separate analyses: one product lattice
  (unknown, undef, constant, not-constant, constant range, overdefined)
  in one element. Dispatch is the CRTP `InstVisitor`, and the public
  `SCCPSolver` is a pimpl over it (`SCCPSolver.h:59-67`), so the template
  machinery compiles in one `.cpp`.
- *Fixpoint.* Two worklists, instructions (`SmallSetVector`) and blocks
  (`SmallVector`) (`:616-624`); `solve()` drains both (`:2250-2276`); a
  block's first visit runs all its instructions in order and suppresses
  pushes of later instructions in the same block (`CurI`, `:1106-1117`).
  Finite height, no cap. IPSCCP is one solve over the module, with
  argument and return tracking for local functions (`SCCP.cpp:133-138`,
  `:159`); function specialization runs over the solved state, bounded
  (`:163`). Single-threaded.

C3. *(read)* **`LazyValueInfo`: a memo, not a solve.** A query pushes
`(block, value)` pairs on an explicit stack that emulates the recursion,
with a `DenseSet` of the stack's pairs to cut cycles
(`LazyValueInfo.cpp:376-399`); answers are cached per block, in the
vector indexed by block number of B7, each entry a
`SmallDenseMap<Value, ValueLatticeElement, 4>` and an overdefined set
(`:124-164`). Work per value is capped at 500, with the comment that the
cap exists only because the overdefined cache is per block (`:52`,
`:532-542`); value handles drop cached entries when IR is deleted
(`:139`). Only what is asked is computed.

C4. *(read)* **MemorySSA: a representation, not a solver.** Built once per
function: accesses chained per block, memory phis placed at the iterated
dominance frontier of the defining blocks, names resolved by one
dominator-tree walk (`MemorySSA.cpp:1508-1590`); no fixpoint anywhere.
Queries walk the side IR's def-use edges through a caching walker whose
upward search stops at 100 accesses (`:76-79`), costing precision only;
`MemorySSAUpdater` keeps it current and passes preserve it as a cached
analysis. The fact "which write may clobber this read" lives in an
SSA-shaped side IR (`MemorySSA.h:9-80`), and every client reads edges.

C5. *(read)* **clang's flow-sensitive framework.**
- *Dispatch.* A CRTP adapter, `DataflowAnalysis<Derived, LatticeT>`
  (`clang/include/clang/Analysis/FlowSensitive/DataflowAnalysis.h:79-196`),
  over a type-erased virtual base whose lattice is an `llvm::Any`
  (`any_cast` in every `...TypeErased` method, `:97-124`); the driver,
  `runTypeErasedDataflowAnalysis`, is compiled once
  (`clang/lib/Analysis/FlowSensitive/TypeErasedDataflowAnalysis.cpp:506`).
  Optional members (`widen`, `transferBranch`) are detected by `Rank0`/
  `Rank1` overload ranking (`:131-170`), the pre-concepts form of a
  `requires` clause.
- *State.* One state per CFG block, in
  `std::vector<std::optional<State>> BlockStates(CFG.size())` indexed by
  block ID (`TypeErasedDataflowAnalysis.cpp:540`); the states inside a
  block are not stored but recomputed by rerunning the block's transfer.
  The environment's maps (`DenseMap`s and `MapVector`s,
  `DataflowEnvironment.h:849-858`) are forked per block; formulas are
  hash-consed into a bump-allocated `Arena` (`Arena.h:21-140`); path
  conditions go to a SAT solver capped at 10^9 iterations
  (`DataflowAnalysis.h:213`).
- *Worklist.* A priority queue in reverse post order with a `BitVector`
  of enqueued block IDs (`clang/include/clang/Analysis/FlowSensitive/DataflowWorklist.h:23-50`;
  a weak-topological-order variant beside it), widening at back edges of
  unstructured loops.
- *Bound.* `kDefaultMaxBlockVisits = 20'000` (`DataflowAnalysis.h:216`);
  exceeding it returns an `llvm::Expected` error (`std::errc::timed_out`),
  and a CFG with more reachable blocks than the cap is refused before the
  solve starts (`TypeErasedDataflowAnalysis.cpp:528-533`, `:554-557`). Intraprocedural.
  Single-threaded.

C6. *(read; mlir-analysis lane, §5.1 A1-A3)* For contrast, MLIR's
`DataFlowSolver` keeps a heap object per (anchor, analysis) in nested
hash maps, a stored dependent set per state, a FIFO queue, and uniqued
program points it never frees.

C7. *(read, a synthesis of C1-C6)* **The state models side by side.**

| framework | state keyed by | dependents | fixpoint | bound, and what it costs | dispatch |
| --- | --- | --- | --- | --- | --- |
| Attributor | (kind, position), lazily | stored, re-recorded per update, 1-bit class | rounds | 32 rounds; precision | virtual update, template mixins |
| SCCP / IPSCCP | `Value *` in one map | the IR's use lists | worklist | none (finite lattice) | CRTP visitor, pimpl |
| LazyValueInfo | (block number, value), a cache | none: a demand stack | on demand | 500 per value; precision | plain functions |
| MemorySSA | a side IR | the side IR's def-use | none: constructed | walker, 100; precision | none |
| clang flow-sensitive | block ID, in a vector | CFG successors | RPO priority queue | 20,000 visits; an error | CRTP over a type-erased core |
| MLIR `DataFlowSolver` | (anchor, TypeID), nested maps | stored per state | FIFO queue | none | virtual |

None of the five LLVM and clang frameworks is threaded. Two of them do
not solve at all (MemorySSA builds a representation; LVI memoizes
answers), and the one that scales to whole modules without a budget
(SCCP) stores no dependents and keeps one flat map.

**D. Threading: the primitives, and how lld and BOLT share a whole
program's data.**

D1. *(read)* **Two pools, not one.** `llvm/Support/ThreadPool.h` defines
`ThreadPoolInterface` (virtual `asyncEnqueue`, `wait`,
`wait(ThreadPoolTaskGroup &)`, `getMaxConcurrency`; `:35-75`), with
`StdThreadPool` (a `std::deque` of `unique_function` tasks under one
mutex and two condition variables, `:147-203`) and
`SingleThreadExecutor`; `DefaultThreadPool` is the former when threads are
enabled (`:260-262`); a `ThreadPoolTaskGroup` (`:269`) lets a worker wait
on its own group while helping drain it. Separately,
`llvm/Support/Parallel.h` runs `parallelFor`, `parallelForEach`,
`parallelTransformReduce`, `parallelSort` and `TaskGroup` on a *global*
executor configured by `parallel::strategy` (`:32`, `:70-81`,
`:194-258`), a work stack with a thread-local thread index
(`llvm/lib/Support/Parallel.cpp:31-187`). `parallelFor` hands out chunks
of `N / (workers * 4)` items from one atomic counter, runs one worker on
the calling thread, and keeps the task count O(threads) (`Parallel.cpp:255-293`).
MLIR does not use that executor: `mlir/IR/Threading.h`'s
`failableParallelForEach`/`parallelForEach`/`parallelFor` run on the
`MLIRContext`'s pool, claim one element at a time from an atomic index,
order diagnostics by element through a `ParallelDiagnosticHandler`, run
serially when the context's multithreading is off, and wait in a task
group so that a nested call from a worker helps instead of deadlocking
(`mlir/include/mlir/IR/Threading.h:36-88`). The pass manager's
op-to-op adaptor is exactly that loop, claiming a cloned pass manager per
worker by compare-and-swap (`mlir/lib/Pass/Pass.cpp:985-1010`). Calling
`llvm::parallelFor` from inside an MLIR pass puts a second pool beside the
context's (*conjecture*: oversubscription, and no participation in the
context's task groups).

D2. *(read)* **lld's idioms for one program's data.**
- *Double-buffered state for a parallel fixpoint.* ICF partitions
  sections into equivalence classes and refines them to a fixpoint (an
  optimistic partition refinement, 3-5 rounds on small programs, more than
  20 on Chromium) (`lld/ELF/ICF.cpp:31-61`). Each section holds two
  class slots, `eqClass[2]`; a round reads slot `cnt % 2` and writes slot
  `(cnt + 1) % 2`, because "we cannot update equivalence classes in place
  because it breaks the invariance that all possibly-identical sections
  must be in the same equivalence class at any moment"; single-threaded it
  uses one slot and converges faster (`ICF.cpp:126-157`). Work is split
  into 256 shards whose boundaries are moved to class boundaries first, so
  no two shards touch one class, and an `std::atomic<bool> repeat` decides
  the next round (`:127`, `:413-445`). The state is two `uint32_t`s per
  section, stored in the section.
- *Owner-computes sharded tables.* To deduplicate millions of names,
  every thread scans all inputs but inserts only the entries whose hash's
  top bits select one of its shards, into that shard's private `DenseMap`;
  offsets are then a per-shard prefix sum
  (`lld/ELF/SyntheticSections.cpp:2934-3033`; the GDB index the same way,
  `:3345-3352`). No locks.
- *Per-worker outputs, dynamic claim.* Relocation scanning claims files
  off one atomic counter and writes into the worker's own shard
  (`lld/ELF/Relocations.cpp:1188-1215`); heterogeneous jobs go to a
  `parallel::TaskGroup` (`lld/ELF/OutputSections.cpp:394`, `596`).
  The one target whose scan mutates a shared section (MIPS) runs with one
  worker (`Relocations.cpp:1196-1199`).

D3. *(read)* **BOLT: cost-weighted static partition.**
`ParallelUtilities::runOnEachFunction(BC, SchedulingPolicy, WorkFunction,
SkipPredicate, ...)` (`bolt/include/bolt/Core/ParallelUtilities.h`)
estimates each function's cost by a policy (`SP_TRIVIAL`, `SP_CONSTANT`,
`SP_INST_LINEAR`, `SP_INST_QUADRATIC`, `SP_BB_LINEAR`, `SP_BB_QUADRATIC`),
cuts the function list into `TasksPerThread * ThreadCount` blocks of equal
estimated cost (20 tasks per thread by default) and hands them to the pool
(`bolt/lib/Core/ParallelUtilities.cpp:38-42`, `121-168`).
`runOnEachFunctionWithUniqueAllocId` gives each task its own annotation
allocator, created under a `RWMutex` (`:170-216`). 21 call sites in
`bolt/lib/Passes` (*measured*). The work is per function; what is shared
across functions is read-only during the parallel phase.

D4. *(read)* **The rest of the kit.** `ConcurrentHashTable`, insert-only,
buckets resized independently (`llvm/include/llvm/ADT/ConcurrentHashtable.h:15-47`),
used by the parallel DWARF linker's type pool
(`llvm/lib/DWARFLinker/Parallel/TypePool.h`); `PerThreadAllocator`, a
sub-allocator per thread for lock-free allocation
(`llvm/include/llvm/Support/PerThreadBumpPtrAllocator.h:23-34`);
`SmartRWMutex` and its scoped reader and writer
(`llvm/include/llvm/Support/RWMutex.h:99-192`). None of LLVM's or clang's
analysis frameworks (C1-C5) is threaded; LLVM's parallelism is in lld,
BOLT, ThinLTO and the DWARF linker, always over data partitioned by an
owner (a file, a function, a shard of a hash) or read-only, and in one
case (ICF) a fixpoint made parallel by giving the next round its own
copy of the state.

**E. TableGen as a language, and generated tables.**

E1. *(read)* **The language at the pin** (`llvm/docs/TableGen/ProgRef.md`).
Records are instances of classes with template arguments; `multiclass`
and `defm` stamp out families (`:1021-1122`); `foreach` iterates over a
list or range (`:1378`); `defset` collects every record defined in its
scope into a global `list<Class>` (`:1309-1333`); `defvar`, `if`,
`assert` (a nonfatal, checked condition, `:1467-1480`), `dump`, and the
new `deftype` (`:1335`). Classes double as subroutines: instantiate an
anonymous record and read its `ret` field (`:1645-1690`). The bang
operators (`:210-232`, Appendix A from `:1748`) include `!cond`, `!foldl`,
`!filter`, `!foreach`, `!isa<T>`, `!exists<T>`, `!initialized`, `!match`
(a regular expression on a string), and `!instances<T>([regex])`, which
yields every record of type `T` defined so far (`:1975-1985`): a list of
"every op that carries trait X" can be computed in TableGen itself,
checked with `assert`, and handed to a backend as one record.

E2. *(read)* **`SearchableTables`: generated lookup tables.**
`include "llvm/TableGen/SearchableTable.td"` gives three classes
(`llvm/include/llvm/TableGen/SearchableTable.td`): `GenericEnum` (an enum
with one enumerator per record of a `FilterClass`, named and valued by
fields), `GenericTable` (a sorted constant array of one C++ struct per
record, with `Fields`, an optional `PrimaryKey` and a generated
`PrimaryKeyName` lookup by binary search, optionally returning a range),
and `SearchIndex` (a secondary key, another generated lookup). Output is
guarded by `GET_<name>_DECL` and `GET_<name>_IMPL`. AArch64's system
operands are the reference user: `class AT<...>` records, `def ATValues :
GenericEnum`, `def ATsList : GenericTable` keyed by `Encoding` with
`lookupATByEncoding`, and `def lookupATByName : SearchIndex`
(`llvm/lib/Target/AArch64/AArch64SystemOperands.td:44-75`), included by
`AArch64BaseInfo.h:499-500`. The emitter lives in `llvm-tblgen` itself
(`llvm/utils/TableGen/SearchableTableEmitter.cpp`, built into the tool
by `llvm/utils/TableGen/CMakeLists.txt:31`, `66`), not in a library, so a
custom backend cannot link it; any `.td` can still be fed to
`llvm-tblgen -gen-searchable-tables`, because the language is the same for
every backend (*conjecture*: our `.td` files include MLIR's `OpBase.td`,
which `llvm-tblgen` parses like any other records; to be tried).

E3. *(read)* **Custom backends the upstream way.** `mlir-tblgen` is a
driver over a registry: a backend is a global
`mlir::GenRegistration` (`mlir/include/mlir/TableGen/GenInfo.h:60`), and
`MlirTblgenMain` (`mlir/include/mlir/Tools/mlir-tblgen/MlirTblgenMain.h:18-23`)
is the `main` a custom tool links to get every upstream generator plus
its own. Backends read records through typed wrappers in
`mlir/include/mlir/TableGen/` (`Operator.h`, `Trait.h`, `Interfaces.h`,
`SideEffects.h`, whose `SideEffect` exposes an effect's name and resource,
`:24-53`, `EnumInfo.h`, `Property.h`, `Pass.h`), so a backend that mirrors
the dialect into another language reads traits and effects as data, not
by matching strings in `.td` text.

E4. *(read)* **The C++ X-macro is TableGen's poor relation.** LLVM still
generates closed dispatch from `.def` files (`Instruction.def` into
`InstVisitor`'s switch, `llvm/include/llvm/IR/InstVisitor.h:24`, `119-160`);
the TableGen form of the same thing is an enum and a table generated from
records, which both C++ and any other mirror (our Idris side) read.

E5. *(read)* **LLVM's rules that bear on all of this**
(`llvm/docs/CodingStandards.md`, `ProgrammersManual.md`). No RTTI, no
exceptions: `LLVM_ENABLE_RTTI` and `LLVM_ENABLE_EH` default off and
exceptions require RTTI (`llvm/cmake/modules/HandleLLVMOptions.cmake:1241-1244`;
`-fno-rtti`/`-fno-exceptions`, `llvm/cmake/modules/AddLLVM.cmake:26-38`).
So `dynamic_cast` and `typeid` are out, and with them `std::any`
(*recalled*: clang's framework uses `llvm::Any` instead, C5, plausibly
for this reason); `std::function` works without RTTI unless
`target_type()` is called, and a visit of a valueless variant aborts
rather than throws (*recalled*, both for lane cxx26 to check). No static
constructors (`CodingStandards.md:600-640`), which constrains global
registries (*conjecture*: `mlir-tblgen`'s `GenRegistration` globals are
tolerated because they live only in a build tool). An API taking a
callable takes it last (`CodingStandards.md:491-494`). The standards say
nothing about template compile time beyond "`#include` hurts compile time
performance" (`:873`); in the code read here, heavy templates sit behind
a pimpl (`SCCPSolver`, C2) or a type-erased core (clang's framework, C5;
MLIR's `walk`, B5). MLIR itself still builds as C++17
(`mlir/CMakeLists.txt:27`), so nothing upstream exercises C++20 concepts in
these headers; a client compiling them as C++26 is on its own for
diagnostics (*read*: §2, we already do).

#### 5.3.2 What it means for idris-mlir

All *conjecture* until wave 2 reads our code; each line names the §2
count or §3 wall it bears on.

M1. **The 48 multi-type `isa<A, B, ...>` ladders** (§2) are not a speed
problem (B1) but a fact restated per use. Over ops they become a trait or
an interface (§5.2, §5.8 own which): the four `isa<ReturnOp, YieldOp>` in
`Transforms/Tail` (§2) are what upstream's `ReturnLike`, a `TraitList`
of the `ReturnLike` marker and `RegionBranchTerminatorOpInterface`, already
says (`mlir/include/mlir/Interfaces/ControlFlowInterfaces.td:638-640`).
Over our own C++ types (lattice elements, solver nodes, plan entries) the
same ladder becomes one `std::visit`, a concept, or a CRTP visitor (B3).

M2. **The 60 variants and 192 `visit`/`get_if`/`holds_alternative`** (§2)
are more accesses than all of LLVM's and MLIR's 4.2 million lines hold
(123), at about a hundred times their density (B3).
Each falls into one of three cases: a sum over pointers or handles (an op,
a block, a value), which is a `PointerUnion` and keeps `isa`/`dyn_cast`
(B4); a sum that is a lattice element, which belongs to the solver layer's
`Lattice` concept (design S1); or a genuine closed sum of our own data,
where the `get_if` chains become one `std::visit` over an overload set
that fails to compile when an alternative is missed (B3).

M3. **The 84 `function_ref`s** (§2) split by where they sit. A callback
into a traversal compiled once and called off the hot path is LLVM's own
idiom (B5) and stays. A callback on a hot path (a transfer function per op
or per edge, a per-use visitor inside a solve) becomes a template
parameter constrained by `std::invocable`, inlined. A callback that hands
code the static type it already knows is §4's "callback threaded through
code that knows its static type", and becomes a template on that type.

M4. **The 87 `worklist`s and `lib/Support/Scc.cpp`** (§2) are what
`scc_iterator`, `post_order`/`ReversePostOrderTraversal`, `depth_first`,
`IDFCalculator` and an RPO priority worklist with a `BitVector` of enqueued
ids already are (B8, C5). Our graphs (exclusivity's graph, `idr-rc-stack`'s
flow graph, the label solve's graph) get them by specializing
`GraphTraits` once, with `getNumber`/`getMaxNumber` so that dominator
trees and cycle info accept them (B7).

M5. **The 212 `DenseMap`/`DenseSet`s** (§2) must be sorted into "one per
solve" (fine) and "one per node" (each one at least 64 buckets, about 1 KB,
once it holds anything; B7). The second kind is the shape of several §3
walls: `idr-rc-stack`'s "candidate bit vector per value, copied along
every edge" and exclusivity's "lattice per value ... nested maps" on the
dataflow framework are per-node containers. LLVM's answer is dense
numbering: state in a vector indexed by a node number, as
`LazyValueInfo`, `GenericDomTree` and clang's framework do (B7, C3, C5),
and as MLIR already offers for blocks (`Block::getBlockID`).

M6. **§3's dataflow wall is a state-model wall, and the frameworks agree**
(C7). The two LLVM solvers that scale to whole modules keep no per-node
heap object: SCCP keeps one flat map and reads dependents off use lists;
clang keeps a vector of block states and recomputes inside blocks. The
two that keep a heap object per fact bound it by laziness (the
Attributor creates an attribute only where one is queried) or by a cap
(`LazyValueInfo`). MLIR's solver does neither. This confirms §3's first
conjecture from outside our code.

M7. **Our recent fixes are the SCCP shape, found by hand.** "Exclusivity
marks the program graph", "`idr-rc-stack`'s inference is the flow graph,
marked", "a component's answer is data" (§2's recent commits, §3):
dependents read off a graph's edges, a mark per node, the answer a value.
The solver layer (S1) makes that one generic mechanism instead of one per
analysis: build the graph once, mark or solve over it, return a frozen
`Solution`.

M8. **Threading.** None of LLVM's analysis frameworks is threaded (C7,
D4); where LLVM is parallel it partitions data by owner or freezes it
(D2, D3). For us that means: per-function analyses run under MLIR's pass
manager (already parallel, D1); whole-program solves run over the
call graph's condensation level by level with `mlir::parallelForEach`
on the context's pool, each SCC writing only its own nodes; and §2's 22
`std::mutex`/`std::atomic`/`SmartMutex` and 10 `parallelFor*` must each
be checked against that model (and against D1's warning about
`llvm::parallelFor` inside a pass). §3's "threads queued on the context's
write lock" (98c6315c) is a mutable type read under the context's lock:
a fact kept in a uniqued mutable type rather than in frozen analysis
data, the exact thing D2's idioms avoid.

M9. **Budgets.** The Attributor's model (a spent round budget forces the
pessimistic state, costs precision, never soundness; C1) and MemorySSA's
(a capped walk returns a conservative clobber; C4) fit AGENTS.md's "a
spent budget leaves the program less optimized and never rejects it".
clang's model (a spent budget is an `llvm::Expected` error; C5) does not:
we must never copy it. An analysis that a refusal rests on gets
termination by construction (a finite-height lattice, or widening), no
cap at all.

M10. **TableGen.** §2's custom backend `idris-mlir-tblgen` and the
hand-written lists in C++ (switches on our enums in several places, §2's
44 `switch`es) have three upstream tools: `!instances<T>` and `assert` to
compute and check record sets in `.td` (E1); `GenericTable`/`SearchIndex`
for generated lookup tables (E2); and `MlirTblgenMain` with
`GenRegistration` and the `mlir::tblgen` wrappers, so the Idris mirror's
generator reads traits and effects as typed data, in a tool that also
runs every upstream generator (E3). LLVM is itself moving `cl::opt`
globals into TableGen-declared option structs
(`llvm/include/llvm/Option/LibraryOptions.td:9-50`,
`llvm/lib/Passes/PassesOptions.td`): a hand list and a static
constructor replaced by one record set.

M11. **The C++ baseline.** We build C++26 against headers that upstream
builds only as C++17 (A1, E5): concepts, `requires` and deducing `this`
are ours to use but never tested upstream inside those headers. No RTTI
and no exceptions hold for us as for LLVM (static linking of LLVM's
libraries built `-fno-rtti`; E5), so `std::any`, `dynamic_cast` and
`typeid` are out; `std::expected` and `std::variant` stay usable, a
`value()` on an error or a visit of a valueless variant aborting instead
of throwing (*recalled*, libc++'s behaviour under `-fno-exceptions`, for
lane cxx26 to check); every C++26 feature lane cxx26 proposes must work
under both flags.

M12. **The 104 `.walk(`s** (§2). The Attributor walks each function once
and indexes its instructions by opcode for every attribute to read (C1,
"walk once"); MLIR's own form of the same idea would be a cached analysis
per function mapping op kind (or trait, or interface) to its ops. Wave 2
counts how many walks in one pass, and across a pipeline stage, re-find
the same ops.

#### 5.3.3 Candidate designs, ranked

Two deliverables: the solver layer (decision D2), ranked S0 to S4, and
the idiom catalog as rules with before and after, I1 to I8. Sizes at §3's
scale are *conjecture*: N is the number of solver nodes (values or program
points), E the edges; the stage-1 module is 71 MB of text and some 70,000
functions, so N in the low tens of millions is the scale to plan for.

**S0. Before any solver: the representation that makes the solve
unnecessary** (MemorySSA's lesson, C4). A fact that is a def-use chain
belongs in the IR, built once and read by every pass, not re-derived by a
solve. Our `!idr.world` token already is, for IO, what MemorySSA is for
LLVM's memory: an SSA chain of every state change. Grades in types
(`!idr.q`) are the same move for linearity. Before S1 is given an
analysis, wave 2 asks of it: could the dialect carry this answer (a type,
a token, an op) so that no pass solves for it? What survives that
question goes to S1. (§5.8 owns the dialect side.) *Buys*: deletes the
analysis. *Costs*: a dialect change, verified after every pass.

**S1. The solver layer: one graph, one state vector, one schedule,
templates throughout.** A synthesis of SCCP's dependents-by-edges (C2),
clang's state-per-node-in-a-vector and RPO priority worklist (C5),
MemorySSA's build-once side structure (C4), LLVM's dense numbering (B7),
`scc_iterator` (B8), and lld's owner-computes parallelism (D2). A sketch
(names *conjecture*):

```cpp
namespace idr::solve {

// A node is a dense index; nothing in a solve is keyed by pointer.
enum class Node : std::uint32_t {};

// The graph is built once from the IR and then frozen: compressed sparse
// rows, forward and reverse. Building it is the only place that hashes.
class Graph {
  std::vector<std::uint32_t> succStart, succ, predStart, pred;
public:
  std::uint32_t size() const;
  std::span<const Node> successors(Node) const;
  std::span<const Node> predecessors(Node) const;
};

// Direction is a type, not a flag.
struct Forward {};
struct Backward {};

enum class Changed : bool { No, Yes };

template <typename L>
concept Lattice = std::regular<L> && requires(L &l, const L &r) {
  { L::bottom() } -> std::same_as<L>;
  { l.join(r) } -> std::same_as<Changed>;
};

template <typename A>
concept Analysis = requires(const A &a, Node n, const typename A::State &in) {
  requires Lattice<typename A::State>;
  typename A::Direction;
  { a.transfer(n, in) } -> std::same_as<typename A::State>;
};

// The answer is data: a frozen vector, cached in MLIR's AnalysisManager.
template <Analysis A> class Solution {
  std::vector<typename A::State> states;
public:
  const typename A::State &operator[](Node) const;
};

// Instantiated once per analysis, in that analysis's .cpp.
template <Analysis A> Solution<A> solve(const Graph &, const A &);

// The two-point lattice is marking: a BitVector and a breadth-first walk,
// linear time. Exclusivity's and idr-rc-stack's markings become calls.
llvm::BitVector mark(const Graph &, std::span<const Node> seeds);

} // namespace idr::solve

template <> struct llvm::GraphTraits<const idr::solve::Graph *>;  // with
// getNumber/getMaxNumber, so scc_iterator, post_order, GenericDomTree
// and GenericCycleInfo all accept our graphs.
```

- *Schedule.* `solve` walks the graph's SCCs with `scc_iterator` (sinks
  first: a backward analysis takes them in that order, a forward one
  reversed); inside an SCC an RPO priority worklist over a `BitVector`
  of enqueued nodes (clang's `DataflowWorklistBase`). An acyclic part
  converges in one visit per node.
- *Composition, explicit in the types.* An analysis that only reads
  another's finished answer takes `const Solution<B> &` in its
  constructor: the dependency is a parameter, the order is whoever builds
  them, and a cycle cannot be written. Analyses that genuinely need each
  other's in-flight state (as MLIR's dead-code and constant analyses do,
  the reason they must load together, §5.1) are one analysis whose state
  is a product, `Product<A, B>`, with componentwise join, as SCCP's
  single lattice element is (C2). No dynamic dependency recording (the
  Attributor's), because our set of analyses is closed and known.
- *Threading, explicit.* Per-function solves run in function passes under
  MLIR's pass manager. Whole-program solves run SCC by SCC over the call
  graph's condensation, level by level, with `mlir::parallelForEach(ctx,
  level, ...)` (D1): each SCC writes only its own nodes' entries of the
  state vector and reads lower levels, which are finished, so no lock and
  a result independent of the schedule (the least fixpoint of a monotone
  transfer is unique; an analysis that widens must widen at points fixed
  by the graph, not by the visiting order, or it loses this). A giant
  SCC, if the stage-1 module's call graph has one, runs serially or in
  double-buffered rounds as lld's ICF does (D2), a choice each analysis
  states.
- *Concepts here, interfaces over ops.* The concepts above constrain our
  own C++ (graphs, lattices, analyses); what an op is or does stays an
  MLIR trait or interface, read while the graph is built. This is §8 Q1's
  proposed line, and S1 depends on it.
- *Memory.* About 8(N + E) bytes of graph (two CSR directions of 4-byte
  ids) plus N times the state's size; for N = 10 million, E = 30 million
  and an 8-byte state, about 400 MB, against about 2 KB per anchor on
  MLIR's solver before any lattice (B7), some 20 GB at the same N
  (*conjecture*, arithmetic).
- *Termination and budgets.* Finite height or widening at SCC back edges
  (clang's `widen`, C5) for every analysis a refusal rests on; an
  optimization-only analysis may stop at a budget and then takes the
  Attributor's pessimistic state (C1, M9). No error on a budget, ever.
- *Dispatch and compile time.* No virtual functions: each analysis
  instantiates `solve` once, explicitly, in its own translation unit
  (`extern template` in the header), which is SCCP's pimpl reason (C2)
  without clang's type erasure (C5). Some 15 to 20 instantiations.
- *What it deletes* (*conjecture*, for wave 2 to confirm): the hand-rolled
  SCC utility, per-analysis worklists and graph types, the per-node
  containers behind §3's `idr-rc-stack` and exclusivity walls, and the
  dataflow-framework users that solve over the whole program.
- *What it costs*: a numbering step per solve (one `DenseMap<Value, Node>`
  while the graph is built, freed after, or a per-function local
  numbering with a base offset); a graph build that must itself be linear
  (e96bb991's quadratic interface queries were in a graph build, §3); and
  an honest header per analysis stating what upstream lacks (§4).

**S2. Upstream's `DataFlowSolver`, scoped and patched, for what is local.**
Analyses whose answer is per function (ranges inside a function, lanes,
copies) stay on upstream's framework, run in function passes so a solver
and its uniqued program points live for one function only, with an
`upstream/` patch for the two per-node containers of B7 (the per-anchor
`DenseMap<TypeID, ...>` and the per-state `SetVector` of dependents, to
inline-small forms) if §5.1 confirms them. *Buys*: §4's first preference;
upstream analyses (`IntegerRangeAnalysis`, `DeadCodeAnalysis`) composed
for free. *Costs*: per-op program points remain, acceptable at function
scale only. *Deletes*: nothing of ours; keeps §2's local users.

**S3. An Attributor (IREE's DFX on MLIR, §5.6) for open, demand-driven
facts.** One object per (kind, position), created on first query, with
dependences recorded per update and a round budget that falls back to the
pessimistic state (C1). *Buys*: laziness (only queried positions cost
anything), an open set of fact kinds, cross-fact composition without a
graph build. *Costs*: a heap object and a `SmallSetVector` of edges per
fact, virtual dispatch per update, rounds; and it is off by default in
LLVM's own pipelines (`attributor-enable` defaults to `NONE`,
`llvm/lib/Passes/PassesOptions.td:14`; *recalled*: for compile time),
used where facts are few (OpenMP offload, `OpenMPOpt.cpp:3538`, `3768`;
AMDGPU). Its strengths, an open set of kinds and laziness, are not our
case: our analyses are a closed set and most of them need every node, so
it ranks below S1, worth it only for a few demand-driven facts per
function.

**S4. `LazyValueInfo`'s memo for sparse queries.** Where a fact is asked
at a few sites (a bounds check, a division), compute on demand with an
explicit stack and a per-block cache in a vector indexed by block id
(C3). *Buys*: no whole-program state. *Costs*: repeated work, a per-value
cap. A tool for one analysis, not a layer.

**The idiom catalog, as rules** (each with LLVM's precedent; the
classification of ops is §5.2's and §5.8's).

- **I1. A ladder over ops is a trait.** Before: `if (isa<ReturnOp,
  YieldOp>(op))`. After: `if (op->hasTrait<OpTrait::ReturnLike>())`
  (`ControlFlowInterfaces.td:638-640`). Cost: comparable, one virtual
  call against a few compares (B1).
- **I2. A per-pass table over ops is a `TypeSwitch` with
  `DefaultUnreachable`** (or `.Default` when the set is open), never an
  `if`/`else if` chain of `dyn_cast` (TypeSwitch.h:150-157; 234 upstream
  uses).
- **I3. A closed sum of our own data is visited once and exhaustively.**
  Before: `if (auto *c = std::get_if<Const>(&v)) ...; else if (auto *r =
  std::get_if<Range>(&v)) ...`. After: `std::visit(llvm::makeVisitor(
  [&](const Const &c) { ... }, [&](const Range &r) { ... }, [&](const Top
  &) { ... }), v);` (a missing alternative does not compile; switch
  dispatch up to 11 alternatives, `libcxx/include/variant:1596`). For a
  sum whose cases are ours to name, a `.def`/TableGen enum and a CRTP
  visitor (`InstVisitor`) is the LLVM form (B3).
- **I4. A sum of handles is one word.** Before: `std::variant<Operation
  *, Block *>`. After: `llvm::PointerUnion<Operation *, Block *>`, with
  `isa`/`dyn_cast` (B4).
- **I5. A hot callback is a template; a cold one is a `function_ref`.**
  Before: `void forEachUse(Value, function_ref<void(OpOperand &)>)` called
  per op in a transfer. After: `template <std::invocable<OpOperand &> F>
  void forEachUse(Value, F &&)`. A traversal compiled once with a cold
  callback keeps `function_ref`, as MLIR's `walk` does (B5); a stored
  callback is a `unique_function`.
- **I6. A worklist is a schedule, and a graph has `GraphTraits`.**
  Before: a `std::deque` and a `DenseSet` of seen nodes. After:
  `scc_iterator`/`post_order` over `GraphTraits`, or `idr::solve::solve`
  (S1) (B8, C5).
- **I7. Per-node state is a vector indexed by a dense number**, never a
  map per node (64 buckets each, B7); small per-node sets are
  `SmallSetVector`/`SmallDenseMap`/`SortedVectorMap`; arenas
  (`BumpPtrAllocator`, `SpecificBumpPtrAllocator`) for solver-lifetime
  objects (C1).
- **I8. A list in C++ that mirrors records is generated**: from ODS by
  `mlir-tblgen` (enums: `EnumAttr`), by `!instances` in TableGen (E1), by
  `GenericTable` (E2), or by our backend through `MlirTblgenMain` and the
  `mlir::tblgen` wrappers (E3).

The costs of the catalog's forms, side by side (*read*, from the cited
headers; sizes on a 64-bit target):

| form | dispatch | callee inlined | size | compile cost |
| --- | --- | --- | --- | --- |
| `isa<A, B, C>` on an op | one compare per type | yes | none | none |
| `hasTrait<T>()` | one virtual call, then compares | no | none | none |
| interface cast | binary search of the interface map | no | none | none |
| `TypeSwitch` | linear `dyn_cast` chain | each `Case` forced inline | `optional<R>` | one instantiation per switch |
| `std::visit`, at most 11 alternatives | `switch` | yes | the variant (index plus largest alternative) | one per visit site |
| CRTP visitor (`InstVisitor`) | `switch` on a generated enum | yes | none | one per visitor |
| `PointerUnion<A *, B *>` | low-bit test | yes | 8 bytes | none |
| `function_ref` | indirect call per invocation | no, unless the callee is | 16 bytes | callee compiled once |
| template callable | direct | yes | the callable | callee per callable type |
| `unique_function` | indirect | no | 32 bytes, heap above 24 | once |

#### 5.3.4 Questions for the owner and for wave 2

*Questions for the owner.*

- **Q-llvm-1. Monomorphized or type-erased solver core?** The owner asks
  for monomorphized C++ (§1); clang chose a CRTP adapter over a core
  compiled once (C5), and SCCP a pimpl (C2), both for compile time. S1
  proposes one explicit instantiation of `solve` per analysis in its own
  translation unit. Is that the line, with compile time measured as part
  of P0?
- **Q-llvm-2. Budgets in the solver layer.** AGENTS.md lets an
  optimization stop at a budget. S1 proposes: analyses a refusal rests on
  have no budget (finite height or widening only); optimization-only
  analyses may stop at one and then take the pessimistic state (the
  Attributor's rule, C1); never an error (clang's, C5). Confirm.
- **Q-llvm-3. Dense numbering as an invariant.** LLVM numbers blocks and
  MLIR at our pin numbers blocks (B7), but nothing numbers ops or values.
  S1 numbers per solve. Alternatives: a numbering held as a cached
  analysis in the `AnalysisManager`; or an upstream patch giving MLIR op
  or value numbers like LLVM's block numbers. Which, if any?
- **Q-llvm-4. Variants.** Rule I3 bans `get_if`/`holds_alternative`
  chains in favour of one exhaustive `std::visit` (or `PointerUnion` for
  handles, I4). A hard rule for the cutover, or wave 2's judgement case by
  case?
- **Q-llvm-5. One TableGen tool.** Should `idris-mlir-tblgen` become a
  `GenRegistration` in a tool built on `MlirTblgenMain` (E3), reading
  ops, traits and effects through `mlir::tblgen::Operator` and
  `SideEffect` rather than raw records, so one tool generates both the
  C++ and the Idris mirror?
- **Q-llvm-6. Determinism as a tested invariant.** S1's whole-program
  solves run SCC levels in parallel. Every solver's answer must then be
  independent of the schedule; should a solver test run each analysis
  with one thread and with many and compare the frozen `Solution`s?
- **Q-llvm-7. The giant SCC.** If the stage-1 module's call graph has
  one SCC holding most of the frontend (an elaborator is mutually
  recursive), SCC-level parallelism buys nothing there. Is serial solving
  of that SCC acceptable, or should S1 carry lld's double-buffered rounds
  (D2) from the start?

*Questions for wave 2* (what our code must be checked for).

- Every `worklist` (87): its order, its deduplication, its node identity
  (pointer or index), and which graph algorithm (B8) or S1 schedule it is.
- Every `DenseMap`/`DenseSet` (212): one per solve or one per node? Every
  per-node map or set costs at least 64 buckets once non-empty (B7).
- Every `function_ref` (84): on a hot path? stored? does the callee know
  the callable's static type?
- Every `std::variant` (60) and its 192 accesses: over handles (I4), a
  lattice (S1), or a closed sum visited by a `get_if` chain (I3)?
- `lib/Support/Scc.cpp`: what does it do that `scc_iterator` over a
  `GraphTraits` specialization does not?
- Every `std::mutex`/`std::atomic`/`SmartMutex` (22) and `parallelFor*`
  (10): which pool (`mlir/IR/Threading.h` or `llvm/Support/Parallel.h`,
  D1), and what is it protecting that should instead be frozen or owned?
- The seven files on `DataFlowSolver` (§2): which solve within one
  function (S2) and which over the whole program (S1)?
- Exclusivity's graph, `idr-rc-stack`'s flow graph and the label solve's

#### 5.3.5 Notes for other lanes

- **mlir-analysis (§5.1).** At our pin a non-small `DenseMap`/`DenseSet`
  allocates at least 64 buckets on first insertion
  (`llvm/include/llvm/ADT/DenseMap.h:272-274`). The solver's per-anchor
  `DenseMap<TypeID, unique_ptr<AnalysisState>>`
  (`DataFlowFramework.h:481`) and each state's `SetVector` of dependents,
  whose `DenseSet` is the same table (`:559`), therefore cost about 1 KB
  each once non-empty: a concrete candidate for an `upstream/` patch
  (inline-small containers, or a flat vector keyed by analysis index).
  SCCP stores no dependents at all (C2), the design contrast. MLIR has
  block numbering at the pin (`Block::getBlockID`, `Region::getMaxBlockID`).
- **cxx26 (§5.5).** clang's `DataflowAnalysis` detects optional members
  by `Rank0`/`Rank1` overload ranking (`DataflowAnalysis.h:131-170`), the
  form `requires` replaces; libc++ at the pin visits a variant of at most
  11 alternatives with a `switch` (`libcxx/include/variant:1596-1690`);
  LLVM and MLIR headers are built upstream as C++17 only (E5). Please
  check `std::expected`'s and `std::variant`'s behaviour under
  `-fno-exceptions` (M11).
- **ecosystem (§5.6).** IREE's DFX is the Attributor (C1); its cost per
  (kind, position) object and its dependency edges are the measure to
  compare against S1.
- **library (§5.7).** clang ships a weak-topological-order worklist beside
  the RPO one (`WTODataflowWorklist`, `DataflowWorklist.h`), Bourdoncle's
  method, worth a source if the library lacks it; lld's ICF is an
  optimistic partition refinement cited to the gold paper ("Safe ICF",
  `lld/ELF/ICF.cpp:58-59`, `69-71`).
- **mlton (§5.9).** lld's ICF (D2) is the same family as an optimistic
  partition refinement for deduplicating functions, our first pipeline
  pass, made parallel by double-buffering the class ids.
- **dialect-design (§5.8).** MemorySSA (C4) is an SSA chain for memory
  state; our world token is one for IO. If the token is the
  representation, "does IO" is read off it, and §2's three
  representations of "does IO" (trait, resource effects, world operands)
  can be one.
- **oom (§5.11).** LLVM bounds analysis memory in three ways: laziness
  (Attributor, LVI), representation (MemorySSA, dense numbering), and caps
  (LVI's 500 per value, clang's 20,000 block visits, which returns an
  error and is therefore not ours to copy). The 64-bucket minimum of
  `DenseMap` (B7) is a footprint multiplier worth knowing.
- **mlir-ods (§5.2).** `!instances<T>`, `assert` and `deftype` (E1),
  `GenericTable` (E2), and `MlirTblgenMain`/`GenRegistration` plus the
  `mlir::tblgen` wrappers (E3) bear on generated tables and on
  `idris-mlir-tblgen`. LLVM's new TableGen-declared option structs
  (`llvm/include/llvm/Option/LibraryOptions.td`) replace `cl::opt`
  globals.
