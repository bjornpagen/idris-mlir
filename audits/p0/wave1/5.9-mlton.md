# 5.9 mlton: a whole-program optimizing compiler's IRs, read as history

MLton compiles Standard ML whole-program: it monomorphizes,
defunctionalizes closures by a flow analysis, contifies, and optimizes
a sequence of first-order SSA IRs. Our pipeline does the same things in
roughly the same order (§2), and many of our walls rhyme with problems
MLton met and solved decades ago. This lane is a programming-language
expert's careful reading of MLton's code (`sources/code/mlton`, a partial
snapshot; the full tree from github.com/MLton/mlton), its documentation
(`sources/docs/mlton`, mlton.org) and its papers
(`weeks-2006-mlton-whole-program`, Cejtin, Jagannathan and Weeks on flow
analysis and closure conversion, Fluet and Weeks on contification).
- **The IRs as representations**: CoreML, XML, SXML, SSA, SSA2, RSSA,
  Machine. What each IR makes unrepresentable, what each pass needs from
  its input, where facts are kept (types, IR shape, side tables) and
  where they are recomputed; how the type system of each IR carries
  what earlier passes proved.
- **The whole-program passes, in detail**: monomorphization; closure
  conversion and its 0CFA-style flow analysis, how it keeps the analysis
  small and fast and represents closure sets as sums; contification and
  its dominator-based analysis; flattening and deep flattening; useless
  (dead fields and arguments) and removeUnused; known-case, local and
  common-subexpression passes; the inliner and its size budgets;
  representation selection (packed sums, `PackedRepresentation`); the
  shrinker and how it simplifies to a fixpoint cheaply.
- **Engineering at scale**: MLton self-compiles a large program; its pass
  driver, how each pass's analysis state is held (property lists on
  IR nodes, `Property` and `HashSet`), its memory footprint and how it
  avoids per-value state blowups; what it does in one linear pass that
  we do with a solver.
- **The lessons**, mapped onto §2's pipeline and §3's walls: which of our
  passes and analyses have a direct MLton counterpart, what MLton's form
  of each is, and which of our walls MLton's representation would have
  made impossible. The mapping is *conjecture* until wave 2.

#### 5.9.1 Findings

**A. The pass driver.**

A1. *(read)* The whole compiler is one composed function over a chain
of IRs, each its own SML structure with its own tree, type checker and
printer: `goXmlSimplify = goToSxml o xmlSimplify`, ... down to
`codegen` (`main/compile.fun:636-647`); the IRs are instantiated once
at the top (`:19-51`: `CoreML`, `Xml`, `Sxml`, `Ssa`, `Ssa2`, `Rssa`,
`Machine`). A translation between IRs (`Control.translatePass`,
`control/control.sml:375-460`) is a typed function `'a -> 'b`; a
simplifier inside one IR is `'a -> 'a` (`:462-495`).

A2. *(read)* Each IR's optimizer is a plain list of `{name, doit,
execute}` records folded over the program (`ssa/simplify.fun:46-122`,
41 SSA passes; `ssa/simplify2.fun:25-30`, 4 SSA2 passes;
`xml/sxml-simplify.fun:31-41`; `xml/xml-simplify.fun:22-25`). The order
is documented as data, with the reason for each constraint in a
comment beside the entry ("useless should run after constant
propagation because constant propagation makes slots of tuples that are
constant useless", `ssa/simplify.fun:59-62`; shareZeroVec's four
constraints, `:105-113`). The list can be replaced from the command
line by name (`:256-278`).

A3. *(read)* The type checker of an IR runs at every IR boundary
(`forceTypeCheck = SOME true` on every `translatePass` and on the
whole-IR `simplifyPass`, `main/compile.fun:385-587`), but **not after
each pass inside an IR** by default: `simplifyPasses` passes
`forceTypeCheck = NONE` (`control/control.sml:497-508`), which
`translatePass` reads as "skip unless `-execute-passes` names it"
(`:413-424`). Machine's checker is off by default as "too slow"
(`main/compile.fun:586-587`, `:596-597`). After every pass the driver
can print `PropertyList.stats`, `HashSet.stats` and the live heap
(`control/control.sml:435-440`): the footprint of the analysis state is
a first-class, per-pass report.

A4. *(read)* What a pass needs from its input is either established by
the pass itself at its start or written down as a contract. Passes
whose analysis walks the CFG but whose rewrite iterates the block
vector call `eliminateDeadBlocks` first (`ssa/useless.fun:501-502`;
the guide: "a small number of optimization passes require that the
input have no unreachable blocks ... These passes explicitly call
`eliminateDeadBlocks`", `doc/guide/src/Shrink.adoc`). Contify states
each phase's precondition and postcondition over the per-function
records (`ssa/contify.fun:229-242, 315-321, 479-494`). Ordering
constraints between passes are the comments in the pass list (A2).
Nothing is assumed of the input that the IR's types and the checker do
not guarantee, except these stated cases.

**B. How analysis state is held: property lists, and values that are
their own constraint graph.**

B1. *(read)* Every IR identifier is an object with a property list,
not a name. `Id.t = T of {hash: word, originalName, printName,
plist}` (`atoms/id.fun:36-39`); identity is pointer equality of the
plist (`:103`), the hash a random word drawn once at creation
(`:107`). `Var`, `Label`, `Func`, `Con`, `Tycon` are all `Id`s
(`atoms/var.fun:14`); SSA types, lambdas and nodes of graphs carry a
plist too (`ssa/ssa-tree.sig:61`). A plist is a `ref` to a list of
existentially typed cells (`lib/mlton/basic/property-list.fun:12`),
each cell an exception constructor minted per property
(`het-container.fun:12-16`): the key is the type, so a peek is a
pointer compare per cell, and a property's value is typed statically
with no cast and no hash.

B2. *(read)* A pass's per-node state is a *property* it creates and
destroys: `Property.getSetOnce (Var.plist, initRaise ...)` returns
`get`/`set` closures over that one property (`property.sig:19-66`).
`initFun f` computes a value on first `get` and caches it on the node;
`initRec` lets the initializer call `get` recursively (a type's
representation from its components', `property.fun:13-17, 35-47`);
`initRaise` makes a missing value an internal error. The `dest*`
variants remember which plists they touched and remove exactly those
cells on `destroy` (`property.fun:57-72`), so a pass's state is freed
when the pass ends, in time linear in what it touched. `Function.clear`
and `Program.clear` drop every property of a function's bound names
(`ssa/ssa-tree.sig:179-182`). The cost is one cons cell and one boxed
exception per (node, property) that is set, found in a list of usually
one to three entries: the driver reports `numPeeks`, `maxLength` and
the average position (`property-list.fun:26-38`), and prints them with
the live heap after every pass (A3).

B3. *(read)* The whole-program analyses are not worklist solvers over
program points. `ssa/analyze.fun` is one generic abstract interpreter,
parameterized by a value domain (`coerce`, `conApp`, `filter`,
`primApp`, `select`, `tuple`, `const`, `fromType`;
`ssa/analyze.sig:19-47`), that visits each reachable block **once**
(`visited` flag, `analyze.fun:245-261`) and emits one constraint per
binding, argument, return and case arm (`coerces` at `:68, 85, 98,
112, 151, 155, 159`). The fixpoint lives in the abstract values: each
is a mutable cell that propagates its own changes. The SSA type
checker is the instance whose values are types and whose `coerce` is
equality (`ssa/type-check.fun:365-450`); `useless`, `constant
propagation` and others are instances with lattice values. One
traversal, one fact per variable (`Property.getSetOnce` on
`Var.plist`, `analyze.fun:28-31`), no state per program point.

B4. *(read)* The lattice cells are union-find nodes with handler lists.
`TwoPointLattice`: `T of value DisjointSet.t`, `value = Bottom of
(unit -> unit) list ref | Top` (`lib/mlton/lattice/two-point-lattice.fun:17-19`);
`from <= to` either fires at once or pushes a closure onto `from`'s
handlers (`:57-64`); `==` unions the two sets and merges their handler
lists (`:66-80`); `makeTop` runs the handlers once (`:52-55`). Each
cell rises at most once and each handler runs at most once, so a solve
costs O(constraints) with no worklist and no iteration count.
`FlatLattice` (Bottom, Point, Top) has the same shape with a
`lessThan` list (`flat-lattice.fun:92-200`). Equality constraints use
union-find, so a whole equivalence class costs one cell.

B5. *(read)* An abstract value's shape is the *type's* shape, and facts
about constructor fields live on the constructor, not on values.
`Useless.Value.fromType` builds a tree mirroring the type: a tuple has
a slot per component, a datatype value is one `Ground` bit
(`ssa/useless.fun:282-318`); each constructor's argument values are
kept once per `Con` (`conInfo`, `:503-529`), so every `ConApp`
coerces into, and every case arm reads from, the constructor's one
record (`conApp`, `filter`, `:531-542`). In closure conversion the
same holds and more: a first-order type (no arrow inside) maps to a
**single shared** abstract value for the whole program (`make = let
val v = new (Type t) in fn () => v end`,
`closure-convert/abstract-value.fun:242-246`), so a variable of a
first-order type costs the analysis nothing of its own; only values
whose types contain arrows get nodes. This is how MLton avoids a
per-value state blowup: the analysis state is sized by the program's
*types and constructors*, plus one cell per variable of a type that
can carry what is being tracked.

**C. The IRs as representations.**

C1. *(read)* The chain (`main/compile.fun:19-51`, `636-647`): CoreML
(polymorphic, pattern matching compiled) → XML (explicitly typed,
polymorphic, higher-order, nested lexical scope) → SXML (the same tree
type, monomorphic) → SSA (first-order, closure-free, CFG of blocks with
arguments) → SSA2 (SSA with objects, mutable fields and sums made
explicit) → RSSA (representation chosen: words, pointers, offsets,
explicit tags) → Machine (registers, stack frames, chunks).

C2. *(read)* SXML does **not** make polymorphism unrepresentable:
`signature SXML_TREE = XML_TREE`, and its invariants ("no PolyVal
decs", "no tyvars in types", ...) are a comment
(`xml/sxml-tree.sig:12-19`, `xml/sxml.sig:17-24`) enforced by the type
checker run at the boundary (`main/compile.fun:471`). SSA does make
closures unrepresentable: `Exp.t` has no lambda and no application
(`ssa/ssa-tree.sig:74-85`); a call names a `Func.t`
(`:116-118`). MLton spends a new IR type where the change of
representation is large (higher-order to first-order, values to
objects, objects to words) and a checked invariant where the change is
an absence.

C3. *(read)* SSA's control flow is explicit and flat. A function is a
vector of blocks; a block has typed arguments (no phi), statements and
one transfer (`ssa/ssa-tree.sig:146-153`). `Case` names its arms as
`(Con.t, Label.t)` pairs, each arm a *jump to a block*
(`:119-121`, `atoms/cases.sig:21-23`), and the arm's block takes the
constructor's fields as its arguments (`ssa/analyze.fun:140-142`:
`filter (test, c, labelValues j)`). A case with 30,000 arms is a vector
of 30,000 pairs; its successors are read off the vector; nothing nests.
The checker requires a non-exhaustive case to have a default and an
exhaustive one not to (`ssa/type-check.fun:109-152`). Calls carry their
continuation in the IR: `Return.t = Dead | NonTail {cont, handler} |
Tail`, `Handler.t = Caller | Dead | Handle of Label.t`
(`atoms/return.sig:21-25`, `atoms/handler.sig:19-22`): tail position
and exception routing are a sum in the call, never an analysis.

C4. *(read)* SSA2 replaces SSA's `Tuple`, `Ref`, `Array`, `Vector` and
constructor applications by one `Object of {args: t Prod.t, con:
ObjectCon.t}` type, `ObjectCon = Con of Con.t | Sequence | Tuple`,
where `Prod` records **per field** whether it is mutable
(`ssa/ssa-tree2.sig:19-43`, `atoms/prod.sig:16-39`). A constructor value
is built as an `Object {con = SOME c}` and then `Inject`ed into its sum
(`ssa-tree2.sig:90-101`); reads and writes take a `Base = Object of 'a
| SequenceSub of {index, sequence}` (`:75-84`). Mutability is a fact of
the field's type, so `ref` is a one-field mutable tuple and the
flattening passes (F3) need no special case for it.

**D. Monomorphization and closure conversion.**

D1. *(read)* `Monomorphise` (XML → SXML, `xml/monomorphise.fun`, 435
lines) is one pass with no worklist. Each polymorphic binding gets a
hash table from type-argument vectors to its instances (`Cache`,
`:42-67`) and a property on its `Var.plist` mapping a type vector to the
instance (`:71-73, 353-361, 378-390`). `monoDec` returns a *thunk*
(`:340-419`); `monoExp` builds every declaration's thunk in order and
forces them in reverse (`:270-283`), so a declaration's body is
monomorphised only after every later use has requested its instances,
and an instance's body may request instances of earlier declarations,
which are forced later still. Datatypes are instantiated the same way,
and constructors are kept only if some instance uses them (`used`,
`:176-259`). The cost is linear in the output; the order is the
program's own scoping, so termination is by construction.

D2. *(read)* Closure conversion (SXML → SSA,
`closure-convert/closure-convert.fun`, 1,167 lines) runs a 0CFA flow
analysis as **one traversal** of SXML that emits constraints
(`:249-391`): a binding `coerce`s its value into its variable's; an
application installs a *handler* on the function's lambda set that, for
each lambda that ever arrives, coerces the argument into the formal and
the body's result into the application's result (`:311-325`); a
constructor application coerces its argument into the constructor's
one abstract value, and a case arm binds its pattern variable to it
(`conArg`, `:218-220, 331-346`). Lambda sets are hash-consed
(`UniqueSet`, `abstract-value.fun:42-44`; `lib/mlton/basic/unique-set.fun`:
a 2^13-bucket table of decision trees, a set's hash the xor of its
members', a five-entry cache per binary operation), so set equality is
pointer equality and a set has a plist. A `LambdaNode` holds its set,
its handlers and its outgoing `coercedTo` edges; `send` pushes only the
*difference* along edges and to handlers
(`abstract-value.fun:59-115`); `unify` merges two nodes by union-find
(`:123-148`). Mutable containers (ref, array, vector, weak) are
unified, not coerced (`:341-345`: a coercion "would imply walking over
the entire vector").

D3. *(read)* Closure sets become sums **per distinct set**, not per
function type: `lambdasInfo` makes one SSA datatype per hash-consed
`Lambdas.t`, one constructor per lambda in it, each carrying that
lambda's environment tuple (`closure-convert.fun:499-538`), memoized on
the set's plist (`:430-431`); an abstract value's SSA type is memoized
on the value itself (`ssaType`, `:473-498`). Where a smaller set flows
into a larger one, the converter inserts a `case` that re-tags
(`coerce`, `:596-644`); an application becomes a `case` over the set's
constructors calling each lambda's function (`apply`, `:676-708`). Free
variables are computed by a separate linear pass
(`closure-convert/lambda-free.fun`) and globals hoisted (`globalize.fun`).

D4. *(read)* The SSA program comes out of closure conversion already
shrunk per function (`closureConvertShrink`, `:752-755`), and the
globals are shrunk through a throwaway function to one block, with an
internal error if the shrinker did not finish the job
(`Accum.done`, `:81-146`): the converter relies on the shrinker as its
normal form.

**E. Contification and the shrinker.**

E1. *(read)* `Contify` (`ssa/contify.fun`, after Fluet and Weeks, ICFP
2001) builds one whole-program graph over functions, continuations and
a root (edges: root to main, to every continuation, to every
unreachable function, to every function called with a dead return and,
unless contifying into main, to every function main calls; tail calls
f→g; non-tail calls c→g; `:298-415`), computes its dominator tree once (`Graph.dominators`,
`:417-422`), and reads each function's return from its ancestor below
the root: `Areturn = Uncalled | Unknown | Cont of Cont.t | Func of
Func.t` (`:34-40, 424-470`). A function whose `A` is a continuation or
another function is spliced into that function as blocks
(`:526-553`), and each result function is shrunk (`:706`). State: one
`FuncData` record per function and one `ContData` per (label, handler),
on plists (`:730-755`). Cost: one graph build, one dominator
computation, one rewrite. It runs three times in the SSA list
(`ssa/simplify.fun:54, 90, 95`).

E2. *(read)* The shrinker (`ssa/shrink.fun`, 1,239 lines; after Appel
and Jim's linear-time shrinking) is per function and makes two linear
sweeps. The first is a DFS from the start label that computes, per
block, an in-degree, an `isHeader` bit (a back edge), occurrence counts
per variable and a **label meaning** (`LabelMeaning.aux = Block | Bug |
Case | Goto of {dst, args: Positions} | Raise | Return`, `:101-119`):
what jumping to that label amounts to, with goto chains already
collapsed through formal positions (`:280-451`). The second rewrites
from the start: a block of in-degree one is inlined at its only jump
(`gotoMeaning`, `:950-970`); a case on a variable whose `VarInfo.value`
is a known constructor or constant jumps straight to the arm and
decrements the other arms' in-degrees, deleting blocks that reach zero
recursively (`simplifyCase`, `:860-946`; `deleteLabelMeaning`,
`:569-598`). Statements are rebuilt *backwards*: `evalStatement`
returns a closure that is applied to the already-simplified rest of the
block, so `isUsed` is known when each binding is kept or dropped
(`:1018-1051`). Forward value propagation and backward dead-code
elimination happen in one pass, with block-indexed arrays and one
`VarInfo` per variable as the only state (`:25-75, 224-234`).

E3. *(read)* The shrinker is the normal form between passes, not a
pass in the list. `ssaShrink` appears in the list only as an optional
name (`ssa/simplify.fun:253`); instead 19 SSA passes call
`shrinkFunction` on each function they rewrote before returning, and
the SSA2 passes and the SSA-to-SSA2 translation shrink their whole
output (*measured*: `grep -l shrinkFunction ssa/*.fun` less the
shrinker and the drivers; `deep-flatten.fun:1155`,
`ref-flatten.fun:1166`, `ssa-to-ssa2.fun:283`; e.g. `useless.fun:1516-1517`,
`flatten.fun:444-445`, `known-case.fun:283, 1011`,
`remove-unused.fun:1196, 1236`, `inline.fun:444-462`,
`contify.fun:706`), and the guide says it "is run after every SSA and
SSA2 optimization pass" (`doc/guide/src/Shrink.adoc`). There is no
pattern driver anywhere in the SSA optimizer: each rewrite is a case
over the IR's closed sums (`Exp.t`, `Transfer.t`), and the only
simplifier is this deterministic, linear, per-function one. Passes that
break SSA (known-case duplicating blocks, local-ref, loop unswitching)
call `restoreFunction` (Appel's §19.1, "use bool vectors to represent
sets of violating variables" only for the violators,
`ssa/restore.fun:9-22`; callers at `known-case.fun:282, 1007`,
`local-ref.fun:253, 362`).

**F. The other whole-program passes: IR, algorithm, state, cost.**

F1. *Inline* (`ssa/inline.fun`, SSA → SSA). *(read)* The decision is a
pure function of the call graph, computed once before any rewrite: a
node per function and an edge per call (`:217-317`), SCCs taken
leaves-first (`:321-327`), and a function in a singleton SCC that does
not call itself is inlined iff `(numCalls - 1) * (size - small) <=
product` (`:271-295`), where `size` already counts the inlined size of
callees decided earlier (`:281-289`); the defaults are `small = 60,
product = 320` (`control/control-flags.sml:1034-1042`). Leaf inlining
bounds its size count with `sizeMax`, which stops counting at the
budget (`inline.fun:82-92, 160-187`; `ssa/ssa-tree.fun:1006`). The
rewrite then copies an alpha-renamed callee at each call, composing the
call's `Return.t` with the callee's returns and raises, which become
gotos (`:375-443`), and shrinks each function once (`:444-462`).
Recursive functions are never inlined by this metric; the budget only
leaves code uninlined.

F2. *RemoveUnused* (`ssa/remove-unused.fun`, SSA → SSA, run four times
in SSA and once in SSA2). *(read)* One demand-driven traversal over
two-point cells: `Used` per variable, label, function and tycon;
`Coned` and `Deconed` per constructor; `MayReturn` and `MayRaise` per
function (`:16-63, 66-281`). Nothing is visited until it is used: a
function's start block is visited when the function becomes used
(`FuncInfo.whenUsed (fi, visitLabelTh start)`, `:680`), a block when
its label becomes used (`:696`), a pure statement's expression when its
variable becomes used (`maybeVisitVarExp`, `:462-470`), a case arm only
when its constructor is ever built (`ConInfo.whenConed (ci,
visitLabelTh l)`, `:574-576`), a continuation only when the callee may
return (`FuncInfo.whenReturns`, `:515`). Liveness, reachability,
dead constructors, dead fields, dead arguments, dead returns and
handlers are one analysis with one cell per name and one handler per
dependency: total work linear in the program. The guide lists eleven
kinds of thing it removes (`doc/guide/src/RemoveUnused.adoc`).

F3. *Useless* (B5) and the flattening passes. *(read)* `Flatten`
(`ssa/flatten.fun:9-60`) keeps one two-point `Rep` ("flatten" / "don't
flatten") per constructor argument, block argument and function
argument, coerced at every use. `LocalFlatten` (`local-flatten.fun:9-40`)
keeps four refs per block argument. `DeepFlatten` (SSA2,
`deep-flatten.fun:266-500`) is the exception: its `Value.Object`
carries eight fields, six of them mutable refs (`coercedFrom`, `flat`,
`finalOffsets`, `finalTree`, `finalType`, `finalTypes`, `:272-279`),
and while a constructor's object is shared per `Con` (`conValue`,
`:556-557, 604-607`), every variable of a tuple or sequence type that
may flatten gets a fresh object (`makeTypeValue`'s `Make`, `:579-613`,
used as the interpreter's `fromType`, `:768-784`), plus a `VarTree`
per variable during the rewrite (`:843-856`); it is the one pass whose memory MLton's guide documents
as a problem ("A number of applications require compilation with
`-disable-pass deepFlatten` to avoid exceeding available memory",
`doc/guide/src/DeepFlatten.adoc`). *(conjecture)* That the one pass
with state per object value, rather than per type or per constructor,
is the one with the documented blowup is the same lesson as §3's table.

F4. *KnownCase*, *CommonSubexp*, *Redundant*. *(read)* KnownCase walks
the dominator tree with scoped state: per-variable stacks of known
constructor values pushed on entry and popped by `post` thunks on exit
(`ssa/known-case.fun:14-20, 80-260`), so its live state is the depth
of the walk, not the program. CommonSubexp keeps one hash table of
canonicalized expressions, a variable index for a total order, and
per-label `add` lists for facts known only on one edge
(`common-subexp.fun:17-45, 103-106, 175`). Redundant (equal block or
function arguments) is partition refinement over classes that carry
plists, iterated until no class splits (`redundant.fun:14-200`).

F5. *Polyvariance* (SXML → SXML, before closure conversion). *(read)*
It duplicates a `let`-bound **higher-order** function at each
reference when `(numOccurrences - 1) * (size - small) <= product`
(`xml/polyvariance.fun:9-13, 98-125`; defaults `hofo = true, rounds =
2, small = 30, product = 300`, `control/control-flags.sml:1343-1348`).
It runs before the flow analysis so that 0CFA sees separate copies and
computes smaller closure sets per copy.

F6. *Representation* (SSA2 → RSSA, `backend/packed-representation.fun`,
2,839 lines). *(read)* Chosen once per program, per *type*:
`TyconRep = One | Objptrs | Small | SmallAndBox | SmallAndObjptr |
SmallAndObjptrs | Unit` (`:1718-1736`), `ConRep = ShiftAndTag | Tag |
Tuple` (`:1350-1359`), each a sum whose constructors carry only the
data that representation needs; the reps are computed by a small
dependency-driven fixpoint over types (`Value` with `affects`,
`:2326-2416`), and the translation asks the result through a record of
functions (`genCase`, `object`, `select`, `update`, `toRtype`;
`backend/representation.sig:19-52`). RSSA's `Switch` is a flat,
sorted vector of `(WordX.t, Label.t)` (`backend/switch.sig:29-35`);
blocks carry a `Kind = Cont | CReturn | Handler | Jump`
(`backend/rssa-tree.sig:137-141`).

F7. *Liveness* (RSSA, `backend/rssa-live.fun`). *(read)* Per function,
never whole-program, and one variable at a time: build the predecessor
graph and each variable's definition block and use blocks once, then
for each variable walk backwards from its uses to its definition,
appending it to each block's live list; membership is O(1) "because the
variable is either at the head of the list or it's not there"
(`:9-31`, `processVar` `:223-255`). The header says why: bit-vector
liveness "is infeasible for MLton due to the large size of and number
of variables in SSA functions" (`:11-13`). Cost: the sum over variables
of the blocks in their live ranges, i.e. the size of the answer.

**G. How MLton stays cheap at self-compile scale.**

G1. *(read)* The scale: the compiler is 160,699 lines of SML and the
basis and library 77,342 more (*measured*, `wc -l` over `mlton/`,
`basis-library/`, `lib/`), compiled whole-program by itself; the guide
asks for "at least 2GB RAM for 64-bit platforms (4GB is preferable)"
(`doc/guide/src/SelfCompiling.adoc`). MLton is single-threaded
throughout (*read*: nothing in `mlton/` names a thread or a lock).

G2. *(read, the mechanisms, collected)*
1. *State lives on the node, typed, and dies with the pass* (B1, B2):
   no global map keyed by name; `destroy` and `clear` free exactly what
   a pass set.
2. *One fact per name, never per program point* (B3): SSA makes a
   variable's definition unique, so a flow-insensitive fact per variable
   is as precise as a flow-sensitive one for everything but liveness,
   and liveness (F7) is per function and output-sensitive.
3. *Constraint propagation, not iteration* (B4, D2): cells are
   union-find nodes with handler lists; a two-point cell rises once; a
   set cell sends only differences; equalities merge classes. No
   worklist over program points, no iteration count.
4. *State sized by types and constructors* (B5, D3, F6): field facts
   are per constructor, first-order values share one abstract value,
   representation is per type, closure sets are hash-consed.
5. *Demand-driven traversal* (F2): code is analyzed only once
   something that reaches it is known to be live.
6. *Scoped state for dominator walks* (F4): push on entry, pop on exit.
7. *Facts written into the IR's types* (C2, C4, D3): after closure
   conversion a closure set *is* a datatype; after useless a dead field
   is *absent* from its type; after representation a type *is* its
   layout. Nothing is carried between passes except the program;
   every analysis is recomputed by the pass that needs it, and that is
   affordable because each is linear (removeUnused runs five times,
   contify three, `ssa/simplify.fun:47-121`).
8. *One linear normalizer, called by every pass* (E2, E3), instead of
   a rewrite driver.
9. *Immutable functions with a lazy, cached CFG and dominator tree*:
   `Function.new` wraps a `ClearablePromise` of the control flow
   (`ssa/ssa-tree.fun:1312-1318, 983-988`), so a rewritten function is a
   new value with a fresh cache and no cache can go stale.
10. *Measurement as part of the driver*: after every pass the driver
   can report property-list and hash-set statistics and the live heap
   (A3).

**I. Defunctionalization beside MLton, in the local papers** *(read,
from text extracted from `sources/papers/*/paper.pdf`; section numbers
as the papers give them)*.

I1. Danvy and Nielsen, "Defunctionalization at Work" (BRICS RS-01-23,
2001), §1: Reynolds's transformation enumerates a whole program's
function abstractions as the constructors of a first-order data type,
dispatched by an `apply` function ("for a whole program, this
existential type can be represented with a finite sum together with the
corresponding injections and case dispatch"); "one can use several
apply functions, e.g., grouped by types, as in Bell, Bellegarde, and
Hook", and "defunctionalization is an integral part of MLton". MLton's
D3 is the finest grouping: one sum per *flow set*, with coercions where
sets meet.

I2. Hovgaard, Henriksen and Elsman, "High-Performance
Defunctionalisation in Futhark" (TFP 2018), §1 and §2.2: Futhark makes
every application's function *statically* known by a type restriction
("a conditional may not return a function, arrays are not allowed to
contain functions, and a loop may not produce a function"), so
defunctionalization specializes each application and introduces no
branching at all; its "static values" (`Dyn | Lam | Rcd | Arr`) are a
type-shaped approximation of values, the same idea as MLton's
type-shaped abstract values (B5) taken to the point where no sum is
needed. This is the other end of the line from MLton: restrict the
language until the closure set is a singleton, against analyze and
build sums.

I3. Kovács, "Closure-Free Functional Programming in a Two-Level Type
Theory" (ICFP 2024), abstract and §1.1: staging with a dependent
compile-time language over a simply typed first-order object language
gives a *guarantee* that object code has no runtime closures, rather
than relying on "general-purpose optimization" whose effect is
"fragile and non-compositional". For us this is a note, not a design:
it bears on how the frontend might promise closure-freedom by type,
not on P0's C++.

I4. *Not read:* Huang and Yallop, "Defunctionalization with Dependent
Types" (PLDI 2023): its text could not be extracted on this machine.

#### 5.9.2 What it means for idris-mlir

*All conjecture until wave 2 reads our code; §2 is the only ground.*

M1. *Our pipeline is MLton's, in MLton's order.* Deduplicate,
defunctionalize, contify, optimize (inline and specialize bottom-up),
symbol DCE, then representation-level work (columns, bufferize, frames,
counting, narrow) and lowering (§2) is monomorphise, closure-convert,
contify, inline, removeUnused, then flatten/representation and the
backend (A1, C1). The difference that matters is not the order but the
IR between the steps: MLton changes the IR's *type* at each large
change of representation (C2), so what a step proved is in the next
IR's types and shape; we keep one dialect from defunctionalization to
lowering, so what a pass proved must live in a type of that dialect,
an attribute, or a recomputed analysis. AGENTS.md already chose the
first for grades (`!idr.q`, §2); MLton says to choose it for every fact
that a later pass reads (G2.7).

M2. *Our walls are MLton's non-choices* (H). Three of §3's eight walls
(ffa91113, 16005000's `remove-dead-values`, b8301ebe) are a per-value
or per-program-point state model, which MLton never has: its analyses
keep one cell per name (G2.2), propagate by handlers (G2.3), and size
their state by types and constructors (G2.4). Two more (e96bb991,
`idr-frames`) are a cost per pair (terminator and successor, member and
result type) that MLton's flat case and demanded instances do not
have; the last three (patterns on any op, the lock, the rebuilt table)
are a driver, a mutable type and a missing memo. The
three fixes already made (ffa91113 "marks the program graph", b8301ebe
"the flow graph, marked, not a set of cells per value", 16005000 "a
component's answer is data") are each a step towards MLton's model,
taken one analysis at a time. P0's solver layer can take the model
whole (Design 1).

M3. *The match with a region per case is the representation behind
e96bb991.* MLton's case is a terminator whose arms are labels (C3); a
30,000-arm case costs a vector, and every successor question is
answered by reading it. MLIR has exactly this mechanism:
`BranchOpInterface` with `SuccessorOperands` whose leading block
arguments are *produced* by the terminator ("branch-on-error ...
internally produces an error object on the error path",
`.toolchain/llvm-project/mlir/include/mlir/Interfaces/ControlFlowInterfaces.h:30-58`,
*read*), which is MLton's arm block receiving the constructor's fields.
After defunctionalization nothing in our program is higher-order, so a
first-order CFG form is available from that point on (Design 2).

M4. *Closure sums per flow set, not per type* (D3). §2 says every
closure "becomes a constructor of a closed sum". If our sum is one per
function type (or per label class) rather than one per distinct flow
set, every `apply` dispatches over every closure of that type, and
whole-program matches of tens of thousands of cases (§3) would be,
in part, apply dispatches that MLton would have split into many small
sums joined by re-tagging coercions. Wave 2 must measure where the
stage-1 module's largest matches come from (Q-W1).

M5. *Counting's liveness is per function, one variable at a time* (F7).
`idr-rc-stack`'s candidate bit vector per value along every edge
(b8301ebe) is the representation MLton's backend rejects by name. Our
counting passes (`idr-rc-cells`, `idr-rc-stack`, `idr-rc-grades`,
`idr-rc-exclusive`, demand, frames; §2) presumably need liveness or
last-use facts; MLton computes them per function, after every
whole-program decision is already in the types, with cost the size of
the answer (Design 4).

M6. *The `data` type and its lock* (98c6315c). MLton's datatype type is
a reference to a tycon whose body lives once in the program
(`Program.datatypes`); per-pass facts about a tycon live on the tycon's
plist for that pass (H). Our `!idr.data`, "a mutable type: a name whose
body the program's table holds once" (§2), puts the body behind MLIR's
mutable-type storage and so behind the context's lock. The MLton form
is an immutable type naming the tycon and an immutable table op holding
the bodies, with each pass building its own tycon-indexed table
(Design 3).

M7. *The optimizer's driver.* `idr-optimize`'s 75 million attempts
(3a96c407, 7987388b) came from patterns that match any op. MLton has
no rewrite driver at all: one linear per-function normalizer dispatching
on the IR's closed sums, run by each pass over what it produced (E3).
Upstream MLIR has the pieces: per-op `fold`, `walkAndApplyPatterns` (a
single walk, no fixpoint, no worklist,
`mlir/include/mlir/Transforms/WalkPatternRewriteDriver.h:20-34`,
*read*), and `simplifyRegions` (unreachable blocks, dead arguments,
block merging; `mlir/include/mlir/Transforms/RegionUtils.h:122-143`,
*read*) (Design 5).

M8. *The inliner is already MLton-shaped* (F1): §2's "inline and
specialize, each function once, bottom-up" is MLton's SCC-leaves-first
decision. What MLton adds: the decision is computed in full before any
rewrite, from sizes that count already-inlined callees, with an
early-exit size count; a recursive function is never inlined; the
budget only leaves code uninlined, as AGENTS.md requires.

M9. *Specialization against the flow analysis* (F5). MLton duplicates
higher-order functions *before* its closure analysis, so each copy
gets its own, smaller closure sets; §2 runs specialization after
defunctionalization, when the label solve has already merged every
call site's closures. Whether our specialization is the same thing as
polyvariance is for wave 2 (Q-W5); the ordering is the owner's (Q-O4).

M10. *Monomorphization never refuses in SML.* MLton's monomorphiser is
total because SML's polymorphism is rank 1 without polymorphic
recursion (D1 terminates by the program's scoping). Idris allows what
SML forbids, and AGENTS.md's `unsupported` refusal of megamorphic
constructs is exactly the boundary MLton never had to draw; MLton
offers no lesson on where to draw it, only on how cheap the admitted
part can be.

M11. *Verification.* MLton type-checks at IR boundaries and not after
each pass (A3), and keeps Machine's check off as too slow. AGENTS.md
requires the grades verified after every pass, which is a stronger
contract than MLton's; MLton's lesson is about its cost: the checker is
the trivial instance of the analysis framework (B3), one linear walk.
Our verifier should be that cheap at 70,000 functions, and wave 2
should measure it (Q-W7).

M12. *Threading.* MLton is single-threaded (G1), so it says nothing
about locks except by omission. What it does say: its per-function
passes (shrink, knownCase, CSE, restore, liveness) touch one function
and its globals, which is what MLIR's pass manager parallelizes over
`func` ops; its whole-program solves are sequential and linear, and
were never the bottleneck it documents (DeepFlatten's memory is, F3).

#### 5.9.3 Candidate designs, ranked

**Design 1. One constraint-generating abstract interpreter, and one
library of cells: the solver layer.** *(conjecture)* The honest solver
layer §1 asks for, in MLton's form (B3, B4, G2):
- *The interpreter* walks each reachable block of each function once
  and, for each op, asks a **domain** for the op's abstract result and
  emits constraints (`coerce from to`, `unify`, `filter` at a case arm,
  per-argument flows at a call, a return, a yield). It finds an op's
  meaning through the dialect's interfaces, never by `isa` (§4), so one
  interpreter serves every domain. A domain is a C++26 type checked by
  a concept (the shape of MLton's `analyze` record:
  `coerce`, `conApp`, `filter`, `primApp`, `select`, `tuple`, `const`,
  `fromType`); the interpreter is a template over it, monomorphized
  per analysis, with no virtual call.
- *The cells* are union-find nodes with handler lists, in three
  shapes: two-point (rises once, `<=` adds a handler, `==` merges),
  flat (bottom, point, top), and set (hash-consed sets that propagate
  differences, D2). A cell lives in a per-pass arena (a
  `SpecificBumpPtrAllocator` per cell type; llvm lane) and is found
  through a dense index of the pass's names (values, blocks, symbols,
  constructors), never a nested map; the arena dies with the pass.
- *State is sized by types*: a value whose type cannot carry what the
  domain tracks shares one cell per type (D2's first-order values);
  field facts live once per constructor (B5).
- *The type checker is a domain*: the grade verifier is the instance
  whose values are types and whose `coerce` is the grade order, as
  MLton's SSA checker is (B3).
- *Composition is visible*: one analysis is one domain; a pass that
  needs two runs the interpreter over their product, or reads the first
  one's answer, written into the IR, before running the second.
- **Buys:** no per-program-point state, no `ProgramPoint` uniquing, no
  iteration count; cost O(program + constraints); one place where every
  whole-program analysis's state model is stated.
- **Costs at §3's scale:** one cell (a union-find word plus a handler
  list head) per value whose type can carry the fact, and per
  constructor, block and symbol; with handlers, a few tens to a few
  hundred bytes per tracked value. If the stage-1 module has on the
  order of ten million values (wave 2 counts them), that is a few GB at
  the very worst, against ffa91113's 627 GB (*conjecture*, to be
  measured). §4's rule for a solver of our own is met by stating that
  measurement in the layer's header.
  It is flow-insensitive per SSA value, which SSA makes precise for
  everything but liveness-like facts (Design 4 covers those).
- **Deletes (if wave 2 confirms):** the separate solvers in
  `Analysis/Ownership` (Exclusivity's solve, Uses, Values, Captures,
  Reuses), `Labels`/`LabelSites` (the defunctionalization label solve
  is D2's 0CFA, a set domain), `Effects`, `Constants` and `Ranges` where
  they are whole-program; the `DataFlowSolver` users that are
  whole-program; every per-analysis worklist.

**Design 2. After defunctionalization, a first-order CFG core: `case`
as a terminator.** *(conjecture)* From defunctionalization on, a match
is a terminator over a sum whose arms are successor blocks, each
receiving the constructor's fields as *produced* successor operands
(`BranchOpInterface`, M3), with the join an ordinary block that every
arm branches to with its result. `cf.br`/`cf.cond_br` for the rest.
- **Buys:** a case's successors are its operand list (e96bb991 cannot
  recur); dominance, `Liveness`, sparse dataflow over block arguments
  and region simplification are upstream's and CFG-native; the state of
  every analysis is per block, never per (region, successor) pair.
- **Costs:** structured passes that want regions (structure loops,
  TRMC, frames, counting's lexical scopes) either run before the
  lowering or recover structure from the CFG; the frontend's `match`
  stays as the structured form up to it. A `func` with a 30,000-arm case
  becomes 30,000 blocks in one region instead of 30,000 regions: fewer
  objects, but one huge region whose dominator tree upstream must build
  (Q-W3).
- **Deletes:** the `RegionBranchOpInterface` implementations and queries
  on `match` in every pass after the lowering; `YieldTargets` and
  `RunsLabels`-style successor plumbing (§2's interfaces) if wave 2
  finds that is what they do.

**Design 3. A fact is written into a type by the pass that proves it,
and nothing else survives between passes.** *(conjecture)* MLton's G2.7
as a rule for P0: the label solve's answer is the closure sums (one per
flow set, D3, with re-tagging coercions where sets meet); usefulness's
answer is the field's absence from its constructor; representation's
answer is the type; grades already are types. Every other analysis is
recomputed by the pass that needs it, by Design 1's linear
interpreter, and cached (`AnalysisManager`) only within a pass
pipeline that preserves it. `!idr.data` becomes an immutable type
naming its tycon, with the bodies in one immutable table op of the
program; each pass's per-tycon facts are a pass-local table indexed by
tycon.
- **Buys:** no rederivation chain, because nothing is derived from a
  derived side table; 98c6315c's lock cannot be taken, because there is
  no mutable type; 73bba53f cannot recur, because the table is built
  once and only read.
- **Costs:** each type-changing pass rewrites every op that mentions a
  changed type (MLton does this in every pass that changes types: it is
  linear); a table change is a new table op.
- **Deletes:** the mutable `data` type's storage and its lock; any
  discardable attribute that holds a proved fact (AGENTS.md forbids
  them already).

**Design 4. Liveness and last use per function, one variable at a
time.** *(conjecture)* Counting (§2's four `idr-rc-*` passes, demand,
frames) gets its liveness from Morgan's per-variable backward walk
(F7): per function, predecessor lists once, then for each value walk
from its uses to its definition, appending it to each block's live
list. Upstream's `Liveness` (the non-dataflow one) should be measured
against it first (mlir-analysis lane).
- **Buys:** cost the size of the answer; no set per value copied along
  edges (b8301ebe cannot recur); trivially parallel over functions under
  the pass manager.
- **Costs:** a live list per block; facts that are not per function
  (exclusivity across calls) stay in Design 1.
- **Deletes:** every bit vector per value in the counting passes.

**Design 5. One linear normalizer, run by each pass over what it
changed.** *(conjecture)* MLton's shrinker (E2, E3) in upstream's
pieces: per-op folders (ODS `hasFolder`), a known-constructor fold of
Design 2's `case` terminator (the shrinker's `simplifyCase`), applied in
one `walkAndApplyPatterns` walk with patterns rooted at named ops only,
then `simplifyRegions` for dead blocks, dead block arguments and block
merging. Each pass calls it on the functions it rewrote, so no pass
leaves garbage for a module-wide canonicalize to find.
- **Buys:** no `MatchAnyOpTypeTag` pattern and no fixpoint driver on
  the hot path (3a96c407, 7987388b cannot recur); a bound: one walk per
  changed function per pass.
- **Costs:** a walk does not revisit what it changed, so a fold that
  enables a fold earlier in the same block waits for the next pass's
  walk (MLton accepts this; its shrinker gets most of it by computing
  label meanings first, E2); upstream's greedy canonicalizer stays for
  the passes that need a fixpoint, measured.
- **Deletes:** any-op patterns in `idr-optimize`; module-wide
  canonicalize runs whose only job is cleanup.

**Design 6. The footprint of every pass as a first-class report.**
*(conjecture)* MLton prints, after every pass, the live heap and the
statistics of its state structures (A3). Ours: a Tracy plot per pass
of the solver layer's arena bytes, cell counts and handler counts, and
the process's footprint, so the next wall is a number in a trace, not
a killed process.
- **Buys:** §3's table becomes measurable before it is a wall. **Costs:**
  a counter per arena. **Deletes:** nothing.

**Design 7. Specialize higher-order functions before the label solve.**
*(conjecture)* MLton's polyvariance (F5) before our defunctionalize:
duplicate a higher-order function per use when `(uses - 1) * (size -
small) <= product`, a budget that only leaves code shared.
- **Buys:** smaller closure sums per copy, hence smaller apply
  dispatches and more known calls for inlining. **Costs:** code size,
  bounded by the budget. **Deletes:** nothing by itself; possibly the
  part of `optimize`'s specialization that recovers what the label
  solve merged.

*Why this order.* Design 1 addresses the cause of three walls at once
(ffa91113, 16005000's `remove-dead-values`, b8301ebe's state model) and
is the layer §1 asks for; Design 2 removes the representation behind
e96bb991 and makes Designs 1, 4 and 5 simpler; Design 3 is the rule
that keeps "no rederivation chains" true after the cutover; Design 4 is
counting's share of Design 1's lesson; Design 5 removes the
optimizer's driver cost; 6 is cheap and makes the rest measurable; 7
is an optimization whose value wave 2 must measure.

  a `ProgramPoint` per op, it is worth stating beside this. Please also
  measure upstream's `Liveness` (the non-dataflow one) against Morgan's
  per-variable walk (F7) at a 30,000-block function.
- **mlir-ods and dialect-design (§5.2, §5.8).** `SuccessorOperands` with
  a produced-operand count
  (`mlir/include/mlir/Interfaces/ControlFlowInterfaces.h:30-58`) is the
  mechanism for a `case` terminator whose arms receive the constructor's
  fields (Design 2). MLton's SSA2 makes mutability a per-field fact of
  the object type (`Prod`, C4) and separates building a constructor's
  object from injecting it into its sum (`Object` then `Inject`): both
  bear on our `con`, `cell.*` and `own.*` ops. Its `Return.t` and
  `Handler.t` (tail, non-tail with continuation and handler, dead) are a
  sum on the call, not an analysis.
- **llvm (§5.3).** Design 1's cells want `SpecificBumpPtrAllocator`
  arenas per cell type, `IntEqClasses` or a union-find with handler
  lists, and hash-consed sets (`FoldingSet` or a uniquer) for the set
  domain; `scc_iterator` for the inliner's leaves-first order.
- **cxx26 (§5.5).** MLton's `Analyze` is a record of functions per
  domain (B3); in C++26 that is a concept plus a template, monomorphized
  per analysis, the pattern §4 asks for.
- **rc (§5.10).** MLton has no counting, but F7's liveness (per
  function, per variable, cost the size of the answer) and F2's
  demand-driven dead-code analysis are the cheap forms of the facts
  Perceus-style insertion needs.
- **oom (§5.11).** MLton's driver reports the live heap and its state
  structures' statistics after every pass (A3); its guide states the
  self-compile's memory floor (G1). DeepFlatten is MLton's own
  documented blowup and its escape is a flag that disables the pass
  (F3), which AGENTS.md's budget rule would phrase as "a spent budget
  leaves the program less optimized".
- **library (§5.7).** Worth snapshotting, as text: Fluet and Weeks,
  "Contification Using Dominators" (ICFP 2001), at
  `https://www.cs.rit.edu/~mtf/research/contification/ICFP01/icfp01.pdf`
  (fetched, but its text could not be extracted here without a PDF
  tool); Cejtin, Jagannathan and Weeks, "Flow-Directed Closure
  Conversion for Typed Languages" (ESOP 2000, LNCS 1782, pp. 56-71,
  doi:10.1007/3-540-46425-5_4), not fetched; Appel and Jim, "Shrinking
  Lambda Expressions in Linear Time" (JFP 1997), the shrinker's basis;
  Morgan, *Building an Optimizing Compiler* §4.13, the liveness
  algorithm. `sources/papers/weeks-2006-mlton-whole-program/slides.pdf`
