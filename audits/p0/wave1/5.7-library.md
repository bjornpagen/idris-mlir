#### 5.7.1 Findings

**A. What the library holds for P0, and what it lacks.**

A1. *(read)* The library holds no primary paper of classical dataflow
theory: nothing by Kildall, Kam and Ullman, Wegman and Zadeck (SCCP),
Choi, Cytron and Ferrante (sparse evaluation graphs), Click and Cooper
(combining analyses), Lerner, Grove and Chambers (composing analyses
and transformations), or Reps, Horwitz and Sagiv (IFDS, IDE, which
appear only as restated in Flix, D4), and none of the Datalog
program-analysis line before Soufflé (bddbddb, Doop) or after it
(Ascent). The SSA book
(`docs/ssa-book/`) is the one stored treatment of sparse, SSA-based
analysis (`INDEX.md:293`). What the library holds instead is the
parallel and incremental half: Soufflé and its B-tree, GPU Datalog,
Slog, differential dataflow, LVars, deterministic parallelism
(`INDEX.md:798-881`, `notes/sharded-compilation/deterministic-fixpoints.md`),
equality saturation and egglog (`INDEX.md:215-281`), and the
data-oriented compilers (`code/zig`, `code/typescript-go`,
`code/pareas`, `code/co-dfns`).

A2. *(read)* Earlier passes over the library already concluded, for
proposal 0005/0011, a recipe for whole-program facts: monotone sets
keyed by canonical content-derived keys, bulk-synchronous semi-naive
rounds, read only after a freeze, non-monotone facts as complements of
a monotone dual, ids assigned after the fixpoint by sort and scan
(`notes/sharded-compilation/deterministic-fixpoints.md:141-157`).

**B. The MLIR papers.**

B1. *(read)* MLIR's own rationale names SSA as what makes "dataflow
analysis simple and sparse" and leaves one challenge open: "to make
CFG-based analyses and transformations compose over nested regions"
(`papers/lattner-2020-mlir/design.tex:34,40`). It cites Click and
Cooper's combination of constant propagation, value numbering and
unreachable-code elimination as the reason to combine passes, and asks
for the four roles (optimize, enable, lower, clean up) to mix "at the
granularity of a single operation rather than sequencing passes on the
full compilation unit" (`design.tex:60-71`).

B2. *(read)* The paper names exactly four ways a pass meets an open set
of ops: traits ("a single bit"), privileged hooks (folders,
canonicalization patterns), optimization interfaces (the inliner's is
the example), and dialect-specific passes, which "are just as useful in
the MLIR system as they are in other compiler systems"
(`implications.tex:23-127`). An honest solver over our own dialect's
semantics is the fourth way, not a departure from MLIR.

B3. *(read)* MLIR's parallelism rests on isolated-from-above ops, and
"this requirement is the reason why ... MLIR does not feature
whole-module use-def chains. Global objects are referenced through
symbol table entries" (`infra.tex:104-116`; `ir_design.tex:129-138`).
So every interprocedural fact (who calls whom, which closures flow
where, what a callee does to its arguments) lies outside the IR's use
lists by design and has to be built as a structure of its own. That
structure is the solver layer's input; nothing upstream builds it for
references that are not calls (`notes/compile-pipeline/upstream-mlir-llvm.md`
§2, read from the pinned tree in an earlier pass).

B4. *(read)* Bhat and Grosser compile Lean's λrc through MLIR with a
case's alternatives as regions, and show SSA's optimizations carry
over: dead-region elimination is plain DCE, and region-level value
numbering is "a rolling hash of the value numbers of all instructions
within the region" for single-block regions
(`papers/bhat-2022-lambda-ultimate-ssa/paper.tex:1757-1800`). Their
region values "may not be passed to other functions ... and may not be
returned", which "ensures that all uses ... can be statically analyzed"
(`:1709-1718`): the representation, not an analysis, bounds the flow.

**C. Sparse, SSA-based analysis (the SSA book).**

C1. *(read)* Dense analysis keeps a fact per (value, program point);
under SSA a fact that changes only at definitions binds to the name,
propagates along def-use links, and skips every point where nothing
changes (`docs/ssa-book/ssa-based-compiler-design.pdf`, book §1.3,
pp. 10-11).

C2. *(read)* The criterion for "can this analysis be sparse" is
Pereira and Rastello's: a *partitioned lattice per variable* (PLV)
problem, whose lattice is a product of one lattice per variable and
whose transfer functions decompose per variable (§11.1.2, p. 152). A
program representation has the *static single information* (SSI)
property for a PLV problem when four conditions hold (Split, Info,
Link, Version, §11.1.3, p. 153); the dense system then becomes one
constraint variable per name, solved by a worklist over instructions
(Algorithms 11.1, 11.2, p. 156). Where SSA lacks the property, the
representation is changed, not the solver: σ-functions at branches
(the dual of φ at joins) and parallel copies split live ranges so the
fact becomes per-name (§11.1.4, pp. 154-155; e-SSA for range analysis,
Fig. 11.2, p. 158). Relational facts ("i < j") are not PLV (p. 152).

C3. *(read)* A backward analysis is a sparse *equation* system only
under static single use (SSU), the dual of single assignment; without
it each use adds an inequation and the old value has to be met in
(pp. 156-157). SSA dead-code elimination is the exception: "a code
under SSA form fulfills the SSI property for dead-code elimination"
(p. 157), one "useful" bit per instruction.

C4. *(read)* Liveness under strict SSA needs no fixpoint: two passes
over a reducible CFG (§7.2.1, p. 98), or a *liveness check* that
answers "is v live at q" from a precomputation that "is independent of
variables" plus v's def-use chain, so that "pre-computed information
remains valid upon adding or removing variables or their uses" (§7,
p. 96).

**D. Datalog and Datalog with lattices.**

D1. *(read, measured)* Soufflé turns a Datalog analysis into a C++
analyzer by three Futamura projections: semi-naive evaluation
specialized to the rules gives a relational-algebra program; that
program specialized gives C++ with a minimal index set (chains of a
lattice of indices, by Dilworth's theorem); the C++ is specialized by
templates at compile time, where "data structure interfaces are
realized in form of C++ concepts rather than polymorphic C++ base
classes to eliminate virtual-call dispatches and run-time type checks",
down to a variadic `Comperator<cols...>` for tuple order
(`papers/jordan-2016-souffle/paper.pdf` pp. 2-5). *Measured*
(Table 1, p. 6, 8 cores): OpenJDK 7 (1.4 M variables, 160 K methods)
context-insensitive points-to in 35 s and 8.5 GB; context-sensitive in
6 h 44 m and 206 GB, where bddbddb, µZ and SQLite did not finish.

D2. *(read, measured)* Parallel semi-naive evaluation is
*phase-concurrent*: within a round the relations read (full and delta)
are never written and the relation written (new) is never read, so
"read operations do not need synchronization; only the write operation
must be synchronized", and relations only grow
(`papers/jordan-2019-concurrent-btree/paper.pdf` p. 3). Their B-tree
adds optimistic read-write locks and "hints" that reuse the last
traversal because derived tuples arrive sorted: up to 59x in
micro-benchmarks, 3x end to end (p. 1).

D3. *(read)* GPU Datalog's relation (HISA) is three flat layers: a
dense row-major data array, a sorted index array (a permutation, join
columns first), and an open-addressing table from the hash of the join
columns to the first matching position; a range query is one probe and
a scan, deduplication is a sort and an adjacent compare, and merging a
delta into the full relation is a concatenation because the delta was
already deduplicated (`papers/sun-2025-gpu-datalog/main.tex:438-660`).
*Measured*: up to 45x over Soufflé on context-sensitive points-to
(`notes/sharded-compilation/deterministic-fixpoints.md:23-24`).

D4. *(read)* Flix adds lattices and monotone functions to Datalog. Its
argument for analyses as rules: sub-analyses "can be easily composed by
taking the union of their rules, and the Datalog solver takes care of
the mutual dependencies", where in a hand-written analyzer "the
decision of how to structure the worklists is global"
(`papers/madsen-2016-datalog-to-flix/paper.pdf` p. 1). IFDS is five
rules over `PathEdge`, `SummaryEdge` and a tabulated `EshCallStart`;
IDE is the same five rules with a micro-function composed in each head
(Figs. 5-6, pp. 10-11). Transfer functions must stay functions, not
tabulated relations, because tabulating them is the whole analysis
(p. 10). Its own solver's admitted costs: boxed values, an AST
interpreter, hash maps where "some would be more efficiently
represented as dense arrays" (p. 11).

D5. *(read)* Unification beats subsets where precision allows:
Steensgaard's points-to is near-linear where Andersen's is quadratic;
Soufflé's union-find `eqrel` keeps an equivalence but forces a "join
modulo equivalence", which egglog removes by canonicalizing every
element to its representative so the join is an equality join
(`papers/zhang-2023-egglog/pointer-analysis.tex:1-90`).

D6. *(read)* Slog makes facts first-class: every (sub)fact is interned
and has an id, so Datalog can state defunctionalization and abstract
machines directly, and relational algebra is balanced over MPI ranks
(`papers/gilray-2022-slog/sec-intro.tex:14-35`); its fact ids are
schedule-dependent unless each bucket's input is sorted first
(`notes/sharded-compilation/deterministic-fixpoints.md:71-72`).

**E. Rewriting as data: equality saturation and egglog.**

E1. *(read, measured)* egg's *rebuilding* separates restoring the
e-graph's invariants (congruence, the hashcons) from `merge`: a merge
only pushes the class onto a worklist; `rebuild` deduplicates the
worklist up to equivalence and repairs one layer of parents per class;
a saturation iteration becomes a read-only search phase, a write-only
apply phase and one rebuild (`papers/willsey-2021-egg/03-rebuilding.tex:99-230,
354-420`). *Measured*: congruence maintenance 88x faster and equality
saturation 21x faster, geometric mean (`_build/speedup-data.tex:1-2`).

E2. *(read)* An *e-class analysis* is a semilattice value per class,
with `make` (from the children's values), `join` (on merge) and an
idempotent `modify`, under the invariant that a class's value is the
join of `make` over its nodes; the same worklist that restores
congruence restores the analysis (`04-tricks.tex:72-240`). The
analysis is data on the canonical node, kept current by deltas.

E3. *(read, measured)* egglog is Datalog with built-in equality and
functions whose `:merge` expression resolves functional-dependency
conflicts (a lattice join or a union). Its database is functional (a
map per function, not a set); rebuilding canonicalizes it; e-matching
is a relational query under a worst-case-optimal join; semi-naive
evaluation makes matching incremental "for free"; about 4,200 lines of
Rust (`papers/zhang-2023-egglog/implementation.tex:4-150`). *Measured*:
3.34x over egg without semi-naive, 9.27x with it (`:255-262`). It
calls egg "artificially limited to a single type and a single analysis"
because the analysis lives in the host's generics (`:195-200`).

**F. Incremental and parallel solving.**

F1. *(read)* LVars: writes are lattice joins and reads are threshold
reads, so a parallel fixpoint is deterministic by construction; handler
pools with `quiesce` detect the fixpoint and `freeze` after quiescence
reads the exact value (`papers/kuper-2014-freeze-after-writing/paper.pdf`
pp. 1-5). *Measured* in the paper: parallel k-CFA up to 202x total
over the functional baseline (`notes/sharded-compilation/deterministic-fixpoints.md:56-59`).

F2. *(read, measured)* Phase-concurrent data structures (operations of
one kind commute within a phase) give a layout independent of
operation order: a deterministic phase-concurrent hash table, up to 52x
on 40 cores (`papers/shun-2014-phase-concurrent-hash/paper.pdf` p. 1);
deterministic reservations (reserve by priority, then commit, a prefix
of iterates per round) make greedy algorithms internally deterministic
(`papers/blelloch-2012-internally-deterministic/paper.pdf` pp. 2, 4-7).

F3. *(read)* Differential dataflow keeps state over a *partial order*
of versions (iteration × input round) and retains indexed difference
traces instead of consolidating them, so an iterative computation
(SCCs included) is updated incrementally
(`papers/mcsherry-2013-differential-dataflow/paper.pdf` p. 1).

F4. *(read)* Build systems are a scheduler (topological, restarting,
suspending) composed with a rebuilder (dirty bit, verifying traces,
constructive traces, deep constructive traces); minimality means each
task runs at most once per build, and early cutoff stops dependents
when a result did not change; deep traces lose early cutoff
(`papers/mokhov-2018-build-systems/paper.pdf` pp. 3, 5, 13-16). MLIR's
`AnalysisManager` is a dirty-bit rebuilder with a topological scheduler
and no early cutoff (*conjecture*, for §5.1 to confirm).

F5. *(read)* typescript-go parallelizes checking with a pool of
checkers, each with its own symbol, type and instantiation caches and
taken exclusively; files are assigned to checkers by a weighted FENNEL
partition of the import graph, ties broken deterministically, because
"putting related files on the same checker reduces duplicated cache
construction" (`code/typescript-go/internal/compiler/checkerpool.go:36-104,
162-280`). The shared state is replicated per worker and the work
partitioned for locality; nothing mutable is shared under a lock.

**G. Data-oriented compiler design.**

G1. *(read)* Zig's `MultiArrayList(T)` derives a structure of arrays
from a struct (one array per field) or a tagged union (a tag array and
an array of the bare union) at compile time, in one allocation
(`code/zig/lib/std/multi_array_list.zig:9-80`).

G2. *(read)* Zig's syntax tree is a `MultiArrayList` of nodes
`{tag, main_token: u32, data: 8-byte union}`; children are `u32`
indices typed by what they index (`Node.Index`, `TokenIndex`,
`ExtraIndex`), absence is a sentinel (`OptionalIndex.none = maxInt`),
offsets are relative (`Node.Offset`), and what does not fit in a node
goes to `extra_data: []u32`, decoded by `extraData(index, T)` from the
fields of `T` (`code/zig/lib/std/zig/Ast.zig:17-33, 283-305, 3014-3086`).

G3. *(read)* Zig's `InternPool` hash-conses every type and value of the
typed compiler into an `Index` (`enum(u32)`), so "two values which have
the same type can be equality compared simply by checking if their
indexes are equal" (`code/zig/src/InternPool.zig:4580-4587`); an entry's
flat form is `Item {tag, data: u32}` with side arrays (`:4574-4578`).
Threading: one `Local` per thread whose `mutate` half only the owner
touches and whose `shared` half others read with acquire loads
(`:1029-1072`), and a power-of-two set of `Shard`s, each a map whose
writers take that shard's mutex and whose readers load atomically
(`:1531-1600`). Thread ids sit in an index's top bits, so indices are
schedule-dependent (`notes/sharded-compilation/whole-program-at-scale.md:140-143`).

G4. *(read)* Pareas (a compiler whose passes run on the GPU) stores the
tree inverted, after Hsu's Co-dfns: a node-type array and a parent
array, in pre-order so a parent's index is below its children's; every
pass is a data-parallel operation over the arrays (prefix sums, sorts,
pointer jumping), and nodes are deleted by marking the parent slot
(`papers/voetter-2021-gpu-frontend-thesis/thesis.pdf` pp. 38-40;
`papers/hsu-2019-data-parallel-compiler/hsu-dissertation.pdf.txt:690-760`).

G5. *(read, measured)* Hash-consing alone traded time for space (91.5 s
to 195 s, 1,680 KB to 480 KB); with memoization keyed by the
hash-consed tags it won both (54 s to 5.06 s, 95,300 KB to 720 KB),
because hashing and equality become integer operations
(`papers/filliatre-2006-hash-consing/paper.pdf` p. 4).

G6. *(read, measured)* MLIR's own Presburger library (FPL, "large
parts ... upstreamed to LLVM's MLIR project") instantiates the whole
library per integer type by templates, computes with 16-bit integers
and retries the computation at a wider type on overflow, so "we only
have to perform a single dispatch as to which library to use, rather
than dispatching for each low-level integer operation"; element-wise
switching "inhibits vectorization" and pays a check per operation.
5.4x over isl (`papers/pitchanathan-2021-fpl/paper.pdf` pp. 2-3).

**C, continued.**

C5. *(read)* In SSA's functional reading, "lexical scope coincides with
the dominance region": a block may nest inside another exactly when
the other dominates it (book §6.2.3, pp. 82-83). In an IR whose
control flow is nested regions rather than a CFG, dominance and scope
are the region tree.

C6. *(read)* The value state dependence graph (VSDG) carries side
effects as explicit *state* edges beside value edges, so ordering is
data, and dead-node elimination is one rule over both kinds of edge
(book §12.5, pp. 179-181).

**E, continued.**

E4. *(read)* Relational e-matching compiles a pattern to a conjunctive
query over one relation per operator and runs it with a worst-case
optimal join instead of top-down backtracking: "up to 6 orders of
magnitude faster" in egg
(`papers/zhang-2022-relational-ematching/abstract.tex`, `eval.tex:77`).

**F, continued.**

F6. *(read)* Composing a solver with queries that are not monotone
needs a schedule: Rouvoet et al. give necessary and sufficient
conditions (critical edges in an incomplete scope graph) under which a
query's answer is *stable*, and delay queries until then, which makes
the derived checkers "sound by construction"
(`papers/rouvoet-2020-knowing-when-to-ask/paper.pdf` p. 2). Datalog's
stratified negation and LVars' freeze are the same rule: read a
complement only after what it complements is complete.

**H. Specialization and supercompilation.**

H1. *(read, measured)* Mitchell's supercompiler terminates by a
well-quasi-order over *bags of source names*: every expression is
labelled by (function, expression index, argument count), a finite
alphabet for a given program, and a sequence of expressions is allowed
to continue only while each new bag has a different set of names or
fewer names than every earlier one; finiteness follows from the
alphabet, and the check is a set comparison and a count
(`papers/mitchell-2010-rethinking-supercompilation/paper.pdf` pp. 6-7).
Compile times "under four seconds" where earlier supercompilers took up
to five minutes; under 300 lines of Haskell (p. 1).

H2. *(read)* Positive supercompilation propagates what a match learned
into each branch (the scrutinee is replaced by the pattern), which is
what makes driving subsume deforestation
(`papers/sorensen-1996-positive-supercompiler/paper.pdf` pp. 1-2, 10-12).

H3. *(read)* Two-level type theory makes binding times types: a
type in the static universe "is guaranteed to be only present at
compile time, and will be staged away"
(`papers/kovacs-2022-staged/paper.tex:322-328`); with a first-order
object language, "all programs ... can be ultimately compiled without
any dynamic closures" (`papers/kovacs-2024-closure-free/paper.pdf` p. 3).
What a binding-time analysis would infer is instead stated, and checked
by typing.

H4. *(read, measured)* GCC's IPA passes communicate through *virtual
clones*, "bodiless call-graph nodes that describe how to derive a
body", so later analyses compose over decisions, not rewritten IR;
ThinLTO decides imports and internalization at a thin link over
summaries that add about 0.8% to IR size
(`notes/sharded-compilation/whole-program-at-scale.md:21-25, 48-53`).

#### 5.7.2 What it means for idris-mlir

All of this is *conjecture* until wave 2 reads our code; the walls are
§3's. Keyed to the brief's four questions: *analyses as data* is M7,
M11 and L4 (facts as lattices on canonical values or as relations,
composed by union of rules); *how solvers compose* is M7 and M8
(one product-lattice fixpoint for mutual dependence, a frozen read for
one-way dependence, summaries across calls); *compact, parallel state
for 70,000 functions* is M8, M9 and L2 (scopes, dense ids, summaries,
phase concurrency); *IR representations that make per-value state
cheap* is M1, M9 and L1 (SSI and single use by construction, the region
tree as dominance, dense numbering, interned types).

M1. **The 627 GB wall is a dense formulation of a sparse problem**
(C1-C3, against ffa91113). A lattice per value is the sparse form; an
`Executable` per program point, a predecessor state per function and
uniqued program points are the dense form's apparatus. The theory says
dense state is needed only for facts that change at points that are not
definitions. In an ownership IR the facts that change at such points
("after here v is consumed", "after here v is shared") are exactly the
ones a representation can turn into definitions: an op that changes a
value's ownership defines a new value, the way σ-functions and parallel
copies split live ranges (C2). Then exclusivity, borrows, stack
lifetimes and reuse become per-value lattices. Two of our facts make
this cheaper than in general SSA: a quantity-1 value is used exactly
once, so for linear values the IR has static single use (C3) and
*backward* ownership analyses over them are sparse equation systems
with no meet against the old value; and until tail loops and the
lowering to `cf`, control flow is nested regions (structured loops
included), so dominance is the region tree (C5), the loop-nesting
forest that C4's liveness check needs is the same tree, and liveness
is a query, not a fixpoint (C4).

M2. **The 52 GB liveness wall is a one-bit problem held as a lattice
per value** (C3, against 16005000). SSA dead-code elimination is "one
useful bit" per op on a backward worklist; deleting dead arguments and
results across calls is a partitioned-variable problem (each argument
independent, §11.1.2), whose interprocedural form is a bit per argument
and result in a per-function summary, solved bottom-up over the call
graph's condensation (D4's `SummaryEdge`, H4).

M3. **The quadratic interface query (e96bb991) is validation repeated
where a parse belongs.** A match with N cases has O(N) flow edges
(parent to each region, each yield back to the parent); asking the
interface per (terminator, successor) pair re-derives that star N times.
The data-oriented reading (D3, G2, G4) is to query the interface once
per op at the boundary and keep the answer as a flat edge array (CSR:
an offset per node, a target array), which the solver reads. The
interface stays the one source of the fact; the array is its parsed
form, scoped to one solve.

M4. **`idr-rc-stack`'s 47 GB is a dense set per value copied per edge**
(b8301ebe). "Can v's cell live on the stack" is a partitioned-variable
problem: candidates do not interact, so a bit vector per value per edge
is the dense encoding of independent sparse problems. The sparse form
is one bit per value propagated on def-use edges, or a reachability
query from v's uses to an escaping use (C4's shape).

M5. **`idr-frames` (43 GB) and the specializer walls are clones
materialized before they are deduplicated** (16005000, 3a96c407). GCC's
virtual clones and ThinLTO's summaries (H4) decide clones as keys
first, hash-cons the keys (G3, G5), and materialize each distinct key
once. Mitchell (H1) shows termination by construction from a finite
alphabet of names, with no round budget, which is AGENTS.md's rule
("terminate by construction ... a spent budget leaves the program less
optimized and never rejects it").

M6. **The context-lock wall (98c6315c) and the per-declaration table
rebuild (73bba53f) are a mutable, nominal type read while it may
change.** Zig's InternPool (G3) reads interned data lock-free and
shards writers; Freeze-after-writing (F1) and phase concurrency (D2)
say read-mostly program facts should be *built, then frozen*, before
any parallel pass reads them, after which no lock is needed. An
interned, structural description of a data type (G3, G5) makes "same
type" an integer compare and memoization keyed by it cheap, where a
symbol-named type forces a module lookup per query (the casework audit
in `notes/compile-pipeline/casework-audit.md` §0, item 3, describes
`!idr.data<@T>` this way: *recalled* from that note, for wave 2).

M7. **Solvers compose in two ways, and the layer should name which.**
(i) Mutually dependent facts are one fixpoint over a product lattice
(Click and Cooper, cited by MLIR's own rationale, B1; Flix's union of
rules, D4; egglog's merge functions, E3); upstream's
`DeadCodeAnalysis` loaded beside SCCP is this kind. (ii) A fact that
only reads another's complete answer runs after it, reading the frozen
result (F1, F6); a non-monotone question ("unique everywhere") is the
complement of a monotone one ("shared somewhere") read after the
freeze (A2). Interprocedural composition is summaries (D4's IFDS and
IDE), scheduled bottom-up over call-graph SCCs; MLIR has no
whole-module use-def chains (B3), so the reference graph (calls plus
closure and constant references) is the one interprocedural relation
the layer builds.

M8. **Threading is phase concurrency over scopes.** A solve over one
call-graph SCC reads callee summaries that are frozen and writes only
its own state and summary (D2's two phases). SCCs whose callees are
done form a wave; waves are the parallelism, with no lock on any state
a solve reads. Where state is a cache rather than a result,
replicate it per worker and partition work for locality (F5), never
share it under a lock. Determinism follows from monotone joins and
sorted hand-offs (F1, F2); thread-tagged ids must never order output
(G3).

M9. **Per-value state is cheap when values have dense numbers.**
MLIR's `Value` is a pointer and has no dense id (*recalled*; §5.1 to
confirm), so per-value state today is a hash map. Every data-oriented
compiler in the library (G1-G4), Soufflé's relations (D1) and GPU
Datalog's arrays (D3) key state by a dense integer: number a scope's
values once, in walk order, and hold every lattice as an array indexed
by that number (a bit vector for one-bit facts). The pre-order walk
also gives each op a subtree interval, so "a encloses b", hence
dominance in structured regions (C5), is two integer compares (G4's
pre-order property).

M10. **Monomorphized C++ is the solver literature's own practice.**
Soufflé's analyzers use C++ concepts, not base classes, and
template-specialized comparators (D1); FPL hoists the one dispatch out
of the hot loop by instantiating the library per representation (G6).
That is §1's "monomorphized template- and concept-heavy C++" as an
engineering result, not a style.

M11. **Rewriting.** egg's read-only search, write-only apply and one
rebuild per round (E1), and relational matching indexed by operator
(E4), are what MLIR's rooted patterns approximate: a pattern rooted on
an op name is an index; a pattern that matches any op is a full scan
(the 75 million attempts of 3a96c407). E-class analyses (E2) are the
model for an analysis kept current across rewrites by deltas, which in
MLIR is a rewriter listener, not a recomputation. Equality saturation
itself solves no wall in §3.

#### 5.7.3 Candidate designs, ranked

Scale used throughout (*conjecture*, for wave 2 to measure): 71 MB of
text at a few tens of bytes per op is on the order of a million ops and
values over 70,000 functions. A one-byte fact per value is then about a
megabyte for the whole module; every wall in §3 is a multiplier on top
of that (per program point, per edge, per pair, per clone).

**L1. Sparse by representation: the dialect gives every ownership
analysis the SSI property** (C2, C3, C5; M1). Rule for §5.8: an op that
changes what may be done with a reference (consume, share, borrow,
give, take, enter a linear scope) defines a new SSA value for the new
state, as σ-functions and parallel copies do; a match's case region
binds the refined scrutinee as a block argument (what positive
supercompilation propagates, H2); a quantity-1 value keeps static
single use by type. Then each analysis's fact is a lattice per value,
and no analysis keeps a fact per program point.
- *Buys:* removes the dense apparatus behind ffa91113 and b8301ebe
  outright; backward analyses over linear values become equation
  systems (C3).
- *Costs:* one value per ownership change (whether `take`, `own.give`,
  `share`, `borrow` and the rest already define one is wave 2's to
  check); case regions with block arguments.
- *Deletes (conjecture):* program-point state in exclusivity, borrows
  and stack lifetimes; any analysis that recovers "consumed here" by
  scanning forward from a point.
- *Made unrepresentable:* a value whose ownership differs at two points
  of its live range; hence the per-point fact that tracked it.
- *Essential, kept distinct (the limit):* relational facts, such as
  whether two values may alias, are not per-variable lattices (C2); they
  stay relations (L4) and are not folded into a per-value lattice behind
  a flag.

**L2. One scoped sparse solver core in the solver layer** (C2's
Algorithm 11.2, D1, D2, G1-G4, G6; M3, M7-M10). A scope is a function
or a call-graph SCC. Building a scope parses the IR once into
read-only arrays; analyses are concept-typed and monomorphized; state
is arrays indexed by dense ids and freed with the scope; callee facts
come from frozen summaries.

```c++
// Built once per scope by one pre-order walk; read-only afterwards.
struct Scope {
  std::vector<Operation *> ops;        // op id = pre-order position
  std::vector<uint32_t> end;           // i encloses j  iff  i < j < end[i]
  std::vector<Value> values;           // value id = walk order
  Csr uses;                            // value id -> op ids
  Csr flow;                            // one interface query per op, not per pair
  std::span<const FuncId> callees;     // into the reference graph
};
template <class A>
concept SparseAnalysis = requires(const A a, const Scope &s, OpId op) {
  typename A::Lattice;                 // trivially copyable join-semilattice
  { A::direction } -> std::convertible_to<Direction>;
  { a.transfer(s, op) };               // reads operand lattices, returns result lattices
};
// Analyses that depend on each other are solved together over the
// product lattice; one worklist of op ids (Algorithm 11.2), no program points.
template <SparseAnalysis... As>
auto solve(const Scope &, const Summaries &frozenCallees) -> std::tuple<Facts<As>...>;
```

  Scheduling: SCCs of the reference graph (calls plus closure and
  constant references, B3) in bottom-up waves; a wave's scopes run in
  parallel because each reads only frozen callee summaries and writes
  only its own (D2's phases), with `llvm::scc_iterator` for the
  condensation. A summary is a small fixed record per function in one
  array indexed by function id (a bit per argument and result for
  usefulness, a lattice per parameter for ownership: D4's
  `SummaryEdge`).
- *Buys:* peak memory is the summaries (70,000 small records) plus the
  scopes in flight, not the module times anything; analyses that today
  each own a solver, a worklist and a `DenseMap` share one engine;
  composition is visible in the type (`solve<As...>`), threading in
  the wave schedule (§4's "threaded by construction").
- *Costs:* the engine (Soufflé's core relational machine is the
  precedent for how small it can be: D1); building a scope is a walk
  plus a transient `Value`-to-id map; a scope view is a second copy of
  def-use structure, held only for one solve (a cached analysis in
  `AnalysisManager` terms, never persisted, never outliving the IR it
  was built from).
- *Upstream first:* intraprocedural facts that upstream computes per
  function stay on upstream (`int-range-optimizations` nested per
  function measured 3 s against 30 s module-wide,
  `notes/compile-pipeline/upstream-mlir-llvm.md` §4). Whether
  upstream's `DataFlowSolver` can instead be patched to scoped, array
  state is §5.1's question; the theory here says the state model, not
  the algorithm, is what must change, and upstream's header admits it
  (§5.1, A2).
- *Deletes (conjecture):* the whole-program `DataFlowSolver` uses in
  ownership analyses, the hand worklists (87 `worklist` tokens, §2),
  most per-analysis `DenseMap` state, exclusivity's own graph and
  `Scc.cpp` if `scc_iterator` serves.
- *Made unrepresentable:* solver state that outlives its scope, a
  per-pair interface query (the edge array is built per op), a solve
  that reads state another thread writes.

**L3. Build, then freeze: interned program tables** (D2, F1, G3, G5;
M6). The table of data types, effect summaries and the reference graph
are built once at a pass boundary as immutable, interned structures (a
structural description hashed to an id), then read lock-free by every
parallel pass; a pass that changes them builds the next version.
- *Buys:* no read under the context's lock (98c6315c); "same type" is
  an id compare; memo tables keyed by ids (G5's 10x).
- *Costs:* a rebuild when defunctionalization or specialization adds
  types; a structural type identity where today's is nominal (§5.8).
- *Deletes (conjecture):* mutable-type fact reads, per-declaration
  table rebuilds (73bba53f).
- *Made unrepresentable:* a read racing a write of a program table; the
  lock is not needed because the table cannot change once frozen.

**L4. Whole-program relations as sorted flat arrays, with union-find
where precision allows** (D1, D3, D5, D6). The label (closure) flow,
the reference graph and effect propagation are relations: tuples in
dense arrays, a sorted index with join columns first, semi-naive rounds
for recursion, union-find canonicalization for analyses whose
constraints are equalities (labels flowing through constructor fields
unify; Steensgaard over Andersen), ids assigned after the fixpoint by
sort and scan (A2). Relations are C++ templates over their columns
(Soufflé's `Comperator<cols...>`, D1), not a runtime-dispatched engine.
- *Buys:* near-linear label and alias solves, deterministic by sort;
  one relational shape for several global facts.
- *Costs:* a few relation templates; precision lost wherever
  unification merges what subsets would keep apart (to be measured
  against today's label solve). Lost precision makes a closure sum
  larger, never unbounded, so it changes code quality, not acceptance
  (AGENTS.md: every closure set of the closed module is a sum).
- *Deletes (conjecture):* bespoke worklists in the label solve and in
  effects. MLton's 0CFA is the serial precedent (§5.9).

**L5. Clones as keys** (H1, H4; M5). Specialization, frames and grade
contexts first compute the set of keys each function needs (a key is
interned, so equal keys are one id), then materialize each distinct key
once; termination comes from keys drawn from a finite alphabet (H1),
so a budget only ever limits profitability.
- *Buys:* memory proportional to distinct keys (16005000's per-pair
  clones vanish); no round-count termination argument.
- *Costs:* a key representation per specializer.
- *Made unrepresentable:* two clones of one key; a termination argument
  that rests on a count.

**L6. Rewrites indexed and analyses maintained by listeners** (E1, E2,
E4; M11). Every pattern rooted on an op name or interface; analyses
that must survive a rewrite are updated through
`RewriterBase::Listener` deltas instead of recomputed. §5.2 owns the
mechanism.

**Not recommended for P0.** Equality saturation for the main pipeline
(no wall in §3 is a phase-ordering problem); linking an external
Datalog engine (Soufflé generates C++ and would be a build-time
dependency; its design, not its code, is what transfers); differential
dataflow (incrementality across builds is proposal 0005's, not P0's).

#### 5.7.4 Questions for the owner and for wave 2

*For the owner.*
- **QL1.** Is a scoped, read-only array view of the IR (L2's `Scope`),
  built per solve and freed after it, acceptable as the solver layer's
  input, given that it restates def-use structure for the length of one
  solve? Or must every solver run over MLIR `Value`s directly, keyed by
  hash maps?
- **QL2.** Should SSI for ownership analyses be a rule of the dialect
  redesign (L1): every ownership change a new value, every case region
  binding its refined scrutinee?
- **QL3.** Composition: should the solver layer state analyses as
  rules over relations (Flix, Soufflé: composition is the union of
  rules, D4) or as transfer functions over one engine (L2)? The theory
  favours rules; the cost is an engine that understands them.
- **QL4.** Is byte-identical output for any thread count a requirement?
  It fixes the threading rules (sorted hand-offs, ids after the
  fixpoint, no thread-tagged ids in output: A2, G3).
- **QL5.** Is equality saturation out of P0's scope?
- **QL6.** Approve the snapshot list in 5.7.6 for `sources/`.

*For wave 2 (the `solvers` and `ods` lanes).*
- For every analysis and solver of ours: is its fact a lattice per
  value (PLV), independent per value (PVP), or relational? Forward or
  backward? Which keep a fact per program point, and is that point an
  ownership change the IR could make a definition (L1)?
- Which analyses run in the same scope over the same facts and could
  share one product-lattice solve; which only read another's finished
  answer (M7)?
- The stage-1 module's counts: ops, values, regions, blocks, functions;
  the size of the largest function; the distribution of call-graph SCC
  sizes (singletons?); the largest match's case count.
- Where a parallel pass reads a mutable type or anything under the
  context's lock; where a program table is rebuilt (L3).
- For each specializer: what its key is, whether keys come from a
  finite alphabet, and whether any budget decides termination (L5).
- Which patterns are not rooted (L6).

#### 5.7.5 Notes for other lanes

- **mlir-analysis (§5.1).** Upstream's sparse analyses are the SSA
  book's Algorithm 11.2 (a lattice per value, a worklist of ops) with a
  heavyweight state model; what C2-C4 say a sparse solve needs is one
  lattice per value and no program-point state, so check what
  `Executable` per block and `PredecessorState` per callable cost when
  regions are structured and the problem is PLV. `DeadCodeAnalysis`
  loaded beside SCCP is Click and Cooper's combination (B1, M7). The
  `visitExternalCall` hook is where an IFDS-style summary (D4) would
  enter.
- **mlir-ods (§5.2).** Rooted patterns are relational matching's index
  on the operator (E4); find whether interface- and trait-rooted
  patterns are tried on every op. egg's read-only match / write-only
  apply / one rebuild (E1) is a model for a parallel or deterministic
  driver.
- **llvm (§5.3).** Precedents for monomorphized solvers: Soufflé's
  concept-typed relations and variadic comparators (D1), FPL's single
  dispatch per computation (G6). `IntEqClasses` and
  `EquivalenceClasses` are the union-find L4 needs; `scc_iterator`
  the condensation L2 needs.
- **cxx26 (§5.5).** Zig derives a structure of arrays from a struct or
  tagged union at compile time (G1); static reflection (P2996) could
  derive L2's state arrays and L4's relation columns from one struct the
  same way, instead of hand-written parallel vectors.
- **ecosystem (§5.6).** IREE's DFX is an Attributor-style solver over
  MLIR; compare its state model with C2's per-value lattices and with
  L2's scopes.
- **dialect-design (§5.8).** L1 is a dialect rule: ownership changes
  define values (SSI), case regions bind refined scrutinees, linear
  values keep single use. Bhat and Grosser's non-escaping region values
  (B4) bound flow by representation. The VSDG's state edges (C6) are
  the theory behind a world token as a value against effects on a
  resource. An interned, structural data type (L3) against
  `!idr.data<@T>`.
- **mlton (§5.9).** MLton's 0CFA in under 2 s by hash-consed sets and
  union-find (`notes/sharded-compilation/whole-program-at-scale.md:78-79`)
  is L4's serial precedent; how MLton holds per-node analysis state
  (property lists) against L2's dense arrays is worth a sentence.
- **rc (§5.10).** Quantity 1 gives static single use (C3): backward
  ownership analyses over linear values are sparse equation systems.
  Borrow inference per parameter is a partitioned-variable problem
  whose interprocedural form is a per-function summary (D4).
- **oom (§5.11).** L2 bounds the compiler's solver memory by
  construction (summaries plus scopes in flight); Soufflé's 206 GB
  context-sensitive run (D1) is a reminder that a correct solver with
  the wrong state still runs out.
