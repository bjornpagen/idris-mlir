# 5.2 mlir-ods: ODS, traits, interfaces and the rewrite infrastructure

The goal is a recipe: for each kind of fact a dialect holds, the ODS
mechanism that declares it and what it generates. This lane owns the
mechanisms (what ODS, traits and interfaces can express and what they
cost); what our dialect should be, its ops, types, names and syntax, is
§5.8's.
- Op definitions: native traits (`NativeOpTrait`, `ParamNativeOpTrait`,
  `verifyTrait`, `TraitList`, `PredOpTrait`), the built-in traits
  (`SameOperandsAndResultType`, `AllTypesMatch`, `TypesMatchWith`,
  `HasParent`, `ParentOneOf`, `SingleBlockImplicitTerminator`,
  `ReturnLike`, `ConstantLike`, `Commutative`, `ElementwiseMappable`,
  `IsolatedFromAbove` and the rest), constraints and predicates,
  properties, builders, assembly formats, verifiers (`hasVerifier`,
  `hasRegionVerifier`, the order of trait verification), folders and
  canonicalizers.
- Effects in ODS: `Arg`/`Res` with `MemRead`, `MemWrite`, `MemAlloc`,
  `MemFree` on resources, op-level `MemoryEffects`, `Pure`,
  `RecursiveMemoryEffects`, stages and full-region effects.
- Interfaces: op, type and attribute interfaces; methods, default
  implementations, static methods, interface verifiers, dependent traits,
  `DeclareOpInterfaceMethods`, external models and promised interfaces.
- Types and attributes: parameters, storage, mutable types (and their
  locking), generated verification, enums (`EnumAttr`, bit enums).
- How upstream dialects classify ops without ladders (`arith`, `scf`,
  `memref`, `linalg`'s structured-op interface and generated op
  families, `vector`, `llvm`'s generated intrinsics); generated op lists.
- Rewrites: rooted patterns and `MatchAnyOpTypeTag`, the greedy driver's
  configuration and listeners, the walk pattern driver, dialect
  conversion, DRR and PDLL as the pinned tree has them (maturity, the
  cost of generated and interpreted patterns).
- Custom TableGen backends: how upstream writes `mlir-tblgen` backends
  and the Python bindings generator, as models for `idris-mlir-tblgen`.
- Bytecode (`BytecodeOpInterface`, the ODS bytecode generator) and the
  printer's aids (`OpAsmOpInterface`, aliases, result names).
- Verification's cost at scale, and verifying after every pass.

#### 5.2.1 Findings

**A. Effects in ODS.**

A1. *(read)* An effect declared in ODS is a `SideEffect` record
(`include/mlir/Interfaces/SideEffectInterfaceBase.td:165-192`) carrying
five things: the effect class (`::mlir::MemoryEffects::Read` and kin),
a `Resource` (a C++ class name plus an optional `code parameters`
expression, `:25-31`), an `int stage`, and a `bit effectOnFullRegion`
(`FullEffect`/`PartialEffect`, `:156-161`). `MemRead<R, stage, range>`,
`MemWrite`, `MemAlloc`, `MemFree` are its four instances
(`SideEffectInterfaces.td:53-88`). The same record is used two ways: in
an op-level `MemoryEffects<[...]>` trait (a static effect, no value) and
as a decorator on an operand, a result, or a `SymbolRefAttr` argument
(`Arg<T, "", [MemRead<R>]>`, `Res<T, "", [MemAlloc<R>]>`).

A2. *(read)* mlir-tblgen turns the declarations into one generated
`getEffects` per op (`tools/mlir-tblgen/OpDefinitionsGen.cpp:3499-3616`):
one `effects.emplace_back(Effect::get(), [value,] [params,] stage,
fullRegion, Resource::get())` line per declaration, with operand and
result decorators expanded over the ODS operand group
(`getODSOperandIndexAndLength`), the value attached as
`&getOperation()->getOpOperand(idx)` or `getOpResult(idx)`. Every
`Resource::get()` is a function-local static singleton
(`include/mlir/Interfaces/SideEffectInterfaces.h:100-104`). The cost at
query time is a small vector push per declared effect, no allocation in
the common case and no lookups.

A3. *(read)* Resources now form a hierarchy: `Resource::getParent()`,
`isSubresourceOf`, `isDisjointFrom`, and `isAddressable()` (a
non-addressable resource may carry no value: `EffectInstance` aborts
otherwise) (`SideEffectInterfaces.h:78-176, 336-345`). CSE reads it: a
write to a resource disjoint from a read's resource no longer blocks
CSE of the read (`lib/Transforms/Utils/CSE.cpp:222-228`), and local
alias analysis treats a non-addressable resource as never aliasing
memory (`lib/Analysis/AliasAnalysis/LocalAliasAnalysis.cpp:530`). The
hierarchy cannot be declared in ODS: `Resource<name, params>` names a
C++ class, and the parent is a `virtual getParent()` in that class.

A4. *(read)* Effects compose in ODS by trait, not by hand. Every
`MemoryEffects<[...]>` trait on an op, including those reached through
a `TraitList`, is collected into the one generated `getEffects`
(`OpDefinitionsGen.cpp:3523-3532`; `TraitList`s are flattened and
duplicates dropped by record identity, `lib/TableGen/Operator.cpp:767-813`).
So `def DoesIO : MemoryEffects<[MemWrite<IOResource>]>;` and
`def MayCrash : MemoryEffects<[MemWrite<CrashResource>]>;` can be listed
together on an op, or bundled once as a `TraitList`, and the generated
method holds both. `Pure` itself is such a bundle:
`TraitList<[AlwaysSpeculatable, NoMemoryEffect]>`
(`SideEffectInterfaces.td:147`).

A5. *(read)* It is all or nothing per op. If an op both declares effects
in ODS and lists `DeclareOpInterfaceMethods<MemoryEffectsOpInterface>`,
the generated and the declared `getEffects` collide and mlir-tblgen
stops with "Unexpected overlap when generating `getEffects`"
(`OpDefinitionsGen.cpp:1027-1050` runs `genOpInterfaceMethods` before
`genSideEffectInterfaceMethods`; `lib/TableGen/Class.cpp:408-420` prunes
the redundant method; `OpDefinitionsGen.cpp:1075-1084`). An op whose
effects depend on its attributes, its types or its regions writes the
whole method by hand; there is no "static part plus dynamic part".
`RecursiveMemoryEffects` is the one sanctioned dynamic form: an op with
it contributes its own declared effects (possibly none) plus those of
every nested op (`lib/Interfaces/SideEffectInterfaces.cpp:57-67, 345-375`).

A6. *(read)* What upstream reads of an effect, at the pin:
`wouldOpBeTriviallyDead` deletes an unused op whose every effect is a
`Read`, or an `Allocate` on one of its own results
(`SideEffectInterfaces.cpp:43-110`); a `Write` or `Free` on any resource,
or an `Allocate` with no value, keeps it. Terminators and symbols are
never trivially dead (`:312-318`). An op with neither the interface nor
`RecursiveMemoryEffects` has unknown effects (`:307-310`).
`isSpeculatable` reads only `ConditionallySpeculatable` (`:377-399`).
**No upstream transform reads an effect's `stage` or its
`effectOnFullRegion`**: outside `lib/TableGen`, the only readers are the
C API and the Python bindings (`lib/CAPI/Interfaces/Interfaces.cpp:371-381`,
`lib/Bindings/Python/IRInterfaces.cpp:189-197`). The rationale document
asks authors to set them anyway
(`docs/Rationale/SideEffectsAndSpeculation.md:98-110`). Nor does any
upstream pass read `parameters` (the attribute an effect instance may
carry). So the parts of an effect that upstream passes act on are: the
effect kind, the resource (its identity, its parents, whether it is
addressable), and the value or symbol it is on.

A7. *(read)* MLIR splits "may do something" into two declarations: memory
effects for what must be kept and ordered, `ConditionallySpeculatable`
for undefined behaviour and non-termination
(`docs/Rationale/SideEffectsAndSpeculation.md:27-76, 111-115`).
"Must not be deleted even if unused" (a syscall, a print) is a `Write`
to an abstract resource; "must not be hoisted past its guard" (division
by zero, a loop that may not end) is `NotSpeculatable` with no memory
effect, which leaves the op deletable when dead (that is how
`arith.divsi` is declared). Non-local exits have no model ("patches
welcome", `:116-117`).

A8. *(read)* The resource tree decides what may be reordered: two
resources conflict only if one is an ancestor of the other
(`isDisjointFrom`, `SideEffectInterfaces.h:149-153`), so **siblings are
disjoint**. Every resource that does not override `getParent` is a child
of `DefaultResource`, the root (`:178-195`). A `Resource` subclass's
`classof` is hierarchy-aware (`:109-115`): `isa<IOResource>(r)` holds for
every descendant of `IOResource`, which makes "does this op do IO" one
`isa` over the op's effect instances, at any depth of the tree.

A9. *(read)* Upstream's precedent for consumption as an effect is the
transform dialect. A handle consumed by an op gets `Read` and `Free` on
`TransformMappingResource` attached to its `OpOperand`, a produced
handle `Allocate` and `Write` on the result
(`lib/Dialect/Transform/Interfaces/TransformInterfaces.cpp:1793-1802`;
resources at `include/mlir/Dialect/Transform/Interfaces/TransformInterfaces.h:1276-1295`).
A trait supplies the whole `getEffects` for a family of ops:
`FunctionalStyleTransformOpTrait` (`TransformInterfaces.h:1324-1345`),
with a `verifyTrait` that requires the op to list the interface. A
use-after-consume check reads those effects (`transform-check-uses`,
`lib/Dialect/Transform/Transforms/CheckUses.cpp`), and a pass infers a
function's per-argument summary (consumed or read-only) from its body
and stores it on the function's arguments
(`lib/Dialect/Transform/Transforms/InferEffects.cpp:26-52`), which the
call op's hand `getEffects` reads by looking the callee up
(`lib/Dialect/Transform/IR/TransformOps.cpp:2050-2085`). That lookup,
`SymbolTable::lookupNearestSymbolFrom`, is a linear scan of the symbol
table's block (`lib/IR/SymbolTable.cpp:364-376`): fine for a transform
script, a wall at 70,000 functions if every query does it.

**B. Traits.**

B1. *(read)* ODS has four trait kinds (`include/mlir/IR/Traits.td:22-66`,
`OpBase.td:30-62`): `NativeOpTrait<"Name", dependentTraits,
extraOpDeclaration, extraOpDefinition>` names a C++ class template
`OpTrait::Name<ConcreteOp>` and may inject code into every op that lists
it; `ParamNativeOpTrait` names `Name<params>::Impl`; `PredOpTrait<descr,
pred>` is a predicate that mlir-tblgen inlines into the op's generated
`verifyInvariantsImpl`; `GenInternalOpTrait` changes only what the
generator emits (`SameVariadicOperandSize`, `AttrSizedOperandSegments`).
`TraitList<[...]>` is a named bundle, flattened at the use site.
`StructuralOpTrait` marks traits verified first.

B2. *(read)* A C++ trait is a CRTP class template; what it gives an op is
decided at compile time by detection, not by virtual calls
(`include/mlir/IR/OpDefinition.h:1577-1700`): a static `verifyTrait(Operation*)`
if present (detected by `detect_has_verify_trait`), a static
`verifyRegionTrait` (run after the regions are verified), a static
`foldTrait` (run by `Op::foldHook` after the op's own folder), and any
member functions, which become members of every op that lists the trait.
`Op<ConcreteOp, Traits...>::verifyInvariants` is the fold
`verifyTraits<Traits...>(op) && op.verify()`
(`OpDefinition.h:2114-2135`). A trait can therefore *supply* an
interface's method: the interface's model calls `op.method(...)` for a
method with neither `body` nor `defaultBody`, and a member the op
inherits from a trait answers it (upstream's
`AlwaysSpeculatableImplTrait` supplies `getSpeculatability` for
`ConditionallySpeculatable`, `SideEffectInterfaces.h:421-430`, bundled
as `AlwaysSpeculatable = TraitList<[ConditionallySpeculatable,
AlwaysSpeculatableImplTrait]>`, `SideEffectInterfaces.td:137-143`).

B3. *(read)* The order of verification is fixed by mlir-tblgen
(`OpDefinitionsGen.cpp:3997-4060`): the generated count traits
(`ZeroOperands`, `NResults<2>`, `OneTypedResult<T>`, ...), then every
`StructuralOpTrait` (`SingleBlock`, `NoTerminator`, `NoRegionArguments`),
then `OpInvariants` (the generated operand, result, attribute, property
and region constraints, `OpDefinition.h:433-443`), then
`BytecodeOpInterface::Trait` if the op has properties, then the native
and interface traits in declaration order, then the op's own `verify()`
(`hasVerifier`). Region traits and `verifyRegions()`
(`hasRegionVerifier`) run on the way out, after every nested op.
`dependentTraits` makes an order requirement a build error: a trait
listing another must come after it (`lib/TableGen/Operator.cpp:779-789`).

B4. *(read)* The cost of asking. `op->hasTrait<T>()` is a virtual call to
the op's `HasTraitFn`, a fold of `TypeID` comparisons over all of the
op's traits (`OpDefinition.h:1569-1571, 2016-2019`;
`OperationSupport.h:331-344`); on a typed op, `ConcreteOp::hasTrait<T>()`
is `constexpr` (`OpDefinition.h:1716-1718`). `isa<SomeOp>(op)` compares
one pointer. `dyn_cast<SomeInterface>(op)` is a binary search in the
op's sorted `InterfaceMap` (`include/mlir/Support/InterfaceSupport.h:206,
272-281`) and, *on a miss*, a virtual call to the dialect's
`getRegisteredInterfaceForOp` fallback (`OpDefinition.h:2164-2191`,
`include/mlir/IR/Dialect.h:180-183`). All three are cheap, but a negative
interface query is the dearest of them.

B5. *(read)* Builtin traits upstream already states as facts that passes
read: `Commutative` (its `foldTrait` moves constants to the right,
`OpDefinition.h:1165-1171`), `Idempotent`, `Involution` (folded by
their `foldTrait`s, which run after the op's own `fold`,
`OpDefinition.h:1944-2012`), `ConstantLike` (the folder's
constants), `IsolatedFromAbove` (the pass manager's and the verifier's
unit of parallelism), `Terminator`, `ReturnLike`, `Elementwise` and
`ElementwiseMappable`, `SameOperandsAndResultType`, `AllTypesMatch`,
`TypesMatchWith`, `HasParent`, `ParentOneOf`, `HasAncestor`,
`SingleBlockImplicitTerminator`, `AffineScope`,
`AutomaticAllocationScope`, `RecursiveMemoryEffects`
(`OpBase.td:65-200`). New since mid-2026: tokens. A builtin `token`
type that may not be forwarded through calls, branches or selects;
`AnyType` excludes it; ODS adds `TokenProducerTrait`/`TokenConsumerTrait`
itself to an op with a `Token` operand or result
(`OpDefinitionsGen.cpp:4050-4060`, `docs/Tokens.md`); the verifier
checks the contract (`lib/IR/Verifier.cpp:318`).

**C. Interfaces.**

C1. *(read)* An interface is declared in ODS (`include/mlir/IR/Interfaces.td`)
with methods (`InterfaceMethod<desc, ret, name, args, body, defaultBody>`),
static methods (`StaticInterfaceMethod`), base interfaces
(`baseInterfaces`, whose concepts the derived interface holds and
asserts registered, `tools/mlir-tblgen/OpInterfacesGen.cpp:284-310`),
an interface verifier (`verify`, with `verifyWithRegions` to run it after
the regions), `dependentTraits`, `extraClassDeclaration`,
`extraSharedClassDeclaration` (code shared by the interface and its
trait), and `extraClassOf` (an interface an op implements only when a
dynamic condition holds). mlir-tblgen generates a `Concept` struct of
function pointers, one per method, and `Model<ConcreteOp>` and
`FallbackModel` that fill it (`OpInterfacesGen.cpp:246-330`): no vtable,
one indirect call per method.

C2. *(read)* The three ways an op gets a method: (1) `body`, the same
source for every op, which the op cannot override; mlir-tblgen
instantiates it in `Model<ConcreteOp>` once per implementing op, unless
the body uses only `$_raw_op` (the `Operation *`), in which case one
`shared_` function serves all (`OpInterfacesGen.cpp:43-51, 271-281,
395-425`); (2) `defaultBody`, placed in the interface's trait and used
unless the op defines the method itself, reached by listing the
interface plain; (3) neither, so each op implements it, reached by
`DeclareOpInterfaceMethods<I, ["methodsToOverride"]>`, which makes
mlir-tblgen declare the methods in the op class
(`Interfaces.td:165-205`). A trait's member function can serve as the
implementation (B2). `PureVirtualInterfaceMethod` and
`InterfaceMethodDeclaration` exist for dialect interfaces only
(`Interfaces.td:88-96`, read only by `DialectInterfacesGen.cpp:111-143`).

C3. *(read)* External models attach an interface to an op, type or
attribute from outside its definition
(`StorageUniquerSupport.h:160-171`; `OpDefinition.h:1774-1782`,
`OperationSupport.h:405-412`, `attachInterface`),
through a dialect extension registered on the `DialectRegistry`; a
promised interface (`declarePromisedInterface`) makes a missing
attachment an error at the use (`OpDefinition.h:2167-2175`, debug builds).
At freeze time a pattern rooted on an interface is placed under every
registered op whose interface map holds it, external models included
(`lib/Rewrite/FrozenRewritePatternSet.cpp:129-140`).

**E. The rewrite drivers.**

E1. *(read)* Pattern roots decide what a pattern costs. A
`FrozenRewritePatternSet` files each native pattern once, at freeze
time (`lib/Rewrite/FrozenRewritePatternSet.cpp:104-142`): a pattern
rooted on an op name goes under that name; one rooted on an interface
(`OpInterfaceRewritePattern<I>`) or a trait (`OpTraitRewritePattern<T>`)
is copied under *every registered op that has it*, so it costs nothing
on any other op; only a `MatchAnyOpTypeTag` pattern goes into the
any-op list, which the applicator merges by benefit with the op's own
list on *every op it visits* (`lib/Rewrite/PatternApplicator.cpp:146-190`).
The 75 million attempts of `3a96c407` are what the any-op list does by
design: ops × any-op patterns × iterations.

E2. *(read)* The greedy driver (`lib/Transforms/Utils/GreedyPatternRewriteDriver.cpp`):
each iteration re-walks the whole region and re-adds every op
(`:868-883`), erases unreachable blocks, processes the worklist (per op:
erase if trivially dead, `op->fold`, then patterns, `:486-625`), then
simplifies regions (dead arguments, and block merging at the default
`Aggressive` level, `:903-909`). Defaults: bottom-up initial order,
`maxIterations = 10`, folding and constant CSE on, region
simplification `Aggressive`, strictness `AnyOp`
(`include/mlir/Transforms/GreedyPatternRewriteDriver.h:165-176`). Not
converging returns `failure()` (`:932`), which a caller must not turn
into a rejection (AGENTS.md's budget rule). A change re-queues the op
*and every ancestor up to the scope*, which is our carried patch 62's
quadratic case on an op of many regions (`upstream/62-greedy-multi-region-ancestors/README.md`).
New at the pin: `enableCSEBetweenIterations` (`:142-161`).

E3. *(read)* The walk driver, `walkAndApplyPatterns`
(`include/mlir/Transforms/WalkPatternRewriteDriver.h:22-35`,
`lib/Transforms/Utils/WalkPatternRewriteDriver.cpp`): one post-order
walk, highest-benefit pattern per op, no fixpoint, no folding, no DCE,
does not revisit changed or new ops, skips unreachable blocks; it may
erase only the matched op and its descendants (checked under
`MLIR_ENABLE_EXPENSIVE_PATTERN_API_CHECKS`). It terminates by
construction, which is AGENTS.md's shape for an optimization.

E4. *(read)* DRR and PDLL at the pin. DRR (`include/mlir/IR/PatternBase.td`,
`tools/mlir-tblgen/RewriterGen.cpp`) generates a native C++
`RewritePattern` rooted on the source op's name
(`RewriterGen.cpp:1127-1129`); upstream uses it in five files: arith's
canonicalizations (53 uses), FIR's (8), SPIR-V's (6), shape's (6) and
shape-to-standard (2). PDLL has **no production user** in the pinned
tree: every `.pdll` file is a test, plus
`include/mlir/Transforms/DialectConversion.pdll`, a helper for PDLL
users. Its "C++" output is not native code: `CPPGen` prints the PDL IR
into a string that `parseSourceString` parses when the pattern set is
built (`lib/Tools/PDLL/CodeGen/CPPGen.cpp:101-115`), and the frozen set
lowers it to `pdl_interp` and runs it on the PDL bytecode interpreter
(`FrozenRewritePatternSet.cpp:23-53, 144-170`).

**H. Verification.**

H1. *(read)* The verifier's order per op (`lib/IR/Verifier.cpp:272-410`):
context checks of operands, results and discardable attributes, each
discardable attribute's dialect `verifyOperationAttribute`, the op's
`verifyInvariants` (B3), the token contract, then each nested op (inline
for non-isolated ops), then on exit all `IsolatedFromAbove` children
**in parallel** (`parallelForEach`, `:357-371`), then
`verifyRegionInvariants`. Dominance is a second walk per isolated op
with its own `DominanceInfo` (`:88-104, 524-559`).

H2. *(read)* A type's or attribute's `verify` runs when the instance is
created (`get` asserts it in debug builds; `getChecked` returns null on
failure, `include/mlir/IR/StorageUniquerSupport.h:176-212`), once per
unique instance, never again: a fact checked in a type's verifier costs
nothing after creation, however many passes run.

H3. *(read)* After every pass the pass manager verifies the op the pass
ran on, recursively, unless the pass preserved all analyses
(`lib/Pass/Pass.cpp:621-642`). A module pass therefore re-verifies all
70,000 functions even if it touched three; a function pass verifies
only its function, on the pass's own thread.

H4. *(read)* Interfaces bring verifiers with them. Listing
`RegionBranchOpInterface` adds `verifyRegionBranchOpInterface` as a
region verifier (`include/mlir/Interfaces/ControlFlowInterfaces.td:358-363`),
which visits every branch point and every successor of each
(`lib/Interfaces/ControlFlowInterfaces.cpp:160-219`): linear in a
match's cases if the op's `getSuccessorRegions` is, and run on every
verify. *(conjecture)* At 70,000 functions the verifier's cost is
linear in ops, parallel over isolated functions, and dominated by
whatever custom `verify` and region verifiers do; the pass manager
counts it inside each pass's time, so wave 2 measures it as the
difference between a run with `--verify-each=0`
(`lib/Tools/mlir-opt/MlirOptMain.cpp:190-193`) and one without.

H5. *(read)* Where a check lives decides its complexity. A symbol
reference checked in an op's `verify()` with `lookupNearestSymbolFrom`
is a linear scan per op (A9), so calls × functions per verify. The
same check in `SymbolUserOpInterface::verifySymbolUses` is run once per
symbol table by the `SymbolTable` trait's region verifier, with one
shared `SymbolTableCollection` (hashed, built once)
(`lib/IR/SymbolTable.cpp:465-499`): linear in calls.

**D. Types, attributes, properties, enums.**

D1. *(read)* A type or attribute definition (`include/mlir/IR/AttrTypeBase.td:159-330`)
declares its parameters (`TypeParameter`, `AttrParameter`,
`ArrayRefParameter`, `OptionalParameter`, `DefaultValuedParameter`,
`StringRefParameter`, `EnumParameter<EnumInfo>` (`EnumAttr.td:503`),
`SelfAllocationParameter`), builders, a declarative `assemblyFormat`
(`params`, `struct(params)`, `custom<...>`), traits (`NativeTypeTrait`,
`PredTypeTrait`, `MutableType`), interfaces
(`DeclareTypeInterfaceMethods`), `genVerifyDecl` (a static
`verify(emitError, params...)`), and `genMnemonicAlias` (a default
`getAlias` for the printer, `:253-254`). mlir-tblgen generates the
storage class (key, hash, equality, allocation), the accessors, the
`get`/`getChecked` builders, the parser and printer; the hand-written
part is the verifier body and any custom directive. The verifier runs
once per unique instance (H2).

D2. *(read)* Mutable types: `MutableType`
(`AttrTypeBase.td:60`) and a storage `mutate`. A mutation takes the
writer lock of one shard of the uniquer, chosen by hashing the storage
pointer (`lib/Support/StorageUniquer.cpp:195-206`); reads of the mutable
part take no lock, so a body must be complete before threads read it.
Two more costs: the bytecode writer always writes a mutable type or
attribute as **text**, even when the dialect has a bytecode interface
("We don't currently support custom encoded mutable types and
attributes", `lib/Bytecode/Writer/BytecodeWriter.cpp:893-900`); and
mutating a base instance is unsupported inside the context's new
transient scope (`include/mlir/IR/MLIRContext.h:149-170`).

D3. *(read)* Properties are an op's inline, mutable, non-uniqued storage
(`include/mlir/IR/Properties.td:29-200`): a C++ `storageType` per
property with conversions to and from an attribute (for the generic
form and for ops read unregistered), a parser, a printer, a hash, and
bytecode read and write (`BytecodeOpInterface`, which mlir-tblgen adds
to every op with properties, `OpDefinitionsGen.cpp:4041-4042`).
Combinators: `IntProp`, `BoolProp`, `UnitProp`, `StringProp`,
`ArrayProp`, `OptionalProp`, `DefaultValuedProp`, `ConfinedProp` (a
predicate checked by the generated verifier), `EnumProp`
(`EnumAttr.td:599`). At the pin, inherent attributes are always held in
properties: the `usePropertiesForAttributes` switch is gone from
`DialectBase.td`, so an op's declared attribute is a field read, not a
dictionary search. A property is never a context lock and never
uniqued; mutating one in place is legal.

D4. *(read)* Enums (`include/mlir/IR/EnumAttr.td`): `I32Enum`/`I64Enum`
with `EnumCase`s, `BitEnum` with bits, groups and a none case; from one
`EnumInfo` mlir-tblgen generates the C++ `enum class`, `stringify`,
`symbolize`, `getMaxEnumValFor`, the bit operators and the field
parser (`tools/mlir-tblgen/EnumsGen.cpp`), and the same record can be
an attribute (`EnumAttr<Dialect, EnumInfo, "mnemonic">`), a property
(`EnumProp`), or a type parameter (`EnumParameter`). The Python
generator reads the same record (`EnumPythonBindingGen.cpp`).

D5. *(read)* Type constraints and the facts they generate
(`include/mlir/IR/CommonTypeConstraints.td`, `Constraints.td`): a
constraint is a predicate plus a summary and a C++ type; mlir-tblgen
emits each distinct constraint once per file as a static function
(`__mlir_ods_local_type_constraint_*`, `include/mlir/TableGen/CodeGenHelpers.h:85-110`;
memref's generated file has 95 references) and calls it from the
op's `verifyInvariantsImpl`. Relational traits (`AllTypesMatch`,
`TypesMatchWith`, `SameOperandsAndResultType`, `FirstAttrDerivedResultType`)
also let mlir-tblgen infer result types and generate the
`InferTypeOpInterface` and builders that take no result type
(`OpDefinitionsGen.cpp:3618-3640`, `genTypeInterfaceMethods`).

**E (cont.). Canonicalization and conversion.**

E5. *(read)* An op's canonicalization is declared three ways: `hasFolder`
(a `fold` the greedy driver calls before patterns, with `ConstantLike`
results materialized through the dialect's `hasConstantMaterializer`
hook, `GreedyPatternRewriteDriver.cpp:497-560`); `hasCanonicalizeMethod`
(a static `canonicalize(Op, PatternRewriter&)`, which mlir-tblgen wraps
into an op-rooted pattern, `OpDefinitionsGen.cpp:3383-3418`,
`include/mlir/IR/PatternMatch.h:913-930`); `hasCanonicalizer` (the op
fills `getCanonicalizationPatterns` itself). All three are rooted.

E6. *(read)* Dialect conversion has a one-shot mode,
`ConversionConfig::allowPatternRollback = false`, which keeps no
rollback state and makes a pattern that fails after modifying IR a
fatal error (`include/mlir/Transforms/DialectConversion.h:1444-1463`;
marked experimental at the pin).

**F. Custom TableGen backends.**

F1. *(read)* A backend is a function `bool(const RecordKeeper&,
raw_ostream&)` registered with a `GenRegistration` and run by
`MlirTblgenMain` (`tools/mlir-tblgen/mlir-tblgen.cpp`,
`lib/Tools/mlir-tblgen/MlirTblgenMain.cpp`). Upstream has a second tool
built exactly this way, `tblgen-to-irdl` (`tools/tblgen-to-irdl/`, a
28-line main and a 583-line backend), which reads every `Op`, `TypeDef`
and `AttrDef` through the `mlir::tblgen` wrappers and emits another
view of the dialect (IRDL). That is the shape of `idris-mlir-tblgen`.

F2. *(read)* The wrappers (`include/mlir/TableGen/`: `Operator`,
`Argument`, `Attribute`, `Property`, `AttrOrTypeDef`, `Interfaces`,
`SideEffects`, `Trait`, `EnumInfo`, `Pattern`, `Pass`, `Constraint`,
`Predicate`, `Format`) compute the derived facts once: flattened and
deduplicated traits with `dependentTraits` checked
(`lib/TableGen/Operator.cpp:767-813`), operand and result decorators
(the effects on each operand), variadic segments, inferred result
types, interface methods. A backend that reads raw `Record` fields
recomputes those facts and drifts from what the C++ sees. The Python
generator (`tools/mlir-tblgen/OpPythonBindingGen.cpp`, 1,532 lines, with
`-bind-dialect` to select one dialect, `:428`) is the closest upstream
model of a foreign-language view of a dialect generated from ODS: one
class per op, accessors per operand group with segment handling,
builders, enums from the same records.

F3. *(read)* Generated op families. `llvm`'s intrinsic ops are ODS
records generated from LLVM's own intrinsic records
(`-gen-llvmir-intrinsics`, `LLVMIRIntrinsicGen.cpp:279`), and each
LLVM op carries its translation as a record field (`llvmBuilder`,
`mlirBuilder`, `include/mlir/Dialect/LLVMIR/LLVMOpBase.td:149-190`)
from which `-gen-llvmir-conversions` emits the translation
(`LLVMIRConversionGen.cpp:181-187, 567-592`). The generated code is a
linear chain of `if (auto op = dyn_cast<X>(opInst))`
(`.toolchain/build/tblgen/tools/mlir/include/mlir/Dialect/LLVMIR/LLVMConversions.inc:1-30`):
a ladder, but one generated from the single source. Linalg's named ops
are generated from OpDSL YAML (`tools/mlir-linalg-ods-gen`) and
classified by `LinalgStructuredInterface`. Arith's families are
TableGen classes that bundle traits and interfaces
(`Arith_TotalIntBinaryOp`, `Arith_IntBinaryOpWithOverflowFlags`,
`include/mlir/Dialect/Arith/IR/ArithOps.td:33-210`); `arith.divsi` is
`NoMemoryEffect` plus `ConditionallySpeculatable` (`:642-643`).

**G. Bytecode and printer aids.**

G1. *(read)* Ops: properties are written natively through the generated
`BytecodeOpInterface`. Attributes and types: through the dialect's
`BytecodeDialectInterface`, which `-gen-bytecode` generates from
`BytecodeBase.td` records (used by builtin, quant, LLVM and tosa); an
attribute or type with no encoding, and every mutable one, is written
as its text and parsed back by the text parser
(`BytecodeWriter.cpp:884-930`). Our carried patches 03 and 25 are in
this reader (nested attributes; properties of an op written
unregistered).

G2. *(read)* Printer aids: `OpAsmOpInterface` (`getAsmResultNames`,
`getAsmBlockArgumentNames`, `getAsmBlockNames`, `getDefaultDialect`),
and per type and attribute `OpAsmTypeInterface`/`OpAsmAttrInterface`
(`getAsmName`, `getAlias`), which `genMnemonicAlias` fills
(`include/mlir/IR/OpAsmInterface.td:24-160`). Readable IR is declared,
not printed by hand.

#### 5.2.2 What it means for idris-mlir

*Conjecture until wave 2 reads our code; each line maps findings onto
§2.*

M1. **One effects model is reachable with what ODS has** (A1-A6, A8).
§2 lists 72 effect declarations beside 139 C++ occurrences of
`getEffects`/`MemoryEffects` and three representations of "does IO"
(the `PerformsIO` trait, `IOResource` effects, a body effect read off
world operands). In ODS terms: one named bundle per kind of effect
(`def Idr_DoesIO : MemoryEffects<[MemWrite<Idr_IOResource>]>`), operand
effects as reusable `Arg`/`Res` classes, "does IO" asked as
`isa<IOResource>` over the op's effect instances (hierarchy-aware, A8),
and the marker trait deleted. The world-operand rule is a fact about
operand *types*, so it is one trait supplying `getEffects` for every op
it applies to (row 3 below, A9's precedent), never a per-op hand method,
and never mixed with ODS effects on the same op (A5).

M2. **Divergence, Crash and Lin are three different MLIR facts**
(A6, A7, A9). Upstream would model "may not terminate" and "may trap"
as speculation (`ConditionallySpeculatable`), which leaves a dead op
deletable, and keep a memory effect only for what must survive when
unused. Our `Divergence` and `Crash` resources keep dead ops alive.
Which is right is a question of Idris's meaning, not of mechanism (Q1
below). `Lin` and consumption match the transform dialect's model
exactly: `Read` and `Free` on the consumed `OpOperand` (A9), which makes
a consuming op never trivially dead (A6), as a `drop` must not be, and
leaves a borrow (`Read` only) deletable. AGENTS.md keeps quantity 1 in
the type; the effect is then derived from the type by one trait, which
is one fact read in one place, not two copies.

M3. **Ordering is a property of the resource tree** (A8). If a crash must
stay ordered with IO and with heap writes, `Crash` cannot be a sibling
of `IO` or `Reference`: siblings are disjoint and CSE already moves
reads across disjoint writes (A3). The tree is a design decision for
§5.8; the mechanism is one C++ header of `Resource` classes.

M4. **Traits that state a checkable fact get a `verifyTrait`** (B2, B3):
§2's `SameValue`. A marker trait no pass reads (`TakesReference`,
`BuildsValue`, `ObservableIO`, §2) is a fact with no reader: it becomes
a pattern root or an interface's classification, or it goes.

M5. **The ladders map onto upstream traits and interfaces** (B4, B5,
C1-C3): four copies of `isa<ReturnOp, YieldOp>` are
`hasTrait<OpTrait::ReturnLike>()` or `RegionBranchTerminatorOpInterface`;
`IR/Canon/Sink.cpp:114` and `StructureLoops/Forms.cpp:132` (§2) become
interface queries. A typed op's `hasTrait` is `constexpr`.

M6. **The 75 million attempts were a root choice** (E1). Every
`MatchAnyOpTypeTag` pattern becomes op-, interface- or trait-rooted; its
cost then scales with the ops that have the root. `idr-optimize`'s
"each function once, bottom-up" is a fixed order over the call graph
(the pass's, §5.1); within one function, a one-shot rewrite is the walk
driver's contract (E3: one post-order walk, no fixpoint, terminates by
construction), not the greedy driver's fixpoint (E2), whose region
simplification and ancestor re-queueing (our patch 62) are what costs
on a match of tens of thousands of cases.

M7. **`Idr_Runtime<"symbol">` is row 12** (B2, C2, F3): a trait class
whose `extraOpDeclaration` injects `static constexpr
::llvm::StringLiteral getRuntimeSymbol()`, an interface
`RuntimeFunction` whose `StaticInterfaceMethod` reads it, one
interface-rooted lowering pattern, and `idris-mlir-tblgen` reading the
same record. Upstream's `llvmBuilder` field (F3) is the same idea with
a generated `dyn_cast` chain where we would use an interface.

M8. **Op families come from lists** (F3): the ~60 platform ops, the
per-signedness word ops and the conversions are TableGen classes
instantiated from one list, each instance carrying its runtime symbol,
its effect bundle and its types. Whether a family stays many ops or
becomes one op with an enum is §5.8's call; ODS generates either.

M9. **Grades: parameters checked once, uses checked per pass**
(D1, D4, H2). `!idr.q<quantity, permission, T, lifetime>` with quantity
and permission as `EnumParameter`s of one `EnumInfo` each, its
well-formedness in `genVerifyDecl` (once per unique type), `!idr.lin<T>`
and kin as builders and printer aliases. What AGENTS.md requires after
every pass is then the part that can change: how values of those types
are used. Those are op- and region-local checks (a linear value used
once, a grade kept across an op), so traits' `verifyTrait` and
`verifyRegionTrait`, which run in parallel per function (H1).

M10. **The `data` table and its walls** (D2, D3; §3 rows 98c6315c,
73bba53f). Upstream reads a mutable type's body without a lock; only
`mutate` and the uniquer's `get` lock. So the context lock of 98c6315c
came from a uniquing or mutating call on a read path (wave 2 checks).
A table kept in an immutable, uniqued attribute is rebuilt and re-hashed
on every change: 73bba53f's quadratic cost is the representation's.
Mutable types are also written as text in bytecode and cannot be
mutated in a transient scope (D2). Properties (D3) are the one place in
an op where a large structure may be mutated in place without the
context.

M11. **Verifying after every pass at 70,000 functions** (H1-H5): linear,
parallel per function, and paid in full by every *module* pass, even
one that changed three functions. The levers are mechanisms, not flags:
passes nested on the function so each verifies its own function on its
own thread; `markAllAnalysesPreserved()` when a pass changed nothing
(the verifier is then skipped); symbol checks in `verifySymbolUses`, not
`verify()`; grades in type verifiers where they cannot change.

M12. **`idris-mlir-tblgen` should read the wrappers** (F1, F2): one
`GenRegistration` per Idris view, in a tool on `MlirTblgenMain`
(`tblgen-to-irdl`'s shape), reading `tblgen::Operator`, `SideEffect`,
`Trait`, `EnumInfo`, `AttrOrTypeDef`, so the Idris side sees the same
flattened traits, the same per-operand effects and the same enums as
the C++.

M13. **DRR yes, PDLL no** (E4): DRR is native and rooted, and upstream
uses it for arith's canonicalizations; PDLL is interpreted, has no
production user at the pin, and parses its patterns from strings when a
pattern set is built.

M14. **Bytecode** (G1, D2): if a stage writes bytecode (the 71 MB stage-1
module), our types and attributes go in as text unless `-gen-bytecode`
encodes them, and every mutable one does regardless.

```tablegen
// Rows 1, 6: resources are C++ classes in one header; ODS names them.
def Idr_IOResource   : Resource<"::idr::IOResource">;
def Idr_HeapResource : Resource<"::idr::HeapResource">;
def Idr_DoesIO : MemoryEffects<[MemRead<Idr_IOResource>,
                                MemWrite<Idr_IOResource>]>;

// Row 2: operand roles as reusable decorators (the transform
// dialect's model of consumption, A9).
class Idr_Consumed<TypeConstraint t>
    : Arg<t, "consumed", [MemRead<Idr_HeapResource>,
                          MemFree<Idr_HeapResource>]>;
class Idr_Borrowed<TypeConstraint t>
    : Arg<t, "borrowed", [MemRead<Idr_HeapResource>]>;

// Row 3: effects that follow from operand types, for a whole family.
// The C++ trait has `void getEffects(...)`; listing the interface plain
// makes its model call the trait's member (as NVGPU's transform ops do
// with FunctionalStyleTransformOpTrait). No ODS effect on these ops.
def Idr_WorldEffects : TraitList<[MemoryEffectsOpInterface,
                                  NativeOpTrait<"WorldEffects">]>;

// Row 12: the runtime function that is a primitive's one meaning.
def Idr_RuntimeFunction : OpInterface<"RuntimeFunction"> {
  let cppNamespace = "::idr";
  let methods = [StaticInterfaceMethod<"the runtime's symbol",
                   "::llvm::StringLiteral", "getRuntimeSymbol">];
}
class Idr_RuntimeSymbol<string sym>
    : NativeOpTrait<"RuntimeSymbol", [], [{
        static constexpr ::llvm::StringLiteral getRuntimeSymbol() {
          return "}] # sym # [{"; }
      }]> { let cppNamespace = "::idr::OpTrait"; }
class Idr_Runtime<string sym>
    : TraitList<[Idr_RuntimeFunction, Idr_RuntimeSymbol<sym>]>;

// Row 23: a family instantiated from one list; each member carries its
// symbol and its effect bundle, and idris-mlir-tblgen reads the same
// records.
class Idr_PlatformOp<string mnemonic, string sym>
    : Idr_Op<mnemonic, [Idr_DoesIO, Idr_Runtime<sym>]>;
```

The one lowering of every primitive to its runtime call is then a
single `OpInterfaceRewritePattern<RuntimeFunction>`, filed at freeze
under exactly the ops that have the interface (E1), and the Idris side
reads `getRuntimeSymbol`'s source, the trait's argument, from the same
record (F2).

**Designs, ranked.**

1. **ODS as the dialect's one source** (rows 1-17, 23, 24). Every fact
   the table lists moves into ODS in the same change; C++ keeps only
   what the paragraph above names. *Buys*: the hand `getEffects` and
   `verify` bodies, the marker traits without readers, and the op
   ladders go (§2's counts are the inventory wave 2 checks). *Costs*:
   build time of generated code (an interface `body` using `$_op` is
   instantiated per op; `$_raw_op` avoids it); no run-time cost beyond
   what the hand code paid. *Deletes*: hand effects and verifiers, the
   `PerformsIO` representation and the world-operand body effect as
   separate facts (M1).
2. **Rooted rewriting** (rows 17, 18). No `MatchAnyOpTypeTag` anywhere;
   one-shot rewrites (inline and specialize bottom-up, lowering to
   runtime calls) on the walk driver; the greedy driver only for
   canonicalization, its non-convergence never an error, its region
   simplification level chosen per use. *Buys*: §3's 75-million-attempt
   class cannot recur; cost scales with the ops a pattern is for.
   *Costs*: patterns written per root; patch 62 stays until upstream
   takes it. *Deletes*: any-op patterns and their internal `isa` filters.
3. **Facts in types, uses in traits, symbols in `verifySymbolUses`**
   (rows 7-10, 15; H1-H5). *Buys*: per-pass verification that is
   local, parallel per function and linear; grades checked once per
   type. *Costs*: the pipeline nested on functions where a pass allows
   it (§5.1 and wave 2 judge which). *Deletes*: whole-module verifier
   walks of ours, symbol lookups in `verify()`.
4. **`idris-mlir-tblgen` on the wrappers, op families from lists** (rows
   12, 22, 23). *Buys*: the Idris side and the C++ read one derived
   view; adding an OS call is one list entry. *Costs*: rewriting the
   backend against `mlir::tblgen`. *Deletes*: the backend's own reading
   of raw records, hand-written family members.
5. **DRR for peepholes, no PDLL** (row 18). *Buys*: declarative,
   native, rooted rewrites for scalar, big-integer and string
   simplifications. *Costs*: DRR cannot express everything; the rest
   are C++ rooted patterns. *Rejected*: PDLL, for E4's reasons.
6. **Bytecode encodings generated** (row 21), if wave 2 finds bytecode
   on a hot path; with it, no mutable type or attribute on that path
   (D2).

*Rejected:* mixing ODS effects and a hand `getEffects` on one op
(mlir-tblgen refuses it, A5); a generated `dyn_cast` chain for lowering
(F3: acceptable upstream because generated, but an interface-rooted
pattern does the same in one rooted pattern); keeping `stage` and
full-region effects as if a pass read them (A6; Q5).

#### 5.2.4 Questions for the owner, and for wave 2

*For the owner.*
- **Q1. Divergence and crash: kept or deletable when dead?** MLIR's
  model makes "may not end" and "may trap" speculation facts, so a dead
  op may be deleted (A7); a `Write` on a resource keeps it (A6). Our
  `Divergence` and `Crash` resources keep it. Which does Idris's meaning
  want for an unused `check.may_loop` or crash, given AGENTS.md's "in
  program order with every other effect"?
- **Q2. Effects that follow from types.** One trait computing effects
  from operand types (world, grade) for a whole family (row 3), or ops
  split until every effect is static in ODS? The first keeps one op per
  semantics where the type already decides; the second makes the
  dynamic case unrepresentable but multiplies ops (the limit of the
  representation-first skill).
- **Q3. The resource tree.** Must a crash stay ordered with IO and with
  heap writes? If so `Crash` is an ancestor of both, never a sibling
  (A8, M3).
- **Q4. DRR allowed, PDLL refused** (E4, M13)?
- **Q5. Effect stages and full-region effects.** No upstream pass reads
  them (A6). Declare them anyway as documentation that ODS keeps, or
  only where a pass of ours reads them?
- **Q6. Verification after every pass.** Accept that a module pass
  re-verifies all 70,000 functions, or make nesting on functions a rule
  of the pipeline's design so verification is per function and
  parallel (H3, M11)?

*For wave 2 (the ods, cpp-ir and cpp-transforms lanes).*
- W1. Every hand `getEffects` and every `MemoryEffects` use in C++: is
  the effect static (rows 1-2), type-dependent (row 3) or recursive

- W2. Every `MatchAnyOpTypeTag` pattern, with the set of ops it actually
  matches: the interface or trait it should be rooted on.
- W3. Every `verify()` and `verifyRegions()`: which checks a trait or
  constraint expresses; any symbol lookup inside `verify()` (H5); any
  whole-module walk of ours run per pass.
- W4. Each of the 275 `isa<` over ops: which trait or interface it
  restates (M5).
- W5. `idris-mlir-tblgen`: does it read raw `Record` fields or the
  `mlir::tblgen` wrappers; what does it recompute (F2)?
- W6. The `data` type: what call took the context's lock in 98c6315c (a
  `get` per read, or a `mutate`), and is the body complete before
  threads read it (D2, M10)?
- W7. Measure the verifier on the stage-1 module: the pipeline with
  and without verification after each pass, and the count of module

- W8. Does any stage write or read bytecode; are our attributes and

- W9. Do passes that change nothing mark all analyses preserved (H3)?
- W10. Which interface method `body`s use `$_op` (one instantiation per

#### 5.2.5 Notes for other lanes

- **dialect-design (§5.8).** The resource tree is design: siblings are
  disjoint (A8, M3). Divergence and traps as speculation or as effects
  (A7, Q1). The builtin `token` (B5) is a non-forwardable reference to
  an op, not a world token: it cannot cross calls, branches, region
  results or `IsolatedFromAbove`, so it is no model for `!idr.world`.
  Mutable types cost a text encoding in bytecode and cannot be mutated
  in a transient scope (D2); a growing table in an immutable attribute
  is quadratic by construction (M10); properties are the mutable place
  in an op (D3). The transform dialect's consumption as `Read` plus
  `Free` on an operand (A9) is upstream's model of a linear value.
  `EnumParameter` fits the grade's quantity and permission (D1). Op
  families vs one op with an enum: ODS generates either (F3, M8).
  `DependsOnParent` (patch 56) for an op whose value depends on its
  parent op.
- **mlir-analysis (§5.1).** No upstream pass reads an effect's `stage`,
  full-region bit or parameters (A6); CSE and local alias analysis read
  resource disjointness and addressability (A3). `RegionBranchOpInterface`
  brings a region verifier that runs on every verify (H4).
  `lookupNearestSymbolFrom` is a linear scan; `verifySymbolUses` gets a
  shared `SymbolTableCollection` (A9, H5). The verifier is parallel only
  over `IsolatedFromAbove` ops (H1). Interface-rooted patterns are
  expanded per op at freeze (E1).
- **cxx26 (§5.5).** MLIR's traits are CRTP plus the detection idiom
  (`llvm::is_detected`, `include/mlir/IR/OpDefinition.h:1577-1700`); an
  op class may hold no data (`hasNoDataMembers`, `:2137-2142`); an
  interface's `Concept` is a struct of function pointers, and its
  `body` is instantiated per op unless written over `$_raw_op` (C1, C2).
  These are the seams where concepts could tighten our own traits'
  C++.
- **llvm (§5.3).** Op families from lists need TableGen's `foreach`,
  `defset` and multiclasses (F3, M8); `SearchableTables` is the
  alternative to row 12 if a runtime-symbol table is wanted outside ops.
- **oom (§5.11).** `MLIRContext::beginTransientScope` frees every type
  and attribute created inside the scope (`include/mlir/IR/MLIRContext.h:149-186`):
  a per-pass bound on the context's growth, with D2's restriction.
- **modular (§5.4).** Worth checking whether Mojo's dialects use DRR,
  PDLL, effect resources and interface-rooted patterns, as a second
  data point for E4 and row 3.
