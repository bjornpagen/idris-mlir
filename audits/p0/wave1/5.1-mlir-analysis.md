# 5.1 mlir-analysis: upstream's analyses, effects and threading

For each mechanism: what it gives, its cost model at §3's scale (bytes
and work per value, op, block, region, function), what a patch would
change, and the evidence (upstream code, tests, commits, RFCs).
- `DataFlowSolver`: `LatticeAnchor`, `ProgramPoint` and their uniquing;
  how `AnalysisState`s are stored and found; the worklist; what a value
  and a program point cost; `DataFlowConfig` and interprocedural mode;
  whether a solve can be scoped (a function, a call-graph SCC) and its
  states freed; what upstream is changing (the pinned tree's history of
  `mlir/lib/Analysis/DataFlow`, RFCs). Why `DeadCodeAnalysis` and
  `SparseConstantPropagation` must load beside other analyses.
- Sparse and dense analyses, forward and backward; `IntegerRangeAnalysis`,
  `LivenessAnalysis`, and `remove-dead-values`' design and scaling. The
  carried patches' reports (`upstream/01`, `05`, `06`, `16`, `22`, `28`,
  `29`, `63`) may be read: they document upstream's behaviour.
- The control-flow interfaces' query costs (`RegionBranchOpInterface`,
  `RegionBranchTerminatorOpInterface`, `BranchOpInterface`,
  `RegionBranchPoint`, successor operands) on an op with tens of
  thousands of regions, and how upstream clients query them at scale.
- Side effects: `MemoryEffectOpInterface`, resources, effects on values,
  results and symbols, effect stages and full-region effects,
  `RecursiveMemoryEffects`, speculation (`ConditionallySpeculatable`),
  `isPure`, `wouldOpBeTriviallyDead`; which upstream passes read which
  (CSE, canonicalization's DCE, LICM, control-flow sink, topological
  sort, mem2reg and SROA, bufferization, inliner).
- The call graph (`CallGraph`, `CallOpInterface`, `CallableOpInterface`,
  SCC iteration), `SymbolTableCollection`, `SymbolUserMap`: their costs
  at 70,000 functions.
- `AnalysisManager`: caching, preservation, nesting, use from parallel
  passes. The pass manager's threading and the `MLIRContext`'s:
  uniquing locks, mutable types, what may be read concurrently.
- Also: `Liveness` (the non-dataflow one), dominance, slice analysis,
  local alias analysis, the action framework and debug counters, and
  bufferization's ownership-based deallocation as a design to learn from.

*Wave 1 written (2026-10-21). Pinned tree: `.toolchain/llvm-project` at
7208ba24; paths below are relative to its `mlir/` unless they say

**In short.** `DataFlowSolver` ran out of memory on our module because
of two container choices, not its algorithm: every value with a state
pays two minimum-size (64-bucket) hash tables, about 2.9 KB for one bit
of liveness (A4, measured). A two-line upstream patch cuts that about
fifteenfold. With it, upstream's sparse analyses can come back, solved
per function in parallel. The facts that cross calls then come from
one summary layer of ours. What stays ours, in one solver layer, is the
problems whose state is per program point and set-valued, and the
summaries over the call graph's SCCs (5.1.3). Large matches need their
control-flow interface queried once per op, not once per region (C).

#### 5.1.1 Findings

**A. `DataFlowSolver`: the state model.**

A1. *(read)* One solver holds four structures
(`include/mlir/Analysis/DataFlowFramework.h:464-488`): the worklist, a
FIFO `std::queue<WorkItem>` with a `DenseSet<WorkItem> pending` beside
it (a work item is a `(ProgramPoint *, DataFlowAnalysis *)` pair); a
`StorageUniquer` that owns every `ProgramPoint` and custom anchor;
`DenseMap<LatticeAnchor, DenseMap<TypeID, std::unique_ptr<AnalysisState>>>
analysisStates`, so every state is its own heap object behind a
two-level hash map, the inner map allocated per anchor; and
`equivalentAnchorMap`, one `EquivalenceClasses<LatticeAnchor>` per state
type. There is no per-scope arena, no way to drop the states of one
region or function short of `eraseState(anchor)` one anchor at a time
(which also updates every state type's equivalence classes,
`:570-593`), and no way to free the uniqued program points at all (the
uniquer lives as long as the solver).

A2. *(read)* Every `AnalysisState` carries a `LatticeAnchor` and a
`SetVector<WorkItem> dependents` (`:541-559`), so a state's footprint is
its lattice plus a `SmallVector` and a `DenseSet` of dependents, both
allocated on first use; `onUpdate` re-enqueues every dependent
(`:536-539`). The solver's own header still says
"TODO: Optimize the internal implementation of the solver" (`:324`).

A3. *(read)* `DataFlowConfig` has exactly one knob,
`interprocedural` (`:283-301`), and `initializeAndRun` silently turns it
off unless the top op is a `SymbolTable` (`lib/Analysis/DataFlowFramework.cpp:119-123`).
There is no knob for scope, for freeing, or for a budget.

A4. *(read, then measured)* **What a state costs, and why.** LLVM's
`DenseMap` never allocates fewer than 64 buckets once it holds anything
(`llvm/include/llvm/ADT/DenseMap.h:272-274`, `roundUpNumBuckets`:
`std::max(64u, MinNumBuckets)`), and `SetVector`'s default `N = 0`
(`llvm/include/llvm/ADT/SetVector.h:55-57, 328`) has no small mode, so
its `DenseSet` is a 64-bucket table from the first insert. The solver
puts one such inner map behind every anchor (`DataFlowFramework.h:481`)
and one such set inside every state that has a dependent (`:559`). So
the fixed cost of "this value has a state" is two 64-bucket hash tables
of 16-byte buckets (about 1 KiB each, before the allocator rounds),
whatever the lattice holds. `sizeof` at the pin (arm64, built from the
pinned headers; first number with `LLVM_ENABLE_ABI_BREAKING_CHECKS=0`,
second with it on, as an assertions build has it):

| type | bytes |
| --- | ---: |
| `ProgramPoint` (uniqued) | 24 / 24 |
| `AnalysisState` (base) | 56 / 80 |
| `AbstractSparseLattice` (adds `useDefSubscribers`) | 160 / 192 |
| `dataflow::Liveness` (one `bool` of payload) | 168 / 200 |
| `Lattice<ConstantValue>` | 184 / 216 |
| `IntegerValueRangeLattice` | 240 / 272 |
| `Executable` (one `bool`, a subscriber set) | 168 / 200 |
| `PredecessorState` | 192 / 232 |
| `Operation` / `Block` / `OpOperand`, for scale | 64 / 80 / 32 |

  Heap per anchor, *measured* on arm64 macOS (libmalloc) with the
  solver's exact container types instantiated from the pinned headers
  over one million synthetic `Value` anchors (harness in
  `/tmp/mlir-sizeof/mem.cpp`, not kept; numbers reproducible from the
  description):

| layout | 0 dependents | 1 dependent | 3 dependents |
| --- | ---: | ---: | ---: |
| pin: a 1-bit state (`AnalysisState` + `bool`) | 1,460 B | 2,756 B | 2,788 B |
| pin: a sparse lattice (Liveness's shape, one subscriber) | 1,588 B | 2,884 B | 2,916 B |
| patch P1: inner map `SmallDenseMap<TypeID, …, 2>`, dependents `SetVector<…, 4>` | 182 B | 198 B | 230 B |
| patch P2: one flat `DenseMap<(anchor, TypeID), State *>`, states in a `SpecificBumpPtrAllocator` | 148 B | 164 B | 196 B |
| our own: one bit in a `BitVector` indexed by value number | 0.13 B | | |

  So at the pin one bit of liveness costs about 2.9 KB, of which more
  than 90 percent is the two minimum-size hash tables; P1, a two-line
  change of container types in `DataFlowFramework.h`, cuts it about
  fifteenfold. That is the "state model" of §3 in numbers. *(measured;
  glibc's allocator rounds differently, so the Linux figures will
  differ by tens of percent, not by the factor.)*

A5. *(read)* **The worklist and the uniquer.** Work items are
deduplicated since #221983 (fe72b96, 2026-09-14), which turned a
`scf.index_switch` of 50 cases from 5,100 region-branch visits into 150
(the PR's own numbers); the pin has it (`DataFlowFramework.h:413-426`).
The order is plain FIFO; the 2022 RFC calls the fixed point "as basic as
possible" and nothing has changed that since
([RFC](https://discourse.llvm.org/t/rfc-a-dataflow-analysis-framework/63340)).
Every `getProgramPointBefore/After` (`:380-406`) goes through the
solver's `StorageUniquer`, which is constructed with threading enabled
(`lib/Support/StorageUniquer.cpp:523`) and never told otherwise
(`DataFlowFramework.h:327-330`): each lookup takes a sharded
reader-writer lock and inserts into a thread-local cache besides the
shard's set (`StorageUniquer.cpp:160-193`), for a solver that is
single-threaded by construction. A program point is thus 24 B bumped
plus two 16-byte hash entries (about 70 to 90 B with load factor;
*conjecture* from the structures, not measured), and none is freed
before the solver dies.

A6. *(read)* **Scoping is supported only in one shape.** A solve is one
`initializeAndRun(top)`; every analysis's `initialize` walks all of
`top` (`SparseAnalysis.cpp:54-105`, `DeadCodeAnalysis.cpp:256-298`,
`DenseAnalysis.cpp:43-59`). With `top` a function (not a symbol table)
the solve is intraprocedural: `DeadCodeAnalysis` marks the callable's
own predecessors unknown (`DeadCodeAnalysis.cpp:152-158`), calls go to
`visitExternalCall` (`SparseAnalysis.cpp:240-243`), and the whole solver
can be dropped after each function. That is a real, supported scope:
per function, with summaries only through `visitExternalCall` and
`visitCallableOperation` overrides that read a table the client keeps.
There is no supported scope between "one function" and "the whole
symbol table": no per-SCC solve, no notion of a summary, and
`eraseState` is per anchor, so freeing a function's states means
naming each of its anchors (`DataFlowFramework.h:570-593`), and the
uniqued program points cannot be freed at all. `initializeAndRun` gained an
`analysisFilter` (#192998, d4ba019, 2026-04-24) that re-initializes only
some analyses on a re-run, which helps a client that re-solves after a
change but not one that wants to bound memory.

A7. *(read)* **Why `DeadCodeAnalysis` and `SparseConstantPropagation`
must be loaded beside everything.** Every sparse and dense analysis
skips an op whose block has no live `Executable`
(`SparseAnalysis.cpp:121-124, 163-165, 459-465`), and only
`DeadCodeAnalysis` ever sets one (`DeadCodeAnalysis.cpp:300-321`). It in
turn decides a branch or region branch only once every operand's
`Lattice<ConstantValue>` is initialized (`:456-469, 471-503, 505-518`),
and only `SparseConstantPropagation` initializes those. The solver's
comment promises to "nudge" uninitialized states when the worklist runs
dry (`DataFlowFramework.h:617-620`); the loop does not
(`DataFlowFramework.cpp:145-155`). Hence `loadBaselineAnalyses`
(`include/mlir/Analysis/DataFlow/Utils.h:22-31`), "an interim fix until a
more robust solution can be implemented", and the Discourse thread it
cites, where the fixes proposed since 2023 (fall back to "all successors
live", liveness built into the solver, declared dependencies) are none
merged ([thread](https://discourse.llvm.org/t/mlir-dead-code-analysis/67568)).
The cost is not only the extra lattice per value: SCCP simulates a
`fold` of every op it reaches and, to undo an in-place fold, reads and
restores its properties through `getPropertiesAsAttribute`
(`lib/Analysis/DataFlow/ConstantPropagationAnalysis.cpp:72-85`), which
uniques a dictionary attribute in the `MLIRContext` per distinct
property set (`lib/IR/Operation.cpp:345-350`): context memory that
outlives the pass and a context lock per op (*read*; the size is
*conjecture*).

A8. *(read)* **Where upstream is going.** The framework's history at the
pin (GitHub, `mlir/lib/Analysis/DataFlowFramework.cpp`): the 2022
framework (9dea117 / ead75d9), program points unified into a uniqued
(block, iterator) storage (#105656, b6603e1; #110344, 4b3f251, 2024), lattice
anchors made equivalence classes so a dense analysis shares one state
across ops that change nothing (#135325, ccbbb17, 2025-04-15: on an
800-line program the author's reaching-definitions peak heap went from
614,554,909 to 245,228,157 bytes, i.e. about 300 KB of heap per line of
IR before the change), worklist dedup (#221983), the analysis filter
(#192998). No RFC or patch addresses the per-state container cost of A4,
per-scope freeing, or summaries; the 2022 RFC's thread already
suggested "run it on a per-function/scc basis … remove the nodes that
are internal to functions to reduce the memory footprint" (jdoerfert,
post 42) and nothing came of it. Upstream is receptive to footprint
work with numbers (#135325's review: "2x faster is a big improvement! Do
you also know how memory footprint is affected?").

**B. Sparse and dense analyses, liveness and `remove-dead-values`.**

B1. *(read)* A sparse analysis keeps one lattice per SSA value
(`SparseAnalysis.h:84-168`), revisits every user of a value whose lattice
changes (`useDefSubscribers`, `SparseAnalysis.cpp:35-42`), and joins
across `BranchOpInterface` edges, region successors, and, in
interprocedural mode, call sites and returns through `PredecessorState`
(`:229-357`). A dense analysis keeps one lattice per program point, that
is, per op boundary (`DenseAnalysis.h:41-58`), unless the client builds
equivalence classes for ops that change nothing
(`DenseAnalysis.cpp:33-41`). Backward analyses take a
`SymbolTableCollection &` from their constructor
(`SparseAnalysis.h:417-418`); forward ones resolve callees with
`resolveCallable()`, a linear scan of the module per call visit at the
pin (`SparseAnalysis.cpp:235-239`, `DenseAnalysis.cpp`'s
`visitCallOperation`), which upstream/05 fixes (16,000 functions:
`--sccp` 8.8 s to 0.7 s).

B2. *(read)* `LivenessAnalysis` is a sparse backward analysis whose
lattice is one `bool` (`include/mlir/Analysis/DataFlow/LivenessAnalysis.h`,
`lib/Analysis/DataFlow/LivenessAnalysis.cpp:36-45`). A value is live if
an op that uses it is not trivially dead, if it flows to a live value,
if it is a non-forwarded branch or call operand, or if it leaves a
public function (`:60-87`). `RunLivenessAnalysis` loads the baseline
analyses beside it and solves the whole op it is given
(`:224-231`), then walks every op and creates a state for every value
the solve never reached (`:236-260`). So every value of the module has
at least one state, at A4's 2.9 KB, plus a `Lattice<ConstantValue>` from
the baseline wherever SCCP reached.

B3. *(read)* `remove-dead-values` (`lib/Transforms/RemoveDeadValues.cpp`)
holds that solver for the whole pass (`getAnalysis<RunLivenessAnalysis>`,
`:791`), builds one `SymbolUserMap` (`:794-799`, #205448, 4ccb701,
2026-07-09, the fix of its own quadratic symbol lookups), walks every
op to collect what to erase (`:809-831`), erases it, and then runs the
region-branch canonicalization patterns of every region branch op
greedily (`:836-865`). Its interprocedural part (dead arguments and
results of private functions, `:272-396`) is the only reason it needs a
whole-module solve; the rest (dead results of region branch ops and
simple ops) is intraprocedural. It is under heavy upstream churn: 35
commits since mid-2025, among them #208881 (0edf624, 2026-10-12, after
the pin), #225355 and #224831 (September 2026), each a correctness fix
(GitHub history of the file).

B4. *(read)* The carried patches say where liveness and
`remove-dead-values` break, besides memory: a dead argument's uses left
null (01, now #208881), uses in code liveness never visits left null
(06), a call rebuilt identical (16), a poison replaced by a poison (22),
a terminator whose operands are all non-forwarded never revisited, a
silent miscompile (28), a non-call symbol use in a nested symbol table
never found, a silent miscompile (29: every idr program is an
`idr.program` nested in the module), and liveness walking an op of n
regions n times through `wouldOpBeTriviallyDead` (63: 10.9, 30.9, 87 s at
1k, 2k, 4k cases). Two of the eight were silent miscompiles on our
dialect's shapes (nested symbol table; a terminator that forwards
nothing), which upstream's own dialects do not exercise.

B5. *(read)* `IntegerRangeAnalysis` is a sparse forward analysis over
`InferIntRangeInterface`, with loop bounds from `LoopLikeOpInterface`
(`lib/Analysis/DataFlow/IntegerRangeAnalysis.cpp:87-172`); its lattice
is 240 bytes before A4's tables (four `APInt`s and a widening counter).
It converges on loop-carried values only through a per-state widening
budget that forces the range to its maximum after enough merges
(`include/mlir/Analysis/DataFlow/IntegerRangeAnalysis.h:28-60`): an
upstream instance of a budget that loses precision and never fails,
the rule AGENTS.md sets for ours. `int-range-optimizations` loads the
baseline and solves the whole op it runs on
(`lib/Dialect/Arith/Transforms/IntRangeOptimizations.cpp:735-736,
770-771`), so it is per-function as soon as it is scheduled on
functions.

**C. The control-flow interfaces on an op of N regions.**

C1. *(read)* The interface's per-edge methods are O(1):
`getSuccessorRegions(RegionBranchPoint(term))` for a terminator,
`getEntrySuccessorOperands`, `getSuccessorOperands`, `getSuccessorInputs`
(`include/mlir/Interfaces/ControlFlowInterfaces.td:185-280, 431-462`),
and `Region::getRegionNumber` is pointer subtraction
(`lib/IR/Region.cpp:62-66`). `RegionBranchPoint` and `RegionSuccessor`
are one pointer each (8 bytes, measured `sizeof`), since the 2025
revamp (#161575, joker-eph, merged 2025-10-28, which also says the API
is "designed around forward-tracking of the chain"). So the edges of an
op are enumerable in O(edges): `getSuccessorRegions(parent())` once,
then each terminator's own successors.

C2. *(read)* Several methods that look per-region enumerate the whole
op on every call:
- `getPredecessors(successor)` and `getPredecessorValues` by default
  walk `getAllRegionBranchPoints()` and ask each point for all its
  successors (`ControlFlowInterfaces.td:281-321`): O(N) per call,
  O(N²) if asked once per region. They are interface methods with
  default implementations, so an op may override them.
- `getSuccessorOperandInputMapping()` with no source builds the map for
  every branch point (`lib/Interfaces/ControlFlowInterfaces.cpp:484-495`);
  the region-branch canonicalization patterns and
  `remove-dead-values`' `processRegionBranchOp` build it per
  application (`upstream/62`'s cause).
- `isRepetitiveRegion(i)` runs `traverseRegionGraph`, which allocates a
  `SmallVector<bool>` of N and a constant vector per terminator
  (`ControlFlowInterfaces.cpp:234-317, 393-402`): O(N) per call, so
  `getEnclosingRepetitiveRegion` from every op of a match is O(N) per
  query (`:530-579`). It is an `extraClassDeclaration`, not overridable,
  but `BufferizableOpInterface::isRepetitiveRegion` is, with
  `defaultIsRepetitiveRegion` as the default
  (`lib/Dialect/Bufferization/IR/BufferizableOpInterface.cpp:1015-1023`).
- `insideMutuallyExclusiveRegions(a, b)` scans all N regions of the
  common ancestor calling `findAncestorOpInRegion` for each, then
  traverses the region graph twice (`ControlFlowInterfaces.cpp:328-391`):
  O(N · depth) per pair. One-shot bufferization caches it per pair
  (`BufferizableOpInterface.cpp:107-118`), which bounds repeats, not the
  cost of each.
- Bufferization's `AnalysisState::getEnclosingRepetitiveRegion(Block *)`
  declares `visitedRegions` and never pushes to it
  (`BufferizableOpInterface.cpp:84-104`), so its region cache never fills
  and every block of a match pays the O(N) traversal: an upstream
  performance bug (*read*; not reported anywhere we found).

C3. *(read)* The framework's region-branch transfer is a recomputation,
not an increment. A sparse forward analysis visiting the program point
after a region branch op joins every known predecessor's operands
(`SparseAnalysis.cpp:298-357`), and a visit does not know which
dependency changed, so each change of any one terminator's operand
lattice costs a join over all N terminators. FIFO deduplication
(#221983) merges changes that are pending at once; it does not bound the
number of separate rounds, so the worst case per op is O(N²) joins
(*read* for the per-visit cost; the round count on our IR is
*conjecture*). `DeadCodeAnalysis` visits the op's entry edges in O(N) per
visit (`DeadCodeAnalysis.cpp:490-547`) and keeps a `PredecessorState`
with an N-entry predecessor set and a `DenseMap<Operation *, ValueRange>`
of successor inputs per program point (`DeadCodeAnalysis.h:94-138`).
The backward analysis walks the parent's entry successors and asks
`getNonSuccessorInputs` for each (`SparseAnalysis.cpp:620-655`); with
liveness's override that was O(N²) until upstream/63 cached
`wouldOpBeTriviallyDead`.

C4. *(read)* How upstream clients query at scale: they do not have to,
because upstream's own multi-region ops are small (`scf.if`: 2,
`scf.index_switch` in tests: tens). The pattern that does scale is the
one `remove-dead-values` and the dataflow framework use per op: enumerate
edges once from the parent and from each terminator, never per region,
and keep the result for the duration of the query. Nothing upstream
caches an op's edge table across queries; `AnalysisManager` could hold
one per function (§F), and an op of ours can override
`getPredecessors`, `getPredecessorValues`, `getSuccessorRegions(Region&)`
and `BufferizableOpInterface::isRepetitiveRegion` with answers that are
O(1) for its shape (a match: every region's one predecessor is the
parent; the parent's predecessors are the terminators; no region
repeats).

**D. Side effects: what can be declared, and who reads it.**

D1. *(read)* `MemoryEffectOpInterface` returns `EffectInstance`s
(`include/mlir/Interfaces/SideEffectInterfaces.h:209-366`): an effect
(`Allocate`, `Free`, `Read`, `Write`, `:437-466`), a resource, optionally
the value, operand, result, block argument or symbol it acts on, a
`stage` and an `effectOnFullRegion` flag. Resources are singletons with a
`TypeID` and, at the pin, a hierarchy: `getParent()` (default
`DefaultResource`), `isSubresourceOf`, `isDisjointFrom`, and
`isAddressable` (`:88-205`). Speculation is a separate interface,
`ConditionallySpeculatable` (`NotSpeculatable`, `Speculatable`,
`RecursivelySpeculatable`, `:373-430`). `isPure` is `isSpeculatable &&
isMemoryEffectFree` (`lib/Interfaces/SideEffectInterfaces.cpp:404`).

D2. *(read)* Which upstream code reads what, at the pin:

| reader | reads | where |
| --- | --- | --- |
| greedy driver's DCE (every canonicalize) | `isOpTriviallyDead` (no uses, `wouldOpBeTriviallyDead`) | `lib/Transforms/Utils/GreedyPatternRewriteDriver.cpp:486` |
| region DCE (`runRegionDCE`, from canonicalize's `simplifyRegions`) and `eliminateTriviallyDeadOps` | `wouldOpBeTriviallyDead`, `isOpTriviallyDead` | `lib/Transforms/Utils/RegionUtils.cpp:371-392, 513-621` |
| `moveOperationDependencies`, `moveValueDefinitions` (utilities) | `isPure` | `RegionUtils.cpp:1324-1470` |
| CSE | `isMemoryEffectFree`; for an op whose only effect is `Read`, `getEffectsRecursively` of every op up to the duplicate, with **resource disjointness and addressability** deciding whether a write blocks | `lib/Transforms/Utils/CSE.cpp:168-246, 264-279` |
| LICM | `isPure` (speculatable and effect-free) | `lib/Transforms/Utils/LoopInvariantCodeMotionUtils.cpp:117` |
| control-flow sink | `isMemoryEffectFree` | `lib/Transforms/ControlFlowSink.cpp:46` |
| inliner | `isMemoryEffectFree` of a callable that is not a symbol, to drop it when unused or inline its one use (symbols go by use counts) | `lib/Transforms/Utils/Inliner.cpp:192-210` |
| SCCP's cleanup | `wouldOpBeTriviallyDead` | `lib/Transforms/SCCP.cpp:95` |
| liveness, `remove-dead-values` | `wouldOpBeTriviallyDead`, `isMemoryEffectFree` | `LivenessAnalysis.cpp:94`, `RemoveDeadValues.cpp:244, 411` |
| local alias analysis | `getEffects` with values and resources; gives up (`ModAndRef`) on any `HasRecursiveMemoryEffects` op | `lib/Analysis/AliasAnalysis/LocalAliasAnalysis.cpp:481-527` |
| bufferization | `hasEffect<Allocate/Free>` on values, `getEffects` | `BufferViewFlowAnalysis.cpp:191`, `BufferUtils.cpp:60`, `OptimizeAllocationLiveness.cpp:61-94`, ownership-based deallocation's `mightHaveEffect<Allocate/Free>` |
| slice analysis | `isMemoryEffectFree` | `lib/Analysis/SliceAnalysis.cpp:320` |
| topological sort, mem2reg, SROA | nothing: they read `PromotableAllocationOpInterface` and kin, not effects | (grep of the files) |

  Nothing in `lib/` reads an effect's `stage` or `effectOnFullRegion`
  (only TableGen, the C API and the Python bindings do), and nothing
  reads an effect on a symbol (only the Python bindings). *(read: grep
  of the pinned tree.)*

D3. *(read)* What declaring buys, concretely: an op with no effects and
speculatable is moved by LICM and control-flow sink and merged by CSE;
an op whose effects are only `Read` (or `Allocate` of its own result) is
erased when unused (`SideEffectInterfaces.cpp:43-111`); an op with only
`Read` effects is merged by CSE past writes to **disjoint** resources
(the pin's resource hierarchy, which CSE consults); an effect on a value
lets alias analysis and bufferization reason per buffer. A
`RecursiveMemoryEffects` op's effects are recomputed by a walk of its
whole body at every query: `wouldOpBeTriviallyDead`,
`isMemoryEffectFree` and `getEffectsRecursively` all walk
(`SideEffectInterfaces.cpp:43-111` and the functions after it), and
upstream says so: "To check recursive operations we need to check all of
the nested operations, which can result in a quadratic number of
queries. We should introduce some caching of some kind"
(`LocalAliasAnalysis.cpp:488-492`). So on a match of 30,000 cases every
greedy visit of it walks 30,000 regions to decide whether it is dead.

**E. The call graph and symbol tables.**

E1. *(read)* `CallGraph` is built by two walks of every op, resolving
each call through one `SymbolTableCollection`
(`lib/Analysis/CallGraph.cpp:74-109`); a node is a region with a
`SetVector<Edge, SmallVector<Edge, 4>, SmallDenseSet<Edge, 4>>` of
edges (`include/mlir/Analysis/CallGraph.h:130-141`), held in a
`MapVector<Region *, unique_ptr<CallGraphNode>>` (`:153`): on the order
of 150 to 700 bytes per function, so tens of MB at 70,000 functions
(*conjecture* from the types). `eraseNode` scans every node's edges
(`CallGraph.cpp:160-174`): O(nodes) per erase. SCCs come from
`llvm::scc_iterator` over the graph traits, bottom-up; the inliner is
upstream's one client of that order (`lib/Transforms/Utils/Inliner.cpp:255-299`),
and it parallelizes only **within** one SCC
(`:517-560`, `failableParallelForEach` over the SCC's nodes), so on a
call graph of mostly singleton SCCs it is serial.

E2. *(read)* `SymbolTableCollection` keeps one
`DenseMap<Attribute, Operation *>` per symbol table, built by one walk
of the table's block on first lookup (`include/mlir/IR/SymbolTable.h:267`):
about 2 MB at 70,000 symbols. `SymbolUserMap` walks every op's symbol
uses once (`lib/IR/SymbolTable.cpp:1050-1075`) into a
`DenseMap<Operation *, SetVector<Operation *>>` (`SymbolTable.h:436`),
whose default `SetVector` is again a 64-bucket set per used symbol
(about 0.5 KB each, *conjecture* from A4's arithmetic: some 40 MB at
70,000 symbols). The symbol-use walk visits each op's discardable
dictionary and its inherent attributes in place, without materializing
properties (`SymbolTable.cpp:536-558`). `resolveCallable()` without a
collection is a linear scan (`upstream/05`).

**F. `AnalysisManager`, the pass manager and the context.**

F1. *(read)* Analyses are cached per op in a `NestedAnalysisMap`
(`include/mlir/Pass/AnalysisManager.h:239-279`): a `MapVector<TypeID,
unique_ptr<AnalysisConcept>>` of analyses and a `DenseMap<Operation *,
unique_ptr<NestedAnalysisMap>>` of children. An analysis is invalidated
after each pass unless the pass marks it preserved or the analysis's
`isInvalidated` says it survives (`:83-131, 184-195`). A nested pass may
read its parent's cached analyses (`getCachedParentAnalysis`, `:299-310`)
but not compute them; child maps are created serially by the parent
before the parallel loop (`lib/Pass/Pass.cpp:966-971`; the inliner does
the same, with the reason: "This prevents thread races when running the
nested pipelines", `Inliner.cpp:538-541`). So the threading
contract is: compute whole-program facts in a module-level pass (or
analysis), read them read-only from the nested, parallel passes, and
let invalidation drop them.

F2. *(read)* The pass manager's parallelism is
`OpToOpPassAdaptor`'s `parallelForEach` over the **immediate** children
of the anchored op that a nested pipeline is registered for
(`Pass.cpp:950-1012`), with one pipeline clone per thread. Functions
inside `idr.program` inside the module are reached by nesting
module → `idr.program` → function; the functions must be
`IsolatedFromAbove`.

F3. *(read)* The context: registered operations are found without a
lock (`lib/IR/MLIRContext.cpp:915-923, 1050-1065`); a parametric type
or attribute is found in a thread-local cache, then under a shard's
reader lock, created under its writer lock
(`lib/Support/StorageUniquer.cpp:160-193`); a mutable type's mutation
takes the shard's writer lock (`:195-210`), and reads of its mutable
part are not synchronized by upstream at all (the caller guarantees no
concurrent mutation). Anything that creates attributes on a hot path
(SCCP's `getPropertiesAsAttribute`, A7; `Operation::getAttrDictionary`
on an op with properties, `lib/IR/Operation.cpp:292-299`; a
`FusedLoc` per `CFGEdge::getLoc`, `DeadCodeAnalysis.cpp:117-121`) grows
the context for good and takes its locks.

**G. The rest.**

G1. *(read)* The non-dataflow `Liveness` (`include/mlir/Analysis/Liveness.h:47-153`,
`lib/Analysis/Liveness.cpp`) is classic block-level liveness per region
tree, a `SmallPtrSet<Value, 16>` live-in and live-out per block: about
300 bytes per block plus the sets' growth, intraprocedural, no solver.
Dominance (`DominanceInfo`) builds a dominator tree per multi-block
region lazily and answers single-block regions by op order; slice
analysis (`getBackwardSlice`/`getForwardSlice`) is a walk with a
`SetVector`; local alias analysis follows def chains and, for region
branch block arguments, `getPredecessorValues`
(`LocalAliasAnalysis.cpp:82`), so it inherits C2's O(N) per query on a
match unless the op overrides it.

G2. *(read)* The action framework (`docs/ActionTracing.md`,
`MLIRContext::executeAction`) and the debug counter built on it are the
upstream way to name, trace and bisect units of work (a pass on an op, a
pattern application) at no cost when no handler is installed; a solver
of ours can wrap its units (a function solved, an SCC) as actions and
get `-mlir-debug-counter` bisection and tracing for free.

G3. *(read)* Ownership-based buffer deallocation
(`docs/OwnershipBasedBufferDeallocation.md`,
`lib/Dialect/Bufferization/Transforms/OwnershipBasedBufferDeallocation.cpp`)
is the upstream design closest to our counting: it is intraprocedural by
construction, fixing a **function boundary ABI** instead of solving
across calls ("ownership is never acquired" for arguments; results pass
ownership; no result aliases an argument, `:55-76`), it computes
ownership in one walk per function through the control-flow interfaces
and refuses IR it cannot model with an error instead of assuming
(`:206-226`), and where static knowledge runs out it emits runtime
conditions (`bufferization.dealloc` with conditions, lowered to alias
checks) that a later simplification pass removes when it can prove
them. Its cost is linear per function and its state is per block, not
per value per program point.

**H. The cost model, projected onto the stage-1 module.**

H1. *(arithmetic from A4's measurements; the counts are wave 2's)* Let
V be the module's SSA values, B its blocks, P its program points (about
one per op plus one per block) at the pipeline point a solve runs.
Upstream liveness as `remove-dead-values` runs it (liveness, plus the
baseline's constant lattice on the same anchors, an `Executable` per
block, program points) costs at the pin about

  V × (2.9 KB liveness + 1.5 KB the second lattice on the same anchor)
  + B × 1.5 KB (an `Executable`, its subscribers inline) + P × 0.08 KB.

With B ≈ V/5 and P ≈ V that is about 5 KB per value, so the measured
52 GB (§3) means V ≈ 10 million values at that point. Whether that is
the stage-1 module after optimize (71 MB of text is nearer one million
ops as the frontend writes it, *conjecture* from line lengths) or a
sign of states beyond these (per-region `PredecessorState`s with their
own 64-bucket maps, `CFGEdge` anchors) is for wave 2 to count. With
patch P1 the same solve is about 0.5 KB per value: some 5 GB at
V = 10 million, and the solve finishes; solved per function, the peak is
the largest function times the threads running.

H2. *(conjecture)* The 627 GB of exclusivity on the framework is, at
2.9 KB of fixed cost per state, some 200 million states: about twenty
per value at V = 10 million, which is what "a lattice per value, an
`Executable` per program point, a predecessor state per function, nested
maps" adds up to when every one of them carries two minimum-size hash
tables and the lattices themselves hold maps. A patched framework would
cut the fixed part about fifteenfold and leave the lattices' own
contents, which for a set-valued dense lattice per program point is the
essential cost, as large as before.

H3. *(read, arithmetic)* The large match is its own wall, apart from
memory: a sparse forward solve joins all N terminators on every visit
of the match's results (C3), and upstream's quadratic helpers (C2, 62,
63) multiply by N whenever they are asked per region. At N = 30,000,
N² is 9 × 10⁸ per match per round. Each of these is fixed by asking per
op instead of per region, which is a property of the client (ours or
upstream's), not of the interface.

#### 5.1.2 What it means for idris-mlir

All of this is *conjecture* until wave 2 checks it against our code.

1. **The framework failed on containers, not on its algorithm.** A4
   says the history of §3 (ffa91113, 16005000) is mostly LLVM's
   64-bucket minimum, paid twice per state. The previous agent's
   inference that `DataFlowSolver` "cannot" do 70,000 functions was
   right about the pin and wrong about upstream: a two-line patch (P1)
   takes the per-value cost from about 2.9 KB to about 0.2 KB, and
   upstream has merged footprint work of exactly this kind (#135325,
   #221983). So the order of preference (§4) points at a patch first.
2. **What should go back on the framework**, as per-function solves:
   the per-value sparse problems we listed as "still on upstream's
   framework" (§2: `Analysis/Constants`, `Analysis/Ranges`,
   `Ownership/Borrows`, `Narrow/{Lanes,Copy}`, `Tail/Returned`,
   `Effects/Constants`), and any analysis of ours whose lattice is per
   value and whose interprocedural part is a summary (`Recursion`,
   `BindingTimes`, `Ranges`' return ranges). Each is a
   `SparseForward/BackwardDataFlowAnalysis` solved with `top` = one
   function, in a function-anchored pass the pass manager runs in
   parallel, reading interprocedural facts through
   `visitExternalCall`/`visitCallableOperation` overrides from a
   module-level summary analysis.
3. **What stays ours, honestly:** problems whose state is per program
   point and set-valued (exclusivity's graph, `idr-rc-stack`'s lifetime
   inference, `Tail/Frames`' plan), the defunctionalization label solve
   (a whole-program closure set, before which nothing is first-order),
   and every interprocedural summary solve over call-graph SCCs, which
   upstream has no mechanism for (A6). Their headers say which of A4
   (fixed cost per state), C3 (no incremental join), A6 (no scope between
   function and module, no summaries) they answer, with the measurement.
4. **`remove-dead-values`** splits in two along B3's line. Its
   intraprocedural part is upstream as it is, run with each function as
   the pass root (the pass supports a non-module root since #225355); its
   interprocedural part (dead arguments and results of private
   functions) is a bit per parameter and per result over the call graph,
   a small summary solve of ours, not a liveness state per value of the
   whole program. The carried patches 06, 16, 22, 28 and 63 stay
   relevant to the per-function runs (28 and 63 above all), and so does
   U2 (5.1.3), without which each per-function run builds the module's
   symbol table. 29 has nothing to act on with a function as root, but
   its fact moves into our signature solver, which must count a
   non-call symbol use (a closure's label) as an unknown caller.
5. **Our match ops must answer the interface per op, not per region**
   (C2, C4): override `getPredecessors`, `getPredecessorValues`,
   `getSuccessorRegions(Region&)` and, once bufferized,
   `BufferizableOpInterface::isRepetitiveRegion`, each O(1) or
   O(answer) for a match; and every client of ours builds an op's edge
   table once. e96bb991's quadratic graph build is this lesson.
6. **Effects pay in upstream passes only where upstream reads them**
   (D2): op-level `Read`/`Write`/`Allocate`/`Free` on our resources, with
   `IOResource` and `ReferenceResource` declared disjoint and
   non-addressable where true, buy CSE across unrelated writes,
   canonicalize's DCE, LICM and sink (with `Speculatable`); effects on
   values buy alias analysis and bufferization. Stages, full-region
   flags and effects on symbols buy nothing upstream; declare them only
   where a pass of ours reads them. `RecursiveMemoryEffects` on a match
   of tens of thousands of cases is a whole-body walk per query (D3);
   whether the match should carry that trait or explicit effects is a
   question for the ODS lane and wave 2.
7. **Threading.** The contract upstream supports (F1, F2): whole-program
   facts computed once in a module-level analysis or pass, read through
   `getCachedParentAnalysis` by function passes that the pass manager
   runs in parallel; no solver shares mutable state across threads; no
   attribute or type is created on a solver's hot path (F3). The
   inliner's per-SCC parallelism (E1) is too narrow for our call graph;
   a wavefront over the SCC DAG (all SCCs whose callees are done, in
   parallel) is the solver layer's to provide.

#### 5.1.3 Candidate designs, ranked

Each is judged by §4 and the representation-first guideline: the fix is
a change of representation (what a state is stored in, what index names
a value, what an op answers about its own shape), never a guard added
around the old one.

**1. Upstream's framework, patched for footprint, solved per function,
with one summary layer of ours (recommended).**
- *Upstream patches* (each `upstream/<bug>/` with report, reproducer,
  test and plan, AGENTS.md):
  - **U1, the state storage.** Either P1: the inner map becomes
    `SmallDenseMap<TypeID, std::unique_ptr<AnalysisState>, 2>` and
    `dependents` a `SetVector<WorkItem, SmallVector<WorkItem, 0>,
    DenseSet<WorkItem>, 4>` (two declarations in
    `DataFlowFramework.h:481, 559`; NFC; about fifteenfold less heap per
    state, A4). Or P2: one flat `DenseMap<std::pair<LatticeAnchor,
    TypeID>, AnalysisState *>`, states in a `SpecificBumpPtrAllocator`
    per state type, which also makes "drop every state of type T" one
    allocator reset (about eighteenfold, and the first per-scope freeing
    the framework would have). Both disable the solver's uniquer
    threading (`uniquer.disableMultithreading()`, one line; A5). Upstream
    plan: a `[mlir][dataflow]` PR with massif numbers on the in-tree
    sccp, int-range and liveness tests and a synthetic many-function
    module; precedent #135325, whose review asked for exactly those
    numbers. Receptiveness: *conjecture*, good for P1 (no API change),
    slower for P2 (`eraseState`'s equivalence-class logic changes).
  - **U2, callee resolution in a scoped solve.** The backward sparse
    analysis resolves every callee before it checks
    `isInterprocedural()` (`SparseAnalysis.cpp:521-540`), so a solve with
    `top` = one function builds the whole module's `SymbolTable` (a walk
    of 70,000 ops) once per function, O(F²) over a function-anchored
    pass, and reads the callee's region from a thread that does not own
    it, the race #155088 fixed for `DeadCodeAnalysis`. The patch checks
    the mode and the analysis scope first, as the forward analysis does
    (`:235-243`), and moves the backward analyses onto 05's per-run
    tables (05's own planned follow-up). *(read; the race is
    conjecture until a TSan run shows it.)*
  - **U3, the quadratic helpers.** Carried: 05, 28, 62, 63. New: fill
    the region cache in bufferization's
    `getEnclosingRepetitiveRegion(Block *)` (C2); find the regions in
    `insideMutuallyExclusiveRegions` by walking each op's ancestors,
    O(depth), instead of scanning every region (C2).
  - **U4, the baseline coupling** (A7): follow open #193112
    (Hardcode84, "Add dependency declaration for dataflow analyses",
    opened 2026-04-20, changes requested by ftynse), whose review
    already floats krzysz00's "skip dead code only if a dead-code
    analysis is loaded". Not ours to lead; when it lands, our solves
    load what they declare and nothing else.
- *Ours, in the dialect:* the match ops override `getPredecessors`,
  `getPredecessorValues`, `getSuccessorRegions(Region&)` and
  `isRepetitiveRegion` (C4) with answers read off their shape.
- *Ours, in the solver layer:* a module-level summary analysis (per
  function: which arguments are live given which results are, constant
  and range facts of returns, recursion facts), solved over the call
  graph's SCCs bottom-up with a wavefront of independent SCCs in
  parallel, iterated inside a recursive SCC up to a budget that only
  leaves facts less precise (AGENTS.md). Function-anchored passes run
  upstream's sparse analyses with `top` = the function, reading the
  summaries through `getCachedParentAnalysis` in `visitExternalCall` and
  `visitCallableOperation` overrides.
- *Buys:* upstream's solver and analyses for every per-value sparse
  problem; peak memory = the largest function's states × threads, not
  the module's; parallelism from the pass manager; no global lock.
- *Costs at §3's scale:* the largest function (a match of tens of
  thousands of cases, say 300,000 values) at about 0.2 KB per value per
  analysis after U1, so some 60 MB per analysis per thread (about
  0.9 GB at the pin without U1); the C3 join over N
  predecessors per visit remains, to be measured on the stage-1 module;
  summaries lose precision inside recursive SCCs unless iterated.
- *Deletes:* (wave 2 lists them) our replacements for per-value sparse
  problems the framework can now hold, and the dropped
  `remove-dead-values` comes back as item 4 of 5.1.2.

**2. Upstream's framework, patched, solved over the whole program as
upstream writes it** (including `remove-dead-values` rooted at the
module).
- *Buys:* the most upstream code and no summary layer at all.
- *Costs:* about 0.5 KB per value after U1 (H1: some 5 GB at
  V = 10 million for liveness), serial (one solver, one thread), paid
  again on every run; exclusivity still out of reach (H2); C3 and the
  helpers of C2 at full module scale; and `remove-dead-values`' history
  of eight carried patches, two of them silent miscompiles on our shapes
  (B4).
- *Use:* as the measured baseline Design 1 is compared against, and as
  the final form of any analysis whose whole-program solve measures
  small.

**3. The solver layer, for what neither covers (exclusivity, rc-stack
lifetimes, frames, the label solve, the summaries of Design 1).**
- One directory, one header per solver naming what upstream lacks (A4:
  fixed cost per state; C3: no incremental join; A6: no scope between a
  function and the module, no summaries) and the measurement that shows
  it, as §4 asks.
- Shared representation, chosen once: values and ops numbered densely
  per function (the index is the coordinate, so a state is a slot in an
  array and a one-bit fact is a bit of a `BitVector`, 0.13 B per value
  measured, A4); an op's control-flow edges read once per op through the
  interfaces (C1) into a compact table; lattices and transfer functions
  as template parameters constrained by concepts, so a solver is
  monomorphic and nothing dispatches per state (§1's C++ directive;
  the cxx26 lane's material); the call graph's SCCs from upstream's
  `CallGraph` and `scc_iterator`; results cached in `AnalysisManager`;
  each unit of work (a function, an SCC) an action, for tracing and
  `-mlir-debug-counter` bisection (G2).
- *Buys:* honest, inspectable composition: which solver reads which
  summary, which runs beside which, is in the code's types.
- *Costs:* code we own, which must earn its place by measurement, one
  solver at a time.

**4. Rejected: a general framework of our own** (an Attributor or DFX
port, or a rewritten `DataFlowSolver`). The failure was the container
choice (A4), not the algorithm, and a second general framework is a
second copy of a mechanism upstream has (one fact, one place). The
ecosystem lane's IREE material may change this only if DFX shows a state
model upstream would not accept.

#### 5.1.4 Questions for the owner and for wave 2

*For the owner:*
- **QA1.** Is "patch upstream's state storage first (U1), then decide

- **QA2.** Per-function solves with summaries (Design 1) as the default

- **QA3.** `remove-dead-values`: split (upstream per function, our

  framework?
- **QA4.** May the solver layer fix one state representation for all
  our solvers (dense per-function numbering, arrays and bit vectors,
  templates and concepts), so every solver of ours shares it?

*For wave 2 (what our code must be checked for):*

- **W2.** For every analysis in §2's lists: its lattice (per value or
  per program point; size), whether it is interprocedural, the

#### 5.1.5 Notes for other lanes

- **llvm:** `DenseMap` allocates at least 64 buckets
  (`DenseMap.h:272-274`); `SetVector`'s default has no small mode; a
  `SmallDenseMap` must have at least two inline buckets to hold one entry
  (the 3/4 load factor), which our measurement tripped over. Containers
  for per-node state at our scale must be chosen with these in mind.
- **mlir-ods:** D2's table is what effects buy upstream; stages,
  full-region flags and symbol effects are unread upstream; the pin's
  resources have a hierarchy and an `isAddressable` that CSE consults;
  the match ops' interface overrides of C4 are ODS
  `DeclareOpInterfaceMethods` with named methods.
- **ecosystem:** compare CIRCT's `IMConstProp` and IREE's DFX state
  models with A4's numbers; the inliner's per-SCC parallelism (E1) is the
  upstream baseline for whole-program scheduling.
- **library:** the summary layer is classic functional-approach
  interprocedural analysis (summaries over SCCs); anything on compact,
  index-addressed solver state and on incremental joins over many
  predecessors bears on C3 and Design 3.
- **cxx26:** Design 3's lattice and transfer concepts are where
  concept-constrained templates replace the framework's virtual
  `AnalysisState`/`DataFlowAnalysis` per state and per visit.
- **rc, dialect-design:** ownership-based deallocation (G3) fixes a
  function-boundary ownership ABI rather than solving across calls, and
  leaves residual runtime checks for a simplifier: a model for counting.
