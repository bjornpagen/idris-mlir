# 5.10 rc: reference counting for a pure functional language, fast

Counting is the heart of what we compile to (§2: cells, stack cells,
grades, exclusivity, reuse), and Koka's Perceus line of work is the state
of the art for doing it fast in a pure language. This lane reads that
work in full, code and papers.
- **Koka** (github.com/koka-lang/koka; `reinking-2021-perceus`,
  `lorenzen-2023-fp2`, `leijen-2017-koka-effects` in `sources/papers`,
  and the FBIP, frame-limited reuse, drop-guided reuse and borrowing
  papers): Perceus's precise counting, dup and drop insertion,
  drop specialization, reuse analysis and reuse specialization, borrow
  inference, fully in-place functional programming, its runtime's
  counting (thread-shared flags, sticky counts, the fast paths), and how
  its compiler represents all of it (its core IR, the passes' order).
- **Lean 4** (`sources/code/lean4`, `ullrich-2019-counting-immutable-beans`,
  `demoura-2021-lean4`): explicit boxing, explicit RC, reset and reuse,
  borrow inference, its IR and its runtime's counting.
- **The rest of the field**: Swift's ARC and OSSA (ownership SSA in SIL,
  `sources/docs/swift`, `sources/docs/swift-rc`), Rust's model
  (`sources/docs/rust-rc`), Lobster's compile-time RC, biased RC
  (`choi-2018-biased-rc`), Pony's ORCA, and compile-time uniqueness from
  linear and quantitative types (`marshall-2022-linearity-uniqueness`,
  Atkey's QTT).
- **For each design**: what is decided at compile time and what at run
  time, the representation that carries ownership through the compiler
  (types, IR forms, side tables), the analyses and their cost, and the
  runtime's fast paths.
- **The lessons**, mapped onto §2 and §3: our cells, grades and
  exclusivity against Perceus and OSSA; which of our counting analyses
  each design makes unnecessary or cheap; what our quantitative types let
  us decide that Koka must test at run time. The mapping is *conjecture*
  until wave 2.

#### 5.10.1 Findings

**A. Koka: Perceus, drop-guided reuse, FBIP.**

A1. *(read)* **The pipeline is three syntax-directed passes over typed
core, per function, no solver.** After boxing, Koka's C backend runs
`parcCore` (dup/drop insertion with drop specialization), then
`parcReuseCore` (reuse), then `parcReuseSpecialize`
(`koka/src/Backend/C/FromCore.hs:91-98`). Each is one traversal of each
top-level definition; none iterates. Parc visits a body *in reverse*,
the live set as mutable state and the owned set, the borrowed parameter
table and a "shape map" as a reader environment
(`koka/src/Backend/C/Parc.hs:13-20`, state and environment at `:795-810`).
Its cost is one visit per expression node times set operations on the
live set (`Data.Set`, so `O(n log n)` per function at worst); its state
is two sets and a map, scoped to one definition and discarded after
(`parcDef` with `isolated_`, `:76-82`).

A2. *(read)* **The rules are Perceus's syntax-directed ⊢s** (Reinking
et al., PLDI 2021, Fig. 8, §3.4): a dup is delayed to the last moment
(a use of a variable that is still live, or borrowed, becomes `dup`:
`useTName`, `Parc.hs:557-569`); a drop is emitted as early as possible,
right after a binding or at the head of a branch (`ownedInScope`,
`:991-998`; `parcGuard`, `:253-283`: a branch drops every owned variable
live in *some* branch but not in this one, and dups every owned pattern
variable it uses). A lambda dups its captured variables at creation
(`parcLam`, `:182-190`). The paper proves the result sound and *garbage
free*: no intermediate state not at a dup or drop holds an unreachable
object (Theorem 4, §3.4). The precondition is explicit control flow
(§2.7.1): exceptions become ordinary returns of an error sum, so no
unwinding path needs drops.

A3. *(read)* **Drop specialization and dup/drop fusion run inside Parc,
per branch, on a shape map built from the patterns.** `inferShapes`
(`Parc.hs:470-509`) records, for each scrutinee, its constructor and
the names of its fields; at the head of each branch `optimizeDupDrops`
first cancels `dup x`/`drop x` pairs and forwards a drop of a box or
newtype to its single child (`fuseDupDrops`, `:412-467`), then for each
dropped parent `y` whose children are known emits
`drop-special(y, unique: drop children; free(y), shared: dup children
used; decref(y))` (`specializeDrop`, `:356-409`), with the invariant
that dups precede drops and parents precede children (`:313-317`). This
is how the paper's Fig. 1c-d arise: the dups of `x` and `xx` move into
the shared arm and vanish from the unique arm.

A4. *(read)* **Reuse is drop-guided: it runs after Parc and turns a
drop into a drop-reuse.** `parcReuseCore` keeps an `Available` map from
*allocation size in bytes* to reuse tokens (`type Available =
M.IntMap [ReuseInfo]`, `ParcReuse.hs:621`). A branch pattern or an
owned parameter of known size makes its variable "deconstructed"
(`ruPattern`, `:322-341`; `ruLam`, `:184-192`); a later `drop x` of a
deconstructed `x` makes a token of `x`'s size available (`ruLet'`,
`:221-283`); a constructor allocation of the same size takes the first
available token and becomes `alloc-at(token, Con(...))`
(`ruTryReuseCon`, `:369-393`); branches intersect what remains
available (`setAvailableIntersect`, `:725-731`) and drop tokens a branch
did not use (`ruBranches`, `:296-303`; `ruGuard`, `:343-354`). The match
is by size, not constructor (a `Bin` can become a `BinR`), and a
drop-special becomes `if is_unique(y) then (drop children; token := &y)
else (dup used children; decref(y))` (`ruLet'`, `:248-281`). This
ordering is the result of Lorenzen and Leijen, "Reference counting with
frame limited reuse" (ICFP 2022, MSR-TR-2021-30 v2, §3): both earlier
algorithms ran reuse *before* Perceus; Koka's original "algorithm K"
reused at a branch head even when the cell was still live (the token is
then always null at run time), and Lean's "algorithm D" (Ullrich and de
Moura, IFL 2019) pushed the reset past the last use, which can hold a
whole structure alive across a call (§3.1, examples A and B). Running
after Perceus uses Perceus's liveness: a `drop` marks exactly where a
cell dies, so turning it into a `drop-reuse` holds no cell longer than
needed (§3.2).

A5. *(read)* **Space is characterized, not just correctness.** The
same paper normalizes Perceus's calculus (λ1n) so that one side
condition (★) on `let` yields three classes: sound, garbage-free (what
Perceus emits), and *frame-limited*: every call may hold at most a
constant factor more memory per stack frame (§4.1, §5.3). Drop-guided
reuse is proved frame-limited (§5.4); algorithm D and unrestricted
borrow inference are shown not to be (§3.1, §4.2). Its conclusion for
borrowing: "Koka currently has no automatic borrow inference and
generally only uses borrowing for built-in primitives" (§4.2).

A6. *(read)* **Borrowing is declared, carried in the definition, and
the inference flag is dead.** A parameter's `Own | Borrow` lives in the
definition's sort, `DefFun [ParamInfo] Fip`
(`koka/src/Common/Syntax.hs:512-515, 572-586`); `Core.Borrowed` is a
name-keyed table *extracted* from those definitions and from externals,
a cache of the IR, not a second source (`koka/src/Core/Borrowed.hs`,
`extractBorrowDef`). The `--binference` flag is threaded to
`genModule` (`FromCore.hs:75-90`) and read by nothing; its help text
says "does not work cross-module!" (`koka/src/Compile/Options.hs:509`)
and its default is off (`:381`). At a call to a function with borrowed
parameters, Parc let-binds the borrowed arguments, makes the call, and
drops them after (`parcBorrowApp`, `parcBorrowArg`, `Parc.hs:192-236`).

A7. *(read)* **Reuse specialization keeps unchanged fields.** At
`alloc-at(token, C(args))` whose token came from a matched `C'(pats)`,
`ruSpecialize` compares each argument with the pattern variable in its
slot (`tryMatch`: the same variable, or `dup` of it, or the same
nullary constructor) and, if at least a quarter of the writes are saved
(`ParcReuseSpec.hs:131`), emits `if token != NULL then (set tag if it
changed; write only the changed fields) else C(args)`
(`ruSpecCon`, `:146-158`). The dups of unchanged fields are then
unnecessary on the reuse path.

A8. *(read)* **FBIP is a check over the same core, a linear type
system without types.** `fip` and `fbip` functions are checked by
`Core.CheckFBIP`, which synthesizes, per expression, the multiset of
owned variables used (`gammaNm`), the reuse credits available by size
(`gammaDia`, with a probability per branch) and a tree of allocations
and calls (`data Output`, `koka/src/Core/CheckFBIP.hs:321-340`); a match
on an owned variable provides a credit of the constructor's size
(`bindPattern`, `provideToken`, `:191-208, 557-567`); a branch join
requires the same variables in every branch or a credit to absorb the
difference (`joinContexts`, `:569-605`); the declared allocation bound
(`fip(n)`, `fbip(n)`) is checked against the tree (`checkOutputEmpty`,
`:685-701`). Violations are warnings (`checkFBIP`, `:57-62`). The
calculus (Lorenzen, Leijen and Swierstra, FP², ICFP 2023, Fig. 4 and
§5) states the relation exactly: FIP ⊂ FBIP ⊂ λfip, and "the FIP
calculus is exactly the subset of λfip that excludes the rules that
require dynamic reference counting" (§5). Koka checks the *definition*
statically but decides *uniqueness at each call* at run time (§1.4.2):
one `reverse` serves both unique and shared lists, where a uniqueness
type system would need two (§1.4.1).

A9. *(read)* **The runtime's fast path is one signed compare.** A heap
block's 64-bit header is `scan_fsize:8, field_idx:8, tag:16,
refcount:32` (`koka/kklib/include/kklib.h:133-141`). The count is 0 for
a unique reference, positive for further same-thread references,
negative for thread-shared ones, which count *down* with atomics
(`kklib.h:102-122`; `koka/kklib/src/refcount.c:100-155`). So `dup` tests
`rc < 0` and otherwise increments non-atomically; `drop` tests `rc <= 0`
(unique or shared: one test for both slow cases) and otherwise
decrements (`kklib.h:752-774`). The slow paths are out-of-line and cold
(`kk_block_check_drop` and kin, `refcount.c:182-236`). Overflow is safe
by a *sticky* band: a count that passes `INT32_MAX` wraps into the
negative range, and from `RC_STICKY_DROP` down drops stop, from
`RC_STICKY` down dups stop too, and the object is never freed
(`refcount.c:105-155`). Static data starts stuck (`KK_HEADER_STATIC`,
`kklib.h:147`). Objects become thread-shared only by an explicit
recursive mark when they cross a thread or enter a shared reference
(`kk_block_mark_shared`, `refcount.c:565-780`; callers in
`koka/kklib/src/thread.c:365-528`, `ref.c:41`); Perceus §2.7.2 argues
the mark costs at most once per object, since shared objects never
become unshared.

A10. *(read)* **Freeing is stackless and specialized at run time
too.** `kk_block_fast_drop_free` frees a block with 0 scan fields
directly, and one with 1 field, or 2 fields whose first is not a
pointer, by looping on the child (a list's spine) without recursion
(`refcount.c:43-86`); everything else goes to a stackless traversal
that keeps the parent chain in the first field of each visited block
and the next field index in `_field_idx` (`refcount.c:317-455`, credited
to Lorenzen). The compiler also emits `dropn(x, scan)` when the scan
count is known statically (`dupDropFun`, `Parc.hs:742-755`), and
`kk_block_dropn_reuse` checks `rc == 0` first (`kklib.h:881-901`).

A11. *(read)* **The representation of counting in Koka's IR is
untyped.** `dup`, `drop`, `drop-reuse`, `is-unique`, `decref`,
`alloc-at` and the drop-special are ordinary applications of named
externals carrying a C template string (`genDupDrop`, `Parc.hs:696-733`;
`genDropReuse`, `genAllocAt`, `genIsUnique`,
`ParcReuse.hs:518-590`), and later passes find them by comparing names
(`getName name == nameDrop`, `== nameDropSpecial`, `ParcReuse.hs:225,
233`; `nameAllocAt`, `ParcReuseSpec.hs:69`). A reuse token is a value of
type `reuse`; nothing in the type says which cell it came from or that
it is used at most once (FP² §5 relies on the construction for that,
and the ICFP 2022 paper argues it, §3.2).

**B. Lean 4: Counting Immutable Beans, now inside LCNF.**

B1. *(read)* **The counting passes moved from the old IR into the new
compiler's impure phase, and run per call-graph SCC.** The impure
pipeline is `pushProj`, `insertResetReuse`, `elimDeadVars`, `simpCase`,
`inferBorrow`, `explicitBoxing`, `explicitRc`, `expandResetReuse`,
`coalesceRC`, `pushProj`, `detectSimpleGround`, `inferVisibility`,
`toposort` (`lean4/src/Lean/Compiler/LCNF/Passes.lean:144-159`). The
driver splits the program into SCCs and runs the whole mono-no-lambda
and impure pipeline *one SCC at a time*
(`lean4/src/Lean/Compiler/LCNF/Main.lean:200-215`), after compiling
any postponed dependency first (`:185-193`). Borrow inference saves the
signatures it annotates (`InferBorrow.lean:446-449`) and the phase ends
with `saveImpure`; a later SCC's passes read a callee's borrow
annotations from the saved signature (`getImpureSignature?`, in
`InferBorrow.lean` and `ResetReuse.lean`'s `classifyUse`). No pass sees
the whole program at once.

B2. *(read)* **Borrow inference is a monotone fixpoint over one SCC.**
Every parameter of reference type starts borrowed, except those of
exported functions (`mkInitParamMap`, `InferBorrow.lean:86-125`); the
solve repeatedly walks the SCC's code, adding variables to an `owned`
hash set for thirteen named reasons (`OwnReason`, `:191-218`: reset or
reuse target, constructor result or argument, projection forward and
backward, call result, owned callee parameter, closure call, partial
application, self tail call, join-point argument and tail call,
annotation), and stops when a pass changes nothing (`infer`,
`:263-290`). Reasons are split into *forced* (correctness: a reset
target must be owned for its count to be exact; a tail call must not be
followed by a `dec`) and heuristic (`OwnReason.isForced`, `:241-260`); a
user's `@[borrow]` overrides only the heuristic ones. Termination is by
monotonicity (a parameter only ever goes from borrowed to owned); the
cost is iterations times SCC size, and the state is one hash set per
SCC.

B3. *(read)* **Explicit RC is a backward liveness walk with "derived
borrows".** `explicitRc` inserts `dec` at the first point a value is no
longer live and `inc` where a value is used owned and stays live, and
treats a value *projected from a borrowed value* as borrowed itself,
since the parent is immutable and keeps it alive
(`ExplicitRC.lean:15-28`), except a `reset` target, which must have an
exact count (`collectResetTargets`, `:37-53`). Its state is a
`LiveVars` of two hash sets (killable and borrowed), a map per join
point, and a parent-child table of derived values (`:51-113`).

B4. *(read)* **Reset/reuse insertion is the paper's R/D/S, made
linear and made aware of owned calls.** `insertResetReuse` follows
"Counting Immutable Beans" (Ullrich and de Moura, IFL 2019): `R` finds
each `cases` on an owned value, `D` finds where it is dead, `S` replaces
a same-shape constructor allocation after that point with `reuse` and
puts a `reset` before it (`ResetReuse.lean:12-31, 83-125, 188-249`). Two
changes from the paper matter here: `D` computes liveness in the same
traversal instead of re-asking at every `let` ("`O(n^2)` where `n` is
the size of the function body", `:200-206`); and `classifyUse` treats
passing the value as an *owned argument* as a live use, so no reset is
placed after it (`:149-182`), which removes the space leak of example B
in the ICFP 2022 paper. Same-type constructors are tried first, then
any compatible layout (`relaxedReuse`, `:59-76`).

B5. *(read)* **The hot and cold paths of a reset are split in the IR,
with "dynamic derived borrows".** `expandResetReuse` turns `let t :=
reset n x` into a join point entered with `isShared` known: on the
unique path the projections of `x` need no `inc`, since `x` itself keeps
them alive, and a `reuse` that writes back an unchanged field skips the
write (`ExpandResetReuse.lean:10-60`). `coalesceRC` then sums the `inc`s
and `dec`s of one variable within a basic block into one each
(`CoalesceRC.lean:10-25`).

B6. *(read)* **Lean's object header: the sign of the count says
single- or multi-threaded, zero says "not counted".** `m_rc > 0` is
single-threaded, `< 0` thread-shared, `== 0` persistent (compact
regions, initialization-time objects), with the same sticky band as
Koka (`lean4/src/include/lean/lean.h:142-160, 631-705`). `lean_dec_ref`
tests `rc > 1` first and otherwise calls a cold path unless the count
is 0 (`:731-740`); `lean_is_exclusive` is `rc == 1` on the
single-threaded path and false otherwise (`:776-782`). So "unique" is
`rc == 1` in Lean and `rc == 0` in Koka: Koka's encoding makes the
unique test and the slow-path test one compare.

B7. *(read)* **Lean checks linearity at run time where a program asks
for it.** Arrays, byte arrays and strings carry a "linearity marker"
bit in the header (`LEAN_LINEAR_MARK_MASK`, `lean.h:242-244`), set by
`markLinear` on an exclusive object, propagated through in-place
updates, and checked where the runtime would copy because the object
is shared: the copy goes through a `_nonlinear` gadget that panics on a
marked object (`lean.h:1135-1156`; `lean4/src/runtime/object.cpp:2023-2160`).
It is a dynamic assertion of what an exclusive grade (`!idr.excl`)
states statically; quantity 1 alone does not state it (G1, G2).

**C. Swift: ownership SSA and ARC.**

C1. *(read)* **OSSA puts ownership on every value and every operand,
and the verifier checks it after every pass while OSSA lasts.** Each
SIL value has one constant *ownership kind*: `None` (trivial values,
addresses, payload-free enum cases), `Owned` (consumed exactly once on
every path), `Guaranteed` (a scoped borrow whose enclosing value is
live over the scope), `Unowned`
(`sources/docs/swift/docs/SIL/Ownership.md:54-190`). Each operand has a
constraint, an ownership kind plus one bit: whether this use *ends the
lifetime* (`:371-384`). Valid SIL requires that the lifetime-ending uses
of a value jointly post-dominate its other uses, exactly one on every
path, so leaks and use-after-free are verifier errors (`:6-25`). A
"forwarding" instruction (casts, `switch_enum`, struct and tuple
extraction) computes its result's kind from its operand's at
construction (`:386-540`), and a non-consuming projection of a
guaranteed value is itself guaranteed, with no scope of its own
(`:296-314`): the same rule as Lean's derived borrows (B3).

C2. *(read)* **OSSA is lowered, and ARC optimization after it is
dataflow.** SILGen emits OSSA, mandatory passes and part of the
optimizer keep it, then it is "lowered" to plain SSA, "from this point
on no ownership verification can be done anymore"
(`sources/docs/swift/docs/SIL/SIL.md:57-69`). OSSA also constrains the
CFG: no critical edges, no unreachable blocks, every cyclic SCC must
have an exit edge (`SIL.md:388-410`). Retains and releases carry
`MayHaveSideEffects` so arbitrary passes do not reorder them
(`ARCOptimization.md:59-79`); pairing them uses *RC identity*, a
per-instruction relation saying which result carries which operand's
count (`:90-180`). *(recalled)* The pairing pass (ARC sequence
optimization) is a bottom-up and top-down dataflow per function; the
document's own section on it is a stub (`:407-410`).

C3. *(read)* **Swift's lifetimes are lexical, Perceus's are precise.**
Named variables get lexical lifetimes, whose ends may not move across
*deinit barriers* (synchronization, weak loads, pointer accesses), so
that user-visible deinitializers run in order (`Ownership.md:743-855`).
Perceus §2.2 contrasts this: scope-tied drops keep `xs` alive while
`map` builds `ys`, where precise drops halve the peak. Idris has no
user-visible deinitializers, so nothing forces lexical lifetimes on us
(*conjecture*).

C4. *(read)* **The uniqueness test is an ordering hazard.** `is_unique`
must not be reordered with anything that changes the count: moving a
retain above it makes it always false and forces a needless
copy-on-write (`ARCOptimization.md:284-366, 857-896`). The runtime's
retain is atomic by default, with a separate non-atomic entry
(`sources/docs/swift-rc/HeapObject.cpp:428-455`). Biased RC (C below,
F1) was built on this runtime because most Swift counts are atomic.

**D. Rust: ownership in the type checker, counting only where asked.**

D1. *(read)* **Ownership is decided entirely at compile time; `Rc` is
a library type, and atomicity is a type.** `Rc` is `!Send` and `!Sync`
(`sources/docs/rust-rc/rc.rs:320-328`), so the compiler proves it never
crosses a thread and its counts are plain `Cell<usize>` updates; `Arc`
is the atomic twin. Koka and Lean decide atomicity per object at run
time by the sign of the count (A9, B6). The uniqueness test is
`strong == 1 && weak == 0` (`rc.rs:1715-1717`); `make_mut` clones when
shared and mutates in place when unique (`:1893-1945`). Overflow aborts
rather than freezing (`:3535-3580`, with the reasoning: it needs
`mem::forget` in a loop). `UniqueRc` is an `Rc` whose type says it has
one owner, convertible once into a shared `Rc` (`:3680-3745`): a
uniqueness grade in a type, with the one-way conversion Marshall et al.
formalize (G1).

**E. Lobster: ownership specialized like types.**

E1. *(read, from the language's documentation page)* **Lobster picks
one owner per allocation at compile time, makes every other use a
borrow, and counts only where a second owner is needed.** The
analysis "is interwoven with type checking" and runs inside Lobster's
flow-sensitive type specialization, which checks functions in
call-graph order and *specializes each function on the ownership its
callers want* for each argument, as it does on types; large functions
and dynamically dispatched ones get one specialization with every
argument borrowed where possible. It removes "around 95% of runtime
reference count operations"; counting remains at run time for the rest;
cycles are reported at exit, not collected
(https://aardappel.github.io/lobster/memory_management.html). There is
no formal treatment ("If you were hoping for pages of equations ...").

**F. Atomicity: biased RC and ORCA.**

F1. *(read)* **Biased RC** gives each object an owner thread with a
non-atomic counter and a shared atomic counter for everyone else; the
object may be freed only when the two sum to zero, and only the owner
can merge them, so it does so (atomically adding its count into the
shared one) before freeing or unbiasing the object; on Swift each
counting operation becomes "more than twice faster in the common case"
and client run time falls by 22.5% (Choi, Shull and Torrellas, PACT
2018, abstract and §3). Its
premise is measured: over 99% of objects in client programs and 93% in
server programs are private to one thread (§3, table of private and
shared objects).

F2. *(read)* **ORCA** (Pony) has no atomic counts at all: each actor
counts its own references, increments and decrements travel in
messages, and the type system's deny capabilities guarantee there are
no data races, so no barriers are needed (Clebsch et al., OOPSLA 2017,
abstract and §1).

F3. *(read)* The Perceus paper names concurrency as one of the three
costs of counting and answers it with the sign bit and a recursive
mark at thread creation (§2, §2.7.2); Rust answers it with a type
(D1); ORCA with a type system plus messages (F2). AGENTS.md puts
threads outside the language, so idris-mlir has none of the three
problems to solve (*conjecture* until wave 2 reads the runtime, and
until proposal 0007's shards say what crosses a shard).

**G. Uniqueness from linear and quantitative types.**

G1. *(read)* **Linearity restricts the future, uniqueness guarantees
the past.** "Linear types provide a restriction on what can be done
with a value 'in the future' whilst uniqueness types provide a
guarantee about what has been done with a value 'in the past'"
(Marshall, Vollmer and Orchard, ESOP 2022, §3, p. 353). Linear logic
derives `!P ⊢ P` (an unrestricted value may be used linearly from now
on); uniqueness logic derives `P ⊢ P°` (a unique value may be forgotten
to be unique, never the reverse). In-place update needs uniqueness.

G2. *(read)* **Idris 2's quantity 1 is the future promise only.**
"A function which takes an argument with multiplicity 1 promises that
it will not share the argument in the future; there is no requirement
that it has not been shared in the past", and an ω variable may be
passed at 0, 1 or ω (Brady, ECOOP 2021,
`sources/papers/brady-2021-idris2-qtt/erasure.tex:34-39`). Uniqueness
follows only from a closed world of construction: if the only way to
make an `Array` is `newArray : (size : Int) -> (1 k : (1 arr : Array t)
-> a) -> a`, "then all arrays are guaranteed to be used linearly, so we
can have in-place update" (`protocols.tex:15-27`). This is AGENTS.md's
"a linear binder does not imply unique heap ownership", from the
source.

G3. *(read)* **FP² draws the same line inside one calculus.** Its FIP
fragment is linear in owned variables (no dup, no drop) and is executed
with no counting and no allocation *if* every owned argument is unique
at the call; uniqueness at the call is either typed (Clean-style, at
the price of two copies of a function, one per uniqueness) or tested at
run time (Koka's choice) (FP², §1.4.1-1.4.2, §2.2). The FIP rules are
syntactic and need no type system (§2.2: "this is a syntactic property
and we do not use a linear type system").

G4. *(read, from the abstract)* **OxCaml carries uniqueness, affinity
and locality as *modes*, beside types, fully inferred**, to allow
in-place update of immutable data and stack allocation (Lorenzen,
White, Dolan, Eisenberg and Lindley, ICFP 2024, "Oxidizing OCaml with
Modal Memory Management", abstract via
https://www.research.ed.ac.uk/en/publications/oxidizing-ocaml-with-modal-memory-management/;
the full text could not be fetched). Locality is the mode that licenses
a stack allocation, which is what `cell.stack` decides (§2).

G5. *(read)* **Upstream MLIR has a per-function ownership scheme of
its own, and a precedent for consumption as an effect.** The
ownership-based buffer deallocation pass works on one
`FunctionOpInterface` at a time "without analysing the call-graph",
fixing the boundary by ABI instead: an argument's ownership is never
acquired, a result's always passes to the caller
(`.toolchain/llvm-project/mlir/docs/OwnershipBasedBufferDeallocation.md:41-77`);
inside a function, ownership is an `i1` SSA value, constant where it
is known and a run-time value where it is not, on the lattice
`uninitialized < unique(X) < unknown` (`:94-130`). And the transform
dialect declares that an op *consumes* a handle as a `Read` plus a
`Free` effect on that operand for `TransformMappingResource`, and asks
"is this operand consumed?" through the effects interface
(`.toolchain/llvm-project/mlir/lib/Dialect/Transform/Interfaces/TransformInterfaces.cpp:1793-1821`):
OSSA's lifetime-ending bit (C1), declared through MLIR's one effects
model.

#### 5.10.2 What it means for idris-mlir

Everything here is *conjecture* until wave 2 reads `foreign/idr`: §2
gives names, not semantics, so each mapping below names the evidence
wave 2 must find.

M1. **Every counting algorithm in the field is per function, and
reads other functions only through signatures** (A1, B1, C2, G5). Koka's
three passes walk one definition each and read callees' `ParamInfo`;
Lean runs its whole impure pipeline one SCC at a time and reads callees'
saved signatures; MLIR's own deallocation pass fixes the boundary by
ABI and never looks at the call graph. The only interprocedural solves
are Lean's borrow inference (a monotone fixpoint inside one SCC, B2)
and Lobster's ownership specialization (in call-graph order, E1).
*None keeps per-value state for the whole program.* Each of §3's
counting walls did: exclusivity on `DataFlowSolver` (a lattice per
value, 627 GB), `idr-rc-stack` (a bit vector per value copied along
every edge, 47 GB), whole-program liveness in `remove-dead-values`
(52 GB). The field's answer to "how is counting linear on 70,000
functions" is that counting is 70,000 independent per-function problems
plus a few bits per parameter.

M2. **Our `dup` and `drop` are Perceus's; our liveness should be the
insertion walk's state, not an analysis.** Perceus decides every dup
and drop from one reverse walk that carries the live set (A1, A2);
Lean's `explicitRc` does the same (B3). If `Uses` and `Values` compute
liveness or use counts that `idr-rc-cells` then reads, that is a
rederivation chain in §0's sense (a fact computed by one component to be
consumed once by another) that Perceus does not have. The precision
argument matters too: Perceus's placement is *proved* garbage free
(A2), so a different placement is either equivalent or worse.

M3. **Our grades are OSSA's ownership kinds, held in types; our
consuming traits are OSSA's lifetime-ending bit.** `!idr.own` is OSSA's
`Owned` (consumed exactly once per path), a borrowed grade with a
lifetime is `Guaranteed` (scoped inside its owner), and "no RC" is
`None` (C1). §2's `ConsumesOperands`, `ConsumesOnly` and the
`Idr_ConsumesOnly` trait list (a marker plus the memory-effects
interface) are the per-operand lifetime-ending bit; the transform
dialect shows the upstream form, `Read` + `Free` on the operand for a
resource (G5). If the grade verifier that runs after every pass is
OSSA's rule (each owned value has exactly one consuming use on every
path, every borrow ends inside its owner), it is a linear walk per
function, and it is the right one; wave 2 checks it is that and not a
solve.

M4. **`!idr.excl` is uniqueness in Marshall's sense, and
`idr-rc-exclusive` decides statically what Koka tests at run time.**
Where Koka emits `if is_unique(x)` at a drop-reuse (A4, A3), an
exclusive operand makes the test constant true: the shared arm (dup the
used children, `decref`) is dead, the reuse is unconditional, and the
drop of an exclusive cell needs no load of its count at all. That is
FP²'s FIP store semantics, "no counting" (G3). This is the one place
our types buy something Perceus cannot have: Koka compiles functions
separately and must serve shared callers (G3), while a whole-program
compiler sees every call site.

M5. **What each quantity decides, precisely** (G1, G2):
- *Quantity 0*: no value exists (AGENTS.md), so no count; Koka has no
  counterpart beyond erased type arguments.
- *Quantity 1 on a binder*: the callee consumes the argument exactly
  once, so the parameter's convention is *owned* by its type, never
  borrowed, and borrow inference has nothing to decide for it. Inside
  the callee it removes no dup that Perceus would have emitted: Perceus
  already emits no dup for a variable used once (A2), so the linear
  binder's real gains are that a `dup` of it is unrepresentable (a
  verifier error, not an analysis result) and that it carries
  uniqueness forward.
- *Uniqueness (exclusive)*: a cell is exclusive at birth (Koka's header
  starts at the unique count, `kklib.h:146`), and stays exclusive while
  it flows only through moves and quantity-1 binders, with no `dup` and
  no ω binder on the way (G2's closed-world argument, run as an
  analysis instead of required of the library). So exclusivity is a
  forward property from allocation sites, killed by the first `dup` or
  ω binding: a two-point lattice per node, which only ever goes from
  exclusive to shared.

M6. **That shape makes `idr-rc-exclusive` linear by construction**, if
its graph has one node per parameter, result and value-flow edge, and
each node is marked at most once (the commit messages of ffa91113 and
e96bb991, "marks the program graph", suggest it is already this shape;
wave 2 measures it). A monotone two-point marking over a sparse graph
is `O(V + E)` with a worklist; the 627 GB came from the state model,
not the problem (§3's conjecture, confirmed by every system here).
`idr-rc-stack` is the same shape on the locality axis (escapes / stays
local, OxCaml's mode, G4; b8301ebe's "the flow graph, marked"). Borrow
inference, if kept, is Lean's: per SCC, monotone (B2). Three markings,
one honest solver layer.

M7. **`Reuses` and `cell.recycle`/`cell.init` against drop-guided
reuse.** `cell.recycle` is Koka's `drop-reuse` and Lean's `reset`;
`cell.init` is `alloc-at` and `reuse` (A4, B4). If `Reuses` pairs a
dead cell with an allocation *before* dup/drop insertion, it is
algorithm K or D, which the ICFP 2022 paper shows fragile or not
frame-limited (A4, A5); if it runs after and turns drops into
`cell.recycle`, it is drop-guided, which needs no analysis beyond a
forward walk per function with a map from size to available tokens,
intersected at joins, and is proved frame-limited.

M8. **`Captures` may vanish under defunctionalization.** Perceus's
lambda rule dups a closure's free variables at creation (A2, `slam`);
after `idr-defunctionalize` every closure is a constructor of a closed
sum (§2), so the lambda rule becomes the constructor rule, and a
closure's captures are its constructor's fields. Wave 2 checks whether
`Captures` computes anything the constructor does not already state.

M9. **No thread-shared counts, so the runtime's fast path is Koka's
single compare without the atomic half** (A9, B6, F3). If nothing
crosses a thread, the sign bit of the count only marks static
(never-freed) cells and overflowed ones; `dup` is a load, a compare and
an add; `drop` is a load, a compare and either a subtract or the cold
free. Lean's "unique = 1" encoding costs a second compare in `dec`
that Koka's "unique = 0" does not (B6).

M10. **The order of our pipeline puts counting after optimization and
before TRMC; Koka puts TRMC before Perceus** (`koka/src/Compile/Optimize.hs:108-109`
runs `ctailOptimize` in core, before code generation's Parc), and the
ICFP 2022 paper credits the combination of TRMC and reuse for its
red-black tree result (§3.2.1). Wave 2 checks that our TRMC keeps the
reuse the counting passes set up.

#### 5.10.3 Candidate designs, ranked

**R1 (recommended). Perceus as MLIR passes: per-function counting that
reads signatures from types, one solver for the three markings, and
the uniqueness test as a folding op.**
1. *Signatures in types.* Each function's parameter and result grades
   (owned or borrowed, exclusive or shared, local or escaping) live in
   its `!idr.q` types, as AGENTS.md already requires of proved facts.
   A per-function pass reads a callee's grades from the callee's type
   and nothing else.
2. *One interprocedural solver, honestly named*: monotone two-point
   markings over one sparse graph (exclusivity, locality, and borrowing
   if kept), each node flipped at most once, run once, its result
   written into the types and its state freed. `O(V + E)` time and one
   bit per node per axis.
3. *Per-function passes, nested under the pass manager on `idr.func`
   so MLIR runs them in parallel*: dup/drop insertion as Perceus's
   reverse walk with the live set as its state (deleting a liveness
   analysis, if `Uses`/`Values` are one); drop specialization and
   dup/drop fusion at each match region's head from the pattern's
   fields (A3); drop-guided reuse as a forward walk with a size-keyed
   token map (A4); reuse specialization (A7).
4. *Static and dynamic uniqueness as one op*: `is_unique %x` is an op
   whose folder returns true when `%x` is exclusive by type; drop
   specialization and drop-reuse emit `scf.if` on it (Lean's
   expand-reset-reuse splits hot and cold paths in IR the same way,
   B5). Where exclusivity was proved, upstream canonicalization folds
   the test and deletes the shared arm; where it was not, the test
   stays and costs one compare. No pass special-cases the static case:
   the type decides and the folder applies it.
5. *Effects declared once*: `dup` and `drop` write the count resource,
   `is_unique` reads it, a consuming operand is `Read` + `Free` on it
   (G5), so no upstream pass can move a `dup` above an `is_unique`, the
   hazard Swift documents (C4).

What it buys: linear total work, per-function state only, parallel by
the pass manager, and every fact computed once and held in a type. What
it would delete (*conjecture*): `Uses` and `Values` as inputs to
insertion; `Reuses` as an analysis (it becomes the rewrite); possibly
`Captures` (M8); `Borrows` off `DataFlowSolver` (§2) into the solver
layer or out entirely (Q1); every C++ path that distinguishes
"statically exclusive" from "tested" drops. Cost at §3's scale: one
walk per function per pass and one marking; the risk is the graph's
construction (e96bb991's quadratic query), which the solver layer must
build from per-op declarations in one pass.

**R2. R1 plus specialization by grade.** Where one caller passes a
shared argument to a function whose other callers pass exclusive ones,
R1 demotes the parameter to shared for everyone and keeps the run-time
test. Lobster instead specializes the function per ownership (E1), and
Clean-style uniqueness typing needs one copy per uniqueness (G3). Our
`idr-optimize` already specializes each function once, bottom-up, under
a budget that never refuses (§2, AGENTS.md); grade could be one more
specialization key. It buys FIP execution, no counting at all, for
exclusive callers of mixed functions. It costs code size and an order
problem: specialization runs before counting in our pipeline, so the
grades would have to be known at `idr-optimize` (Q2).

**R3. Koka as it is: no static exclusivity.** Delete `idr-rc-exclusive`
and test uniqueness at every destructive match. Certainly linear and
simplest, and Koka's measurements say the test is cheap (A9, Perceus
§4). But it discards a fact our types let us derive and AGENTS.md says
this compiler exists to exploit; it is the baseline R1 must beat in a
measurement, not the plan.

**R4 (runtime, with any of the above). Koka's header without the
atomic half.** One 32-bit count with 0 meaning unique (one compare
covers "free" and "special" in `drop`, A9), negative only for static
and overflowed cells (sticky, never freed), no atomics (M9); `dropn`
with the scan count known statically; Koka's stackless free with the
parent chain threaded through the first field (A10); and, under R1, a
drop of an exclusive cell that frees its children and itself without
reading the count. Wave 2 compares this with `runtime/`.

#### 5.10.4 Questions for the owner and for wave 2

*For the owner:*
- **Q1. Borrow inference.** Koka turned it off because a borrowed
  parameter can hold memory the callee would have freed, by an amount
  no constant bounds (A5, A6); Lean infers it per SCC and lets a user
  annotation override the heuristic part (B2); MLIR's deallocation
  fixes it by ABI (G5). Keep inferring borrows, restrict inference to
  the frame-limited cases (the caller uses the argument later, or it
  has constant size, FP² §5), or declare borrowing only on runtime
  primitives?
- **Q2. How much exclusivity is static.** R1 proves what one marking
  can and tests the rest at run time; R2 also specializes functions by
  grade, under `idr-optimize`'s budget, at a cost in code size and a
  change of pipeline order. Which, and is a run-time uniqueness test an
  acceptable fallback where the proof fails (AGENTS.md: linearity is a
  performance property, so the test changes speed, never meaning)?
- **Q3. A space guarantee.** Perceus's insertion is garbage free;
  drop-guided reuse is frame-limited (A5); reuse before insertion and
  unrestricted borrowing are neither. Should idris-mlir state one of
  these as a property of compiled programs, with a test, the way the
  grades are verified?
- **Q4. Threads and shards.** Confirm that no counted cell is ever
  shared between threads, so the runtime needs no atomic count and no
  mark-shared pass; and say what proposal 0007's shards will pass
  between them (ORCA's messages, F2, are the model if anything does).
- **Q5. Precise lifetimes.** Idris has no user-visible destructors, so
  nothing requires Swift's lexical lifetimes (C3). Confirm that drops
  go at last use, everywhere.

*For wave 2* (what our code must be checked for):
- **W1.** Which pass inserts `dup` and `drop`, and whether liveness or
  use counts (`Uses`, `Values`) are computed by one component and read
  by another, or are the insertion walk's own state (M2).
- **W2.** Whether `Reuses` pairs cells before or after dup/drop
  insertion, by constructor or by size, and whether a `cell.recycle`
  token can be held across a call (M7, A4).
- **W3.** What `idr-rc-grades` writes, and whether parameter and
  result grades sit in function types so callers read them locally
  (R1.1).
- **W4.** `idr-rc-exclusive`'s graph after e96bb991: nodes per value
  or per parameter, whether each node is marked once, its peak memory
  and time on the stage-1 module (M6).
- **W5.** The grade verifier: is it OSSA's rule, linear per function,
  and does it read consumption from declared traits and effects or
  re-derive it in C++ (M3)?
- **W6.** The runtime's header and count: encoding of "unique",
  atomics present or not, overflow, static cells, how a cell is freed
  (recursion, stackless, a known scan count), and whether an exclusive
  drop still reads the count (M9, R4).
- **W7.** Each ownership op against the field's: `take` and `unpack`
  against FP²'s destructive match, `share` against uniqueness logic's
  one-way `P ⊢ P°`, `own.adopt` and `own.give` as possibly two
  directions of one conversion, `lin.enter` and `lin.use` against QTT's
  binder rules, `borrow` against OSSA's guaranteed scope; and which of
  them are one op with different effects (§1's directive).
- **W8.** Whether counting runs on `idr.match` regions (Perceus's tree)
  or on a CFG, and whether TRMC, which runs after counting here and
  before it in Koka, keeps the reuse counting set up (M10).
- **W9.** Whether arrays after bufferization are freed by our code or
  could be by upstream's ownership-based deallocation (G5).

#### 5.10.5 Notes for other lanes

- **mlir-analysis (§5.1).** Lean runs its counting pipeline one
  call-graph SCC at a time and passes facts on through saved signatures
  (`lean4/src/Lean/Compiler/LCNF/Main.lean:200-215`): a working
  precedent for §3's "scoped solve". MLIR's ownership-based
  deallocation is per function by design (G5).
- **mlir-ods (§5.2).** Consumption as `Read` + `Free` on the operand
  for a resource is upstream's idiom (`transform::consumesHandle`,
  G5); in ODS it is `Arg<T, "", [MemRead<R>, MemFree<R>]>`. It is
  OSSA's lifetime-ending bit (C1).
- **dialect-design (§5.8).** OSSA's per-value ownership kinds,
  forwarding instructions and RC identity (C1, C2) are the closest
  prior art to `!idr.q`; Koka's counting ops, untyped externals found
  by name comparison (A11), are the counterexample. `memref`'s
  `alloc`/`alloca`/`realloc` split matches `cell.new`/`cell.stack`/
  `cell.init`-at-a-token; a uniqueness test that folds on an exclusive
  type is one op serving the static and the dynamic case (R1.4).
- **oom (§5.11).** Koka and Lean freeze an overflowing count (the
  object is never freed: a bounded leak, never a use-after-free); Rust
  aborts (D1). The frame-limited bound (A5) is the formal tool for
  "how much extra memory may reuse and borrowing hold".
- **library (§5.7).** Worth snapshotting: Lorenzen and Leijen,
  MSR-TR-2021-30 (frame-limited reuse, fetched to
  `/tmp/rc-lane-dl/flreuse-tr.pdf`); Pinto and Leijen, "Exploring
  Perceus for OCaml" (ML workshop 2023); Lorenzen et al., "Oxidizing
  OCaml" (ICFP 2024), whose full text could not be fetched; Lobster's
  memory-management page; and a full Lean 4 compiler tree, since
  `sources/code/lean4` holds none of it.
- **cxx26 (§5.5).** The solver layer's two-point markings are one
  algorithm over different node and edge types: a template over a
  graph concept, not three classes.
