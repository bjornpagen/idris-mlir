# P0 wave 2, lane 15: frontend-translate

Scope: the frontend's translation of checked TT into `idr`:
`compiler/src/IdrisMLIR/Frontend/Translate.idr` and `Frontend/Translate/`
(Cases, Closed, Dictionaries, Errors, Forced, Given, Instances, Keys,
Primitives, Programs, Recursion, Shapes, State, Terms, Types),
`Frontend/Walk.idr`, `Resolve.idr`, `Program.idr`, `Driver.idr`;
`compiler/src/IdrisMLIR/Term.idr`, `Types.idr`, `Ids.idr`, `Loc.idr`.

Marks: *read* (path:line, commit, proposal section), *measured* (count, with
command), *recalled*, *conjecture*.

## 1. Reading notes

What in the proposal bears on the frontend's translation of TT into `idr`
(the Idris side). Most of §5 is about the C++ side; the notes keep what
constrains what this side emits, how it represents what it holds, and what
the redesigned dialect will expect of it.

**§1–§4 (frame).**
- §1: the `idr` dialect is "a historical accident", redesigned whole
  "with every rename it needs"; the Idris side's generated mirror is in
  P0's scope (Goal paragraph: "the Idris side's generated mirror of the
  dialect"). Whatever the dialect becomes, this lane's output changes
  with it.
- §2: the Idris frontend is "about 31,000" lines (`compiler/src`); the
  dialect's surface (§2's list) is what `Translate` emits today; `data`
  is a mutable type whose body "the program's table holds once"
  (`#idr.types<...>`). Grades: `!idr.q<quantity, permission, T,
  lifetime>`, `!idr.lin<T>` = (one, plain). AGENTS.md: a proved fact is
  never a discardable attribute.
- §3: the stage-1 module is 71 MB of text, ~70,000 functions, matches of
  "tens of thousands of cases" (proposal 0001, measured). Every §3 wall is
  downstream of this lane's output: the size of what the frontend writes
  is the N of every later pass. Rows 73bba53f (the table of data types
  rebuilt per declaration) and 98c6315c (a mutable type's facts read
  under the context's lock) concern the `data` table this side emits.
- §4: representation first binds before any other point; "one fact, one
  place"; AGENTS.md whole (grades in types, no budget rejects).

**§5.1 mlir-analysis.** C1–C4: a match op of N regions must answer
`RegionBranchOpInterface` per op, not per region; the large match is
"its own wall" (H3: N = 30,000 → N² = 9 × 10⁸ per round). The frontend
decides N for every match written in the source (`Cases.idr`); whether
the widest matches are those, or defunctionalization's dispatches
(lane 06), is §5.9's Q-W1 (§3.2 below). H1: "71 MB of text is nearer one million ops as the
frontend writes it" (conjecture); W1 asks V, B, P, F and the distribution
of regions per op on the stage-1 module — this lane holds the frontend's
side of that count. D3: a `RecursiveMemoryEffects` match of 30,000 cases
is walked whole at every greedy visit.

**§5.2 mlir-ods.** Row 22 (the Idris side's view generated by
`idris-mlir-tblgen` over the `mlir::tblgen` wrappers), M12; row 14/D4
(enums generated once for both sides); row 13 (properties for op
configuration: what this side writes as attributes becomes properties);
M10 (the `data` table: a table in an immutable uniqued attribute rebuilt
on every change is quadratic; properties are the one mutable place);
row 21/M14 (bytecode: if a stage writes bytecode, mutable types go as
text); B5 (builtin `token` is not a model for `!idr.world`). W8 (does any
stage write bytecode) touches `Emit`/the driver. Q2 (effects that follow
from operand types, a world, a grade) concerns what this side emits as
types.

**§5.3 llvm.** S0: "Before any solver: the representation that makes the
solve unnecessary... could the dialect carry this answer (a type, a
token, an op) so that no pass solves for it?" — the frontend is where
answers Idris already proved can be carried into the IR. B7/I7: dense
numbering is LLVM's newest representational move; per-node state in a
vector indexed by a dense number (the same lesson applies to the
frontend's own maps over names). I8: a list that mirrors records is
generated. M10: hand lists in C++ mirroring records; the Idris mirror's
generator should read typed wrappers.

**§5.4 modular (read most carefully).** F11, F22: Mojo's elaborator is a
demand-driven, concurrent, suspendable monomorphizer from roots, instance
keyed by an interned `(ParameterExprArrayAttr, GeneratorOpInterface)`,
sugar stripped to canonical form so key equality is pointer equality;
`comptime if` elaborates the taken branch only; duplicates merged after
(F4); generators shrunk before instantiation (F22: "fewer, smaller,
simpler generators are faster to instantiate"); no instance cache across
modules, whole-program. F20/F24: Mojo erases traits to `!kgen.type` and
origins before elaboration — "what we must not do" (5.4.2 item 8:
`!idr.lin<T>` and the grades survive specialization). F21: traits nominal,
no dynamic dispatch, witness tables only during elaboration, built
lazily ("eagerly elaborating all conformances will vastly increase the
workload"); `Variant` a closed sum over a pack. F23: the one refusing limit
is an opt-in depth (forbidden here). Design 5: instances keyed by
interned arguments, a two-tier cache; "facts read by many threads live
in immutable attributes built once, never in a mutable type". Q-M5:
whether specialization should move to Mojo's shape — the frontend
already monomorphises from TT (this lane), so Q-M5 concerns the C++
specializer *and* the frontend's split of the work.

**§5.5 cxx26.** C++ only; nothing in the Idris frontend. D4a: "an op's
runtime symbol, its refusal category, its effect row: each is emitted to
C++ and to Idris from the one record, never typed into a C++ `switch`"
— the Idris-side half of that (the refusal categories this lane raises)
is in scope: `Translate/Errors.idr` must read the categories from the
generated record, not hold them as strings.

**§5.6 ecosystem.** Item 1: "a state exists only for what the problem is
about"; for us "the grade in `!idr.q<...>` already answers, for many
values, the question counting or exclusivity asks ... a solver's domain
is the values whose *type leaves its question open*". The grade is
written by this lane: how many values the frontend gives a decided grade
(lin/erased) versus an open one is the frontend's half of W-E2. D6:
IREE writes an analysis answer into types and regrets a lossy mapping —
"the type should hold the answer's own bits". Q-E2: where a summary is a
fact later passes rely on (a function's effects, its parameters'
grades), should it become IR? The frontend already knows several of
these (quantities from TT; erasure; totality) and is the cheapest place
to write them. Item 8/W-E8: is the IR region-structured throughout —
this side emits only structured `idr.match`, no `cf` (to check).

**§5.7 library (data-oriented design, read most carefully).** G1–G4: Zig's
`MultiArrayList` (struct of arrays), its AST of `{tag, main_token, data}`
with `u32` indices typed by what they index, absence as a sentinel,
`extra_data: []u32`; Zig's `InternPool` hash-conses every type and value
into an `Index` so equality is an integer compare; Pareas/Co-dfns invert
the tree into parent arrays. G5: hash-consing plus memoization keyed by
the hash-consed tags won both time and space (Filliâtre: 54 s → 5.06 s,
95 MB → 0.7 MB). G6: one dispatch hoisted out of the hot loop. H1:
Mitchell's supercompiler terminates by a well-quasi-order over bags of
source names (a finite alphabet), no round budget. H3: two-level type
theory makes binding times types; first-order object language compiled
"without any dynamic closures" — a design point the frontend's
monomorphisation already approaches. H4: GCC virtual clones / ThinLTO
summaries decide clones as keys first, materialize each distinct key
once. M5: "`idr-frames` and the specializer walls are clones materialized
before they are deduplicated"; L5 "clones as keys": compute the set of
keys each function needs (interned), materialize each once, termination
from a finite alphabet. M6/L3: the `data` table as an interned,
structural description built once and frozen; "`!idr.data<@T>`" as a
symbol-named type forces a module lookup per query (casework audit §0
item 3, recalled). L1: SSI by representation — "a match's case region
binds the refined scrutinee as a block argument" (what positive
supercompilation propagates, H2); "a quantity-1 value keeps static single
use by type". Whether the frontend's `idr.match` binds the refined
scrutinee per case is this lane's to check. M9: "MLIR's `Value` is a
pointer and has no dense id" — per-value state by dense numbering;
applies to the frontend's own maps over names and de Bruijn indices.
Wave-2 question: "for each specializer: what its key is, whether keys
come from a finite alphabet, and whether any budget decides termination
(L5)" — the frontend's monomorphiser is a specializer (§3 below).

**§5.8 dialect-design (read most carefully).** This lane writes the IR
§5.8 redesigns, so every DS4 row is a change to what the frontend emits.
- The carrier table (5.8.2, "who needs the fact"): a fact needed at every
  use lives in a type; one op's meaning in a property; what an op does in
  an effect; a classification in a trait/interface; a function's property
  in an analysis. The frontend today decides the carrier for every fact
  it emits (§2, §4 below).
- T1: "the type is the only per-value carrier every transformation keeps"
  (AGENTS.md's grades-in-types is MLIR's grain). T3: normalize at
  construction; "the unrestricted grade is the bare type, never a
  wrapper". T4: one enum of the legal grades, not (quantity, permission).
  T6: a function type carries conventions and effects (Koka rows, Mojo
  `FnEffects`). T7: `ValueFacts` holds "contains a linear field",
  "contains a reference", "trivially copyable", "has a runtime form",
  computed at construction. T8/DS3: recursive data types — DS3.1 an
  immutable table on `program`, types naming an entry *by index*
  ("costs: adding a type rebuilds the table (73bba53f's cost) unless the
  frontend emits it whole"); DS3.2 CIR's identified types; DS3.3
  structural with de Bruijn back-references; DS3.4 rejected by B9.
- N1/S3: "a constructor or a field is an index into its data type,
  printed by name" (stored indices, printed names). DS4 row `con`,
  `field`, `tag`: "the constructor and field stored as indices and
  printed by name".
- O5: "compose before fusing": `io.put_sint %x` is `io.write
  (str.show_sint %x)`; DS4 rows for `put_*`. These are primitives the
  frontend emits from `%extern`s (`Translate/Primitives.idr`).
- DS4 rows the frontend emits directly: `!idr.q`→`!idr.g<T,#grade>`
  (DS1.1); `world`, `world.new`, world operands (DS2.1 deletes the world
  value "after the frontend"); `check.*` → `arith.cmpi` + one `idr.check
  %cond, <reason>`; `check.crash`/`crash_str` → one terminator
  `idr.crash`; `divs/divu/...` → `arith`; `closure`, `apply` legal only
  before defunctionalization; `delay`, `suspend`, `force`, `memo.run` → a
  `lazy.` family; `func`, `call`, `return` → `func.*` unless `!idr.fn`
  carries conventions and effects; `match_lit` on words →
  `scf.index_switch`/`cf.switch`.
- Owner questions in scope: **DD-Q1** (may `!idr.lin<i64>` normalize to
  `i64`), **DD-Q4** (signedness: arith's school vs CIR/POP's; "the
  frontend has already monomorphized the source types"). DD-Q3 (world)
  and DD-Q7 (own function op) also decide what this lane emits.
- Wave-2 items for the `frontend-mirror` lane (this lane's half): which
  (quantity, permission) pairs occur and what the lifetime parameter
  holds; every op with a `UnitAttr`, optional operand or enum; where world
  operands are read.

**§5.9 mlton (read most carefully).** The frontend is MLton's front half:
monomorphisation (D1) and the representation choices before closure
conversion.
- D1: `Monomorphise` is one pass, no worklist: per polymorphic binding a
  hash table from type-argument vectors to instances; `monoDec` returns a
  thunk; declarations' thunks built in order and forced in reverse, so a
  body is monomorphised only after every later use requested its
  instances; datatypes instantiated the same way, constructors kept only
  if some instance uses them; "cost linear in the output; the order is
  the program's own scoping, so termination is by construction".
- M10: "Monomorphization never refuses in SML"; Idris allows what SML
  forbids, and AGENTS.md's `unsupported` refusal is the boundary MLton
  never drew — "MLton offers no lesson on where to draw it, only on how
  cheap the admitted part can be".
- B1/B2: every identifier is an object with a property list; identity is
  pointer equality; per-pass state is a typed property, freed when the
  pass ends. B5: abstract-value shape is the type's shape; facts about
  fields live on the constructor; first-order types share one abstract
  value. C2: MLton spends a new IR type where the representation change is
  large, a checked invariant where it is an absence (SXML = XML + no
  polymorphism, checked at the boundary). C3: a case's arms are a vector
  of `(Con, Label)`; the arm block takes the constructor's fields as
  arguments. C4: SSA2 builds a constructor's object then `Inject`s it into
  its sum; mutability per field in the object type. F6: representation
  chosen once per program, per type (`TyconRep`, `ConRep` sums carrying
  only what each representation needs).
- G2.7: "Facts written into the IR's types ... Nothing is carried between
  passes except the program". G2.4: "state sized by types and
  constructors". H table rows 73bba53f ("new datatypes are pushed to a
  list and emitted once") and 98c6315c.
- M4/Q-W1: where the stage-1 module's largest matches come from (source
  matches, apply dispatches, or the table of data types) — the source half
  is the frontend's `Cases.idr`.
- M9/F5/Design 7/**Q-O4**: polyvariance (specialize higher-order functions
  before the flow analysis) against specializing after defunctionalization.
  The frontend already monomorphises before defunctionalization; Q-O4's
  evidence is partly here.
- Design 3/**Q-O3**: every fact a later pass reads written into a type by
  the pass that proves it; an immutable `!idr.data` naming a tycon with
  bodies in one table op; everything else recomputed. The frontend is the
  first "pass that proves" (TT's facts).
- Q-O1 (match as CFG terminator after defunctionalization): the frontend's
  `idr.match` stays the structured form up to that lowering (Design 2
  "costs"), so this lane's emitted form is unaffected either way.

**§5.10 rc.** R1.1 "Signatures in types": parameter and result grades
live in the function's `!idr.q` types, read by callers locally. M5:
"*Quantity 1 on a binder*: ... the parameter's convention is *owned* by
its type ... a `dup` of it is unrepresentable". G2: "quantity 1 is the
future promise only" — a linear binder does not imply unique ownership
(AGENTS.md); uniqueness follows only from a closed world of construction.
So the frontend's job is to write quantity 1 where TT has it and nothing
more; exclusivity is a later analysis. M8: `Captures` may vanish under
defunctionalization (closure captures become constructor fields).

**§5.11 oom.** O1: every compiler wall was a representation. A1: "each
solver's header states its state's size in the program's units"; a state
sized by a product of two program quantities is a wall waiting. The
frontend half of stage 1 (450–528 s, 6.5 GB) is not in §3's table; the
same bar applies to the frontend's own state (§2, §8 below). C7: a budget
counted in program units keeps stage 2 = stage 3; the frontend's
budgets/fuel, if any, must be in program units and never refuse.
Wave-2 item 7 ("every solver and pass whose state is sized by a product
of two program quantities") applies to the frontend's instance tables.

### 2.2 The pipeline it runs (*read*)

`Program.program` (`Program.idr:172-244`): find `main` (`entryPoint`,
`:139-159`), validate the registry (`:117-120`), check imports and pragmas
(lane 16), `checkReachable`, `checkGrowth` (lane 16; returns a `Bool`,
`:224-232`), then `translateIOProgram` (`Programs.idr:145-173`), which runs
lane 16's worklist `Finite.translateFrom` over `translateInstance`
(`Programs.idr:44-80`). Each instance: look the definition up by name
(`:46`), classify its parameters against the static arguments it was
requested at (`classify`, `:63`), re-pattern its clauses (`Forced.clauses`,
`:66`), translate its compile-time case tree (`Cases.tree`), wrap array
ties, and store a `TFn` in `TS.fns` keyed by its symbol string (`:80`).
The worklist translates instances one at a time, serially; an instance
that matched a dictionary field before any construction site gave it is
translated again in a later round (`Finite.idr:355-440`, 1d25638c). The
whole Core is then assembled (`Programs.idr:129-134`), streamed to
`Emit` (lane 14) as the bytecode module (`Program.idr:69-81`), and printed
whole as the Core dump (`Program.idr:242`, `Term.showSource`).

## 5. Target design

All of it stays inside the subset both hosts compile (AGENTS.md): plain
Idris over base (`Data.SortedMap`, `Data.IOArray`, `Data.Buffer`), no
`%extern`, total, no `covering` added. Every design is *conjecture* until
built and measured; each names the line the skill asks for.

**D-1. One instance identity, minted once, dense.** A request's `Link`
(lane 16's identity, kept as the finiteness proof's object) is looked up
once in one table `SortedMap (Link Form) InstanceId`; a new link mints the
next `InstanceId` (a `Nat` below the table's size, the order of first
request), and every other fact about the instance is a column indexed by
it: its definition, its request, its `TFn` once translated, its key and
its symbol (printed once, when first needed by Emit or a message). Data
instances the same (`DataInstanceId`). `TS.fns`, `seen`, `fnOrder`,
`named`, `symbols` and `instances`' string keys go; `FnId`/`DataId` become
the ids, and Emit prints a symbol from the column (lane 14). The
`#idr.instance` attribute carries a typed identity (ID-2) rather than
argument texts, for C++ to key specialization by (lane 09, 0003 B7).
- *Deletes:* ST-2, ID-1, TM-7, TM-8, KY-3, PG-7, the symbol-collision
  internal error's second map.
- *Line:* two structures disagreeing about one instance becomes
  unrepresentable (one table; the order, the set and the symbol are
  columns of it).

**D-2. Facts of a definition, a type constructor and a constructor, read
once at the boundary.** One table per kind of thing the translation asks
about, by context index, filled the first time it is asked and frozen
after (the facts depend only on the definitions, `State.idr:474-487`):
- per definition: its `GlobalDef`, its kind as the translation's sum
  (constructor, type constructor, primitive, pattern definition, foreign,
  extern, hole), its erasure vector (`Vect arity Use`, the one reader of
  0003's five), whether it is a projection and which, its termination
  verdict (`Terminating`), its origin, its resolved `Hook` (one sum, from
  the registry's table validated at start, RS-1), its runtime binders
  when it has no static argument;
- per type constructor: `TyConFacts` with `roles : Vect arity Role`,
  natness, and `TyConKind = NatLike | Word | Ordered o (Maybe Ty) |
  ValueArray | Data` (TT-4), interface membership (TT-13);
- per constructor: its type constructor, its tag, its quantities, its
  natural role (0003 C3).

## 8. Risks, unknowns, measurements needed

**Risks.**
- *Memo keys that miss a dependency (D-3).* A classification depends on
  more than the callee and its static arguments: what the call offers
  (`Offer`, `Instances.idr:105`), dictionary fields read from runtime
  records (`Instances.idr:356-361`), and implementations that close over
  runtime values (`Instances.idr:404-440`). A memo keyed on less is a
  silent miscompile of exactly the kind 3934cc0c fixed (one type, two
  identities, alternatives compiled to `unreachable`). The memo's key
  must be the full static input, and a debug run comparing memoised and
  recomputed answers is its gate.
- *Determinism.* Symbols must stay a function of the key alone
  (`Term.idr:573-586`), never of an id, so stage 2 = stage 3 holds
  whatever order instances are minted in.
- *Two hosts.* Tables on `Data.IOArray` must be as cheap under idris-mlir
  as under Chez; idris-mlir's compile of base's arrays is not measured
  (0011 §6 says the gains on Chez are memory, not time).
- *The fork (D-4).* Each restored fact changes the TTC (`ttcVersion`) and
  is lane 17's; until it lands, the reconstructions are load-bearing.
- *Cutover coupling (D-6).* Core changes reach Emit (lane 14), the harness
  readers of the Core dump (§2.5) and every test's module; the change is
  one, with the dialect.

**Unknowns.**
- Where translate's 172 s goes inside the phase (normalisation,
  keying, clause re-patterning, location conversion): no profile exists.
- What the 6.5 GB peak is made of: Idris's loaded context, Core trees,
  `Loc`s, key token lists, the Core dump string.
- Whether the stage-1 module's widest matches are source matches, crash
  enumerations (CS-4) or defunctionalization's apply dispatch (lane 06).
