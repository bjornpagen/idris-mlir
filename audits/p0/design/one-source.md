# P0 design: one source, the dialect's specification in Idris

Written 2026-10-21 at e96bb991 (upstream 7208ba24c) for the owner's
question of that day: "this is the ultimate upstream, monomorphic
concept/template tablegen philosophy taken to its extreme. do you agree?
perhaps our tablegen has to be even higher level, or dear god, maybe
generate the tablegen? can we deeply flesh this out? i need to
understand." Two rulings came while it was written (proposals/0000 §2;
AGENTS.md "The Idris side"), and it is built on both:
- **D15**: "our higher level spec should not be in a python dsl, opdsl,
  etc... it should just be idris. obviously. we have chez so we can always
  bootstrap. always idris."
- **D16**: "tablegen FULLY 100% generated by idris is the right move. i
  approve. it must be an extremely hard cull and cutover."

So this designs the level D16 chose: the `idr` dialect's one source is a
typed Idris specification, every `.td` under `foreign/idr` its output.
Grounds: *read* (path:line), *measured* (command given), *recalled*,
*conjecture*, *decision* (a D-number); nothing was built or run.
`design/typed-effects.md` did not exist yet; §5 hosts effects in function
types as the coordinator described them. "effects §1.4" is
`design/effects.md`, "CTC" `design/compile-time-cpp.md`, "14 TD3" lane
14's item, "5.2 F3" `wave1/5.2-mlir-ods.md`.

## 0. In plain words

**Do I agree?** Yes, with one correction: "even higher-level TableGen" is
the wrong axis. TableGen's trouble is not its level. It has no sums, no
proofs and no functions, so each invariant of ours is either a string a
C++ backend checks later or a check nobody wrote. Moving up inside
TableGen (L2) removes repetition and nothing else. D16 changes the
language the source is written in, to one whose type checker proves the
invariants, and prints TableGen from it. TableGen becomes what it is good
at: the input format of upstream's `mlir-tblgen`.

**The picture.** One Idris package, `idris-mlir-spec`, states every
static fact as data: ops and families, types, grades, the resource tree,
each op's effects, the row of atoms a function type carries, the runtime
ABI, the pipeline, refusal rules, endings, crash causes, clocks. Its types
make the bad states unwritable: a cycle in the tree, an op that declares
no effect, a pipeline whose stages do not chain, a rule with no category.
One Idris program, `specgen`, prints from it the `.td` files
`mlir-tblgen` reads (which write the dialect's C++ as today), C++ headers
of constants only our C++ reads, and Idris builders the frontend cannot
import directly. The frontend and the harness import the spec's closed
sets (rules, endings, clocks, grades) directly: those copies stop existing.

**The direction flips.** Today TableGen is hand-written, a C++ backend
reads it, and the Idris side is generated last (`Makefile:154-162`).
After the cutover Idris is first: stock Idris on Chez builds and runs
`specgen` before any C++ compiles. Chez and Idris build from source with
the host's C compiler and need no LLVM (`tools/bootstrap.sh:1424-1459`),
so the build always starts (D15).

**Hand-written stays** (§9) the C++ that is semantics: folders, essential
verifiers, region interfaces, the effect derivation's walk, solvers, the
runtime. The spec names them and holds no C++. **The owner decides**
(§11.3) four things, one at a time.

## 2. The ladder, level by level

The ladder holds, with one correction: L3 and L4 are one step, a spec
above TableGen, and D15 says its language is Idris.

**L0, hand C++**: 9 hand `getEffects`, 22 hand `verify()`, 37 hand folders
(03 R3, 04 C40), four readings of "does IO" (02 §3.1), the bit-to-resource
table and three reverses (02 E23-E25). P0 deletes it.

**L1, ODS per op**: today. TableGen's language is barely used: one
`!foreach` (`IdrBase.td:341`), one `defvar` (`IdrClosureOps.td:15`), one
`assert` (`Passes.td:66`), no `multiclass`, `defm`, `defset` or
`!instances` (*measured*, `grep -n`); so 59 platform ops are 59 hand
`def`s (`IdrPlatformOps.td`). Cross-record facts are checked, where at
all, by `idris-mlir-tblgen` (3,255 lines, eleven generators,
`idris-mlir-tblgen.cpp:3221-3255`), partly by C++ spelling (14 T05-T19).

**L2, higher-level TableGen** (`llvm/docs/TableGen/ProgRef.md`:
`multiclass` :1021, `defset` :1309, `foreach` :1378, `assert` :1467,
`!instances` :1975):

```tablegen
class Idr_DivRow<string m, string cls, Idr_Case part, Idr_Case sign> {
  string mnemonic = m; string cppClass = cls; Idr_Case part = part; Idr_Case sign = sign;
}
defset list<Op> Idr_DivisionOps = {
  foreach r = [Idr_DivRow<"divs", "DivSOp", Idr_Quotient,  Idr_Signed>,
               Idr_DivRow<"mods", "ModSOp", Idr_Remainder, Idr_Signed>] in
    def Idr_ # r.cppClass : Idr_DivisionOp<r>;
}
multiclass Idr_IOFamily<string m, dag args> { def Op : Idr_IOOp<m> { let arguments = args; } }
defm Idr_PutStr : Idr_IOFamily<"put_str", (ins Idr_StrRead:$str)>;
defvar Idr_AnyEffect = !foldl([]<MemoryEffect>, !instances<Idr_Atom>(), acc, a,
                              !listconcat(acc, a.effects));
```

It makes one state unwritable: a family member without its family's
traits (03 R1). It cannot have sums (an op declaring effects "in exactly
one of five ways" is five optional fields and a backend check, effects
§1.10 a-c), proofs (`assert` sees one record; coverage or a chained
pipeline needs `!foldl` contortions or a backend's `PrintFatalError`, CTC
R4), typed references (`Idr_Rule<"fields">` names a group by text,
effects §1.10 g), or an Idris reader (the mirror still needs a C++
backend, 14 §2.2). It buys repetition only; D16 excludes it. Its one
lesson kept: a family is a function of its constants.

**L3, a spec in another language** (OpDSL's Python, SPIR-V's grammar,
IRDL): excluded by D15; lessons in §3.

**L4, typed Idris data**: decided by D16. What it makes unwritable is
§4.3; the Idris side imports it or Idris prints it; Idris's type checker
checks every cross-record fact. §4 to §9.

## 3. Upstream's precedents, as lessons

Read at the pin. None is a model (D15); each shows how such a source
lives or dies.

**Linalg OpDSL.** Python (`python/mlir/dialects/linalg/opdsl/`: `lang/`
2,828 lines, `ops/core_named_ops.py` 1,440; *measured*) is dumped by hand
(`update_core_linalg_named_ops.sh.in:22-31`) to a checked-in YAML,
`LinalgNamedStructuredOps.yaml`, 5,361 lines, 59 ops (*measured*: `grep -c
'^--- !LinalgOpConfig'`), headed "AUTOGENERATED from core_named_ops.py"
(:1-2). At build time `mlir-linalg-ods-yaml-gen` (C++, 1,281 lines) turns
it into a `.td` and a `.cpp.inc` (`Dialect/Linalg/IR/CMakeLists.txt:2-25,
49`), included at `LinalgStructuredOps.td:1395`. It is being deprecated,
"its operations slowly being moved into TableGen's ODS format"
(`docs/Dialects/Linalg/OpDSL.md:3-6`): `matmul`, `batch_matmul`,
`contract` and `elementwise` are hand ODS now (`LinalgStructuredOps.td:550,
691, 824, 970`) and gone from the YAML (*measured*). The DSL is "not ... a
build tool of the core compiler"; the YAML "must be updated and reviewed"
(`OpDSL.md:32-35`).

**The SPIR-V generator.** `utils/spirv/gen_spirv_dialect.py` (1,123 lines)
fetches Khronos's grammar and HTML over the network (`requests.get`, :50,
:86, :96), rewrites sections of checked-in `.td` marked "Generated from
SPIR-V spec; DO NOT MODIFY!" (`SPIRVBase.td:487-4123`, `:4439-4848`), and
regenerates each op def keeping its "manually specified sections"
(`existing_info`, :690-818; :947-1008). It is run by hand
(`define_inst.sh`), never by the build.

**LLVM intrinsics.** `tools/mlir-tblgen/LLVMIRIntrinsicGen.cpp` (281
lines) prints ODS text from LLVM's `Intrinsic` records (:213-253). No
CMake file runs it; its one user is `test/mlir-tblgen/llvm-intrinsics.td`
(*measured*), and `LLVMIntrinsicOps.td` is 1,909 hand lines. What matured
is the fact on the op: each LLVM op's translation is a field
(`llvmBuilder`, 5.2 F3) that `-gen-llvmir-conversions` reads at build time
(`Dialect/LLVMIR/CMakeLists.txt:44, 51`).

**IRDL.** Dialects defined as IR (`IRDLOps.td:34-661`). `tblgen-to-irdl`
(28 + 583 lines) drops every trait, effect and interface (*measured*: its
one match for them is an `#include`). `mlir-irdl-to-cpp` (143 lines, plus
`IRDLToCpp.cpp`, 829) refuses variadic operands and results and all but a
handful of ops (`IRDLToCpp.cpp:711-753`); its one user is a test dialect
(`cmake/modules/IRDLToCpp.cmake:1-12`).

**Lessons.**
1. *A source that cannot say everything loses ops back to hand ODS*, as
   OpDSL lost `matmul`: ours must say every construct we use, or name a
   hand C++ hook, before the cutover (§8.2). D16 leaves no hand `.td`.
2. *A file both generated and hand-edited is two sources* (SPIR-V): every
   "manual section" becomes data or a named hook.
3. *A generator outside the build rots* (intrinsics; OpDSL's manual step):
   `specgen` runs in `make build`, and `make check` holds it current (§7).
4. *A spec without effects cannot be ours* (IRDL); ours is effects first.
5. *Upstream commits the intermediate and reviews it*, running the last
   step at build time; ours: committed `.td`, `mlir-tblgen` at build time.
6. *What matured is a fact as a field on the op* (`llvmBuilder`; ClangIR's
   lowering emitter, 5.6 F2, *recalled* via 14 §1); an Idris record field
   is that, typed.

## 4. The specification

### 4.1 Its shape

- **Where**: `compiler/spec/`, package `idris-mlir-spec`, modules
  `IdrisMLIR.Spec.*`, depending on `base` alone; the generator is
  `compiler/specgen/` (*conjecture*, a placement: `compiler/` is where the
  Idris side lives).
- **Modules**: `Core` (names, arity, constraints, docs, the vocabulary of
  upstream ODS names), `Effects`, `Types` (types, grades, bodies,
  bytecode layouts), `Ops.<Family>`, `Dialect` (the op list and its global
  proofs), `Runtime`, `Pipeline`, `Rules`, `Endings`, `Clocks`, `Expect`,
  `Hooks` (the hand C++ the spec names).
- **One encoding rule, for both hosts.** A closed set is an enum and its
  facts total functions, so a new case without facts is a coverage error.
  Ops are values in family lists built by family functions, so a member
  is its family applied to its constants. A relation between fields is an
  erased (quantity 0) proof found by `auto` at the definition, so it fails
  at that line. A property over all records is a decision the type checker
  evaluates, next to the lemma that turns it into a proof (the skill's
  rule for `So`).

### 4.2 Concrete Idris

Sketches in the spec's real shape; none was compiled.

**The resource tree** (effects §1.2; its node set waits on DP-01 to DP-03):

```idris
module IdrisMLIR.Spec.Effects
%default total

||| Whether an effect on a node may name a value.
public export
data Reach = Addressable | Opaque

||| A child's reach under its parent's. No case puts an addressable node
||| under an opaque one (upstream aborts on that at run time,
||| SideEffectInterfaces.h:164-173).
public export
data Fits : (child, parent : Reach) -> Type where
  OpaqueAnywhere  : Fits Opaque r
  BothAddressable : Fits Addressable Addressable

||| What ops act on, each declared after its parent.
public export
data Node = Heap | Count | Memo | Fresh | IO | Halt | Exit | Diverge

order : Node -> Nat      -- declaration order; a wrong entry can only refuse a tree
reach : Node -> Reach

||| Upstream's root, or a node declared earlier whose reach admits this
||| one: a cycle, a later parent, or addressable-under-opaque cannot be
||| written.
public export
data Parent : Node -> Type where
  Root  : Parent n
  Under : (p : Node) -> {auto 0 before : LT (order p) (order n)}
       -> {auto 0 fits : Fits (reach n) (reach p)} -> Parent n

public export
parent : (n : Node) -> Parent n
parent Heap = Root
parent Count = Under Heap
parent Memo = Under Heap
parent Fresh = Root
parent IO = Root
parent Halt = Under IO       -- [DP-03 ods-Q3]
parent Exit = Under IO       -- D14: exit is its own effect, under IO
parent Diverge = Under Halt
```

**How an op says what it does** (effects §1.6, §1.10):

```idris
public export
data Kind = Read | Write | Allocate | Free

||| An effect on a value the op names: only on a node a value can reach.
public export
data OnValue : Type where
  On : (k : Kind) -> (n : Node) -> {auto 0 ok : reach n = Addressable} -> OnValue

||| A condition read off a value's type; one hand C++ predicate each.
public export
data When = IfOwned | IfMemoSum | IfCellPointer | IfLinear | FromCalleeRow

public export
record TypedRule where
  constructor MkTypedRule
  effects : List (Kind, Node)
  group   : Name                     -- an operand or result group of its op
  when    : When

||| Exactly one way: declaring nothing, or both effects and rules, cannot
||| be written (effects §1.10 a, b, c).
public export
data Effects = Static (List (Kind, Node))    -- [] is Pure
             | Typed (List1 TypedRule)
             | Recursive                      -- its regions' effects
             | RunsUnknown                    -- apply, force: every atom
             | Definition                     -- func, program

||| How control leaves the op; a no-successor terminator names the atom
||| that stops the run (effects §1.10 e).
public export
data Leaves = FallsThrough | Branches | Stops Atom
```

**An op, and two families** (03 R1; CTC §2.3(b)):

```idris
public export
record Op where
  constructor MkOp
  mnemonic : String
  family   : Family             -- the family and its constants, one value
  ins      : List Operand       -- name, arity, constraint, value effects
  outs     : List Result
  regions  : List Region
  attrs    : List Attr          -- inherent only: no field for a discardable one
  effects  : Effects
  leaves   : Leaves
  stages   : Stages             -- first and last legal stage, ordered
  meaning  : Meaning            -- Runtime Symbol | HandFolder | NoFold
  guards   : List Guard
  format   : Format             -- a typed AST of ODS's assembly format
  doc      : Doc
  {auto 0 named   : Names format ins outs attrs}   -- the format names what exists
  {auto 0 ruled   : RuleGroups effects ins outs}   -- each rule's group exists
  {auto 0 guarded : GuardOperands guards ins}      -- each guard's operands exist
  {auto 0 stops   : StopsOnHalt leaves effects}    -- a stopping terminator writes Halt

public export
data DivPart = Quotient | Remainder
public export
data Signedness = Signed | Unsigned

||| Each op is the family applied to its constants, so they cannot
||| disagree (CTC R6's `bool`s go).
public export
division : DivPart -> Signedness -> Op
division part sign = MkOp
  { mnemonic = divName part sign, family = Division part sign
  , ins = [word "lhs" sign, word "rhs" sign], outs = [wordResult "result" sign]
  , regions = [], attrs = [], effects = Static [], leaves = FallsThrough
  , stages = always, meaning = Runtime (divSymbol part sign)      -- [DP-17]
  , guards = [MkGuard Nonzero ["rhs"] DivisionByZero]
  , format = operandsThenType, doc = divDoc part sign }

public export
divisionOps : List Op
divisionOps = [division p s | p <- [Quotient, Remainder], s <- [Signed, Unsigned]]

||| Base's IO primitives: each reads and writes what the outside sees and
||| calls the runtime function its mnemonic names.
ioOp : (m : String) -> (ins : List Operand) -> (outs : List Result)
    -> {auto 0 named : Names Generic ins outs []} -> Op
ioOp m ins outs = MkOp
  { mnemonic = "io." ++ m, family = IO, ins, outs, regions = [], attrs = []
  , effects = Static [(Read, IO), (Write, IO)], leaves = FallsThrough
  , stages = from Higher, meaning = Runtime (rt ("io_" ++ m))
  , guards = [], format = Generic, doc = ioDoc m }

public export
ioOps : List Op         -- [DP-02 decides the world's operands]
ioOps = [ioOp "put_str" [readStr "str"] [], ioOp "put_char" [word32 "ch"] []]
```

`Symbol` holds a stem and prints `idris_rt_` before it (14 T44 goes); the
generator prints `Division<DivSOp>` from `family`, set by the same call.

**Grades** (01 C1-C2; DS1): `Quantity`, `Permission`, `Lifetime` enums;
the legal grades one enum, so an illegal pair has no constructor; `join`,
`times`, `fitsIn` total over the declaration order, their laws proved by
case split (2³, 4³, 3³ cases, CTC §7.5), deleting CTC's `semilattice()`.

**The pipeline** (CTC §2.3(f); 13 T1, T2):

```idris
public export
data Stage = Higher | First | Graded | Owned | Lowered
public export
data Anchor = OnProgram | OnFunction

public export
record Pass where
  constructor MkPass
  name     : String
  anchor   : Anchor
  from, to : Stage
  kind     : PassKind           -- decide | apply | restructure
  doc      : Doc

||| A step whose contract does not start where the last ended, or a
||| function pass at program level, does not type-check.
public export
data Pipeline : Anchor -> Stage -> Stage -> Type where
  Done : Pipeline a s s
  Run  : (p : Pass) -> (why : String) -> {auto 0 here : (p.anchor = a, p.from = s)}
      -> Pipeline a p.to u -> Pipeline a s u
  Nest : Pipeline OnFunction s t -> Pipeline OnProgram t u -> Pipeline OnProgram s u
```

**Rules, endings, the ABI**: a refusal `Rule` record with required

Ending` with `status : Ending -> Bits8` (DP-18) and an evaluated proof the

### 4.3 What its types prove, and what each proof deletes

| invariant | held by | deletes (read) |
| --- | --- | --- |
| no cycle; parents first; addressable never under opaque | `Under`'s erased `before`, `fits` | effects §1.10 d; CTC §2.3(d)'s `parentsPrecede`, `symmetric` |
| a value effect only on an addressable node | `On`'s erased `ok` | upstream's run-time abort, met at build time (effects §1.10 d) |
| one way to declare effects | the `Effects` sum | effects §1.10 a, b, c |
| rule groups, guard operands, format names exist | erased `ruled`, `guarded`, `named` | effects §1.10 g; the guard-name check (`IdrBase.td:295-308`) |
| a stopping terminator writes `Halt` | `Stops Atom`, erased `stops` | effects §1.10 e |
| coverage; the projection round-trips and never says less | decisions the type checker evaluates (`0 covered : So (all covers allOps)` beside `coversSo`) | effects §1.10 f, §2.4's `static_assert`s |
| dense enums from zero | an enum's position is its number | CTC R2's generator refusal |
| a member keeps its family's traits and constants | members are family applications | 03 R1's hand members; CTC R6's `bool`s |
| the pipeline chains; anchors nest | `Pipeline`'s indices | CTC §2.3(f)'s T0 check; the order held twice (13 DP-01) |
| a rule has a category and scope | required fields | `Profile.outsideLanguage` (16 G5) |
| no discardable attribute | no such field | `tests/facts-in-types` and its planted `.td` |
| grade laws; only legal grades | case-split proofs; one enum | CTC `semilattice()`; `QType`'s full product (14 G03) |
| distinct statuses; every cause has a message | evaluated proof; total function | the harness's three copies (19 C4) |
| distinct mnemonics and class names | evaluated proof over `allOps` | mlir-tblgen's duplicate-def error, met earlier |
| a symbol has its prefix; an ABI kind exists | `Symbol`'s shape; `AbiKind` | 14 T12, T13, T44 |

A proof done in Idris is not done again in C++ (CTC R4: "A check repeated
at a later time is deleted"). The C++ keeps only checks that need a C++
type: a generated declaration's hand definition (the linker), a concept's
specialization (`requires`), laws over C++ code.

### 4.4 The two-host subset

The spec, `specgen` and the frontend importing it compile under stock
Idris and under idris-mlir. The tests draw the line (*read*): a `Type`
stored as a run-time field is refused, `unsupported (dependent field)`
(`tests/dependent-field-type-field`), and accepted erased (its
`near/Main.idr`, `MkBox : (0 _ : Type) -> Box`); a type computed from a
run-time value with varying representation is refused, `unsupported
(type)` (`tests/type-dependent`), and accepted where the function matches
on the value (its `near/`); a dependent pair of one representation
compiles (`tests/show-dependent-pair`, `(n ** Vect n Int)`). So the spec
stores no type at run time, keeps every proof at quantity 0, indexes by
erased stages and anchors, and stores names, lists and enums. Every form
in §4.2 is of that kind (*conjecture* until gate A, §8.3). Richer
encodings (an `Op` indexed by its groups) wait until idris-mlir accepts
them; a form one host lacks is never used.

## 5. Effects as types in the source

effects.md keeps the row in a property on `idr.func` and `idr.call`; the
coordinator's direction puts it in the function type (`!idr.fn<(ins) ->
(outs), row>`, DS2/T6). Either way the row is a set of atoms; only where
it is stored changes, and the spec hosts both.

**Declared as data** (`IdrisMLIR.Spec.Effects`): `data Atom` (effects
§1.4; its set waits on DP-01 to DP-03, with D14's `exit`) and `atom : Atom
-> AtomFacts`, each with its node, the effects a call holding it declares
(`onCall`), its LLVM locations and whether it stops a return; `project :
Kind -> Node -> Naming -> List Atom`, effects §1.4's rule as a total
function; the seed (`total` removes `Diverge`, D13); proofs by case split
and evaluation: `0 roundTrip : (a : Atom) -> projectAll (onCall (atom
a)) = [a]`, never-less, coverage over `allOps`.

**Printed as monomorphic C++** (`EffectTree.h.inc`, `EffectFacts.h.inc`):
`enum class Atom`; `using Row = EnumSet<Atom>` with `height` the atom
count, so the solve's `FiniteHeight` concept holds by construction (CTC
§3.4); `project[kind][node][naming]`; `onCall[atom]` as a constant array of
(kind, resource) pairs; the LLVM table; `Of<Op>` and `EffectRules<Op>`
(effects §2.3); and, in `.td`, the row as a bit enum whose cases are the
atoms (effects §1.4), a parameter of the function type.

**Hand C++, generic over those types** (§9): `derive(fn)`, one walk that
projects `Of<Op>` or the instance's rules, joins each call's callee row
and applies the seed (effects §3.6); `summarize<CalleesFirst,
RowProblem>`, one explicit instantiation (CTC R13), writing rows at
program level (effects §4.1); and V1, `derive(fn) ⊆ row(type(fn))` in
`FuncOp::verifyRegions`, in parallel. With the row in the type, effects
§4.1's V2 (a call carries exactly its callee's effects) is the signature
check `verifySymbolUses` already makes: one verifier rule fewer.

**A call's answer to upstream's passes.** `idr.call` lists the typed rule
`FromCalleeRow`; the one hand `TypedEffects` trait (effects §2.2)
emplaces `onCall[atom]` for each atom set in the callee type's row, a loop
over the bits of a constant table. The callee type sits on the call (a
property verified once against the symbol), so the answer reads no symbol
table: CSE and DCE see a call's real effects for a bit loop.

**Not generated, and why.** The row calculus's rules (subsumption, call,
function) are few and fixed; their engine is the walk and join above.
Printing it from an Idris rule language would be a compiler from rules to
C++, Greenspun's "ad hoc ... implementation of half of" a logic language.
The spec holds vocabulary, tables and proofs; the engine is tens of lines
of C++ (*conjecture*).

## 6. The generator

### 6.1 Where a fact goes

A fact `mlir-tblgen` reads is printed into `.td`. A fact only our C++
reads is printed straight into a header, never routed through `.td` to a
C++ backend that would derive again what the spec knew (D10). A fact only
Idris reads is imported from the spec, unless the subset forces a print.

### 6.2 What `specgen` writes

| output | for | replaces (read) |
| --- | --- | --- |
| `foreign/idr/include/idr/IR/*.td`, `Target/ScheduleOps.td`, `Transforms/{Passes,InnerPasses}.td` | `mlir-tblgen`, every generator unchanged | the 21 hand files |
| `.../IR/Generated/{OpIndex,Families,EffectTree,EffectFacts,RuntimeAbi,Guards,Endings,Clocks,StageFacts,RuleCategories,ExpectProperties}.h.inc`; the pipeline's body | our C++ | `-gen-runtime-abi-defs`, `-gen-guards`, `-gen-big-to-word`, `-gen-rule-categories`; CTC §2.3's planned backends; `Pipeline.cpp:61-197` |
| `runtime/Generated/{idris_rt_ops.h,Instances.cpp}` | the runtime | `-gen-runtime-abi-decls`; CTC §2.3(e) |
| `compiler/src/IdrisMLIR/{Dialect,Syntax,Encoding}/Idr.idr` | the frontend | `-gen-idris-{dialect,syntax,bytecode}` for `idr` |
| nothing: `Spec.Rules`, `Spec.Endings`, `Spec.Clocks`, grades, stages imported | the frontend, the harness | the enum copies in `Syntax/Idr.idr`; `IdrRules.txt`, `IdrPassRoles.txt`, `IdrPassStages.txt` |

Builders stay printed because each takes its op's own attribute types: a
generic `build : (o : Op) -> Attrs o -> ...` is a type computed from a
run-time value with varying representation, refused unless it matches on
every op (§4.4). A printed builder is a plain function typed `Op n` over
`Vect n Value` (14 TD3, TD4), and reads well in an error.

### 6.3 Printers, not interpreters

Each output language is a small typed Idris AST printed once: a TableGen
`Def` (name, parents with arguments, fields over `Str | Int | Bit | Ref |
List | Dag | Code`), a C++ declaration tree, an Idris declaration tree; no
`{0}` templates (14 T04). Each spec constructor maps to one ODS construct,
so a generated `def` reads like hand ODS, with a comment naming the spec
definition. `specgen` has no semantics: `mlir-tblgen` still interprets
ODS, and clang the headers.

### 6.4 Determinism

Outputs are a pure function of the spec: the file list is data, order is
declaration order, and no map iteration or directory listing enters. Only
strings and integers are printed; an integer's decimal text is unique, so
both hosts print it alike by definition, and no `Double` is printed
(AGENTS.md: "Never: the hosts agreeing by coincidence", 14 X01). No time,
environment, path or host fact is read. A file is rewritten only when its
bytes change (TableGen's `-write-if-changed`, `llvm/lib/TableGen/Main.cpp:64`),
so ninja rebuilds only what a change reaches.

### 6.5 What happens to `idris-mlir-tblgen`

Every generator that reads our records goes: the runtime ABI, guards,
word ops, rules, pass roles and stages (`idris-mlir-tblgen.cpp:2749-3219`),
and the `idr`-only parts of the syntax, dialect and bytecode generators
(data table, identified types, guards, primitives, the world;
`:984-1189, 1393-1678, 2099-2200`). What stays is essential: the Idris
builders of the upstream ops the frontend writes (`arith`, `math`,
`memref`, `tensor`, `ub`, `builtin`; `tools/dialects.sh:79-90`) and
`builtin`'s encoders. Those facts are upstream's records, which D16 leaves
upstream's, and only a TableGen backend reads them through the
`mlir::tblgen` wrappers without re-deriving them (5.2 F2). The admitted set
is ours: the spec prints `IdrAdmitted.td`, one record per upstream op we
use naming upstream's def (a wrong name is TableGen's own error), and the
slim backend writes builders for those alone (14 TD6, G01); about half
its lines go (*conjecture*).

### 7.3 The two hosts

Stock Idris on Chez builds and runs `specgen` in every build, so the build
starts from the host's C compiler alone (D15). idris-mlir must compile and
run the spec and `specgen` too (AGENTS.md), its run reproducing the
committed outputs byte for byte. That is no oracle in AGENTS.md's sense:
the committed files specify what the generator writes, and neither host's
output is the reference; it sits beside `make self`'s "stage 2 the same as
stage 3" (`Makefile:33-35`). The owner confirms the reading (§11.3).

### 7.4 What a change costs

- *A spec edit*: Idris recompiles the changed spec modules and `specgen`
  under Chez, then `specgen` runs: unmeasured, to measure first (§10).
- *An op change* rewrites one family's `.td`; `IdrOps.h.inc` changes and
  its ~260 includers rebuild (CTC §7.1, *measured* there), as today.
- *An effect-table change* rewrites `EffectFacts.h.inc`, included only by
  its readers (CTC §7.4).
- *The frontend* rebuilds when a spec module it imports changes; closed
  sets live apart from the op tables (*conjecture* on Idris's rebuilds).

## 8. The cutover

### 8.1 Two hard cutovers, in order

- **A. The source moves.** The spec states today's dialect; every hand
  `.td` is deleted in the same change, replaced by its printed form; the
  generators of §6.5 go. Gate: `mlir-tblgen`'s outputs are byte-identical
  to today's (header path aside), the frontend's modules byte-identical,
  the suites unchanged. "The source moved" stays apart from "the dialect
  changed", so a regression in A is a printer bug.

After A there is no hand `.td`, and no dual path in either.

## 9. Brooks's limit: what stays written by hand

Representation removes accidental complexity, not essential complexity.
These are essential, and the spec only names them:
- **Semantics in C++**: the hand folders (21 beside the generic runtime
  fold, 03 §5.4), the essential verifiers (`match`, `match_lit`,
  `constant`, `memo.run`, `transpose`, `return`, `program`; 03 R3), region
  interface methods, custom directives' parse and print, the data table's
  storage, interface default bodies, the four `When` predicates and the
  `TypedEffects` trait (effects §2.2), the derivation and its solve (§5),
  the solver layer (CTC §3.4).
- **The runtime**: each function's body is its meaning (AGENTS.md); the
  spec holds the ABI only.
- **Interface signatures**: C++ spellings the spec cannot type.
- **Upstream's records**: `OpBase.td` and kin, and the ops we admit, read
  by the slim backend (§6.5).
- **The Idris side's logic**: the frontend, Emit and the registry's 124
  contract rows (14 R09). Whether an op's spec names the base primitive it
  implements, so the IO rows are generated, is NQ-14-5 reopened: both are
  Idris now, so its old objection (coupling ODS to base's spelling, 14
  TD10) is weaker.
- **`specgen` itself**: hand Idris, small and total.

## 10. Risks, and the limit

- **Greenspun's rule.** The spec models ODS in Idris and could grow into
  "an ad hoc, informally-specified, bug-ridden, slow implementation of
  half of" ODS. Three rules bound it: model only the constructs our
  dialect uses; one spec constructor per ODS construct, printed one to
  one; a printer, never an interpreter, `mlir-tblgen` keeping ODS's
  meaning. §5's rule engine is the sharpest temptation, and is refused.
- **The subset.** A proof form one host lacks may not be used (§4.4);
  unknown until the spec compiles under idris-mlir at gate A.
- **Error messages.** A local invariant fails at its line ("can't find
  `Fits Addressable Opaque`"); a global decision fails as an unsolved `So`
  naming the property, not the op (*conjecture*), so its decision returns
  the offending record as the refutation, for the REPL. mlir-tblgen and
  clang errors point at generated files: flat, one `def` per op with its
  spec name in a comment, checked in, readable and greppable.
- **Compile time.** Evaluated proofs run in both elaborators (a quadratic
  name check over about 190 mnemonics is ~18,000 string compares,
  *conjecture*: seconds), and the frontend's build includes the spec.
  Measure before A: each host's compile of spec and `specgen`, and one
  spec edit to a rebuilt compiler.
- **Upstream moves** (LLVM tracks main): an ODS syntax change is one
  printer's; a new ODS construct waits for the spec to say it (lesson 1).
- **Two generators remain**, `specgen` and the slim backend, printing
  against one hand Idris vocabulary (`MLIR.idr`).
- **A broken spec stops the build** unless the outputs are committed.
- **Where a higher level is not worth it**: the row calculus's engine,
  interface signatures, folds, runtime bodies: lifting them adds a
  language and removes no branch.
