# 0008: OpenTelemetry for Idris, after hs-opentelemetry

**Status:** proposed (2026-10-09). Nothing here is built.

**Sources.** None vendored yet. Stage O0 vendors them into `sources/` by its
conventions:
- hs-opentelemetry, the Haskell implementation by Ian Duncan, used and
  maintained at Mercury (github.com/iand675/hs-opentelemetry): its api,
  sdk, propagator, exporter and instrumentation packages;
- the OpenTelemetry specification and the semantic-conventions registry
  (github.com/open-telemetry/opentelemetry-specification,
  semantic-conventions);
- opentelemetry-rust, for the exporter side reached through 0001.

Until O0, every claim about hs-opentelemetry below is *recalled*, and O0
corrects it.

## What it changes

A first-party library, `libs/otel`, shipped beside `mlir-linear`, gives Idris
programs on idris-mlir tracing, then metrics and logs, by the OpenTelemetry
specification. Its API and package structure follow hs-opentelemetry closely
(*recalled*):
- an API package that libraries instrument against;
- an SDK package that applications configure;
- propagators;
- exporters;
- instrumentation for common libraries;
- the `inSpan` bracket as the everyday entry point.

Where Idris and this compiler can do better, the design says what it changes
and what it deletes.

## The design

### 1. Spans are linear

- **In hs-opentelemetry** (*recalled*), a span is created and ended inside a
  bracket (`inSpan`). A span created with the lower-level API must be ended
  by hand, and forgetting to is a silent leak of an unfinished span.
- **Here,** `startSpan` returns a span at quantity 1, which must be consumed
  exactly once by `endSpan`, or by `recordError` and then `endSpan`.
  Forgetting to end a span, or ending it twice, is a type error. `inSpan`
  stays as the convenient bracket over the same linear core.
- **What it deletes:** the runtime state checks an SDK needs for "ended
  twice" or "never ended".

### 2. Attributes are typed by their key

- **The representation.** A semantic-convention key carries its value type:
  `Key "http.request.method" String`, `Key "http.response.status_code" Int`.
  An attribute is a key paired with a value of exactly that type.
  hs-opentelemetry's `ToAttribute` class (*recalled*) becomes the interface
  for user-defined keys.
- **One representation.** The convention keys are generated from the
  semantic-conventions registry (YAML), never written by hand. The registry
  is the one source; a convention bump is a regenerate.
- **What it deletes:** misspelled keys and wrongly typed values, which are
  runtime data-quality bugs in every other SDK.

### 3. Context is a value carried by the task

- **In hs-opentelemetry** (*recalled*), the current context lives in
  thread-local storage, which works with GHC's threads.
- **Here,** there are no threads (AGENTS.md), and the runtime is shards with
  task frames (0005). The current context is task-local, a slot in the task
  frame. It is carried explicitly:
  - across `fork`/`join`, where a child task inherits its parent's context;
  - across shard messages, where the context rides in the message envelope
    as a value.
- **Propagators** read and write W3C `traceparent`/`tracestate` (and B3) at
  the process boundary: HTTP headers in the server and client
  instrumentation.
- **What it deletes:** context lost across async boundaries, the classic
  tracing bug. A task cannot run without its frame, and the frame holds the
  context.

### 4. Zero cost when off, by specialization

The compiler is whole-program and evaluates closed calls at compile time.
- When the tracer provider is a compile-time constant no-op, every
  `inSpan`, attribute and event folds away during compilation. No branch on
  "is tracing enabled" remains at run time.
- When the provider is configured at run time, sampling decides at the root
  span, and unsampled spans carry one bit.

This is the strongest difference from a library-only design: the decision is
made by the optimizer, not by a runtime check at every call site.

### 5. The SDK on shards

- **Span processors:** batch spans per shard, in a per-shard buffer with no
  atomics, and flush on a reactor timer (0005). A simple processor exports
  synchronously for tests.
- **Metrics** (stage O4): counters, histograms and gauges aggregate per shard
  with plain counts and are merged at export. This is the shard model's
  strength: there is no contended atomic on any hot path.
- **IDs and time:** trace and span ids come from a per-shard random source (a
  runtime primitive). Timestamps come from base's clock primitives, already
  registered (monotonic and wall clock).
- **Resources:** service name, version and host, detected once at start.

### 6. Exporters

- **First:** an in-memory exporter, used by the tests' golden span trees, and
  a JSON-lines file exporter. Neither needs a network.
- **Then:** OTLP over HTTP with protobuf encoding.
  - The protobuf encoder is generated from OTLP's `.proto` files (one
    representation).
  - HTTP comes either through Rust interop (0001: a client crate) or through
    0005's runtime sockets, whichever lands first; the exporter depends on
    a small transport interface, not on either.
- **gRPC** follows, through Rust.

### 7. Instrumentation, and the compiler itself

- **Libraries:**
  - the HTTP server and client on shards;
  - bumbledb's queries (`../bumbledb/proposals/0003-idris-port.md`), where a
    prepared query's span is compiled into its kernel's entry and exit;
  - the relational core.
- **Dogfooding:** the compiler instruments itself. The frontend's `logTime`
  phases and the pipeline's step timings become spans, so a self-compile
  produces a trace of where its time goes. The slow self-compile of
  2026-10-09 is exactly the case that wanted one.

## Rules it keeps

- **No threads, no shared mutable state:** shards, per-shard buffers,
  messages.
- **No C:** network transport through Rust (0001) or the runtime's sockets.
- **Facts in types:** spans linear, attributes typed by key.
- **No oracle.** The tests' golden span trees and the OTel specification are
  the meaning, not another SDK's output.
- **Whole-program compilation,** which is what makes the no-op fold away.

## Rejected alternatives

- **Binding an existing SDK** (opentelemetry-rust or the C++ SDK) as the
  whole implementation. It would bring threads and atomics, and it would
  lose linear spans, typed keys and compile-time removal. Rust stays only as
  a network transport.
- **Thread-local context:** there are no threads, and task-local is what the
  runtime has.
- **String-keyed attributes:** typed keys from the registry instead.

## Decisions

- D1. `libs/otel`, shipped with the compiler, API and SDK split as in
  hs-opentelemetry.
- D2. Spans are linear; attributes are typed by key, with keys generated
  from the registry.
- D3. Context is task-local and travels with fork/join and messages.
- D4. A no-op provider is removed by compile-time evaluation; there are no
  runtime enabled-checks.
- D5. Per-shard buffers and metric aggregation; no atomics.
- D6. Exporters depend on a transport interface, so Rust or runtime sockets
  can serve it.
