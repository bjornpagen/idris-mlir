## C12 The pass registry and the pipeline order

Producer: U06. The one declaration of every idr pass
(`foreign/idr/include/idr/Transforms/Passes.td`), the pipeline that
orders them (`foreign/idr/lib/Transforms/Pipeline.cpp`), the header that
registers them (`foreign/idr/include/idr/Transforms/Pipeline.h`), and the
driver and support declarations U06 keeps for other lanes. Paths below are
under `foreign/idr/` unless named. Line numbers are the tree at a3e61f3a.

### 1. How a pass is declared, built and owned

- Every idr pass is one `def` in `include/idr/Transforms/Passes.td`, which
  U06 alone writes. A lane that needs a pass added, removed or changed
  (argument, anchor, statistic, dependent dialect) reports it; it never
  declares a pass elsewhere.
- `Passes.h.inc` is generated by `mlir_tablegen(Passes.h.inc
  -gen-pass-decls -name Idr)` (`include/idr/Transforms/CMakeLists.txt:4-6`,
  unchanged, the coordinator's).
- The constructor is the generated one, `idr::create<Def>()`, the only
  constructor of every pass: no `def` sets `constructor`, and only
  `IdrExpect` has an option, so only it also has
  `idr::create<Def>(idr::<Def>Options)` (read: the generated
  `Passes.h.inc:595-599` for `IdrExpect`). The base the pass derives from is
  `idr::impl::<Def>Base<Derived>`; a statistic is the member the table names.
- Each pass's owner declares it with `#define GEN_PASS_DECL_<DEF IN UPPER
  CASE>` followed by `#include "idr/Transforms/Passes.h.inc"` inside
  `namespace idr { }` in the header the table names, and defines it with
  `#define GEN_PASS_DEF_<...>` in one `.cpp` of its own lane, as every pass
  does today (for example `include/idr/Transforms/Stack.h:12`,
  `lib/Transforms/Stack/Stack.cpp:38`).
- `idr::registerIdrPasses()` is the generated registration
  (`GEN_PASS_REGISTRATION`, `Pipeline.h:41-42`); `Pipeline.h` includes
  every header the table names, so registration sees every constructor.

**Invariants** (a spec check of U18's reads them):
- No `Option` or `ListOption` in `Passes.td` but `IdrExpect`'s `holds`, the
  test API. No pass option selects behaviour.
- Every argument starts with `idr-`; every anchor is `::mlir::ModuleOp`,
  `::idr::FuncOp` or `::mlir::func::FuncOp`.
- A pass is registered only where it is one stage, or one step of one
  stage, of the one pipeline (section 3).

`ListOption<"holds", "holds", "std::string", "The properties that must hold">`
(`Passes.td:855-857`). Its description names no property: what each
property checks is the comment on its declaration in

What changed against `Passes.td` at a3e61f3a, and why (every other row
keeps its argument, anchor, statistics and dependent dialects as today):
- New: `IdrOptimize` (0004 §4 stages 6 to 9, D45), `IdrStructureLoops`
  (0003 §5, D27), `IdrBufferize` (0003 §8, D18; upstream's
  `one-shot-bufferize` takes its options as strings and cannot be given
  the runtime's `allocationFn` and `memCpyFn`), and `IdrConstants`, the
  constants step of idr-optimize's inner pipeline (stage 9, C10), a step
  of the one pipeline like idr-identity and idr-redirect.
- `IdrEffects`'s description is C10's: it runs on a defunctionalized
  module, as the ready set writes the entries, and refuses one that still
  applies a closure or forces a suspension.
- `IdrContify` keeps its argument and statistic and moves its declaration
  to `Optimize.h`, since `Simplify.h` is deleted; the pass is replaced
  whole (0004 §4 stage 5).
- `IdrDefunctionalize` loses `numClosures` (no key stays a closure, 0004
  §2.4) and gains `numConstructors` and `largestBoxedSum`, the record D48
  asks for (C06).
- `IdrLower` drops `linalg` from its dependent dialects and adds `affine`:
  it makes no linalg op, and its view expansion makes `affine.apply`
  (C16).
- `IdrRc` loses its two options, `IdrDemand` its one (0004 §6).
- `IdrExpect` adds `tensor` and `scf` to its dependent dialects: the
  emitted module its `quantities-kept` parses holds them (C22). Its
  description stops listing the properties (C24).
- Deleted (0004 §6 and D45; 0003 §15): the defs of the round, the inliner,
  the specializer, the loop breakers, the round's facts, the outliner of
  regions, the in-bounds prover and the vectorize pass. Their headers'
  `GEN_PASS_DECL` lines go with them (`Simplify.h:23-26`, `Inline.h:24`,
  `Specialize.h:32`, `Isolate.h:12`, `InBounds.h:37`, `Vectorize.h:12`).
- `Passes.td`'s header comment stops listing the nested steps by name:
  "The nested steps a module pass runs itself are not declared here:
  their module pass builds them and keeps their statistics."

The descriptions are U06's text, written from 0004 and 0003; they are
documentation, not a seam. A lane whose pass does something its
description does not say reports the sentence.

### 3. The pipeline

`include/idr/Transforms/Pipeline.h` after the cutover, exactly:

```cpp
namespace idr {

#define GEN_PASS_REGISTRATION
#include "idr/Transforms/Passes.h.inc"

// idris-mlir's pipeline, idr-deduplicate to idr-tail-calls, into `pm`, a
// manager on builtin.module. Never idr-target: the driver runs it first,
// and idris-mlir-opt runs it by name.
void buildPipeline(mlir::OpPassManager &pm);

// Registers --idr-pipeline with the pass registry.
void registerIdrPipeline();

} // namespace idr
```

Fixed choices, each with its reason:
- Every canonicalizer is `idr::createCanonicalizerPass()`
  (`include/idr/Transforms/Canonicalize.h:42-44`, U03's), the one
  configuration.
- Row 5 keeps today's `canonicalize = false` (`Simplify.cpp:97-109`): the
  removal's own canonicalization folds region-branch patterns on the
  matches alone and leaves a constructor that still holds a world or a
  linear value.
- Row 8 runs on the module, not in row 7's group as 0003 §7 sketches it:
  `eliminateEmptyTensors` analyzes function boundaries only when it is
  given a `ModuleOp` (read:
  `M/lib/Dialect/Bufferization/Transforms/EmptyTensorElimination.cpp:208-228`),
  through the module driver C18 generalizes to `FunctionOpInterface`; on a
  nested `idr.func` it would run without the boundary analysis and resolve
  callees across siblings, which a nested pass may not read.
- No `idr.func(canonicalize)` follows defunctionalization as today
  (`Pipeline.cpp:108-109`): idr-optimize cleans every function once.
- idr-effects, idr-identity, idr-redirect, idr-constants and
  idr-binding-times are registered and not added here: idr-effects's code
  runs inside rows 2 and 4 (D34, D38), idr-identity, idr-redirect and
  idr-constants are steps of row 4's inner pipeline (C07, C10), and
  idr-binding-times is a remark of what row 4 computes per component. idr-expect is a test API. idr-target is the
  driver's, before row 1.
- Stages 13 to 16 (translation, the runtime, O3, partition, code
  generation per bin, the link) are the driver's (`lib/Driver/Run.cpp`,
  `Compile.cpp`) through C13, not passes.
- `registerIdrPipeline()` registers `idr-pipeline`, "idris-mlir's
  pipeline, the idr dialect to the LLVM dialect", as
  `mlir::PassPipelineRegistration<>` calling `buildPipeline(pm)`.

### 4. The driver around the pipeline

`lib/Driver/Run.cpp`: one `mlir::PassManager` on the module;
`mlir::applyPassManagerCLOptions(pm)` (which gives
`-mlir-print-ir-tree-dir`, `-mlir-print-ir-after-all`, crash reproducers
and the like); `idr::profile::addInstrumentation(pm)`; timing; then
`pm.addPass(idr::createIdrTarget())` and `idr::buildPipeline(pm)`. No other
instrumentation is added.

The module is parsed with the dialects C22 says the emitted module holds
(`builtin`, `idr`, `arith`, `math`, `memref`, `ub`, `tensor`, `scf`):
today's set (`Run.cpp:225-227`) gains `tensor` and `scf`, which the
frontend writes for arrays (0003 §4.1). `idr::registerFlowInterfaceExternalModels`
(C05, declared in U02's `include/idr/IR/Flow.h`, which each caller
includes) is called on that
handoff registry, and on the registry of idris-mlir-opt and of
idris-mlir-reduce, so the flow rule holds from the parse on.

The command line after the cutover (`lib/Driver/Options.cpp`, in this
order): the input; `-o` ("the executable, or with -c the archive of its
objects"); `-c`; `-p`; `--package-path`; `--prefix`; `--no-prelude`;
`--log-actions-tags`; `--runtime`; `--runtime-bitcode-section`;
`--print-runtime`; `--prepare-runtime`; `--print-target-triple`;
`--print-link-flags`; `--print-target-cpu`; `--num-threads`. Profile.cpp
keeps `--time-trace` and `--time-trace-granularity`. MLIR's registered
options: the printer's, the context's, the pass manager's, timing and
action logging (`mlir::tracing::DebugConfig::registerCLOptions`); the
debug counter is not registered in idris-mlir (D46), so
`-mlir-debug-counter` is an unknown option there, exit status 2.
idris-mlir-opt keeps upstream's counter (`MlirOptMain.cpp:707`).

A refusal is recognized by C04's `idr::refusalRule` on the
`mlir::Diagnostic`, never by its text; the driver's handler sets the
verdict from it.
