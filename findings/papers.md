# Papers: three thunks, one coroutine identity

The lazy cell we lower by hand is the shared thunk Peyton Jones updates in place. Bhat's value-semantics thunk and Ullrich's task are the other two protocols, and the three stay separate. The enter function, the done function, and the call to `idris_rt_lazy_kept` are that shared thunk written out by hand. The MLIR for it is `llvm.coro.id`, the switched-resume identity. The one-shot case is a different identity, `llvm.coro.id.retcon.once`. A thread is neither identity.

## Many resumes after the value is stored

**read** Peyton Jones, *Implementing lazy functional languages on stock hardware: the Spineless Tagless G-machine*, JFP 2(2), 1992, §3.1.2 (p. 135), `sources/papers/peytonjones-1992-stg/paper.pdf`. A thunk is a closure. The first force physically updates it with its value. In the self-updating model the STG machine uses, that update overwrites the thunk with a value that itself has a code pointer, because every later force re-enters the thunk-turned-value. The code pointer is the flag: the value's code returns immediately. §10.6 (p. 193) is the in-place form of that overwrite: when the result is small enough, the updating code writes it over the closure (`UpdatePtr[0] = Cons_Info` and the fields) instead of writing an indirection.

**read** §4.2 (pp. 147–148). The update flag on a lambda-form is `u` or `n`. Flag `u` means the closure is updated with its head normal form if it is evaluated, which is what makes the later re-entries see the stored value. Flag `n` is safe when the compiler proves the thunk is evaluated at most once; the update is then omitted. §3.1.2 (p. 136) says the same for the self-updating model. The two flags are the shared thunk and the at-most-once thunk. Update analysis, which would set `n`, is named there as work in progress, not a finished algorithm.

**read** Our cell is the `u` case, written out as two functions. `!idr.lazy<T>` is one cell whose code pointer is the state: the first force writes the value over the payload and replaces the pointer, and every later force returns what was written (`foreign/idr/include/idr/IdrOps.td:104-109`). `idr.suspend` builds the cell and does not run the function; `idr.force` is the value, computed on the first force and shared (`IdrOps.td:584-610`). The label of a suspension is a cell large enough for the value as well as the captures, and the code pointer is replaced when the value is written (`foreign/idr/lib/Layout/Labels.cppm:16-17`, `foreign/idr/lib/Layout/Layouts.cppm:55-57` and `111-113`). Lowering emits that pair: `done` loads the stored value, and `enter` calls the callee, stores the result over the payload, stores `done` as the code pointer, and returns the result (`foreign/idr/lib/Lower/Runtime.cppm:210-212`, `257-331`). A persistent cell (count 0, not a stack cell) is recorded by `idris_rt_lazy_kept` so the value it now owns is released when `main` returns (`runtime/idris_rt.h:218-223`, `runtime/Rc/Counting.cppm:40-61`). `enter` is what calls it (`Runtime.cppm:326-330`). Those two outlined functions and that call are the homegrown thunk.

**read** §3.1.3 (pp. 136–137). On entry the code pointer can be overwritten with a black-hole pointer, so a re-entry before the update is a loop. The same overwrite, with a queue-me pointer, is how the paper synchronizes concurrent threads on one thunk. Our `enter` does not overwrite the pointer before the call (`Runtime.cppm:296-331`). The threads decision already excludes a second schedule of effects (`findings/decision-threads-pointers.md:9-16`). The black-hole is the loop check; the queue is a thread. This note does not move either into the thunk, and it does not change that decision.

## A value-semantics thunk is not the heap cell

**read** Bhat and Grosser, *Lambda the Ultimate SSA*, CGO 2022, `sources/papers/bhat-2022-lambda-ultimate-ssa/paper.tex:1071-1078`. The LEAN program they compile is strict. The published `lp` operations are data constructors, pattern matching, closures, and join points (`paper.tex:992-999`). There is no thunk operation in that IR.

**read** The published contrast is in the related work (`paper.tex:2176-2190`). The Intel Haskell compiler's MIL represents laziness as heap values and manipulates the heap, so its analysis of lazy values uses memory semantics instead of value semantics. GRIN's monadic encoding has pointer semantics, not value semantics, and recovers the pointers with a whole-program points-to analysis. The same section says GHC lowers laziness at the step from STG to C--, which is where the encoding becomes hard to optimize (`paper.tex:2154-2158`).

**read** The source still contains the draft that named the value-semantics side, commented out of the published paper. A thunk in memory is a pointer to the function and the arguments (`paper.tex:1030-1036`). The draft IR added `lp.force` and `lp.thunkify` so laziness stayed an SSA value (`paper.tex:960-967`). Those lines are comments. They are not the dialect the paper evaluates. They are the sentence the related work is aiming at: a thunk the optimizer sees as a value, against a heap object the optimizer sees as memory.

**read** Our shared cell is the heap side of that contrast. By the time `idr-lower` runs, the suspension is a closure cell whose code pointer will be overwritten (`Lowering.cppm:99-100`, `Runtime.cppm:272-331`). The value-semantics side we do have is earlier, and only for the cases that never need the cell. A suspension with one use is the call: `ForceOfOneUse` replaces the force with a call of the callee and erases the suspend (`foreign/idr/lib/Dialect/Ops/Lazy.cc:14-28`). A constant suspension used once is the same call (`Lazy.cc:32-63`). Forces in different arms of one match each call, because only one arm runs (`Lazy.cc:66-98`). Those rewrites are already MLIR. They are the at-most-once thunk of STG §4.2, kept as a value. The shared thunk is still the heap cell.

## A thunk is not a task

**read** Ullrich and de Moura, *Counting Immutable Beans*, IFL 2019, `sources/papers/ullrich-2019-counting-immutable-beans/array.tex:1-12`. Every runtime value starts with a kind tag: `ctor`, `pap`, `array`, `string`, `num`, `thunk`, or `task`. The paper calls `thunk` self-explanatory. The next subsection is the task.

**read** `threadsafety.tex:1-14`. `Task.mk : (Unit -> α) -> Task α` converts a closure into a task and executes it in a separate thread. `Task.bind` waits for one task and starts another. `Task.get` waits and returns the value. `threadsafety.tex:50-53`: `Task.mk` and `Task.bind` call `markMT` on the values they will share, before the new task exists, while those values are still reachable from one thread. A task is a second thread and a change of the reference-count tag. A thunk is a kind of value on the calling thread.

**read** `async.execute` is that task in this tree's MLIR. Its body can be executed concurrently with the successor (`.toolchain/llvm-project/mlir/include/mlir/Dialect/Async/IR/AsyncOps.td:44-48`). The async dialect's coroutine ops exist to lower those tasks: async-to-LLVM converts regions inside `async.execute` to LLVM coroutines and relies on switched-resume lowering (`AsyncOps.td:437-448`). `async.runtime.resume` resumes the coroutine on a thread managed by the runtime (`AsyncOps.td:607-611`). `async.coro.id` is the switched-resume identifier inside that pipeline (`AsyncOps.td:450-454`), not a second spelling of a lazy cell. Bhat's runtime list names task-based parallelism as a library feature of strict LEAN (`paper.tex:1077-1078`), beside the thunk Ullrich keeps as its own kind.

## What the papers refuse to collapse

Three protocols. Each paper draws one of the lines; none of them is a reason to merge the other two.

1. **Many resumes after the value is stored.** STG flag `u` (§3.1.2, §10.6): the first entry stores the value and replaces the code pointer; every later entry returns that value. Our `enter` / `done` pair is this protocol (`Runtime.cppm:272-331`). On `llvm.coro.id` the same sharing is the promise and a null resume. A completed switched-resume coroutine is a null resume function (`.toolchain/llvm-project/llvm/docs/Coroutines.md:109-111`). The same object can be asked whether it is complete (`llvm.coro.done`), resumed only when it is not, destroyed even after a normal completion, and projected to its promise (`Coroutines.md:72-85`, `589-596`, `878-890`). `llvm.coro.resume` of a coroutine that is not suspended is undefined (`Coroutines.md:860-876`). The consumer example loads the promise of a coroutine that is still resumable (`Coroutines.md:633-648`). After the final suspend the resume pointer is null, so a later force is that done-check and a load of `llvm.coro.promise` (`Coroutines.md:900-910`). It is another entry of the cell, in STG's sense, and it is a resume of the computation only the first time.

2. **One-shot resume.** STG flag `n` (§4.2): evaluated at most once, no update, no cell that later entries read. Bhat's value-semantics thunk is this side against the heap cell (`paper.tex:2176-2190`; the commented `lp.force` / `lp.thunkify` at `paper.tex:960-967`). LLVM spells it `llvm.coro.id.retcon.once`: the coroutine suspends exactly once, and the continuation returns the result (`Coroutines.md:136-152`, `1383-1404`). Returned-continuation lowering does not get the allocation elision switched-resume gets (`Coroutines.md:167-171`). `CoroElide` removes a `coro.id` frame whose begin does not escape (`.toolchain/llvm-project/llvm/lib/Transforms/Coroutines/CoroElide.cpp:247-272`, `451-457`). That is an escape check on `llvm.coro.id`. It is not STG's update flag, and it is not `retcon.once`.

3. **A thread.** Ullrich's `task` (`array.tex:3-12`, `threadsafety.tex:8-9`). STG's queue-me pointer is the same collapse, a thunk used as a thread rendezvous (§3.1.3). `async.execute` and `async.runtime.resume` are that rendezvous (`AsyncOps.td:46-48`, `607-611`). The threads decision stands (`findings/decision-threads-pointers.md:9-16`).

## The construct

**read** The distinction is which coroutine identity the frontend emits (`Coroutines.md:46-49`, `63-66`, `123-127`, `148-152`). `llvm.coro.id` is switched-resume: resume and destroy pointers at fixed offsets, the promise for the value, a null resume when finished (`Coroutines.md:63-111`). `llvm.coro.id.retcon.once` is the one-shot resume (`Coroutines.md:1383-1404`). This pin's MLIR LLVM dialect defines `llvm.coro.id`, `llvm.coro.begin`, `llvm.coro.suspend`, `llvm.coro.resume`, and `llvm.coro.promise` (`.toolchain/llvm-project/mlir/include/mlir/Dialect/LLVMIR/LLVMIntrinsicOps.td:708-771`). It does not define `llvm.coro.id.retcon.once`, `llvm.coro.done`, or `llvm.coro.destroy`. `llvm.coro.id.async` is a third identity, an async context the frontend resumes (`Coroutines.md:173-199`); the MLIR async runtime then resumes it on a thread (`AsyncOps.td:607-611`).

The shared thunk is `llvm.coro.id`. `idr.suspend` is the ramp: the frame exists, the body has not run. The first `idr.force` is the resume that runs to the final suspend and stores the promise. Every later `idr.force` is the done-check and a load of the promise. `CoroSplit` splits the function into the ramp, the resume, and the destroy (`Coroutines.md:90-111`). Destroy is a separate entry from completion (`Coroutines.md:78-80`). Counting frees a cell when its last reference drops (`runtime/idris_rt.h:210-214`); a count-0 cell is not freed, which is why `enter` records it with `idris_rt_lazy_kept` (`Counting.cppm:51-69`). The outlined `enter` and `done`, and that call, are the hand-written frame.

The one-shot thunk stays a value. `ForceOfOneUse`, `ForceOfOneConstant`, and `ForceInOneCase` (`Lazy.cc:14-98`) are that case in MLIR today. The identity for it, once the lowering of a thunk is `llvm.coro`, is `llvm.coro.id.retcon.once`, which this dialect does not spell yet. **conjecture:** until that intrinsic has an op, the canonicalizer's direct call is the one-shot path, and a shared `llvm.coro.id` frame is the wrong substitute. `CoroElide` does not know "evaluated at most once"; it knows "the handle does not escape" (`CoroElide.cpp:247-272`). A thunk that is stored and forced on one path still has an escaping handle.

A thread is not an identity we emit for a thunk. No thread pool.

## Highest construct

The highest MLIR construct that applies is `llvm.coro.id`.

The requirement it forces us to accept is the switched-resume frame: resume and destroy at fixed offsets, the value in the promise, a null resume when the computation has finished, later readers loading the promise, destroy separate from that completion, and `CoroSplit` / `CoroElide` as the passes that split and remove the frame. The one-shot case is `llvm.coro.id.retcon.once`, a different identity. That requirement is not one to delete. It is the shared thunk in MLIR. The outlined enter and done functions are what it replaces.

`async.execute` / `!async.value` is higher on the ladder and does not apply. Its requirement is a concurrent task (`AsyncOps.td:44-48`), which is Ullrich's `task`. `async.coro.*` is that task lowered onto switched-resume and `async.runtime.resume` (`AsyncOps.td:437-448`, `607-611`). That requirement is one to delete.
