# Async dialect

`async.execute` and `!async.value` are a task. `async.coro.*` is a typed spelling of the LLVM switched-resume intrinsics, inserted while that task is lowered. Neither is `Future a` on the thread that runs `main`. The homegrown thunk lowers through `llvm.coro` directly, as `llvm.coro.resume` on that caller.

## The task

`async.execute`'s body may run concurrently with its successor. A fully sequential run, the body finishing before the successor starts, is a legal execution of the op (read: `.toolchain/llvm-project/mlir/include/mlir/Dialect/Async/IR/AsyncOps.td:46-52`). The result is still a concurrent task. `!async.token` becomes available when the operation that created it completes (read: `.toolchain/llvm-project/mlir/include/mlir/Dialect/Async/IR/AsyncTypes.td:28-33`). `!async.value<T>` is a value that may be unavailable now and available later (read: `AsyncTypes.td:36-42`). A dependency that is not an explicit token or value is illegal, including one through shared global state (read: `AsyncOps.td:54-57`). The dialect describes itself as asynchronous execution (read: `.toolchain/llvm-project/mlir/include/mlir/Dialect/Async/IR/AsyncDialect.td:27-28`).

The lowering that exists outlines every `async.execute` into a private function. The transformation is not reversible (read: `.toolchain/llvm-project/mlir/lib/Dialect/Async/Transforms/AsyncToAsyncRuntime.cpp:307-311`). After `async.coro.begin` that function saves its state, calls `async.runtime.resume`, and suspends; the pass walks every `async.execute` and does this (read: `AsyncToAsyncRuntime.cpp:377-395`, `804-805`). `async.runtime.resume` resumes the coroutine on a thread the runtime manages (read: `AsyncOps.td:607-616`). LLVM conversion replaces it with a call to `mlirAsyncRuntimeExecute`, passing a wrapper whose body is `llvm.coro.resume` (read: `.toolchain/llvm-project/mlir/lib/Conversion/AsyncToLLVM/AsyncToLLVM.cpp:241-265`, `808-811`). The runtime queues that call on `llvm::DefaultThreadPool` (read: `.toolchain/llvm-project/mlir/lib/ExecutionEngine/AsyncRuntime.cpp:21-26`, `75`, `395-397`; `.toolchain/llvm-project/mlir/include/mlir/ExecutionEngine/AsyncRuntime.h:134-137`).

`async.runtime.await` blocks the caller until the operand is available or in error (read: `AsyncOps.td:596-604`). The runtime waits on a mutex and a condition variable (read: `AsyncRuntime.cpp:182-186`, `369-374`). A token and a value are allocated with reference count 2, one hold for the caller and one for the task that emplaces them, and both carries a mutex, a condition variable, and a list of awaiters (read: `AsyncRuntime.cpp:171-186`, `188-206`). `async.runtime.num_worker_threads` reads the pool's concurrency (read: `AsyncOps.td:727-733`; `AsyncRuntime.cpp:439-440`). Reference-count operations at this level are the runtime's own, added from liveness after the execute ops are gone (read: `AsyncOps.td:675-695`; `.toolchain/llvm-project/mlir/include/mlir/Dialect/Async/Passes.td:56-66`).

`async-to-async-runtime` is that lowering, and once it runs, `async.execute` is illegal (read: `Passes.td:43-45`; `AsyncToAsyncRuntime.cpp:840-844`). The conversion to LLVM rewrites `async.execute` to update result types. It does not run the region (read: `.toolchain/llvm-project/mlir/include/mlir/Conversion/AsyncToLLVM/AsyncToLLVM.h:25-32`; `AsyncToLLVM.cpp:1104-1111`). With `async-dispatch` off, the parallel-for pass still builds an `async.execute` per block after the first and calls only the first block directly (read: `.toolchain/llvm-project/mlir/lib/Dialect/Async/Transforms/AsyncParallelFor.cpp:639-640`, `681-701`). No pass lowers `async.execute` onto the caller alone.

Sequential execution is a legal schedule of the op. The executable this tree lowers to is the pool. Taking `async.execute` as the suspension takes that pool with it. The threads decision stands: a second schedule of effects is outside the language, and there is no scheduler to add without replacing the heap (read: `findings/decision-threads-pointers.md:8-16`). The pool is a requirement to delete.

## The frame the task lowers through

`async.coro.id`, `async.coro.handle`, and `async.coro.state` are types for lowering to LLVM and the async runtime through LLVM coroutines (read: `AsyncTypes.td:70-99`). The ops are the switched-resume intrinsics, so the IR between `async.execute` and LLVM stays typed (read: `AsyncOps.td:433-448`). `async.coro.id` becomes `llvm.coro.id` with alignment 0 and three null pointers, which is the switched-resume id (read: `AsyncToLLVM.cpp:345-352`; `.toolchain/llvm-project/llvm/docs/Coroutines.md:65-66`). `async.coro.begin` sizes and aligns the frame and allocates it with the aligned allocation function (read: `AsyncToLLVM.cpp:374-407`). `async.coro.free` frees that memory (read: `AsyncToLLVM.cpp:429-439`). `async.coro.suspend` becomes `llvm.coro.suspend` and a switch on its return code to the suspend, resume, and cleanup successors (read: `AsyncOps.td:507-517`; `AsyncToLLVM.cpp:541-561`). The outlined function is marked `presplitcoroutine` (read: `AsyncToAsyncRuntime.cpp:245-248`).

Those coro ops are produced together with the runtime ops. The initial suspend is the `async.runtime.resume` above. On yield, the lowered body stores into the runtime value, marks it available, and branches to cleanup, which frees the frame and ends the coroutine (read: `AsyncToAsyncRuntime.cpp:216-232`, `733-746`). A later `async.await` of a value loads that runtime object (read: `AsyncToAsyncRuntime.cpp:616-629`, `692-698`). The payload is a byte buffer owned by `AsyncValue`, beside the mutex (read: `AsyncRuntime.cpp:188-200`; `AsyncRuntime.h:75-80`). The coroutine is not entered again to return the stored value.

`async.func` is the same machinery with a hot start: the lowering sets up the coroutine and does not suspend at entry (read: `AsyncToAsyncRuntime.cpp:486-489`). An `async.await` inside it still saves state and calls `async.runtime.await_and_resume` (read: `AsyncToAsyncRuntime.cpp:616-629`). If the operand is already ready, the runtime resumes inline; if not, the resume is an awaiter, and it runs on the thread that emplaces the operand (read: `AsyncRuntime.cpp:323-333`, `400-410`).

The MLIR LLVM dialect defines `llvm.coro.id`, `llvm.coro.begin`, `llvm.coro.size`, `llvm.coro.align`, `llvm.coro.save`, `llvm.coro.suspend`, `llvm.coro.end`, `llvm.coro.free`, `llvm.coro.resume`, and `llvm.coro.promise` (read: `.toolchain/llvm-project/mlir/include/mlir/Dialect/LLVMIR/LLVMIntrinsicOps.td:708-770`). Tablegen under `mlir/include` defines no `llvm.coro.destroy`, no `llvm.coro.done`, and no `llvm.coro.id.retcon` or `llvm.coro.id.retcon.once`. LLVM's switched-resume ABI still stores the resume and destroy pointers at fixed offsets, represents a finished coroutine with a null resume, projects the value with `llvm.coro.promise`, and requires `llvm.coro.destroy` even after normal completion (read: `Coroutines.md:72-83`, `109-121`). Returned-continuation, `llvm.coro.id.retcon` and `llvm.coro.id.retcon.once`, is the other ABI in that document (read: `Coroutines.md:123-152`). It is not an op of this dialect.

## Future a

`fork : Lazy a -> Future a` and `await : Future a -> a` are pure. `fork` is `prim__makeFuture` of a thunk that forces the lazy value (read: `third_party/Idris2/libs/contrib/System/Future.idr:10-22`). The Chez foreign starts that thunk with `fork-thread` and has `await` wait on a mutex and a condition (read: `third_party/Idris2/support/chez/support.ss:518-533`). That thread is the second schedule the threads decision excludes. `!async.value` with `async.await` is the same shape in this runtime: a side object, a mutex, a condition variable, and a worker. It is a task. It is not `Future a` resumed on the caller.

`async.coro.*` is that task's frame. The frame is freed when the body stores the value, and a later read loads the runtime object. A force that runs on the caller, and a later force that returns the stored value, does not have an op here. `async.runtime.resume` is the resume this dialect emits, and it is the pool.

`idr.suspend` rejects a capture whose type is the world (read: `foreign/idr/lib/Dialect/Ops/Lazy.cc:188-190`). A suspension of this shape has no operand a second world could occupy.

## The thunk

`!idr.lazy<T>` is one cell. The code pointer is the state: the first force writes the value over the payload and replaces the pointer, and every later force returns what was written (read: `foreign/idr/include/idr/IdrOps.td:104-110`). `idr.suspend` builds that cell and does not call the function. `idr.force` is the read. One result, the suspended value (read: `IdrOps.td:584-610`). A suspension with a single use is rewritten to the call, in MLIR (read: `foreign/idr/lib/Dialect/Ops/Lazy.cc:14-28`). The shared cell is lowered by hand. Two private functions, enter and done: enter calls the callee, stores the value, stores done's address over the code pointer, and calls `idris_rt_lazy_kept`; done loads the stored value and returns it (read: `foreign/idr/lib/Lower/Runtime.cppm:210-212`, `257-260`, `272-331`). `idris_rt_lazy_kept` records a persistent cell so the value it stored is released when main returns (read: `runtime/idris_rt.h:218-223`).

That enter/done pair is the homegrown frame, and it should be MLIR. The lowering is `llvm.coro` on the caller. `idr.force` is `llvm.coro.resume` of the handle, and the value is `llvm.coro.promise`. The thunk does not go through `async.execute`, and it does not go through `async.coro.*`. The only producer of `async.coro.*` emits `async.runtime.resume` in the same function, and `async.coro.begin` / `async.coro.free` allocate and free outside the counted heap.

A later force, once the value is stored, loads that storage and does not resume. A finished switched-resume coroutine has a null resume, so the second entry cannot be `llvm.coro.resume` (conjecture, from `Runtime.cppm:323-331` and `Coroutines.md:109-111`). The memo has to sit in storage that outlives the running frame. The cell is that storage. Whether `idris_rt_lazy_kept` remains once an explicit destroy releases the frame is open. `coro.id` against `coro.id.retcon.once` belongs to the frame note: this dialect, and the MLIR LLVM dialect beside it, spell only `llvm.coro.id`.

The highest MLIR construct that applies is `llvm.coro` switched-resume, the LLVM dialect intrinsics `llvm.coro.id`, `llvm.coro.begin`, `llvm.coro.suspend`, `llvm.coro.resume`, and `llvm.coro.promise`. The requirement it forces is that frame, resumed by the caller: resume and destroy pointers at fixed offsets, the value in the promise, a null resume when the coroutine is finished, and a destroy even after completion. That requirement is not one to delete. It is what replaces the enter/done pair. The thread pool behind `async.execute` and `async.runtime.resume` is a requirement of the task, and that requirement is one to delete.
